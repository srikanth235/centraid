# native-v0-resilience

**Goal:** preserve a repeatable native v0 smoke and resilience matrix across the Home springboard, all eight blueprint covers (Photos, Docs, Agenda, Tasks, People, Notes, Tally, and Locker), and Settings.

There is no bottom-tab navigator (`apps/mobile/src/navigation.ts`): all eight apps are full-screen covers launched from Home's tiles, and Settings opens from the vault drawer. Each surface is therefore entered the way a user enters it — by the tile's `Open <name>` accessibility label — and asserted on a string that only the opened screen publishes ("Search photos", "Add document or folder", "Create event", "APPEARANCE"), never on the tile or drawer label, which can be visible before the destination opens. Covers dismiss with a native swipe-down gesture Maestro cannot drive, so each surface starts from a fresh launch; React Navigation state is not persisted, so every launch lands on Home.

**Setup:** install a development build, start Metro, and expose a reachable gateway through `MAESTRO_GATEWAY_URL`. The flow clears app state, mints a pairing ticket, and redeems it through ticket-only onboarding, accepting the named-owner direct completion or the unnamed-profile branch, before exercising the shell. For the manual matrix, grant photo-library permission and seed at least one local photo, one document, and one calendar event. Run the 50k deterministic fixture with `cd apps/mobile && bun test timeline-50k` before the device flow.

**Automated steps:** configure the declared gateway; launch without clearing state; open all eight blueprint covers from Home plus Settings from the vault drawer. On Android, create a Tally group through the mounted UI, enable the OS airplane mode through Maestro, add an expense, assert its `queued` chip, force-stop and relaunch without clearing state while still offline, reopen Tally, and assert the same expense and chip remain before restoring the network in a `finally` cleanup. Both platforms then force-stop and relaunch once more and assert Home returns. This catches navigation regressions and proves the production UI → session → SQLite outbox → mounted multi-vault reader restart path on the platform whose simulator exposes a real airplane control.

**Automated pending-write companion:** `apps/mobile/src/lib/replica/multi-vault-reader.test.ts` drives real `NativeReplicaSession.write()` calls for a Tally expense, Task add, Agenda RSVP, and Note create while disconnected, closes that session, then mounts and remounts the production multi-vault reader over the same SQLite file. `apps/mobile/src/apps/tally/PendingRestartJourney.test.tsx` mounts the rendered Tally surface over that restarted production reader. Together they assert all four rows, stable intent keys, queued status/chip, vault provenance, and the Agenda row's captured canonical base version on iOS-compatible infrastructure. Run them through the mobile package test script; the Android device step above is the visual/touch and OS lifecycle proof.

**Manual network matrix (record observations in the run verdict):**

1. The Android lane automates the Tally add/restart assertion. Manually add a Task, Agenda RSVP, and Note in the same airplane-mode session; each projected row must appear immediately with a `queued` chip and “Waiting for a connection.” Force-stop and relaunch without clearing state; all three rows must still be present. Existing Photos, Docs search, and Agenda ranges must also remain readable.
2. Disable airplane mode and verify the four queued intents settle without duplicate rows. Exercise one parked result (reason and Settings → Approvals affordance) and one denied/conflict/failed result (reason plus Retry and Discard); a conflict must print expected and actual versions.
3. Start a large upload on Wi-Fi, walk onto cellular, then back to Wi-Fi. With Wi-Fi-only enabled the queue must halt and resume; with it disabled the iroh tunnel should heal without restarting the part ledger.
4. Force-kill during every visible upload state and relaunch. The queue should resume by SHA/part receipt and create one CAS object.
5. On Android, leave the foreground service active until the six-hour cap in a soak run; the next lifecycle drain must resume and the notification must always state `Backing up N of M`.

**Verdict:** PASS when the automated flow succeeds and the run verdict records the manual network observations for the device/OS under test.
