# native-v0-resilience

**Claim:** Settings still loads from the all-apps sheet, the app survives an OS process restart, and on Android a write made offline survives that restart and settles once the radio returns. If this passes when it should not, a release ships in which Settings is unreachable from Home, or a write made on a train is silently lost on arrival.

**Goal:** hold the device-only half of native v0 resilience — the Settings place reached through the all-apps sheet, an OS process restart, and on Android the offline write → process death → reconnect → settled arc.

**Where the covers-open claim lives, and why it is not here.** "Every tile opens its cover" is not a device-only claim, so it is held at its cheapest honest tier: `apps/mobile/src/screens/Home.test.tsx` generates a sweep from `apps/mobile/app-conformance.json` over every bundled app, and each cover additionally has its own device journey on the per-merge canary and nightly lanes (`run-home-apps-suite.mjs`, `run-photos-suite.mjs`). The ten-surface tour this flow used to run measured **187 s** on the PR gate (run 33573882728), the largest single line in a twelve-minute budget that a fully passing suite overran, and decision E-device-only plus [`pr-gate-budget.md`](pr-gate-budget.md) remedy 3 ("move a claim down a tier") both name that move as the correct first one ([#905](https://github.com/srikanth235/centraid/issues/905)).

**How Settings is reached.** There is no bottom-tab navigator (`apps/mobile/src/navigation.ts`) and no vault drawer: Settings is a **place**, reached from the band's More tab through the all-apps sheet, and `screens/home/AllAppsSheet.tsx` says so at the handle ("Settings is reached from HERE, not from a drawer"). The route is `home-band-more` → `home-all-apps` → `home-place-settings`, each hop taken by handle and each waiting on the _next_ surface's handle, so no hop keys on copy. Settings is the last row of the sheet's places half, so it is scrolled to at full visibility rather than tapped where the sheet has clipped it. Arrival is asserted on `settings-screen` and on `APPEARANCE`, the first section heading Settings publishes and a string nothing else in the app renders.

The hop rides in the first chunk of the Android airplane arc, off the Home that `configureGateway` leaves the app on, so it costs no launch of its own; on iOS, which has no airplane arc, it is its own small chunk, so the claim holds on both platforms.

**Setup:** install a development build, start Metro, and expose a reachable gateway through `MAESTRO_GATEWAY_URL`. The flow seeds the Tally demo scenario (`ctx.ensureDemo("tally")`, idempotent — the Android journey below needs one real group), clears app state, mints a pairing ticket, and redeems it through ticket-only onboarding, accepting the named-owner direct completion or the unnamed-profile branch, before exercising the shell. For the manual matrix, grant photo-library permission and seed at least one local photo, one document, and one calendar event. Run the 50k deterministic fixture with `cd apps/mobile && bun test timeline-50k` before the device flow.

**Automated steps:** configure the declared gateway; open Settings from the all-apps sheet and assert `APPEARANCE`. On Android, force-stop and relaunch without clearing state, open one group's ledger **while the gateway still answers** (the composer divides between that group's members, and they arrive with the group payload), enable the OS airplane mode through Maestro, add an expense through the composer's two typed fields, assert the foot names where the write lands before the commit, commit it, and assert the `QUEUED` row and its reason sentence on the band's Waiting place. Then force-stop and relaunch without clearing state while still offline, reopen Tally, return to Waiting, and assert the same row, reason and own-scope sentence. **Then restore the radio and prove the round trip closes** (see below). Both platforms then force-stop and relaunch once more and assert Home returns; the post-restart Home frame is also published to `artifacts/e2e/ui-impact/issue-799-mobile-native-home.png` as the UI-impact evidence that the launcher is all-native after the WebView app cover retired (#799). This proves the production UI → session → SQLite outbox restart path on the platform whose emulator exposes a real airplane control.

**The offline round trip ([#890](https://github.com/srikanth235/centraid/issues/890) W4).** The claim is one arc — **offline write → survives process death → reconnects and settles** — and it stops being a claim about the product if it ends at the middle step. So after the post-restart `QUEUED` assertions the flow disables airplane mode with the app foregrounded on Waiting (the state a member is in when a train leaves a tunnel), then force-stops and relaunches once more: `native-session.ts` flushes the outbox on every session open and on AppState changes, so the relaunch is what makes the drain deterministic rather than a race against retry backoff. The settled state is asserted in the surface's own words — `contrib-model.ts` drops an `executed` intent from Waiting entirely ("it settled, and the ledger below is where it now lives"), so a drained outbox is the in-flight section saying `Nothing in flight.`, not a row that turned green. The empty sentence is guarded against vacuity by asserting Waiting's own scope line beside it and the queued reason's absence. The radio restore is the settled chunk's first command rather than a chunk of its own, and the `finally` cleanup runs the same directive only when that chunk was never reached — so a failure anywhere in the arc still leaves the emulator online, without a second `maestro test` on every green run.

**iOS is an honest gap here, and stays one.** `setAirplaneMode` is a Maestro Android command driving the emulator's radio; the iOS Simulator exposes no airplane control to any CLI Maestro can reach, so this device has no way to be taken offline on that side at all. The store/read half of the same contract is held on every platform by the integration companions below. Faking offline in JS is explicitly not the fix: a faked radio proves the fake.

**Why Waiting, and not the expense's description.** Tally's writes are ordinary and queue in the durable outbox; its derived reads are gateway RPCs, because `queries/dashboard.ts` holds the app's one balance engine (`apps/mobile/src/apps/tally/tally-gateway.ts`). An offline relaunch therefore lands no ledger at all, and the description the flow typed is on no screen. Waiting is the surface that is true offline: it folds `session.pendingChanges()` — this device's own outbox — into rows with a status chip and a reason. The pre-#872 flow asserted the description after the offline relaunch; that assertion named a dashboard read rather than the queued write, and would be red against the rebuilt cover for a reason unrelated to its claim.

**Automated pending-write companion:** `apps/mobile/src/lib/replica/multi-vault-reader.test.ts` drives real `NativeReplicaSession.write()` calls for a Tally expense, Task add, Agenda RSVP, and Note create while disconnected, closes that session, then mounts and remounts the production multi-vault reader over the same SQLite file. `apps/mobile/src/apps/tally/PendingRestartJourney.test.tsx` is the rendered half: it records an expense through the real `TallyAddScreen`, reads it back through `TallyHome`'s Waiting place, then closes session, reader and store and rebuilds all three over the same `node:sqlite` file — asserting the same queued row, the same durable intent id, and the pending expense itself through the mounted reader's overlay. Together they cover stable intent keys, queued status/chip, vault provenance, and the Agenda row's captured canonical base version on iOS-compatible infrastructure. Run them through the mobile package test script; the Android device step above is the visual/touch and OS lifecycle proof.

**Manual network matrix (record observations in the run verdict):**

1. The Android lane automates the Tally add/restart/reconnect assertion. Manually add a Task, Agenda RSVP, and Note in the same airplane-mode session; each projected row must appear immediately with a `queued` chip and “Waiting for a connection.” Force-stop and relaunch without clearing state; all three rows must still be present. Existing Photos, Docs search, and Agenda ranges must also remain readable.
2. Disable airplane mode and verify the remaining three queued intents settle without duplicate rows (the automated lane already covers the Tally one). Exercise one parked result (reason and Settings → Approvals affordance) and one denied/conflict/failed result (reason plus Retry and Discard); a conflict must print expected and actual versions.
3. Start a large upload on Wi-Fi, walk onto cellular, then back to Wi-Fi. With Wi-Fi-only enabled the queue must halt and resume; with it disabled the iroh tunnel should heal without restarting the part ledger.
4. Force-kill during every visible upload state and relaunch. The queue should resume by SHA/part receipt and create one CAS object.
5. On Android, leave the foreground service active until the six-hour cap in a soak run; the next lifecycle drain must resume and the notification must always state `Backing up N of M`.

**Verdict:** PASS when the automated flow succeeds and the run verdict records the manual network observations for the device/OS under test.
