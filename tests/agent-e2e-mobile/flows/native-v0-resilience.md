# native-v0-resilience

**Goal:** preserve a repeatable native v0 smoke and resilience matrix across the Home springboard, all eight blueprint covers (Photos, Docs, Agenda, Tasks, People, Notes, Tally, and Locker), and Settings.

There is no bottom-tab navigator (`apps/mobile/src/navigation.ts`): all eight apps are full-screen covers launched from Home's tiles, and Settings opens from the vault drawer. Each surface is therefore entered the way a user enters it — by the tile's `Open <name>` accessibility label — and asserted on a string that only the opened screen publishes, never on the tile or drawer label, which can be visible before the destination opens. Covers dismiss with a native swipe-down gesture Maestro cannot drive, so each surface starts from a fresh launch; React Navigation state is not persisted, so every launch lands on Home.

**Every arrival marker is the string its own app's journey already uses**, traced to where the cover publishes it: Photos and People take a band destination (`Collections`, `Touch`), Docs the All shelf's foot sentence with its count, Agenda and Notes a header control (`Go to today`, `New note`), Tasks the capture field at the foot of every Tasks destination, and Tally and Locker each cover's **app-bar ambient sentence** — which is what the v17 rebuild ([#872](https://github.com/srikanth235/centraid/issues/872)) gave both of them in place of a fixed subtitle. The pre-rebuild list keyed on `Search photos`, `Add document or folder`, `Create event`, `New task title`, `Person name`, `Search notes`, a Tally subtitle and a Locker subtitle; of those, only the Notes string still existed anywhere in the repository, and that one on the web seat's frame rather than on this cover. A marker matching nothing is a step that is red for a reason unrelated to its claim, which is the other half of what [#483](https://github.com/srikanth235/centraid/issues/483) is about — so the markers now agree, file for file, with `photos-library.mjs`, `docs-drive.mjs`, `agenda-week.mjs`, `notes-library.mjs`, `tally-derived.mjs` and `locker-gate.mjs`.

**Setup:** install a development build, start Metro, and expose a reachable gateway through `MAESTRO_GATEWAY_URL`. The flow seeds the Tally demo scenario (`ctx.ensureDemo("tally")`, idempotent — the Android journey below needs one real group), clears app state, mints a pairing ticket, and redeems it through ticket-only onboarding, accepting the named-owner direct completion or the unnamed-profile branch, before exercising the shell. For the manual matrix, grant photo-library permission and seed at least one local photo, one document, and one calendar event. Run the 50k deterministic fixture with `cd apps/mobile && bun test timeline-50k` before the device flow.

**Automated steps:** configure the declared gateway; launch without clearing state; open all eight blueprint covers from Home plus Settings from the vault drawer. On Android, open one group's ledger **while the gateway still answers** (the composer divides between that group's members, and they arrive with the group payload), enable the OS airplane mode through Maestro, add an expense through the composer's two typed fields, assert the foot names where the write lands before the commit, commit it, and assert the `QUEUED` row and its reason sentence on the band's Waiting place. Then force-stop and relaunch without clearing state while still offline, reopen Tally, return to Waiting, and assert the same row, reason and own-scope sentence before restoring the network in a `finally` cleanup. Both platforms then force-stop and relaunch once more and assert Home returns; the post-restart Home frame is also published to `artifacts/e2e/ui-impact/issue-799-mobile-native-home.png` as the UI-impact evidence that the launcher is all-native after the WebView app cover retired (#799). This catches navigation regressions and proves the production UI → session → SQLite outbox restart path on the platform whose emulator exposes a real airplane control.

**Why Waiting, and not the expense's description.** Tally's writes are ordinary and queue in the durable outbox; its derived reads are gateway RPCs, because `queries/dashboard.ts` holds the app's one balance engine (`apps/mobile/src/apps/tally/tally-gateway.ts`). An offline relaunch therefore lands no ledger at all, and the description the flow typed is on no screen. Waiting is the surface that is true offline: it folds `session.pendingChanges()` — this device's own outbox — into rows with a status chip and a reason. The pre-#872 flow asserted the description after the offline relaunch; that assertion named a dashboard read rather than the queued write, and would be red against the rebuilt cover for a reason unrelated to its claim.

**Automated pending-write companion:** `apps/mobile/src/lib/replica/multi-vault-reader.test.ts` drives real `NativeReplicaSession.write()` calls for a Tally expense, Task add, Agenda RSVP, and Note create while disconnected, closes that session, then mounts and remounts the production multi-vault reader over the same SQLite file. `apps/mobile/src/apps/tally/PendingRestartJourney.test.tsx` is the rendered half: it records an expense through the real `TallyAddScreen`, reads it back through `TallyHome`'s Waiting place, then closes session, reader and store and rebuilds all three over the same `node:sqlite` file — asserting the same queued row, the same durable intent id, and the pending expense itself through the mounted reader's overlay. Together they cover stable intent keys, queued status/chip, vault provenance, and the Agenda row's captured canonical base version on iOS-compatible infrastructure. Run them through the mobile package test script; the Android device step above is the visual/touch and OS lifecycle proof.

**Manual network matrix (record observations in the run verdict):**

1. The Android lane automates the Tally add/restart assertion. Manually add a Task, Agenda RSVP, and Note in the same airplane-mode session; each projected row must appear immediately with a `queued` chip and “Waiting for a connection.” Force-stop and relaunch without clearing state; all three rows must still be present. Existing Photos, Docs search, and Agenda ranges must also remain readable.
2. Disable airplane mode and verify the four queued intents settle without duplicate rows. Exercise one parked result (reason and Settings → Approvals affordance) and one denied/conflict/failed result (reason plus Retry and Discard); a conflict must print expected and actual versions.
3. Start a large upload on Wi-Fi, walk onto cellular, then back to Wi-Fi. With Wi-Fi-only enabled the queue must halt and resume; with it disabled the iroh tunnel should heal without restarting the part ledger.
4. Force-kill during every visible upload state and relaunch. The queue should resume by SHA/part receipt and create one CAS object.
5. On Android, leave the foreground service active until the six-hour cap in a soak run; the next lifecycle drain must resume and the notification must always state `Backing up N of M`.

**Verdict:** PASS when the automated flow succeeds and the run verdict records the manual network observations for the device/OS under test.
