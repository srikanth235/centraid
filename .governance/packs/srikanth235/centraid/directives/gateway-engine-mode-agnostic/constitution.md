### gateway-engine-mode-agnostic

- **Directive**: code under `crates/gateway-core/src/**` and `crates/gateway-server/src/**` may not branch on which deployment it is running in. Specifically, deployment-discrimination identifiers (`GatewayMode`, `GatewayKind`, `DeploymentMode`, `HostingMode`, `gateway_mode`, `gateway_kind`, `deployment_mode`, `hosting_mode`, `is_hosted`, `is_standalone`, `is_cloudflare`, `is_worker`, `is_self_hosted`) are forbidden in tracked source files. What genuinely differs between the deployments goes behind a port: `ByteStore` for where bytes live, `StateStore` for where state lives, the adapter's own path for how a member is admitted, and `ChecksumMode` for which evidence a store can produce — which is deliberately *not* on the forbidden list, because it is a property of the store the adapter was pointed at rather than of the adapter, and the conformance suite runs both of its halves.
- **Rationale**: the gateway is **one protocol with two deployments** (#1029 §3) — a paid hosted offering on Cloudflare and a standalone server anyone can self-host — and *neither is the reference implementation: the protocol and its conformance suite are*. The property that makes that work is the one v0 named "same code, three hosts": once the engine starts checking which host it lives inside, the paths diverge and "works on the hosted one" becomes a class of bug again — this time on a phone somebody is restoring, which is the worst place to find it. The subject moved from `packages/server/src/engine/` to the two gateway crates when v1 replaced the TypeScript server; the principle did not move at all, and a check whose glob matched nothing would have been a check passing for the wrong reason.
- **Enforced by**: `.governance/packs/srikanth235/centraid/directives/gateway-engine-mode-agnostic/check.sh`
- **Door**: hook (pre-commit), and again in CI.
- **Host enforces**: the `governance` workflow.
- **Rule observes**: nothing; the discriminating identifiers are a fixed list.
- **Also enforced in-repo**: `crates/gateway-core/tests/wasm_clean.rs::no_rule_branches_on_which_deployment_it_is_running_in` scans the rules crate from inside `cargo test`, and `crates/gateway-server/tests/no_rules_here.rs::this_adapter_never_asks_which_deployment_it_is` scans the adapter. Those fail a run; this refuses a commit. Neither is a substitute for the other, and the directive is what holds the principle for a gateway crate that has no test of its own yet.
- **Exceptions**: per-line waiver `// governance: allow-gateway-engine-mode-agnostic <reason>` for the rare case where a gateway genuinely needs to know which deployment it is (none today; the architecture promise is that no such case should exist).
