# `contracts/apps/photos`

Photos' parity bundle: a **frozen golden** of what the TypeScript tree's own Photos handlers answered, captured before that tree was removed in [#1020](https://github.com/srikanth235/centraid/issues/1020), and compared value for value by `crates/apps/photos/tests/parity.rs`.

## What is here

| File | How it was made |
| --- | --- |
| `manifest.json` | The bundle's own declaration: the eight query names, the case counts, the three `order: "set"` cases, and why presentation is deferred. |
| `rows.json` | Every row of the twenty-one tables the eight queries read, by table, as canonical JSON — rows plus the committed DDL, never a `.db.gz` (D-1020-D3-11). |
| `queries.json` | `{query, input, output}` for all eight queries at 21 fixed inputs. |
| `commands.json` | `{command, input, status, output}` for 32 `media.*`/`enrich.*` cases, **seven of them refusals**. |
| `scenarios.json` | The three ontology scenarios a photograph is subject to: ONT-22, ONT-26, ONT-28. |
| `sample/*.png` | The demo roll's frames. Each file's length is asserted against `sample/manifest.json` by `crates/apps/photos/tests/parity.rs`. |
| `sample/manifest.json` | Generated from those files by `cargo xtask photos-sample` (#1025 S4): width, height, long edge, byte size and the BLAKE3 `content_hash`, plus the one inline video payload the demo seed carries as base64 rather than as a file — whose bytes are now `INLINE_VIDEO_BASE64` in that generator, because a frame whose bytes nothing holds is a digest nobody can check. |
| `recognition-placement.md` | Open question 9's third execution site, designed and **not built** — a proposal for the owner to integrate. |

## How the bundle was made

The capture founded a fresh vault, ran the app's demo seed plus a scripted command set through the **real** typed vault commands, ran the two sweeps, then invoked every Photos query through the real handler path and wrote what came back. Nothing here was typed from a belief about the handlers, and nothing was generated by the Rust side. That generator went with the TypeScript tree, so a change to these four files is a reviewed change in expected behaviour; only `sample/manifest.json` is still regenerated (`cargo xtask photos-sample`).

## Why ids and ORDER are compared, and not just shapes

`rows.json` is the state `queries.json` was read from, and both are canonicalised in **one pass over one vault**: an identifier gets the same token wherever it appears, so `id-0049` in a query's answer is the row `id-0049` in `rows.json`. That is what lets `crates/apps/photos/tests/parity.rs` build its vault **from the rows** and then compare the ported answers _including the page's order_ — not counts and field names.

Two consequences of the same pass:

- **Host-clock instants are one token**, `(host-clock)`. SQLite writes `created_at`/`updated_at` off its own clock, which no injected clock holds still. The token is parenthesised on purpose: `(` sorts below every digit under BINARY collation, and the host clock is below the 2099 fixture epoch — so an undated asset, whose `taken_at` falls back to `created_at`, still rides the END of a newest-first page exactly where the real instant put it. An angle-bracketed token sorts ABOVE the digits and would have moved those assets to the front of every page.
- **A 64-hex sha is not a token.** It is a fact about the bytes, it is reproducible, and a port compares it.

## The one case that is not the swept state

`storage` appears twice. The case marked `phase: "unswept"` was read **before** the sweeps ran: `computedAt: null` with every bucket zero. Every other case, and every row, is the swept state. The pair is the whole of D-1020-P1 — two answers that differ in `computedAt` alone, which is the difference between "nothing to free" and "not counted yet", and the one a renderer gets wrong.

The sweeps were run by the capture because **no command writes what they write**: `blob_custody_rollup` is `refreshCustodyRollup`'s and `media_asset_phash.cluster_id` is `recomputeDuplicateClusters`'s. Without them `duplicates` answers `{clusters: []}` for every corpus — which would have made the fixture agree with a port that does nothing.

## The `THUMB_EDGE` coupling, which is why `sample/manifest.json` exists

Every frame is **≤ 360 px on its long edge on purpose**: that is the Photos grid's `THUMB_EDGE` "known small" ceiling, so a tile paints the original instead of probing a `?variant=thumb` derivative the gateway's preview backstop has not generated yet. The manifest records the dimensions and `every_shipped_sample_is_small_enough_for_the_grid_to_paint_directly` fails if any frame grows past the ceiling — including the assertion that one frame sits _exactly_ at it, so the test would notice the ceiling moving.

## Two things the comparison does not carry

**Presentation is not compared** (`design: "deferred"`, D-1020-D3-9). Outputs carry `partyHueValue`, `identityInitials` and `figureTone` from `packages/design`; the manifest declares them deferred and the parity test does not read them. A golden is never edited to drop fields, so those fields are present and unread.

**Three rosters compare as a SET.** `photos.faceQueue.parties`, `photos.faces.parties` and `photos.people.parties` order by `core_party.display_name`, which SQLite compares under `BINARY` collation and the captured implementation rendered under `localeCompare`. For an ASCII roster the two agree; for a non-ASCII one they do not, so those cases' ordering is not part of the comparison (D-1020-D3-6).
