# `contracts/apps/photos`

Photos' parity bundle: what v0's own handlers answer, generated from the v0 tree and compared value for value by the Rust port.

## What is here

| File | How it was made |
| --- | --- |
| `manifest.json` | The bundle's own declaration: the eight query names, the case counts, the three `order: "set"` cases, and why presentation is deferred. |
| `rows.json` | Every row of the twenty-one tables the eight queries read, by table, as canonical JSON — rows plus the committed DDL, never a `.db.gz` (D-1020-D3-11). |
| `queries.json` | `{query, input, output}` for all eight queries at 21 fixed inputs. |
| `commands.json` | `{command, input, status, output}` for 32 `media.*`/`enrich.*` cases, **seven of them refusals**. |
| `scenarios.json` | The three ontology scenarios a photograph is subject to: ONT-22, ONT-26, ONT-28. |
| `sample/*.png` | Copied **byte for byte** from `packages/blueprints/apps/photos/sample`. Asserted identical by `crates/apps/photos/tests/parity.rs`. |
| `sample/manifest.json` | Generated from those files: width, height, long edge, byte size, sha256, plus the one inline video payload v0's seed carries as base64 rather than as a file. |
| `recognition-placement.md` | Open question 9's third execution site, designed and **not built** — a proposal for the root to integrate. |

## One generator, one oracle, one command

`contracts/tools/export-photos-parity.ts` founds a fresh v0 vault, runs the app's own 551-line demo seed plus a scripted command set through the **real** typed vault commands, runs v0's two sweeps, then invokes every Photos query through the real handler path and writes what came back. Nothing here was typed from a belief about v0, and nothing was generated by the port.

`tests/quality/photos-parity.contract.test.ts` is that generator's **emitter and its check**, as Tally's is: with `CENTRAID_WRITE_CONTRACTS=1` it writes the four files, and without it it rebuilds the bundle from the live v0 tree and asserts equality with what is committed. So "the fixture passes in v0 too" is one command, not a second suite that could rot.

```
node node_modules/vitest/vitest.mjs run --config vitest.quality.config.ts \
  tests/quality/photos-parity.contract.test.ts
bun run format && git diff --exit-code contracts/apps/photos
```

With `CENTRAID_WRITE_CONTRACTS=1` in front, the same command regenerates. A second run writes nothing — that is what makes the generator idempotent rather than merely re-runnable.

## Why ids and ORDER are compared, and not just shapes

`rows.json` is the state `queries.json` was read from, and both are canonicalised in **one pass over one vault**: an identifier gets the same token wherever it appears, so `id-0049` in a query's answer is the row `id-0049` in `rows.json`. That is what lets `crates/apps/photos/tests/parity.rs` build its vault **from the rows** and then compare the ported answers _including the page's order_ — not counts and field names.

Two consequences of the same pass:

- **Host-clock instants are one token**, `(host-clock)`. SQLite writes `created_at`/`updated_at` off its own clock, which no injected clock holds still. The token is parenthesised on purpose: `(` sorts below every digit under BINARY collation, and the host clock is below the 2099 fixture epoch — so an undated asset, whose `taken_at` falls back to `created_at`, still rides the END of a newest-first page exactly where the real instant put it. An angle-bracketed token sorts ABOVE the digits and would have moved those assets to the front of every page.
- **A 64-hex sha is not a token.** It is a fact about the bytes, it is reproducible, and a port compares it.

## The one case that is not the swept state

`storage` appears twice. The case marked `phase: "unswept"` was read **before** the sweeps ran: `computedAt: null` with every bucket zero. Every other case, and every row, is the swept state. The pair is the whole of D-1020-P1 — two answers that differ in `computedAt` alone, which is the difference between "nothing to free" and "not counted yet", and the one a renderer gets wrong.

The sweeps are run by the generator because **no command writes what they write**: `blob_custody_rollup` is `refreshCustodyRollup`'s and `media_asset_phash.cluster_id` is `recomputeDuplicateClusters`'s. Without them `duplicates` answers `{clusters: []}` for every corpus — which would have made the fixture agree with a port that does nothing.

## The `THUMB_EDGE` coupling, which is why `sample/manifest.json` exists

Every frame is **≤ 360 px on its long edge on purpose**: that is the Photos grid's `THUMB_EDGE` "known small" ceiling (`packages/blueprints/apps/photos/media.ts:16`–`:28`), so a tile paints the original instead of probing a `?variant=thumb` derivative the gateway's preview backstop has not generated yet. v0 states the coupling in a comment in `seed.js` and **nothing on either side tested it** (wave 4 census, §A seam 3). The manifest records the dimensions and `every_shipped_sample_is_small_enough_for_the_grid_to_paint_directly` fails if any frame grows past the ceiling — including the assertion that one frame sits _exactly_ at it, so the test would notice the ceiling moving.

## Two things the comparison does not carry

**Presentation is deferred** (`design: "deferred"`, D-1020-D3-9). Outputs carry `partyHueValue`, `identityInitials` and `figureTone` from `packages/design`, which has no Rust home until `design/` lands. A generated fixture is never edited to drop fields, so those fields are present and not read.

**Three rosters compare as a SET.** `photos.faceQueue.parties`, `photos.faces.parties` and `photos.people.parties` order by `core_party.display_name`, which SQLite compares under `BINARY` collation and v0 renders under `localeCompare`. For an ASCII roster the two agree; for a non-ASCII one they do not, so those cases' ordering is not part of the comparison (D-1020-D3-6).
