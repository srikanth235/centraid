# `contracts/apps/photos`

Photos' parity bundle. What is here, what is not, and the one command that finishes it.

## What is here

| File | How it was made |
| --- | --- |
| `manifest.json` | The bundle's own declaration: the eight query names, the command-case count, the `order: "set"` cases, and — for now — `fixtures: "pending-regeneration"`. |
| `sample/*.png` | Copied **byte for byte** from `packages/blueprints/apps/photos/sample`. Asserted identical by `crates/apps/photos/tests/parity.rs`. |
| `sample/manifest.json` | Generated from those files: width, height, long edge, byte size, sha256, plus the one inline video payload v0's seed carries as base64 rather than as a file. |
| `recognition-placement.md` | Open question 9's third execution site, designed and **not built** — a proposal for the root to integrate. |

## The `THUMB_EDGE` coupling, which is why `sample/manifest.json` exists

Every frame is **≤ 360 px on its long edge on purpose**: that is the Photos grid's `THUMB_EDGE` "known small" ceiling (`packages/blueprints/apps/photos/media.ts:16`–`:28`), so a tile paints the original instead of probing a `?variant=thumb` derivative the gateway's preview backstop has not generated yet. v0 states the coupling in a comment in `seed.js` and **nothing on either side tested it** (wave 4 census, §A seam 3). The manifest records the dimensions and `every_shipped_sample_is_small_enough_for_the_grid_to_paint_directly` fails if any frame grows past the ceiling — including the assertion that one frame sits *exactly* at it, so the test would notice the ceiling moving.

## What is NOT here, and why it is not a skipped test

`rows.json`, `queries.json`, `commands.json` and `scenarios.json` — v0's own answers — are not committed. Producing them needs `bun install` plus `bun run build` and the whole v0 handler graph, and the machine the lane ran on had **2.6 GB of disk free** with four Rust lanes sharing one 18 GB cargo target; `bun install` in this worktree needs about that much on its own.

So instead of a fixture nobody could generate or a test that reads green while proving nothing:

- the generator is **committed and unrun**: `contracts/tools/export-photos-parity.ts`, with a header saying so and naming the evidence the run must produce;
- `manifest.json` declares `fixtures: "pending-regeneration"`;
- `crates/apps/photos/tests/parity.rs`'s `the_fixture_bundle_is_declared_pending_and_says_so_out_loud` **asserts that declaration**, so the Rust suite being green cannot be mistaken for parity by anyone reading it.

Nothing here was typed by hand from a belief about v0, and nothing here was generated by the port.

## Finishing it

In a worktree with disk:

```
bun install && bun run build
node node_modules/vitest/vitest.mjs run --config vitest.quality.config.ts \
  tests/quality/photos-parity.contract.test.ts
bun run format && git diff --exit-code contracts/apps/photos
```

Expected evidence:

1. four JSON files appear here;
2. a **second** run of the same command writes nothing — `git diff --exit-code` passes, which is what makes the generator idempotent rather than merely re-runnable;
3. `the_fixture_bundle_is_declared_pending_and_says_so_out_loud` **fails**. That failure is the signal: replace it with the comparison and drop `fixtures` from `manifest.json`.

The oracle test under `tests/quality/` is the fixture's emitter **and** its check, as Tally's is: with `CENTRAID_WRITE_CONTRACTS=1` it writes, and without it it rebuilds the bundle and asserts byte-equality with what is committed. So "the fixture passes in v0 too" is one command rather than a second suite.

## Two things the comparison will have to carry

**Presentation is deferred** (`design: "deferred"`, D-1020-D3-9). Outputs carry `partyHueValue`, `identityInitials` and `figureTone` from `packages/design`, which has no Rust home until `design/` lands. A generated fixture is never edited to drop fields.

**Three cases compare as a SET.** `photos.faceQueue.parties`, `photos.faces.parties` and `photos.people.parties` order by `core_party.display_name`, which SQLite compares under `BINARY` collation and v0 renders under `localeCompare`. For an ASCII roster the two agree; for a non-ASCII one they do not, so the case's ordering is not part of the comparison (D-1020-D3-6).
