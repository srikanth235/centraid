### Wave 2 — the fulfillment engine

- `packages/vault/src/grant/fulfillment.ts` (new, 489 lines): `fulfillShareGrant` — one pass over a grant's audience parties. For each: no channel → `mintGrantInvitation` + `awaiting_channel` (peer vault known) or invitation-only (no vault to name); live channel but peer vault not mounted here → `syncing` with a detail naming the vault; deliverable → the view strategy: the prior projection is found via the audience's `core_share_origin`, scrubbed with `unshareFromVault`, and the CURRENT closure re-projected in one audience transaction — origin-authoritative re-projection, no CRDT, so an origin caption/body edit follows on the next pass and a crash can never leave the audience empty under a live grant. Per-grant `max_size_bytes` (default: the commons ceiling constant — no second budget) is checked before ANY state moves in any branch — the closure is read ahead of the party loop, so an over-ceiling grant leaves no fulfillment row whatever mix of parked, unreachable, and deliverable audiences it has; `ShareGrantMaxSizeError` names grant and sizes. The owner is skipped when a circle audience contains the granter. `propagateShareGrantRevocation` — stops sync, hard-deletes the audience projection (no tombstone, the v1 default). A DELIVERED row ends `removed` only by looking inside the audience vault (deleting the projection, or finding it verifiably already gone, each with its own detail); an unreachable delivered peer keeps `remove_sent` with an honest detail, never a faked `removed`; a row that never got past `awaiting_channel`/`syncing` ends `removed` with the detail "nothing had been delivered; there was nothing to remove" — never a fabricated "removal sent" to a peer that received nothing. Pending grant invitations are withdrawn with the grant.
- `packages/vault/src/grant/fulfillment-edit.ts` (new, 192 lines at wave time, 225 now after the waves 5–7 seam fix added `shareGrantEditRefusal`): `routeShareGrantEdit` — resolves a command's container via `commonsRoutesForCommand` (the declared table, never string heuristics), finds live `share_grant` rows over the resolved containers, and hands delegation to `commonsGrantForCommand` so the commons rail's own decision routes the write; commons steward/quota/recovery behavior untouched. Two v1 refusals are explicit `refusal` results, never silent success: co-contribution outside `tally.group`, and an edit grant over a container with no commons rail (the #750 failure mode).
- `packages/vault/src/grant/fulfillment-invite.ts` (new, 188 lines): `mintGrantInvitation` reuses the commons machinery (`queueCommonsInvitation` when the peer vault is known, `createCommonsClaimInvitation` when nothing is), written into the origin vault — the row `channelForParty` reads to answer `invited`; a standing pending invitation is reported, not re-minted, so a claim token never rotates out from under a sent link. `withdrawGrantInvitations` hard-deletes pending invitation rows carrying a share-grant id on revoke.
- `packages/server/src/serve/grant-fulfillment.ts` (new, 137 lines): the host seam — `fulfillGrantsForSubject` (every live grant over a subject, failures isolated per grant and reported with reasons, not thrown) and `propagateGrantRemoval`. ## Decisions

The judgment calls the diff cannot show.

#825 re-pins packages/server/src/routes/route-security.ts after the grant-routes owner-tier row. Qualities, demonstratedRed, and matrixGovernanceFingerprint are unchanged. Prior: #821.

**Atlas first-paint census does not COUNT grant-plane tables (#825, rebase-onto-#828 gates).** Registering `share.grant` and `share.fulfillment` in `VAULT_TABLES` is required — portable export and the replica change log would otherwise restore a vault that had forgotten who it shares with. Atlas stats first paint, though, is one `COUNT(*)` per registered table, and those two statements pushed the measured Atlas SQL from 140 to 142. The budget is not widened: grant-plane row counts are not required to draw Atlas Kinds on first paint (life-data packs and the rest of the Sharing machinery still count), the lazy graph still maps both tables via `atlasTables()`, and "how many grants" is already answered by the grant surfaces. Widening `atlas.sqlStatements` 140 → 142 would have been the #807 enrichment pattern; cutting the extra first-paint queries is the tighter answer.

**Rulings land ahead of code, deliberately.** Wave 0 records the #825 decisions as current answers while the grant tables do not exist yet; the issue's execution plan orders it so ("docs coherent before any code moves"), and the G-section says so in one line. Glossary Code cells name the table names the schema wave ships (`share_grant`, `share_fulfillment`), not file paths that do not exist yet.

**Edge/closure vocabulary stays put until the code dies.** The glossary's `edge`, `closure`, `projection` rows and the `placement_intents` synonym row still describe live code; they are wave-8 retirement-sweep work, not wave-0 work.

**Give row deleted, not annotated.** Following the file's own precedent for **lend**, the retired vocabulary moved to the closing paragraph rather than surviving as a struck-through table row.

**Audience is `audience_kind + audience_id`, not `audience_party_id`.** The issue's sketch says "who (person or circle)", but a circle is not a party (`social_circle`, not `core_party`), so one FK column could not be honest about both. The kind column makes the polymorphism explicit; `granted_by` stays a real `core_party` FK.

**Migration is hybrid, not per-party-for-everything.** A named circle whose members agree on one capability **and contain no refusal** stays **one circle-audience grant** — this also keeps a live grant over an empty named circle alive (at the conservative `view` floor) where per-party decomposition would silently drop it. Implicit circles, capability-variant circles, and circles containing a refused member decompose per party (`read→view`, `read+write→edit`): a circle-audience row over a roster containing a refused party would keep reaching that party through the roster union, so a refusal forces decomposition, and refused members — never a standing permission — get no grant. The limit case is a deliberate, tested ruling: a live named-circle grant **every** member refused permits no one and migrates to nothing; the commons row and the refusals survive untouched as the record, and re-sharing the circle re-creates it. Collisions (two commons grants reaching the same party × subject) are ranked deterministically: strongest capability, earliest granted_at, then source grant id — tested. One consequence decomposition accepts: a decomposed grant no longer follows the circle's roster, so a party added to that circle later is not reached until the owner shares again — the price of never reaching a refused party; wave 2's roster-recompile work records this in `docs/decisions.md` when it lands.

**A member with no binding row gets no fulfillment row.** The fulfillment PK needs a `peer_vault_id` and there is none to name; absence simply means "no channel yet" — the channel question is answered separately by `channelForParty` over bindings and pending invitations, so nothing needs a placeholder row. A member whose only binding is revoked keeps that vault id at `awaiting_channel`. This is the absent-never-empty rule applied at the schema layer, not a data loss.

**`packages/vault/src/grant/` is deliberately outside `share-reachability.json` in this wave.** The reachability gate demands a production caller for every export of the listed share modules, and the grant store's production callers arrive with the gateway routes; adding the glob before they exist would force a fake caller. The glob lands in wave 3 — wave 2's engine is itself production-uncalled until the routes wire it, a promise the wave-2 audit re-dated.

**Writers take input objects, readers stay positional.** Every write needs a caller-supplied timestamp (no host clock in the vault), matching `share/party-vault-binding.ts`'s house style.

**View delivery is scrub-then-reproject in one audience transaction (wave 2).** `projectShareClosure` dedupes by sha256 and row id — right for one-time placement, wrong for a standing grant (a caption edit would never land). The engine finds the prior projection via the audience's `core_share_origin`, removes it with `unshareFromVault`, and projects the current closure, all under one transaction, so a crash never leaves the audience empty under a live grant. Membership-not-snapshot costs no code: `readShareClosure` re-walks the container every pass.

**`removed` is never faked; `syncing` is honest transit (wave 2).** A delivered row advances past `remove_sent` only by looking inside the audience vault; an unreachable delivered peer keeps `remove_sent` with a detail saying the peer has not acknowledged; a never-delivered row ends `removed` with a detail saying nothing had been delivered — three distinct honest answers, each tested. A live channel whose peer vault is not mounted on this host reports `syncing` with the vault named — the ask stands, the grant has not failed.

**Revoke withdraws the grant's own pending invitations (wave 2).** `withdrawGrantInvitations` hard-deletes pending `share_commons_invitation` rows carrying a share-grant id — leaving them would keep `channelForParty` answering `invited` for a grant that no longer stands. This touches a table whose lifecycle the commons plane owns, but only rows the grant plane itself minted and only while still pending; accepted/refused history is untouched. If commons should own the verb, a commons-side withdraw is the follow-up shape.

**Per-grant ceiling reuses the commons budget constant (wave 2).** `max_size_bytes ?? COMMONS_DEFAULT_MAX_SIZE_BYTES`, checked before any fulfillment state moves so an over-ceiling grant leaves no row; `ShareGrantMaxSizeError` names grant and sizes. No second budget exists.

**The server seam isolates failures per grant (wave 2).** One over-ceiling or unreachable audience must not stall everyone else's delivery: `fulfillGrantsForSubject` reports each grant's outcome with reasons instead of throwing, and stays unwired until wave 3 adds the `build-gateway.ts` hook — nothing calls it in production yet, deliberately.

**The refresh doorbell is subject-scoped, not row-scoped (wave 3).** The post-commit hint carries entity *types*, never row ids, so a refresh pass covers every live grant subject in the vault (one `SELECT DISTINCT` over `share_grant`; a vault with no grants pays one indexed read). Narrowing by committed type would silently drop G-membership — a photo added to a shared album commits the membership row, not the album — so the wide pass is the correct one. Coalescing is per vault at 250 ms; the doorbell swallows its own failures so fulfillment can never fail a commit.

Its costs, stated plainly and accepted for v1 rather than claimed away:

- It fires on **every provenance commit** in the vault, not only on commons commands. `recompileCommonsGrants` is the narrower neighbour, not the equal one — it runs `onCommonsCommandSequenced`. A vault with no live grants still pays one indexed read per commit; a vault with grants pays a pass per 250 ms window of writing.
- The **first** ring of a window runs the pass **synchronously on the committing request's path** (`ring` calls `pass` immediately, then arms the trailing window). A burst therefore costs one inline pass plus one trailing pass, not zero inline work.
- Each pass **unconditionally scrubs and re-projects** every live grant's closure — `unshareFromVault` then `projectShareClosure`, in one audience transaction. Idempotent in OUTCOME, not free and not silent: row ids are stable (sha256 + `core_share_origin` lineage), but every audience device sees a full delete-then-insert pass through its change stream. "An extra pass changes nothing" is true of the audience's final state and false of the work and the traffic; the wave-2 comment in `grant-fulfillment.ts` says so.

The accepted trade is correctness-first: a cheaper doorbell needs either row-level commit hints (which the gateway does not carry) or a diff between the projected and current closure (which the engine deliberately does not keep, because origin-authoritative re-projection is what makes a crash unable to leave an audience half-updated). Narrowing it is a follow-up shape, not a v1 requirement.

**`POST /centraid/_gateway/edges` refuses cross-owner pairs (wave 3).** The issue retires the delivery path (`/_peer/edge/give`); leaving the gateway verb that queues a cross-owner give would leave a verb whose only delivery path 404s — a mocked fact. It now refuses with `cross_owner_give_retired` and honest copy; same-owner placement (place/add/move within one owner's vaults) is exactly as before.

**`routeShareGrantEdit` stays allowlisted; its gateway wiring is wave-5 work (wave 3 ruling).** Its real seam is `packages/vault/src/gateway/gateway.ts`'s `invoke`, beside `commonsGrantForCommand` — but the router returns a route (with refusals like "shared for view only") whenever *any* grant exists over a container, so raw wiring would refuse the owner's own edits to subjects they shared for view. The wiring needs actor-awareness and an end-to-end edit proof, which is wave 5's Docs integration exactly; the allowlist entry carries this reason until then. **Landed, with the actor-awareness sharpened (waves 5–7 audit).** The seam does not consume `route.refusal` at all: because that field folds the container's whole grant set together, the caller filters the route's grants to the ones whose audience resolves to the acting party and re-asks the engine over that subset (`shareGrantEditRefusal(route, actorGrants)`); an actor no grant reaches is still left to the consent layer, and the owner still short-circuits before the query. The end-to-end proof is `share-grant-seam.test.ts`'s "where an audience's edit is actually enforced" describe. The second allowlist entry, `share-effects.ts#listQueuedEffects`, keeps the outbox's only inspection point while the outbox still holds obligations — deleting the read belongs to the wave-8 sweep that decides the outbox's shape.

**Dead receive-side give transport was deleted, not allowlisted (wave 3).** The retirement made `pullEdgeClosure`, the queued-blob-pull reads, and the wire-shape verifiers production-unreachable; allowlisting dead code would weaken the gate to go green. What is dead but still *referenced* — `runBlobPull` + the `pull-blob` effect kind (no producer left), `giveEdgeOverPeer`/`denyEdgeOverPeer`, `edges-reconcile-remote.ts`, `collectDerivativeBlobs`, the `deliver-refusal`/`await-answer` effect kinds, cross-owner `receiveSettingFor` rows, `EdgesRouteDeps.peerDial` — is inventoried for the wave-8 sweep.

**The registry decides the verbs; the kit never hardcodes a capability (wave 4).** `edit` is drawn only where `GET …/grants/subjects` answers it, and an unreadable registry offers nothing rather than everything. Capability is derived, not stored: `picked ?? defaultCapability(alreadyStanding)`, so a grant already standing for `edit` never opens as a silent downgrade. Two halves the wave-4 audit added. The registry read has **three** states, not two — `null` (not answered yet), readable-and-empty (the refusal), unreadable (`SubjectRegistry.readable === false`) — because initialising it to `[]` painted "A document cannot be shared as a standing grant" and disabled Share for as long as the gateway took to answer, refusing on the vault's behalf. And what Share SUBMITS is clamped to what the picker could draw (`drawableCapability`): a subject the registry has since narrowed to view-only still carries its old `edit` grant, and a member cannot un-pick a verb that was never drawn. `grantOverSubject` now matches the audience being granted as well as the subject, so a circle's `edit` inside the `?partyId=` union cannot widen a new grant to the person herself.

**One write door per seat, one copy table for both (wave 4).** Only six thin transport calls differ between web (`window.centraid.grants` bridge) and mobile (`nativeGrantDoor(baseUrl)`); parsing, refusal handling, "already shared", and the revoke sentences are decided once in `grant-door.ts`/`grant-copy.ts`. The confirm-dialog copy is the kit's and honestly tensed ("their vault is asked to remove its copy" — the ask, before the act); the after-sentence is always the route's `message` rendered verbatim, never authored client-side, so the engine's three honest removal answers reach the person unparaphrased.

**Not-yet is never an error color (wave 4).** `awaiting_channel`, `channel: null`, and `invited` all paint the seam token — "not yet, and not wrong" — never the `--net`/`--danger` rung (`--danger` is solved from the same base as `--net` in `packages/design/src/roles.ts`, so they are one consequence and not two); `fulfillment: []` renders "Not sent yet", `channel: null` "Not reached yet", `severed` "Link ended", and a 404 audience is `{known: false}`, each with a test. Hosts supply `audiences` and `subjects` (People holds the roster, each app its own objects; `subjectNoun` reads the existing placement registry, no second noun table) and wire `onStatus` to their StatusLine — the kit renders no toast or status line of its own.

**UNKNOWN IS NOT A CLAIM (wave-4 audit).** Four findings, all the same defect wearing four coats: a sheet stating a fact the read had not established.

- **Object-first fabricated reach.** The pinned-subject branch never read a channel, but the reach line rendered `channelReach(null)` for any party audience — so a person on a live channel was told "Not reached yet / Sharing sends an invitation first." Reach is a fact about the PERSON, not about which door the sheet was opened with, so the object-first branch now runs its own `forParty` read beside `forSubject`; a reach read that fails leaves the channel unknown and never blanks the standing list the other read answered.
- **`channel: undefined` is now a fourth state, distinct from `null`.** `null` on the wire is the definite "this vault has never reached them"; an absent key, a non-object, or a state this build does not recognise is DRIFT and parses to `undefined`, which `channelReach` answers `unknown` and the sheets draw as "Checking…". A claim about someone's reach is only ever as good as the read that produced it.
- **Unknown audience no longer collapses.** `forAudience`'s `{known: false}` was parsed and discarded, so a 404 circle read "Nothing shared with Ski trip yet."; worse, the primary `?partyId=` 404 threw through `forParty` and arrived as "Shares could not be read." Both transports now answer `undefined` for a 404 on the party read as they already did for the audience read, `PartyReach` carries `known`, and both sheets say `This vault has no record of <name>.` The unreadable sentence is reserved for actual read failures.
- **No silent capability upgrade.** A standing `view` grant plus "Can edit" plus Share made the route answer `{outcome: "exists"}` with the capability untouched, and the sheet said "Already shared with Priya" — reporting a widening that did not happen. The door now compares the returned grant's capability against the request and answers `exists_other_capability`, which both sheets render as `Already shared with <name> for viewing; changing access is not offered yet — revoke and share again to change it.` Auto revoke-and-regrant is deliberately NOT implemented: it transiently deletes the audience's copy, which is not a decision to make by accident.

Also fixed in the same pass: `docs/blueprint-seats.md` §A named `window.centraid.share({…})` as the one sharing verb and now records `window.centraid.grants` beside it; `grant-wire.ts` had no test and now has its own suite; `esbuild` is declared in `apps/web` rather than reached through hoisting.
