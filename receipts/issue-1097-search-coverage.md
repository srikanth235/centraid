## Decisions

**R1 — fold into the entity's own index.** Applied as the table above. The fold expression is one SELECT, written out in every trigger (SQL has no macros and the schema has no views; a first view would be a new object class for the snapshot, the DDL replay and the sealed scan to learn). The base triggers keep the names `fts_<table>_ai/_au/_ad`; they now insert from `FROM <table> p LEFT JOIN … WHERE p.rowid = new.rowid` rather than from `new.*`, so they and the child triggers run one statement shape. `UPDATE OF <columns>` lists keep a `row_version` touch from re-indexing. An UPDATE that moves a child to another parent (a merge re-points a profile, a channel or a memo) re-indexes the old parent too.

**R1a, R1d — weights, in the door.** 1.0 for the id and every pre-existing column, 0.5 for each folded column. The first version stored them in each rebuilt index's `_config` (`INSERT INTO <fts>(<fts>, rank) VALUES('rank', 'bm25(…)')`); the coordinator's ruling R1d moved them out, because a row of data cannot be in `contracts/schema/vault-ddl.sql`, so a vault built by replaying it ranked differently from a founded one and the fixture vaults the apps' parity tests run on could not stand for a real one. Now `Domain::weights` holds one weight per index column in order (the unfolded domains all 1.0), `Domain::rank_function()` renders `bm25(…)`, and the door binds it to `AND <fts>.rank MATCH ?` — FTS5's rank override — so `ORDER BY <fts>.rank` and the `(rank, id)` keyset are unchanged. `SqliteDoor::open` refuses an index whose column count is not the list's length (`bm25` takes weights by position); `tests/door.rs` also checks that each weight sits on the column it names against a list written out separately. The ranking is tested on a replayed vault and on a founded one, and a test in `door.rs` and one in `search_coverage.rs` hold that no index stores a rank row.

**R1b — what is not folded.** A trashed profile's `nickname`, `role` and `met` (the profile is joined with `deleted_at IS NULL`, and trashing or restoring one is an UPDATE of `deleted_at`, which `fts_core_party_from_people_profile_au` re-indexes); a `general` category. A party never had a `deleted_at` guard in its index and still has none: the people read model filters trashed profiles after the door (`people::roster::load_search`).

**R1c — a Locker memo is in no index.** Every fold and every child trigger selects annotations by `target_type` (`core.party`, `tally.expense`), so a `locker.item` annotation matches no trigger, and `fts_knowledge_annotation`, the one index that held it, is retired. `search_coverage.rs` plants a memo through `locker.set_memo` and scans every `fts_*` table: matched in each index, looked up in each vocabulary, and searched as text in every shadow table's cells, with a party memo as the positive control.

**R3 — the vocabulary.** `fts_<index>_vocab`, `fts5vocab(<index>, 'row')`, persistent because the read connection is `query_only`. The name was checked against everything that recognises an FTS shadow table: `log::guard::FTS_SHADOW_SUFFIXES` (`_content`, `_data`, `_docsize`, `_idx`, `_config`), `contract_vault::is_fts_shadow` (the same five suffixes), `backup::snapshot::census_of` (skips `CREATE VIRTUAL TABLE`), `core.rs::user_tables` and `ontology::base_tables` (skip `fts_%`). `_vocab` is none of the five, so it is a virtual table everywhere it matters and the DDL replay creates it after its index (the file sorts `fts_x` before `fts_x_vocab`). `migrations.rs::render_baseline` treats any `<virtual>_…` table as a shadow, but it renders the v0 corpus only, which has no vocabulary. A rung that rebuilds a domain index must drop its `_vocab` first (the rung header says so).

**Choices of the lane that the proposal did not rule.**

- **The rung is idempotent**: every DROP is `IF EXISTS` and every CREATE follows its DROP. The suites wind a founded head file back by pragma (`chat_proposals.rs`, `chat_schema.rs`, `collection_kind.rs`, `backup_v2_rung.rs`) and climb again over objects that are already the rung's; without this they fail with "already exists".

- **`category` is listed in `FOLDED`** although it is a column of `tally_expense`: the rung folds it on purpose (and not when `general`), and the list is the place that says so.

No member-facing writer, so `fts_core_content_item` is unchanged (the proposal's "if a census finds a writer").

**Limits and findings outside the lane, named and not fixed.**
