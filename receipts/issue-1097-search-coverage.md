## What changed

### Lane A — rung 013, the vault tests, the door's column checks

A member who typed a person's nickname, email or memo, an event's place, a task's project, or an expense's category, group, line item or memo found nothing, because the text lived in a table whose index nothing read. Rung thirteen folds it into the index the search door does read, so one probe per domain still answers (Home stays at seven). The door ranks a folded column at half a label's weight.

- **The rung.** `contracts/migrations/013_search_coverage.sql`, `LADDER` version 13 `search-coverage`. Four indexes are dropped and created again with the columns below after the ones they had, backfilled from live rows with the SELECT their triggers run; child-table triggers re-index the parent.

  | Index | Gains | Folded from |
  | --- | --- | --- |
  | `fts_core_party` | `nickname`, `role`, `met` | `people_profile` of the party, only while it is not trashed |
  | | `channels` | every `social_contact_channel.value` and `normalized_value` of the party |
  | | `memo` | every `knowledge_annotation` with `target_type = 'core.party'` (written by `people.add_note`) |
  | `fts_core_event` | `location` | `core_place.name` through `location_place_id` |
  | `fts_schedule_task` | `project` | `schedule_project.name` through `project_id` |
  | `fts_tally_expense` | `category`, `group_name`, `items`, `memo` | the category unless `general`; the group's `social_circle.name`; every `tally_expense_line_item.description`; the `tally.expense` annotation |

  Weights (R1a, R1d): the id and every column an index had weigh 1.0, every folded column 0.5. They are **not** in the rung or the index: each `Domain` in `crates/search/src/domains.rs` carries one weight per index column in order, and the door passes them with every query as FTS5's rank override.
- **Retired** (nothing read them, their text is folded): `fts_people_profile`, `fts_core_place`, `fts_schedule_project`, `fts_social_circle`, `fts_knowledge_annotation`, with their 25 shadow tables and 15 triggers. **Added**: `fts_<index>_vocab`, an `fts5vocab(<index>, 'row')` table for each of the seven domain indexes (`fts_knowledge_note`, `fts_core_party`, `fts_core_event`, `fts_schedule_task`, `fts_tally_expense`, `fts_core_content_item`, `fts_core_document`), none for Locker. 19 child triggers, named `fts_<index>_from_<child table>_<ai|au|ad>`.
- **The door.** `domains::FOLDED` names every folded index column with its source `(table, column)`; `assert_no_sealed_column` holds the sources to the sealed registry; `SqliteDoor::open` refuses an index with a column that is neither the base table's nor listed, or whose column count is not its weights' length; every query carries `AND <fts>.rank MATCH 'bm25(…)'`.

### Lane B — the correction engine

A member who typed `budegt` found nothing, and so did one who typed `recieve` for a vault that holds `received`: each word of a query is a quoted prefix phrase, and a slipped letter is not forgiven. The assistant already had a typo rule (Damerau distance one) and search did not share it. Lane B lifts that rule into the kit and adds `Search::correct`, a correction that is a lookup in the vault's own vocabulary (the `fts5vocab` tables of rung thirteen), run only when a surface's whole exact answer was empty.

- **The one rule (R5).** `crates/apps/kit/src/spelling.rs`: `within_one` and `one_edit` with `TYPO_MIN` (4) and `PREFIX_MIN` (3), moved out of `crates/assist/src/native/resolve.rs` without a change and with their test; the assistant's callers (`resolve.rs`, `search.rs`, `whr.rs`) use the kit's. New beside them: `words` (the one tokenization of a typed query; `match_expression` now uses it), `fold_like_index` (what `unicode61 remove_diacritics 2` stores for a word), `eligible`, `near_prefix` (a prefix of the term, length `|w|-1 ..= |w|+1`, within one edit, the word's own length preferred, `None` when the term starts with the word) and `correct_words` (the words that changed, joined by single spaces, or `None`; the best prefix wins by documents, then shorter, then lexicographic). The assistant's Levenshtein `edit_distance` and `word_score` are untouched (R5a), with a comment beside them that says why.
- **The door.** `Search::correct(principal, entities, query) -> Result<Option<String>, SearchError>`, a trait default of `Ok(None)` so `RecordingSearch` in `crates/core/src/app_query.rs` and the fakes compile unchanged. `SqliteDoor::correct` refuses an entity that is not one of the seven domains with `NotADomain` (so `locker.item` is refused, with or beside others), asks each named domain's `fts_<index>_vocab` whether any term starts with the folded word (a range on `term`, `LIMIT 1`), and for an unknown word reads the candidates: the terms that start with the word's swapped first two letters and then those that start with its first letter, in term order, at most `MAX_VOCAB_SCAN` (8,192) rows per word per domain in all (R4a). A vault without the vocabulary tables is `IndexUnusable`, naming the table.
- **The measurement.** `correction_latency_on_fifty_thousand_terms` in `crates/search/tests/door.rs` (`#[ignore]`, the command is in its doc comment); figures in Verification.

### Lane C — the walkers, the correction pass in every app's search, and `corrected` on the wire

Locker and Tally answered a search by walking rows with a plain `contains` over title, username and address (Locker) or the description (Tally), so none of what a member typed beside them was found and a typo was forgiven by nothing. Every other app searches through the full-text door, which now corrects. Lane C widens the two walkers, gives them a correction of their own, wires the door's correction into the six surfaces that use it (Home, Notes, Docs, Tasks, Agenda, People), and adds `corrected` to all eight search answers. Doctrine digest the lane worked under: law `b4ce8d9df2f4` (`node .governance/law/brief.mjs`).

- **The walkers (R6).** Locker's `ItemRow::searchable` is the title, username, address, note, full name, email, phone and card brand; the loader adds the aliases (`locker_item_alias`, now every alias of an item) and the newest memo (`knowledge_annotation` on `locker.item`, one bounded read under `DECORATION_ROWS`). Tally's `searchable` is the description, the category unless it is the default `general`, the group's name, each line item's description and the memo (`memos_statement`, one read of the ledger's window). A sealed cell is not on `ITEM_COLUMNS`, so it can be neither matched nor offered; `cardholder`, `address`, `network` and `expiry` are still not searched.
- **The correction of a walker.** `spelling::WalkedWords` (kit) is the vocabulary of the rows the walker just walked, lowercased and not unaccented (the walkers match by lowercase `contains`, so a word it offers is a word the re-walk finds), each word counted once per row, a word under three letters never offered. `known` is "some walked word holds it"; `candidates` are the words that start with the typed word's first letter or with its first two letters swapped (R4a). The exact walk runs; only when it is empty is the correction built and the walk run again over the same rows, and `corrected` is set only if that finds something. Locker is not a search domain, so it asks no index and no vocabulary.
- **The kit fix.** `correct_words` trims leading and trailing characters that are neither letters nor digits before the eligibility check and leaves them out of the replacement (`budegt?` is `budget`).
- **The core (R4, R8).** `corrected_search` (`crates/core/src/app_query.rs`) runs the exact term; if its answer is empty and carries no denial it asks `Search::correct` for the surface's own entities, runs the surface again with the corrected words, and keeps them only if that run found something. `RecordingSearch::correct` forwards to `inner` with `query`'s error-keeping. Home runs it over the seven domains, Notes, Docs, Tasks and Agenda over their one, and People over `core.party` with the live-profile fold inside the run, so the answer judged empty is the one the member sees.
- **The wire.** `string corrected` on `VaultSearch` (2), `NotesSearch` (2), `DocsSearch` (3), `TasksSearch` (4), `AgendaSearch` (2), `PeopleSearch` (2), `TallySearch` (3) and `LockerSearch` (4): additive, each the next number after the message's last, none of them a number any `reserved` statement holds in those messages.
- **Home's people.** `core.party` is every party in the vault, and Home returned all of them; a Tally friend or a trashed person opened nothing in People. Home now drops a `core.party` hit with no live `people_profile` (`deleted_at IS NULL`), in one bounded read like `photo_assets`, before the answer is judged empty.
- **Stale comments.** People's `search` no longer says the index registers no profile or annotation domain; the `fts_core_party` comment no longer calls it an external-content table (it is in `crates/vault/src/commands/core.rs`, not `crates/core/src`, as the lane brief said).

### Lane D — the whole word, the shells, and the Ask action

The core said what it corrected; no shell showed it, and what it said could be a prefix (`sunscree`). Lane D makes the answer a whole word (D0), carries `corrected` through every machine (D1), draws it once per platform and offers Chat on an empty Home search (D2), and runs it on the simulator (D3). Doctrine digest the lane worked under: law `b4ce8d9df2f4` (`node .governance/law/brief.mjs`).

- **D0 — R4b, Rust.** `correct_words` still chooses the winning prefix group (most documents, then shorter, then first); the answer is now the **highest-`docs` whole term in that group** (ties: shorter, then lexicographic), and that word is both what is searched again and what `corrected` shows. `sunscren` is `sunscreen`; `recieve` is `received` when the vault holds `received`; `budeg` is `budget`, not `budge`. A term offered by two domains adds its documents, as before. Both walkers inherit it through `WalkedWords`. Pinned prefixes moved in `crates/search/tests/door.rs` (`recive`, `recieve`, `budeg`, the multi-word query) and one test was added there (`a_correction_is_the_whole_word_the_vault_holds`, over a founded and a replayed vault); `spelling.rs` gained `a_correction_is_the_whole_term_of_the_winning_prefix` and a walker assertion for `sunscren`. No walker or door test elsewhere pinned a prefix.
- **D1 — state.** `SearchField.corrected = 4`. `SearchLaw.answered(l, s, answeredTerm, corrected = "")` records it only for an answer that is current and for a term that is not blank; a new term (`SearchLaw.term`) and a close clear it. `answerIsCurrent` now compares the trimmed terms (the core reads the trimmed one, so `sunscren ` answered by `sunscren` is current). Every machine passes its answer's `corrected`: Home (`HomeSearchEvent.DataArrived.corrected = 3`, through a `SearchLens` of its own), Notes (`SearchArrived.corrected = 2`), Docs (`DocsDriveEvent.DataArrived.corrected = 3`), People (`PeopleHomeEvent.DataArrived.corrected = 3`), Tasks, Tally and Locker (read from the held core answer; Locker's `decorate` sets it only while the answer's term is the field's). **Agenda is the exception:** its search is a mode of the home screen (`search_open`, `search_term`), not a `SearchField`, so it keeps `AgendaHomeState.search_corrected = 19`, set where the answer lands and cleared by a new term, a close, a refusal and a re-open.
- **D2 — views.** One line under the open field, in the secondary text style, id `search-corrected`, drawn **inside the shared field component** (`CentraidSearchField`, SwiftUI and Compose) that every app's search slot, the Docs folder page, Home's search page and Tally's search page already use; Photos' own slot passes no `corrected` and draws nothing. The words are `KitWords.searchCorrected`, over `SEARCH_CORRECTED`. Home's no-match state gains `EmptyState.action_label` = "Ask about “{term}”" and `HomeSearchData.ask_question` = "Find {term}", both finished by the machine; the view reports `HomeSearchEvent.Asked` (the machine records the term as a recent search) and the **shell's router** (`ShellModel.askChat`) pops to Home's root, opens the Chat tab and sends the question.
- **Waiting for the chat.** A `ChatEvent.Sent` right after `Opened` is dropped (the session starts a moment later), so `ChatFlow.askWhenReady` waits for `ChatMachine.canAsk` (a session up, nothing answering) for at most 8 s, starts a new chat when the open one already holds a thread, and sends; `ChatBridge.openAsking` runs the open and the wait in order on one coroutine. With no model on the phone the chat never becomes ready, the Chat tab shows its download step, and the question is **not** queued behind a download.
- **Left out, as the brief allows.** The app search empty states do not share one search component (each machine builds its own `EmptyState` and event), so the Ask action is on Home only; Tasks, Notes, People, Docs, Agenda, Tally and Locker keep their no-match sentences unchanged. **Android has no Chat tab** (`HomeScreen.kt` draws only Home and Backup), so its Home no-match state draws without the action; the corrected line is on both platforms.

## Decisions

**R1 — fold into the entity's own index.** Applied as the table above. The fold expression is one SELECT, written out in every trigger (SQL has no macros and the schema has no views; a first view would be a new object class for the snapshot, the DDL replay and the sealed scan to learn). The base triggers keep the names `fts_<table>_ai/_au/_ad`; they now insert from `FROM <table> p LEFT JOIN … WHERE p.rowid = new.rowid` rather than from `new.*`, so they and the child triggers run one statement shape. `UPDATE OF <columns>` lists keep a `row_version` touch from re-indexing. An UPDATE that moves a child to another parent (a merge re-points a profile, a channel or a memo) re-indexes the old parent too.

**R1a, R1d — weights, in the door.** 1.0 for the id and every pre-existing column, 0.5 for each folded column. The first version stored them in each rebuilt index's `_config` (`INSERT INTO <fts>(<fts>, rank) VALUES('rank', 'bm25(…)')`); the coordinator's ruling R1d moved them out, because a row of data cannot be in `contracts/schema/vault-ddl.sql`, so a vault built by replaying it ranked differently from a founded one and the fixture vaults the apps' parity tests run on could not stand for a real one. Now `Domain::weights` holds one weight per index column in order (the unfolded domains all 1.0), `Domain::rank_function()` renders `bm25(…)`, and the door binds it to `AND <fts>.rank MATCH ?` — FTS5's rank override — so `ORDER BY <fts>.rank` and the `(rank, id)` keyset are unchanged. `SqliteDoor::open` refuses an index whose column count is not the list's length (`bm25` takes weights by position); `tests/door.rs` also checks that each weight sits on the column it names against a list written out separately. The ranking is tested on a replayed vault and on a founded one, and a test in `door.rs` and one in `search_coverage.rs` hold that no index stores a rank row.

**R1b — what is not folded.** A trashed profile's `nickname`, `role` and `met` (the profile is joined with `deleted_at IS NULL`, and trashing or restoring one is an UPDATE of `deleted_at`, which `fts_core_party_from_people_profile_au` re-indexes); a `general` category. A party never had a `deleted_at` guard in its index and still has none: the people read model filters trashed profiles after the door (`people::roster::load_search`).

**R1c — a Locker memo is in no index.** Every fold and every child trigger selects annotations by `target_type` (`core.party`, `tally.expense`), so a `locker.item` annotation matches no trigger, and `fts_knowledge_annotation`, the one index that held it, is retired. `search_coverage.rs` plants a memo through `locker.set_memo` and scans every `fts_*` table: matched in each index, looked up in each vocabulary, and searched as text in every shadow table's cells, with a party memo as the positive control.

**R3 — the vocabulary.** `fts_<index>_vocab`, `fts5vocab(<index>, 'row')`, persistent because the read connection is `query_only`. The name was checked against everything that recognises an FTS shadow table: `log::guard::FTS_SHADOW_SUFFIXES` (`_content`, `_data`, `_docsize`, `_idx`, `_config`), `contract_vault::is_fts_shadow` (the same five suffixes), `backup::snapshot::census_of` (skips `CREATE VIRTUAL TABLE`), `core.rs::user_tables` and `ontology::base_tables` (skip `fts_%`). `_vocab` is none of the five, so it is a virtual table everywhere it matters and the DDL replay creates it after its index (the file sorts `fts_x` before `fts_x_vocab`). `migrations.rs::render_baseline` treats any `<virtual>_…` table as a shadow, but it renders the v0 corpus only, which has no vocabulary. **Lane B — R4, R4a, R5, R5a, and the bound.**

- **R4 — correction, not a fuzzy OR.** `Search::correct` runs only when the surface's whole exact answer was empty; the caller runs `query` again with the words it returns and says what it searched for. A query that found something is never touched, and a replacement is always a prefix of a term the named domains' vocabularies hold, so a word the vault has not got is never invented. A word is read when it has four letters or more and nothing but letters; a word the vocabulary holds, as a term or the start of one (search is a prefix search), is kept as typed.
- **R4a — a slip in the first letter is not corrected, except a swap of the first two.** The scan reads the terms that start with the word's first letter and those that start with its first two letters swapped; that is what bounds it. `gudget` is not `budget`; `ubdget` is.
- **R5 — one Damerau-1 implementation, in the kit.** `within_one` and `one_edit` moved without a change; the assistant's resolver, the `where` language's codes and the name-reach tiers read the kit's, and the assistant's test of the rule (`resolve::tests::one_edit_reads_a_slip_of_one_letter_and_a_swap`) stays where it was, passing through the kit, with the same assertions copied into the kit beside the new ones.
- **R5a — the assistant's Levenshtein `word_score` stays.** It scores a search's words with a limit of two for a word of seven letters or more, a different measure on which the 0.8B evaluation depends. The two are not unified and a comment beside `edit_distance` says why.
- **`MAX_VOCAB_SCAN` = 8,192.** Measurement, on the machine and the vault of Verification item 15: scanning the bound (8,192 rows, term order, one domain) costs about 7 ms; a word asked over four domains of a vault of 50,000 words costs about 3 ms p50 and 11 ms at most, a three-word query 5 ms p50 and 17 ms at most. The busiest first letter of that vault (English initials, `s`) holds 2,948 terms of one domain and the busiest English bucket is about a ninth of a vocabulary, so 8,192 holds a whole bucket of a vault of about 70,000 terms in one domain and the alphabetically-first 8,192 of a bigger one. The worst case is arithmetic and not a figure: 16 words × 7 domains × 8,192 rows, which needs a vault of hundreds of thousands of terms; the budget below is for the vaults this measurement stands for. **Budget: p50 ≤ 10 ms and max ≤ 50 ms per call**, on a vault of up to 50,000 terms, measured in the test profile (the workspace crates unoptimised, SQLite at opt-level 2), so the shipped figure is lower. The bound could not be taken from the bucket size alone: the vocabulary table honours a range on `term` and returns its rows in order (plan `SCAN … VIRTUAL TABLE INDEX 1539`, no temporary b-tree; 913 virtual machine steps for 100 rows and 18,013 for 2,000, about 9 per row), so the limit stops the walk and nothing sorts a bucket.

**Choices of the lane that the proposal did not rule.**

- **The fold is a table proved against the tokenizer, not a normalisation crate.** `fold_like_index` is Rust's per-character lowercase plus 100 code point ranges (a precomposed Latin letter to its ASCII letter, both cases), 8 ranges of combining marks the tokenizer drops, and two special folds (the micro sign, the final sigma). `ø`, `æ`, `ß`, `ł`, `đ`, `ı` stay as the tokenizer keeps them; `İ` is `i`. The table was generated from the tokenizer (every code point, through an FTS5 table and its `fts5vocab`) and `fold_like_index_is_what_the_index_stores` re-compares it over every code point of the blocks it claims (Latin, combining marks, Latin Extended Additional, letterlike signs; 796 code points are token characters there). Another script is lowercased one character at a time; for one the tokenizer folds differently (Cherokee, a few Greek variants) the folded word differs from the stored term by a letter and the correction can only land on a term the vocabulary holds, so the worst outcome is the word's own stored form.
- **`eligible` is asked of the folded word.** `Café` is `cafe` and eligible; a word with an apostrophe or a hyphen (`o'brien`, `e-mail`) is two terms in the index and is kept as typed, and so is a word with a punctuation mark stuck to it (`budegt?`). Known limitation, owner question below.
- **A missing vocabulary is an error, not `Ok(None)`.** A vault from before rung thirteen answering "nothing to correct" would read as "your words are fine".
- **Entities are checked before anything is read and counted once.** A duplicate in `entities` does not double a term's documents.
- **The two scans share one allowance.** The swap's range goes first (a prefix of two letters, a few hundred terms at the most) and the first letter's bucket gets what is left, so a word costs at most `MAX_VOCAB_SCAN` rows in a domain whichever way it is read.
- **A cheap necessary test runs before `within_one`** (`plausibly_one_edit_apart`: what two texts one edit apart share at their ends covers all but two letters of the shorter). Without it the Rust side was a third of the cost of a call (p50 4.2 ms against about 3 ms for one word over four domains, measured before and after); the test `the_cheap_filter_never_rejects_a_pair_within_one_edit` checks every pair of up to five letters over a three-letter alphabet.

**Limits and findings outside the lane, named and not fixed.**

- **Owner question.** A word with punctuation stuck to it (`budegt?`, `(budegt`) is not corrected, because the folded word is not all letters; the exact search forgives the punctuation (it is a separator to the tokenizer). Trimming the ends before the check would correct it. Should the correction trim?
- **For lane D.** `RecordingSearch` (`crates/core/src/app_query.rs:344`) wraps another door and implements `query` only; with the trait default it will answer `None` for every `correct` until it forwards the call to `inner` (the error-keeping of `query` applies to it too).
- **For the close.** The proposal names `docs/decisions.md` for the rulings above; this lane records them here and in `crates/search/README.md` and leaves the decisions register to the close.
- The consent pipeline is the same hand-off as `query`'s: `correct` reads the owner's vocabulary and takes a `Principal` it does not yet use. When the walls land, `correct` has to walk them for each entity it is given, or a correction would offer a word a grant cannot read.

**Lane C — R4, R4a, R6, R8 (the Rust half), the Home people filter, and the wire.**

- **R4 — one helper, judged on the answer the member sees.** `corrected_search` is the only place a surface asks for a correction. It runs the exact term; the answer must be empty *and* carry no denial; the door corrects against the surface's own entities; the surface runs again, and the corrected words are kept only if that run found something. So a correction never rides on an exact answer, never goes around a denial, and never reports words that found nothing. People and Home put their drops inside the run (the live-profile fold, the photo asset and the people filter), because a raw hit that the surface then drops is an empty answer, and a surface judged on raw hits would report an empty answer as a full one when every exact hit was then dropped, and never correct it (Home's last test step: `zelda friend` only matches a Tally friend, and `zleda` finds the person only through the correction).
- **R4a — the walkers read the door's first-letter rule.** `WalkedWords::candidates` offers words that start with the typed word's first letter or its first two letters swapped; `gudget` is not `budget`.
- **R6 — the walkers keep walking.** Locker and Tally still walk bounded windows (`SEARCH_ROWS` 500 and the ledger's 2,000) and the correction vocabulary is built from those same rows, so nothing scales beyond the window the walk already reads. The memo and alias reads are bounded by `DECORATION_ROWS` (4,000) and `LEDGER_ROWS` (2,000). A word is searched by lowercase `contains` as before, not folded for accents: a vault that holds `café` and a member who types `cafe` is a one-edit correction to `café` (the accent is a letter to `within_one`), which the re-walk then finds. Locker asks no index and no vocabulary: it is not a search domain, and the correction reads only the words of its own rows, none of them sealed.
- **R8 (Rust half) — `corrected` on the wire.** Field numbers: `VaultSearch.corrected = 2`, `NotesSearch.corrected = 2`, `DocsSearch.corrected = 3`, `TasksSearch.corrected = 4`, `AgendaSearch.corrected = 2`, `PeopleSearch.corrected = 2`, `TallySearch.corrected = 3`, `LockerSearch.corrected = 4`.
