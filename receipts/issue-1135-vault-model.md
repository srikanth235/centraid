- **The gate** (`crates/vault/src/commands/mod.rs`) writes one `journal` row for every command, in the command's own transaction (`refused` for authority, schema and precondition refusals; `failed` in a transaction of its own after a rollback). `command_definition`, the check rows, explanations and the hash-chained access receipts are gone; `Registry::install` and the ontology-version gate with them. `journal.rs` replaces `audit.rs` and keeps the sealed-input tokenising and scrub.

A kind's search text is one function (`text_of`) over its own row and children plus the bodies of live notes about it. Locker is not indexed.

### Falsification

The two claims the rest of the lane leans on, each with a throwaway check.

1. **"The incremental search index is the rebuilt one, so a command that forgets to touch is red."** Check: removed `ctx.touch(id)` from `entity.retitle` (line marked `FALSIFY`, restored after). First result: the test stayed green, because a later `person.merge` in the script re-indexed the retitled person and hid the omission. The script was the weak part, not the claim: the last command of the script is now a retitle of a note nothing re-indexes afterwards. Second result: red (`a command changed searchable text and did not touch`); restored, green. A second, permanent check (`an_edit_that_forgets_to_touch_is_caught_by_the_same_comparison`) writes a body without touching and asserts the incremental and rebuilt dumps differ.
2. **"Garbage collection finds every reference from `PRAGMA foreign_key_list` alone."** Check (a throwaway test file, deleted): `CREATE TABLE zz (h TEXT REFERENCES blob(hash))` inside a commit, with no change to `blob.rs`; `collect_blobs` kept the blob while a row pointed at it and collected it once the row was deleted. The permanent commitment 3 populates every hash column of the model and requires each populated column to be a declared foreign key, and requires `blob::references` to equal the declared set.

### A2 — the word list

`search_word (n INTEGER PRIMARY KEY, word TEXT NOT NULL UNIQUE) STRICT` is in the baseline (`contracts/migrations/001_baseline.sql`, and `contracts/schema/vault-ddl.sql` regenerated by `export-ladder-ddl`): the words the index holds, numbered in the order they first arrived.

- **The fold and a tokenizer moved to `centraid_ontology::text`** (`crates/ontology/src/text.rs`; `crates/ontology/src/text/token_chars.rs` is generated). `centraid_apps_kit::spelling::fold_like_index` is a re-export, so no caller changed. `index_words(text)` splits where `unicode61 remove_diacritics 2` splits and folds each word. **The split is not `char::is_alphanumeric`:** the bundled SQLite takes a code point as part of a word by a category table older than Rust's and treats a code point it has no category for as a letter (957,058 code points differ from the standard library's answer), so the engine's own table of 400 ranges is copied into `token_chars.rs`, written by an ignored test that reads it back from SQLite. Tests: the fold over every code point of the blocks it claims (moved from the kit unchanged), `index_words` against the engine's terms over mixed text (punctuation, digits, apostrophes, emoji, Greek, Cyrillic, Devanagari, CJK, combining marks) and over every claimed code point, and **the split over every code point there is** (4.5 s).
- **The vault writes the list.** `reindex_one` adds the words of title and body after it inserts the row (`INSERT OR IGNORE`, so a word keeps its number); `rebuild` rewrites the list from the rows; a purge (`index::purge`, called by `entity.purge` in `crates/vault/src/commands/entity.rs`) takes the words of the entity's title and text that `search_vocab` no longer holds once its row is gone. The index is contentless, so an edit that drops a word cannot name it: **the word stays until a `rebuild`** (a purge names only what the entity holds now). The list is a superset of the vocabulary, never missing a word the index can find; `search_word` joins `is_index` in `crates/vault/src/log/guard.rs`, so a commit's change census does not report it and the ontology page (`scripts/docs-site/src/content/ontology-body.html`, `crates/vault/src/ontology_doc.rs`) lists it.
- **Commitments.** After the scripted run every `search_vocab` term is in `search_word`; after a rebuild the list equals the vocabulary and is a subset of the incremental one; `the_word_list_gains_a_word_on_index_and_loses_it_on_a_purge_or_a_rebuild` covers the purge, the kept shared word, the dropped-by-edit word and the rebuild (`crates/vault/tests/commitments.rs`).

### A3 — the cache

`Vault::words()` returns a `Words` (`crates/vault/src/words.rs`, wired in `crates/vault/src/file.rs` and `crates/vault/src/lib.rs`); `Words::current(&connection)` returns the words in arrival order as a `Ref<[String]>`. It asks the table one statement (the highest `n`, the count, and the word at the cached last `n`) and: **keeps** the cache when the three agree with it; **reads the tail** (`WHERE n > ?`) when the highest number and the count grew by the same amount and the word at the old last number is the cached one; **reads whole** otherwise (a purge, a rebuild, a restore, a rolled-back number given out again to another word). It refuses inside a commit (the rows may be rolled back) and, instead of panicking, when a slice from an earlier call is still held and the table has changed. `Words::loads()` counts each kind of read. Unit tests: first read whole and unchanged not read again; empty table; appended words as a tail; a word already there appends nothing; a rolled-back write never reaches the cache and its numbers are given out again; a number given out again to another word; a purge (below the top, at the top, with more arriving); a rebuilt or restored table as long as the old one; a read inside a commit; a held slice; and a real `Vault` following its commits.

**The statement is three subqueries**, not `SELECT max(n), count(*)`: with two aggregates in one query SQLite reads every row for both (7.4 ms mean at 150,000 words, found by measuring the first version), where the highest number is a descent of the tree and the count walks its pages.

**Timings** (150,000 words of 4 to 11 letters; an ignored test, `cargo test -p centraid-vault --lib words::tests::the_cost -- --ignored --nocapture`, nothing committed as a fixture; the test profile, SQLite optimised):

| | in memory | on disk (hot page cache) |
| --- | --- | --- |
| full load | 65 to 97 ms | 67 ms |
| validation, nothing changed | 32 µs | 0.86 ms |
| of which `max(n)` / `count(*)` / word at `n` | 3 µs / 29 µs / 6 µs | 11 µs / 856 µs / 22 µs |
| 1,000 appended words, read as a tail | 0.9 ms | 3.8 ms |

**What the check cannot see**, in the module's doc: it reads three numbers and a word, so a table that agrees on all four but differs below the top is kept. The writer only appends; a purge or a rebuild that agrees on all four would have to remove the top words and append as many that end in the word that was at the top.

- **`PRAGMA optimize`** (with `analysis_limit = 1000`, so its cost is bounded however large the vault is) runs when a `Vault` closes (`close`, `finish` or a drop; `Held` in `crates/vault/src/file.rs` wraps the one connection so that every way out goes through it) and at the end of `index::rebuild` (`crates/vault/src/index.rs`). No assertion changed or moved. A close after that writes nothing, and the cost of the first is the pages the statistics occupy (one or two 64 KiB ranges) in the next pass.

## Search rework, lane B

The door, Home, the correction, the fill rule and Money's search, in five slices, each one commit. The earlier ruling in [#1097](https://github.com/srikanth235/centraid/issues/1097) that shaped these surfaces is not binding on this work (owner's instruction); the comments and docs that cited it for what changed here are rewritten to the current state.

### B1 — the door's statement (`cd0b657ad`)

`SqliteDoor::open(connection, words: &Words)` takes the vault's cache (`vault.words()`); every caller passes it. The statement is two tiers in one CTE: tier 0 is the entities whose **title** holds every word (`{title} : (expr)`), uncapped; tier 1 is the newest `TAIL_ROWS` (500) other matches by rowid (`(expr) NOT ({title} : (expr))`, so an entity is in one tier only), with the kind, trash, `title <> ''` and excluded-id filters **inside** the cap. Order and keyset are `(tier, rank, id)`; the cursor's sort key is `tier:rank`. A query whose words are all one character is `NoSearchableWords`, which every surface already draws as its empty-term answer (`MIN_WORD_LETTERS`).

`EXPLAIN QUERY PLAN` of the tail leg (held by `the_tail_leg_streams_the_index_and_does_not_sort_its_matches`, `crates/search/src/sqlite.rs`): `SCAN search VIRTUAL TABLE INDEX 192:rM2` (`ORDER_ROWID | ORDER_DESC`, the order is the module's), `SEARCH e USING INTEGER PRIMARY KEY (rowid=?)`, and no `USE TEMP B-TREE` inside the leg; tier 0 is `INDEX 0:rM2`; the final `USE TEMP B-TREE FOR ORDER BY` orders at most `title matches + 500` rows. Tests in `crates/search/tests/door.rs`: tier order against score and age, the cap with a single-kind search among 520 newer other-kind matches, exclusion lets older rows fill the cap, keyset across tiers, a malformed cursor, the one-character rule.

### B2 — Home in one statement (`98c74d4bf`)

`Search::query_each(principal, &EachRequest)` answers at most `per_kind` rows of each kind by `row_number() OVER (PARTITION BY e.kind ORDER BY tier, rank, id)`; the default asks `query` once per kind (a test double or a recorder that forgot to forward is slow, not wrong, and a test holds them equal). Home asks once for the six linkable kinds and the five named kinds (`queries::load_targets_each` in Notes; `named::all`, `named::is_named`), eight per kind, with the memo narrowing, the live-people filter and the app routing unchanged. The powerbox and the per-app searches still call `query`. The tail cap counts across the kinds asked in one `query_each`, so a body-only match of a kind older than the newest 500 matches of the kinds beside it is not answered; a title match always is. Plan (`the_per_kind_statement_reads_the_index_once_per_tier`): `INDEX 0:rM2`, `INDEX 192:rM2`, entity by key, the window and the final order as temp b-trees over the legs' rows.

### B3 — the correction over the word list (`842531e84`)

`Search::correct` reads `Words::current` lazily (the first word that needs it) and filters it through a hook (`SqliteDoor::corrected(query, in_realm)`; `correct` passes all), so a later realm column can hide words from a surface. The rules are `centraid_apps_kit::spelling`'s: `is_known` (some word starts with it), `near_words` (one edit anywhere with the typed first letter, else one that changes it, else the fragment inside a longer word of four letters or more), `rank_order` (documents, then shorter, then first), `try_correct_words` (the shared tokenization with a fallible step). The documents come from `SELECT doc FROM search_vocab WHERE term = ?`; a word no document holds is not offered. `MAX_VOCAB_SCAN`, `prefix_end`, `holds`, `neighbours` and `terms_under` are gone. `begins_near` is a fast form of `near_prefix`, held equal to it over every pair of a three-letter alphabet. `WalkedWords` stays for Locker.

Timing (release, 150,000 random words of 4 to 11 letters, `near_words` plus `is_known`, nothing committed): 4 to 9 ms for a word with no candidate or an in-word one. A synthetic 20,000-entity vault (debug build): a two-letter `query` 3.8 ms, `query_each` over eleven kinds 3.9 ms, three-letter 1.5 ms, no match 0.4 ms.

### B4 — the fill rule (`8a477a8a8`)

`corrected_search` now takes a row count and a `fill`. An exact answer with fewer than three rows (`FILL_BELOW`) and no denial asks for a correction and runs again; the exact rows come first, then the corrected rows not among them (`filled`, keyed by id), up to the surface's window, and the words are reported only if they added a row. An empty exact answer is replaced by the corrected rows, as before. Every surface passes its own key: Agenda, Notes, Docs, Tasks, People, Chat, Photos (its own copy of the flow is now `corrected_search`), Home (per kind). No search answer pages past its window, so a filled answer has no continuation to carry. `SEARCH_CORRECTED` is "Including results for “{corrected}”" (`copy/shared.json`, built into `SharedCopy` at build time); the design table, the screen and wire comments, the shell comments and the maestro flows say the same.

## Locker lane

A Locker item is an entity of kind `locker_item`, and Locker uses the vault's shared commands. Worker branch `claude/amazing-fermat-9nt6tr-locker`, from `193d872`. The owner's and the root's rulings of 2026-10-22 (L1, L4, L5, L6, L8, L9) bind; #1097's rulings do not. Law digest `965cf4419f70`.

### What the schema is now

- `entity.kind` admits `locker_item` and `Kind::LockerItem` is the 26th kind (`crates/vault/src/model.rs`). `locker_item(id PK, kind GENERATED 'locker_item', type, username … key_id)` joins `entity(id, kind)` with `ON DELETE CASCADE` like every kind; `entity.id` is today's `item_id`, and title, stamps, version and the trash pair are the entity's. `locker_item.starred`, `archived_at`, `row_version`, the touch trigger, the indexes `entity` already gives, and `locker_tag` are gone. The children (`locker_item_field`, `_alias`, `_address`, `_passkey`) keep their `item_id` column and reference `locker_item(id)`; their own `row_version` triggers stay. `receipt.item_id` is still a value with no foreign key, so a receipt outlives a purge. `contracts/migrations/001_baseline.sql` is edited in place; `contracts/schema/vault-ddl.sql`, `contracts/schema/vault-commands.txt` and the schema section of `scripts/docs-site/src/content/ontology-body.html` are regenerated, never hand-edited.
- The five sealed cells, `locker_item_field.value_sealed` and `locker_item_passkey.private_key` stay `lk1:` ciphertext. No entity-wide reader carries one: the journal tokenises the five cells and a duplicate's nested `fields[].value` (a `name[].key` path in `sealed_input`, `crates/vault/src/journal.rs`); a Locker item has no revision; `text_of` answers `None` for the kind and the index holds nothing of it; a page over `entity` or `edge` serves an item only to a read `page::reaches_locker` names. `crates/vault/tests/locker_plaintext_gate.rs` holds each of these readers.

### The commands

- `locker.trash_item`, `restore_item`, `purge_item`, `star_item`, `unstar_item`, `archive_item` and `unarchive_item` are deleted, and so is the `tags` input of `locker.add_item`, `edit_item` and the duplicate's tag copy (a duplicate still copies the source's `tag` edges, not its flags). Trash, restore, purge and empty-trash are `entity.*`; the star and the archive are `flag.set` and `flag.clear`; tags are `tag.add` and `tag.remove`. 13 `locker.*` commands remain (12 and the reveal receipt).
- `entity.purge` and `entity.empty_trash` are `Risk::Medium` with `confirm: true` for every kind (Locker's former level). Trash wins over archive: an archived item can be trashed, `restore` returns it to the archive, and `locker.counts` counts a trashed item as trashed only. `entity.purge` deletes a Locker item's sidecars explicitly (a cascade fires no trigger), and its receipts stay.
- The assistant's principal is `Principal::Assistant` (`crates/vault/src/access.rs`). `commands::execute` refuses, before any precondition and under the predicate `assistant_is_closed_out_of_locker`, every `locker.*` command and every command whose input names, at any depth, a Locker item's id or the word `locker_item`; the assistant's `entity.empty_trash` skips Locker's rows. The core's chat door (`Handle::assistant_door`) runs as that principal.
- The wire page door no longer pages `locker_item` (13 tables, `crates/core/src/api.rs`). Locker's trash and Home's count read `entity` with `kind = 'locker_item'`, named `locker.trash.rows` and `home.locker`.

### Callers moved

`crates/apps/locker` folds an item from its entity row, its kind row and its `tagged` edges in three reads named `locker.phone.*` (`crates/apps/locker/src/phone.rs`, `queries.rs`); its manifest has 19 actions and 28 scopes, the seven lifecycle actions and two new tag actions naming the shared verbs (`crates/apps/locker/manifest.json`, `commands.rs`, `manifest.rs`). `crates/core/src/locker/transfer.rs` files tags, star and archive through `tag.add` and `flag.set`. `crates/centraid/src/bin/seed-demo-vault.rs` does the same and counts Home's Locker tile off `entity`. In `mobile/shared`, Locker's trash is the kit's over `entity` and `entity.restore`/`entity.purge`, the item page runs `entity.trash`, `entity.restore`, `flag.set` and `flag.clear`, and the editor files the item and then `tag.remove`/`tag.add` one write at a time (`LockerHeld.owed`), staying open until the last. Home's tile counts `entity`, not archived by an `edge` subquery. `RowRoutes` opens a `locker_item` reference at the item's page, behind the lock wall. `copy/notes.json` no longer says Locker items cannot be linked: a note may link an item by an edge, the link renders its title, and the powerbox's foot says only that it does not offer them (the `[[` powerbox is not extended here).

### Decisions the rulings did not cover
