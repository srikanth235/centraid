A few ideas behind your phone vault.

These short primers explain the shared model, local database, protected values, and backup flow used by Centraid. Each one points to the current implementation and member guide.

§01 · shared model

Agree on the nouns, once.

An ontology is a shared model of the things a system stores and the relationships between them. Centraid's apps use one model so a person, event, payment, note, document, or photo can be connected without creating a separate copy for each app.

This matters in ordinary use: a person page can show the events and notes linked to that person, while those records remain themselves in Calendar or Notes. Imported records retain provenance; records created in Centraid have no external source row. Links describe a relationship and do not transfer ownership of the linked record.

§02 · SQLite on the phone

The database is a file the phone owns.

SQLite is an embedded database engine: the phone app opens a database file directly instead of asking a database server over a network. Centraid's Rust core on the phone owns the live vault and is its only writer. Native iOS and Android screens call that core for reads and typed actions.

A single vault lets a domain operation keep its related changes together. Search and history read from the same records the apps use; derived totals are calculated from those records instead of maintained as a second balance. The backup device receives sealed backup data, not a live database connection or a query to run.

§03 · Locker

Metadata can be listed. Secrets stay sealed.

Locker keeps item metadata available for its list, while values such as a password, card number, secure note, or one-time-code seed are sealed. Listing an item does not reveal its value. A protected reveal asks for the phone owner's check; leaving Locker or locking it clears revealed values and typed drafts.

The assistant can find a Locker item and show a protected card. The member taps Reveal, the phone checks its owner, and the value is shown to the member without passing through the model or being kept in chat. A one-time-code seed can be restored with the vault, but is not revealed in the app or history. A search result or backup never becomes another way to read a secret.

§04 · backup and recovery

A sealed copy can travel. The key stays with you.

The phone makes encrypted backup data for a gateway that the member controls. Pairing starts with a fresh code shown by the gateway; the phone enters it and both sides compare a safety number. The one-use pairing code expires after a day, so create a fresh code for a new pairing instead of keeping it as a permanent access link. Once paired, the phone uses its durable gateway credentials for backup requests.

The gateway stores sealed data under opaque names and does not have the recovery key. It cannot read the records, list the vault's contents, or act as another app client. Without a gateway connection, apps continue to use the phone's vault; only the backup waits.

The recovery key is shown as 24 words. Keep it somewhere safe and separate from the phone. On a replacement phone, those words recover the key needed to restore checked records. Original files acknowledged by the gateway can be fetched later; files that never reached a gateway may be unavailable if the source phone is lost. Files still held only in the phone's photo library can be imported again from that library.

§05 · typed actions

The screen asks. The phone core decides.

An app screen does not write database rows on its own. It asks the Rust core to perform a named operation, such as completing a reminder or moving a record to Trash. The core checks the operation's rules and owns the durable change. The same boundary keeps imported data, app actions, and assistant proposals from bypassing those rules.

The assistant can find records and prepare typed actions, but every write waits behind a confirm card and runs only when the member taps it. When a turn proposes more than one write, the card shows the whole chain before anything runs. For example, a suggested category or a possible duplicate does not silently change a Money record.
