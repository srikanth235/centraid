Chapter 1 · data

One phone vault. One writer.

Centraid keeps the live vault on your phone. The phone's Rust core is its only writer; the nine apps read and change records through that core. A backup device stores sealed backup data without being able to read the vault.

§01 · the vault

One live SQLite vault file.

The live vault is one SQLite file on the phone. Its shared model has one entity table and typed records for each kind, such as a note, document, event, task, person or transaction. Links, earlier versions and the search index are shared too. Totals, counts and other summaries are derived from the real rows when read, rather than kept as another value that can drift.

A record gives a file its identity and history; the original bytes are separate. Depending on the item, the bytes may be in the phone's local file store, still in the phone's photo library, or available only from an acknowledged backup. A file being staged for import is not yet a record. Previews and extracted text are derivatives, not replacements for the original. Imported and followed records keep provenance; records created by typing have no source row.

Apps declare their available queries and actions in checked manifests. A normal app read goes through load(app, query, params), which checks the app and query and decodes typed parameters before calling its reader. A confirmed change goes through act(app, action, input), which checks the action and input and commits through the vault's write boundary. The app catalogue is code in the release: apps do not receive member-managed grants, and the phone remains the sole writer.

Chat reads records through the paged vault door. Its confirmed writes use act, like other confirmed app changes. Chat has no free SQL write path, and the gateway cannot write the live vault.

§02 · records and protection

Connected records, kept private.

one shared model

Links, history and search

Apps link records through the shared link model, with Locker links visible only inside Locker. Edits keep earlier values for supported records. Search uses one vault index and excludes sealed Locker values; a trashed record leaves search. Imported and followed records keep their source details so the vault can explain where they came from.

the sensitive boundary

Locker stays behind its wall

Locker's sealed values are encrypted in the vault and are not put in search, links, logs or the assistant model's reach. Chat can show a protected Locker card with a Reveal action; the phone checks the owner, and the revealed value never passes through the model. Locker's own export is a separate confirmed action, requires a fresh owner check and goes to the system save sheet. Export everything leaves Locker out.

Deleting moves eligible records to the shared trash first; they can be restored before the purge date. Delete forever and empty trash permanently remove them. Export and recovery details are in Devices, and the app exports and Locker exception are in Apps.

§03 · sealed backup

A backup device stores sealed copies.

Backup state is separate from the live vault. The phone makes page-identical snapshots and seals the vault data and content files before sending them to a member's backup device. A gateway stores opaque sealed objects under keyed names; it cannot read their content or schema. Only an acknowledged copy is reported as backed up. The gateway does not query the live vault, receive app writes or act as another client.

Restoring uses the recovery key and a backup copy to rebuild the vault on a phone. The phone keeps seven daily, four weekly and six monthly snapshots when those periods contain snapshots, and always keeps the newest. It computes which files no retained backup needs and sends signed deletion requests. The gateway enforces a hold of at least seven days after a request before purging those objects. See Backups: check and retention for the retention rules, and Devices for setup and recovery.
