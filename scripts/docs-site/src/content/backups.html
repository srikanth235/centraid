Backups · recovery

A backup is real when it is acknowledged.

Your phone is the vault and its only writer. It seals the backup before sending it to a gateway you control. Recovery needs both your 24-word recovery key and a reachable gateway with a sealed copy.

What a complete backup means

Records count as backed up only when a gateway acknowledges them and confirms their content. If a file still waits, the Backup screen shows how many and why. A manual backup sends records on mobile data, but not heavy originals. Photos follow your Wi-Fi or cellular rule; video originals never cross a metered link.

Pair a backup device

On a machine you control, run centraid-gateway serve --data-dir DIR. In the phone's Backup screen, scan its fresh QR code and compare every group of the safety number with the number shown by the gateway. Stop if they differ. Pair each gateway separately; each keeps its own sealed copy.

The phone makes direct HTTPS connections and checks the certificate fingerprint carried in the QR. It works offline; backup waits when the gateway is unreachable. Background work runs only in the windows the operating system grants, and force-quitting stops it until the next launch.

Keep the recovery key and a reachable backup

Your recovery key is 24 words. Those words derive the keys that open your backup. The phone may also keep a protected copy with iCloud Keychain on iPhone or Google on Android when that platform can restore it. The Backup screen says where the key is saved; keep the 24 words even when it is saved elsewhere.

The words alone cannot restore a lost vault: you also need a reachable gateway that holds its sealed backup. Centraid cannot replace a missing key or a missing backup.

Restore to a new phone

Choose Restore my vaults, provide the 24 words if the phone cannot use a key restored by its operating system, and connect to a reachable gateway. If you need a new QR, run centraid-gateway pair --data-dir DIR beside the running gateway. Pairing codes are single-use and expire after a day.

The phone checks the records before it claims a new writer position. If it cannot establish that the copy is newest, it asks before claiming. Originals that reached the gateway can be fetched later; an original that never arrived may be unavailable after the source phone is lost.

A verified takeover stops backup work to that gateway and invalidates the old phone's token there. The old phone learns only when it contacts a gateway. Once it has learned of any verified move, ordinary member write actions are refused. Its backup pass may continue to other gateways that have not moved; the whole backup door stops only after every paired gateway has moved.

Check a backup and understand retention

Check my backup restores records from each reachable gateway into a scratch copy, verifies files by name and opens a bounded sample. The result says whether the copy opened, had a problem, or could not be checked. The check needs free space equal to the vault size, plus one tenth and 64 MiB.

The phone keeps up to seven daily, four weekly and six monthly snapshots, counting only periods with a snapshot; the newest is always kept. A deleted file stays while a kept snapshot needs it. After the phone requests deletion, the gateway holds the copy for at least seven days; if it is paused or offline, it may keep it longer. There is no exact deletion date to promise.

What a backup cannot promise

Only a reachable gateway can acknowledge a backup. A backup device stores sealed records and objects, not the keys that open them. Keep its data directory and identity safe. A second gateway somewhere else can protect against losing both your phone and a nearby backup device.
