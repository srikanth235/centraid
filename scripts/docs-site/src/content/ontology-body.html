§01 · Thesis

One life. One model. Apps become projections.

Your life is usually modelled by whoever shipped the app: your heart rate belongs to a watch vendor, your invoices to an accounting service, your relationships to a contacts silo. Centraid inverts the ownership. A single, person-owned SQLite file on the member's phone holds the canonical record, and every app is a screen over it. The model is small on purpose: an entity for everything with a title and a trash, a kind row for what it is, typed edges between them, blobs for bytes, and an origin and a source for whatever is followed. Everything else is computed when it is read.

The product is the substrate, not the apps. The phone is the vault: its core is the one writer. A machine the member controls may hold a sealed copy for backup, and it can read nothing in it. Read the page top-down as a member, bottom-up as an engineer: screens render projections; kinds add columns; the kernel keeps identity and history; the gate is the only way in.

§02 · Entity map

Twenty-six kinds, three hosts, eight relations

Every kind is a row in entity, and each has exactly one host: the table that holds the columns only that kind has. Eleven kinds have a table of their own. The six kinds that are words the member names share concept; the eight that are things that hold things share container. A kind table carries its kind as a generated constant and a composite key into entity, so the engine, not a trigger, refuses a task filed under a notebook.

Eight relations join them

An edge is a typed, directed join of two entities. edge_shape names which kinds each relation may join and a trigger refuses any other pair; an edge's ends never change. What only one relation has (position, state, anchor, label_id) is a typed column on the edge.

  • containsalbum → photo, list → person — ordered membership; a note, document, task or event has its holder as a column instead
  • taggedanything → tag or flag — a word put on a thing: also a star, a pin, an archive
  • aboutnote, task or event → anything — a memo, a journal entry, a task about Mum, an anniversary
  • linksnote → anything — a [[wikilink]] with its anchor in the text
  • attachedanything → document or photo — a file brought to a thing
  • attendeeevent → person — a guest, with their answer on the edge
  • withactivity → person — who a call or a visit was with
  • relatedperson → person — labelled by a relation concept

A star, a pin or an archive is a tagged edge to a flag. A memo or a journal entry is a note with an about edge. A thumbnail, a caption or extracted text is a derivative of a blob. A followed contact, event, file, workout or statement line is a source under an origin. Last contacted, a balance and a total are computed at read, never stored.

Physical target: local-first SQLite

STRICT tables throughout. An entity's id is a text key minted once on the phone, offline-safe and meaningless; a seeded word has a readable one (flag:starred). Money is never floating point: an integer of minor units beside an ISO 4217 currency. Timestamps are ISO-8601 UTC text, with the IANA zone beside them where a wall clock matters. A hash is only ever a foreign key into blob. The file is one rung of one migration; a release that must migrate adds the second.

§04 · Principles

Five commitments the model never breaks

Each is checked by a test that asks the founded file, so a change that breaks one is red before it ships (crates/vault/tests/commitments.rs).

P1

One shape for what is shared, a column for what is not

A title, a trash and an id are on entity and nowhere else; every kind has exactly one host; a typed pointer into a shared host carries a generated constant. A second table for “a thing with a title” is the defect this model exists to prevent.

P2

Own the meaning, claim the bytes

The durable asset is the graph. Bytes are named by hash in blob; every column that holds a hash is a foreign key into it, and garbage collection asks SQLite which columns those are rather than keeping a list.

P3

Words are data until the code must read them

A word the code interprets is a CHECK and an enum, held equal by a test. A word the member names is a concept row. No app roster, no per-app decoration table and no stored aggregate is in the file.

P4

Writes are commands, and commands leave evidence

The gate validates the input, checks authority, runs preconditions, the handler and postconditions, and writes one journal row in the same transaction. The journal is evidence: it cannot be updated and nothing reads it to learn a fact. The assistant acts through the same commands.

P5

Following is a merge, never an overwrite

A followed system's record is merged with the row per field against what it last stated: the member's edit wins on that field, the system's change lands on the rest, and an absence in a complete read trashes only an untouched row.

§05 · The rules

Eight enforced commitments, then how a table is added

The stance in §01 survives contact with engineering only if these are enforced, not hoped for. The numbers are the rows of docs/vault-ontology.md, each tied to a test.

Every kind has exactly one host

The tables with an (id, kind) cascade are exactly the kinds' hosts, and a kind table's generated constant equals its name.

The trash pair lives on entity

deleted_at and purge_at are on no other table: a Locker item is an entity, and its trash is its entity's.

A hash is a foreign key into blob

Every column holding one is declared, so the byte plane finds every reference from foreign_key_list alone.

Delete rules are chosen, not defaulted

Kind rows, child rows, edges, revisions and a category's budgets and rules cascade; only source.entity_id and message_attachment.entity_id null; every other pointer has no action.

An edge joins only what edge_shape allows

Checked exhaustively over relation × kind × kind, and the relation list equals the CHECK.

The incremental index equals a rebuild

After every search-relevant command, the one search table is what a rebuild would write. A seeded red proves the comparison can see an untouched edit.

Concept and container lists equal the code's

The CHECK lists are Kind::CONCEPTS and Kind::CONTAINERS, and seed keys are folded.

No table outside the spec is founded

The set of tables of a new vault is a list a test holds, and so is the set of tables on this page.

Adding or changing a table

In the same change: edit the one baseline and regenerate vault-ddl.sql; decide the table's place first (a new kind is a row in the kind CHECK, in Kind, with a host, and nothing else; a new relation is a CHECK value, a Rel and edge_shape rows; anything else is a child of one kind and cascades from it); make a hash column a foreign key; put searchable text in text_of and have the command call ctx.touch; write the typed commands; then give the table a sentence in ontology_doc::TABLES and run export-ontology-page. The page test is red until you do.
