# Current decisions

This file is the adjudication layer over the repository's append-only evidence. It records the decisions that are in force, deliberate non-goals, and supersession chains that keep old evidence from being mistaken for current truth. The linked issues and receipts carry the rationale and implementation history; this file carries the current answer. Update a row when the answer changes and link the issue that settles the change.

## Product positioning

Centraid is a personal, local-first **superapp**: one shell wrapping many first-party apps whose content characters could not be more different. The shell, the vault, and the apps ship together as one product — the owner installs Centraid, not apps into Centraid.

Ruled 2026-08-15 by [#799](https://github.com/srikanth235/centraid/issues/799), which retired the serving plane that made the older "personal app builder" framing true:

- **Not an app builder.** There is no authoring surface, no scaffolder a person points at a blank app, and no build-and-publish loop. `conversation.kind='build'` names the workspace-capable assistant thread, not a retired app-authoring product.
- **Not a platform.** There is no third-party, user-built, or generated app plane, no code store, and no install-from-elsewhere path. The catalogue is the bundled system apps this repo ships.
- **The gateway serves data, never UI bytes.** Every app UI is first-party code in the release: an inline React route in the shared shell, or the same app as an Expo screen on mobile. See [Inline system apps](#inline-system-apps).

Automations remain owner-authored — the automation compiler is a live "builder" in the narrow, internal sense and keeps that word ([blueprints README](../packages/blueprints/README.md)). Retired positioning vocabulary and its replacements are in [glossary.md](glossary.md#forbidden--discouraged-synonyms-broader); the binding design statement of the same idea is [DESIGN.md](../DESIGN.md).

## Package boundaries (#801)

Ruled 2026-08-16 by [#801](https://github.com/srikanth235/centraid/issues/801). A workspace package exists only if it has a **distribution** split, a **hard technical wall** (native build, zero-runtime-dep, React Native `src` resolution), or an **independently published contract**. Architectural seams that meet none of those (automation must not import an ACP backend; engine imports nothing above it) are enforced by import-boundary lint and tests, not extra package.json edges.

Kept packages and why:

| Package | Test | Why it stays |
| --- | --- | --- |
| `core` | distribution + technical wall | Thin clients consume protocol/blob/time without server code; RN `src`; zero-dep |
| `server` | distribution | The backend unit; desktop and `centraid-gateway` consume it whole |
| `vault` | distribution + published ontology | Desktop consumes it directly |
| `backup` | technical wall + published format | Node builtins only; `centraid-storage-provider/1` + `centraid-snapshot/2` |
| `blueprints` | distribution | Server needs manifests/handlers; client/mobile need UI chunks |
| `design` | distribution + RN `src` | Shared by every app |
| `client` | distribution | Browser-safe React shell for desktop/web/mobile |
| `tunnel` | native wall | Rust data plane + napi |
| `cli` | distribution (deliberate) | Depends only on contracts to prove wire parity |
| `test-kit` / `model-runtime` | private leaves | Shared tests; pinned native inference |

Supersedes any prior rationale that treated `protocol`, `blob-format`, `time-engine`, `gateway`, `app-engine`, `automation`, or `agent-runtime` as independently publishable workspace packages. Those names remain historical in receipts and changelogs.

## Gateway founding and recovery

A fresh gateway founds itself: it creates `Shared` and `Personal` and enrolls the host device as owner on both. An existing data directory is never modified by founding. There is one ticket concept — the pair ticket — and web/PWA and mobile onboarding are ticket-only. The former founding ceremony and `vaults:initialize` / `vaults:restore` routes are not part of the current surface. Recovery kits remain a backup-plane export and are consumed by `centraid-gateway recover`. Settled in [#603](https://github.com/srikanth235/centraid/issues/603).

## Ownership, sharing, and peer transport

The ruling from [#726](https://github.com/srikanth235/centraid/issues/726): **one owner per vault, structurally enforced; there are no roles.** Authorization asks which owner a proved device binds to and whether that owner owns the vault. Sharing is placement, not row filtering: data crosses by projection into an audience vault, and no one queries another person's vault. Commons is circle-backed co-owned residency. The Give half — a receiver-owned snapshot as a member-facing act — is superseded by [#825](https://github.com/srikanth235/centraid/issues/825); a share is a standing grant and closure projection is internal fulfillment transport ([Sharing v1](#sharing-v1--the-grant-plane-825)). The authentication boundary is transport-first (Iroh `EndpointId` proves the device; custody of the data directory proves the host) with no password/session/OIDC plane, which remains the standing [#599](https://github.com/srikanth235/centraid/issues/599) security decision minus its role vocabulary. Schema, tables, and mechanics live in [ARCHITECTURE.md](../ARCHITECTURE.md#vault-ownership-and-sharing-726) and [SECURITY.md](../SECURITY.md); vocabulary in [glossary.md](glossary.md#owners-gateway-726).

## Commons

Commons is circle-backed, steward-serialized multi-writer state from [#731](https://github.com/srikanth235/centraid/issues/731). The steward orders member-signed commands into a monotonic log; members apply checkpoint plus tail and compute balances from identical rows. Non-steward writes require the bound vault signature and fresh nonce. v0 uses deterministic last-write-wins by steward sequence; invalid commands are refused rather than surfaced as retriable conflicts.

## Experimental features (v0)

Automations and connectors ship in the release binary but are **off by default** in v0; the gate exists for owner + enthusiast early feedback ([#774](https://github.com/srikanth235/centraid/issues/774)). Resolution per feature mirrors Resource mode: `CENTRAID_EXPERIMENTAL` env (authoritative when set) &gt; durable prefs `gateway.experimental.*` &gt; host option &gt; off, applied at serve boot. Off means absent: no capability advertisement (C1), no routes, no webhook ingress — clients hide or wall the surface from the one capability detection point. Turning a feature off leaves its durable data intact. System recognition recipes (photo OCR, faces, embeddings, transcripts) are **not** gated: schedulers always run and the gate lives in the reconcile row-set, so the photos pipeline keeps flowing while user automations stay dark. There is no remote flag service and no per-user targeting — each user owns their gateway; the opt-in switch is the allowlist. Clients treat an **unanswered** capability question as unknown, never as off, wherever a stale answer would reshuffle standing navigation: mobile places never hide on unknown (offline cold starts keep their band), and the desktop route wall stays a blank frame until resolved. The desktop launcher/palette are the recorded exception — they boot at off because hiding beats flashing against a loopback gateway that answers within a frame (see `packages/client/src/react/shell/capabilities.ts`).

The proposed fixed-window replacement for steward-side ack-gated compaction is **not adopted**. The current `share_commons_cursor` ack and retention behavior remains until unconditional checkpoint digest verification and real dogfood lag measurements justify a change. The instrumentation is exposed through the commons diagnostics described in [logs.md](logs.md#commons-sync-observability-731); the proposal and its rejected alternatives live in [#731](https://github.com/srikanth235/centraid/issues/731).

## Recognition automations and derived data

Recognition is self-contained automation. `photo-ocr`, `transcript`, `embed-image`, `embed-text`, and `faces` read bytes through `ctx.vault.content`, run their bundled implementation, and persist through `ctx.vault.invoke`. The automation engine owns scheduling, consent, retries, cursor watermarks, and ledger history. There is no service wire, `ctx.infer`, or `ctx.enrich`. A recipe may declare a consented `ctx.delegate` variant — `photo-ocr` and `doc-text-extractor` do — and which engine runs it is answered by the policy cascade below, not by the recipe alone ([#807](https://github.com/srikanth235/centraid/issues/807)). Device-side model inference is not part of the product; clients consume replicated derived rows. See [recognition-automations.md](recognition-automations.md) and [Photos derived ledger](photos/derived-ledger.md).

Faces consume only an open `enrich_request(capability='faces')` or a prior consent stamp. `media.forget_person` removes regions, embeddings, derivation stamps, and clusters. `enrich_derivation` is the provenance record, and model upgrades are backfills that leave older rows serving until replacements land. The stamp is keyed by **engine profile** as well as target and variant ([#807](https://github.com/srikanth235/centraid/issues/807)): several profiles' results for one variant coexist, and consumers read the one `preferredDerivation` ([`packages/vault/src/enrich/derivation.ts`](../packages/vault/src/enrich/derivation.ts)) resolves — never a hand-picked row.

## Generic enrichment (#807)

Ruled 2026-08-17 by [#807](https://github.com/srikanth235/centraid/issues/807). Enrichment is four independent layers, and conflating any two is what made the old single-scalar policy unable to grow. The binding statements live in [blueprint-seats.md](blueprint-seats.md#enrichment-doctrine) and [recognition-automations.md](recognition-automations.md).

| Id | Current decision |
| --- | --- |
| **E-capability** | A capability is a typed contract — input kind to versioned output schema — registered in [`capability-registry.ts`](../packages/server/src/enrich/capability-registry.ts). Apps consume capabilities by contract only. `EnrichDomain` stays closed at `photos \| docs`; an app is not a domain, so Tally receipts ride `docs` and app-level differences are expressed by the cascade's app scope. |
| **E-engine** | An engine profile is a named bundle of capability + engine + parameters. Bundled deterministic models are immutable `built-in` profiles; member profiles bind a harness, model, config pins and prompt revision. Profiles are **gateway prefs** (`enrich.profile.*`) because execution is a device property — see [config-ownership.md](config-ownership.md). |
| **E-egress** | Every engine carries a computed egress class — `on-device`, `gateway` (the member's own infrastructure, not egress), or `provider`. It is a fact about the harness, never a user knob, and a profile can never claim a lower class than its engine implies. |
| **E-policy** | Policy is one scoped cascade — vault, domain, collection, item — stating per capability: enabled, engine profile, trigger. `NULL` inherits; most specific wins. Rules and consent are **vault-owned** because permission travels with the data. There is exactly one resolver, inside `decideEnrichmentGate`; a second policy path is a defect. |
| **E-ceiling** | The legacy per-domain tier survives as the vault-default layer, its values read as egress ceilings (`off`, `on-device`, `gateway`). Only that layer sets the ceiling, so no rule, profile, or per-item choice can widen egress. It is **not a member-facing control** ([#815](https://github.com/srikanth235/centraid/issues/815)): enrichment runs on the gateway, and where it runs is not a choice, so Settings → Enrichment offers no per-domain tier. The gate is unchanged, so a row a stored ceiling refuses says so at that row — removing the control must not turn a refusal back into silence. |
| **E-consent** | Egress consent is keyed capability × egress class (× optional scope), asked once, receipted, and evaluated **independently** of the cascade. The tier is the recorded answer for `on-device` and `gateway`; `provider` requires an explicit granted row, and an absent answer is not a grant. |
| **E-plural** | Derived results are keyed by engine profile and coexist. Consumers read the policy-preferred result through the one resolver; re-enrichment is backfill, never destructive. |
| **E-faces** | Faces stays built-in, on-device-class only. Biometric egress needs its own proposal before any delegate engine may claim it. |
| **E-oneshot** | A per-item "enrich with X" is a one-shot run with stamped provenance, not a standing item rule; durable rules stop at collection scope. |
| **E-budget** | Triggers live in the cascade; resource budgeting stays in the gateway Resource mode machinery. Enrichment grows no second throttling policy, and provider-cost ceilings are out of scope. |

Blueprints gain nothing from this: apps declare consumed capabilities and never touch inference, and `app.json#knobs` stays cosmetic. The per-app enrichment surface writes host-owned policy through host UI.

## Typography and design contracts

The design contract is binding in [DESIGN.md](../DESIGN.md) and lowered by `@centraid/design`. Shared semantic roles use one spelling across shell, blueprint, and native lowerings; size and line-height may differ by renderer, while family and weight express the role. The composable `--t-*-size` rungs are the supported escape from shorthand font roles, and `kit.css` consumes them rather than owning a second scale. The `--t-tiny` family/weight exception remains explicit in the role-parity contract until a separately named eyebrow role can replace it. See [design machinery](design-machinery.md) and [#686](https://github.com/srikanth235/centraid/issues/686).

The seat and north-star contract is orthogonal to form factor: mobile is `origin`, desktop is `custodian`, and web/PWA is `viewer`; record-only apps use replica data, byte-bearing apps use the custody triple. Locker is disabled on the viewer seat, and Photos uses a merged timeline plus automatic frame-owned backup. See [blueprint seats](blueprint-seats.md).

The design-gallery gate screenshots the product, not a fixture. Ruled 2026-08-15 under [#799](https://github.com/srikanth235/centraid/issues/799): the SH and SH-c lanes capture the built web shell's `#ui-preview` surface, and every capture renders the product's self-hosted Instrument Sans woff2 faces — loaded from the same `FONT_FILES` manifest the shell serves, gated by `document.fonts.ready` plus an explicit resolution probe so no fallback face can be baked into a baseline. This supersedes the `system-ui` bootstrap fixture and discharges the one-time maintainer baseline decision recorded against [#781](https://github.com/srikanth235/centraid/issues/781): baselines are Linux-captured and byte-deterministic there; if a darwin run shows a residual rasterizer delta, the remedy is per-platform baseline directories, never a widened diff tolerance. BI and MO are deliberately token-lowering lanes, not component screenshots: MO has no DOM, and photographing the shell's React blocks under the blueprint lowering would depict components no blueprint app renders (the two DOM compositions merge under [#765](https://github.com/srikanth235/centraid/issues/765)). A lane's narrower claim is stated in the gallery manifest's `laneClaims` rather than left to be misread as component coverage.

**The 400 register renders in a 470 face on native, and only on native.** Ruled 2026-08-19. DESIGN.md still specifies two weights (400 / 600) and nothing in the ramp may name a 470: this is a **lowering**, in the same place and for the same reason as the size delta. `NATIVE_DELTA_BY_FAMILY` already grants touch surfaces +2px size and +3px leading over a desktop pane at the same role, and that step scales the glyph without scaling the stroke's optical presence; iOS compounds it, because CoreText draws with grayscale antialiasing where a desktop browser gets stem darkening. Same token, same face, objectively lighter strokes on the phone — so the register reads correct at a desk and thin on the device, and no edit to the shared ramp could fix one without wrecking the other. 470 rather than the 500 `@expo-google-fonts` ships: 500 overshot by eye, and 470 sits ~73% of the way from 400 to 500 in measured ink coverage. The face is a derived SIL OFL instance bundled at `apps/mobile/assets/fonts/`, whose provenance, licence and regeneration procedure are recorded in its own README; the 400 static is no longer loaded on native, because nothing there renders it. Web and desktop are untouched, which means the design-gallery lanes keep photographing weight 400 — the gallery depicts the ramp's specification, and the device now deliberately differs from it on this one axis.

System state follows the signal ladder settled in [#785](https://github.com/srikanth235/centraid/issues/785): ambient ribbon → glance destination → push only for a human decision → cause-focused drill-down. The signal vocabulary is exactly quiet, attention, and urgent; healthy state earns no hue or animation. Persisted route ids remain stable while member-facing destinations are Vault, Activity, System, and On this phone. Seat filtering is presentation only, and omitted launcher destinations remain deep-link reachable with an explanatory state. The Assistant remains a full route and also appears as a frame companion; its pointer rail reserves content width rather than reproducing the reference prototype's overlay limitation. See [assistant companion and system signals](system-signals.md).

## The app navigation rail (#835)

Ruled 2026-08-21 by [#835](https://github.com/srikanth235/centraid/issues/835). An app's own destinations navigate on **one axis across the product**: a vertical 232px rail on the leading edge of its content, on a pointer seat.

- **An app earns a rail by having more than four destinations of its own.** Below that the app bar's segmented control carries them and the rail would be a column of three rows. Photos (seven) and Docs (five plus the folder tree) meet the test.
- **Two navigation columns is not two spines, and invariant 1 still holds.** The band is reserved for the frame. The **stem answers which app**, at `--w-stem`, and never moves; the **rail answers where in it**, at `--w-app-rail`. Where the route also has an info rail, the three columns are three questions — which app, where in it, what is this.
- **Exactly one surface carries them per seat, never two and never none** (`apps/_shared/nav-seat.ts`): the frame's compact band where the app's band claim was honoured, the rail on a pointer seat with room for a column beside the set, and the horizontal shelf strip everywhere between. A destination reachable only from the rail is a defect, so every rail row is a shelf the app's own tables already route to.
- **Counts have one source.** The rail, the strip and the band's More sheet read one per-shelf map per app; a folder's count and the Folders shelf's own read `apps/docs/folder-counts.ts`. A count that disagrees with its shelf header is a defect.
- **The rail spends no identity.** No hue, no icon chip, no badge, no dot, no motion, and no new rung, weight, colour, radius or control recipe. The two geometry metrics it needed — `metrics.appRail` and `metrics.appRailRow` — are in `packages/design`, not at the call site.
- **Deliberate non-goals**, each stated by the handoff and not designed: expandable rows (sub-folders, named albums under Albums), drag onto a rail row to file or add, a resizable or remembered width, and automatic collapse of the frame's stem when an app rail is present — that last one is a frame decision, and ⌘B still does it by hand.

Where the shipped rails differ from the design reference, and why, is the register in [design divergences](design-divergences.md#the-app-navigation-rail-835).

## Photos place and cartography (#816)

Ruled 2026-08-17 by [#816](https://github.com/srikanth235/centraid/issues/816). Place is a first-class dimension of memory, and the three answers below — how a place is named, which surface owns the experience, and what is drawn under the pins — are decided independently.

| Id | Current decision |
| --- | --- |
| **P-ladder** | A place is named by a phrase ladder, in falling order of what the vault knows: a name the member gave it; a settlement name from the gazetteer when the opt-in gazetteer automation is on; a phrase relative to a member-named place; then "A place with no name yet". A coordinate is never printed as a name. Raw coordinates appear only behind an explicit exact-location action the member takes on one item. |
| **P-gazetteer** | Coordinate-to-settlement naming ships as an **opt-in, zero-egress automation** over a vendored open dataset (GeoNames `cities15000` class, CC-BY): the lookup runs against bundled bytes, so nothing is requested and no coordinate leaves the device. A member-entered name is authoritative and derived naming never overwrites it. |
| **P-mobile-first** | The Expo mobile app is the **primary Photos surface**: it is where place work is designed, built, and accepted first, and a wave exits on mobile evidence. It runs as a dev client with config plugins — never Expo Go, never a webview. Web is the **curation surface** and lands after mobile, not before. |
| **P-cartography** | Cartography has two modes. On mobile the real map is the default: iOS renders Apple MapKit through `expo-maps`, Android renders MapLibre (`@maplibre/maplibre-react-native`) against OpenFreeMap vector tiles — both keyless, no account, no vendor API key in the app. The **"Use real maps"** setting (on by default) swaps to the Private sketch, the zero-egress projection both surfaces already share ([`place-map.ts`](../packages/blueprints/apps/photos/place-map.ts)). Web is sketch-only and its CSP stays `'self'`. Trip-card covers always render the offline projection, in either mode, because a card is an artifact rather than a live view. |
| **P-shared** | A relative phrase ("3.4 km NE of Home") is readable only to someone who knows where Home is, so it is a **private** rung: it never renders in a shared or exported context, and never in a title a card carries. In a shared context the ladder falls straight from the member's name to the gazetteer name to "A place with no name yet". Place metadata rides along on a share only by the member's explicit choice, at a precision they chose. |
| **P-egress** | In real-map mode the map provider sees which areas are viewed. That is disclosed plainly where the setting lives — it is **not** consent-gated, because it is base-layer traffic a member turns off with one switch. No vault bytes, coordinates of items, names, or photographs are ever sent to a map provider under either mode. |

| Id | Current decision |

| **L-linked** | A person is **linked** exactly when a live `share_party_vault_binding` row names their party. ## Sharing v1 — the grant plane (#825)

Ruled 2026-08-19 by [#825](https://github.com/srikanth235/centraid/issues/825). A share is a **standing grant**, and the audience's bytes are a replica under it. One app-agnostic infrastructure carries every app: `share_grant(grant_id, audience_kind person|circle, audience_id, subject_type, subject_id, capability view|edit, granted_at, revoked_at, granted_by)` states the member's sentence, `share_fulfillment(grant_id, peer_vault_id, state awaiting_channel|syncing|delivered|remove_sent|removed)` carries per-audience-vault delivery. Capabilities are `view` and `edit`; `comment` is reserved and unimplemented. These rulings land ahead of the code waves of #825, per its execution plan.

| Id | Current decision |
| --- | --- |
| **G-membership** | Container semantics are **membership, not snapshot**. A grant on an album or folder covers its contents now and later; an item added after the grant is shared by the grant, with no second act. |
| **G-view** | View grants sync forward. The origin is the sole author of a `view` subject and delivery is **re-projection on change**, not a CRDT merge. Divergence between origin and audience copies is a bug to fix, never the resting state. |
| **G-edit** | Edit grants route writes back through the existing commons command routing ([`commons-routing.ts`](../packages/vault/src/share/commons-routing.ts)): the commons machinery is the `edit` **fulfillment strategy**, not a second product concept beside grants. The [#750](https://github.com/srikanth235/centraid/issues/750) rule survives as the registry gate — a subject type with no fulfillment answer cannot be offered. v1 ships edit co-contribution for `tally.group` only; albums and folders are view-capable and their edit strategy is deferred. |
| **G-revoke** | Revoke is **one verb, uniform, and honestly best-effort**. `revoked_at` stops sync and sends removal; a sovereign system cannot scrub a peer's disk, and the copy says so plainly — "no longer shared; her vault has been asked to remove it". Removal on the audience side is a hard delete: no tombstone row survives it. Qualified 2026-08-21 by [#839](https://github.com/srikanth235/centraid/issues/839): defect D1 reaches a revocation that settles `removed` while the audience keeps the projection. The ruling stands as the intent; the divergence is pinned, not tolerated — see [Adversary lanes](#adversary-lanes-and-provisional-evidence-839). |
| **G-channel** | ~~Share subsumes linking.~~ **Superseded 2026-09-01 by [#903](https://github.com/srikanth235/centraid/issues/903): linking IS the prerequisite.** A person is reachable exactly when a live `share_party_vault_binding` names their party, and the People link ceremony is the only thing that writes one. A party grant naming anyone else is refused by the `share.*` pack in the ruled vocabulary, and no invitation is minted on the member's behalf — there is no second way to reach a person. The **channel** narrows to two states, `live\|severed`, both read off a binding; `awaiting_channel` survives with its meaning narrowed to "the peer vault is known and the link to it has ended". **Circle grants are exempt from the refusal**: [G-membership](#sharing-v1--the-grant-plane-825) already covers members now and later, so an unlinked member is a delivery question — undeliverable until they link, then delivered on the next pass with no re-grant — rather than a reason to cost the member their circle, the same reasoning [V-mask](#grants-v2--one-authority-plane-883) uses for a refusal standing inside a granted one. |
| **G-copy** | Copy-as-share retires, code and all. The give / edge-answer verbs and the transport beneath them — the give route and client, the remote reconciler, the audience-side ranged blob pull and the `/_peer/blob/chunk` route it read, the `await-answer` / `deliver-refusal` / `pull-blob` outbox kinds, and the per-link "receive gives" preference — are **deleted**, not gated, and no "give a copy" verb replaces them in v1. [`readShareClosure`](../packages/vault/src/share/read-closure.ts) / [`projectShareClosure`](../packages/vault/src/share/project-closure.ts) survive as **internal fulfillment transport** only — machinery beneath a grant, never a member-facing act. |
| **G-audience** | Audience-first is the primary key. "Everything Priya can reach" is one query over `share_grant`; People's person screen is the grant dashboard, and Share and Revoke return there through it. |
| **G-subject** | `people.person` is never a subject. A person is the **audience** side of a grant; subjects are the shared things — album, folder, document, asset. |

**A retired obligation is drained, not retried.** A gateway upgraded across G-copy can still hold queued `share_effects` rows whose transport no longer exists — a cross-owner `deliver-give`, or one of the three retired kinds. Leaving them queued would keep a sweep dialing a verb that answers `not_found` and parking the edge with a network-sounding reason: a queue claiming a delivery might still land. Marking them `done` would be worse, because `done` means discharged and nothing was. So `retireDeadShareEffects` (`packages/server/src/serve/share-effects-retire.ts`) runs once at every writable `gateway.db` open: the obligation row is deleted and its edge moves to the terminal `failed` with the reason "giving a copy to another person's vault was retired; share it as a grant instead". `failed` is right here where it is wrong for a retry — the verb was withdrawn, which is exactly the finality it claims. An edge that already reached an answer (completed, denied, revoked, failed) keeps it; `share_access_receipts` is untouched, so every copy that DID land stays audited, and no delivered copy is un-delivered. The `link_receive_settings` table is dropped in the same pass, being a stored answer to a question nothing asks.

**Grants deliver to vaults mounted on the same gateway (v1 limit).** Fulfillment resolves an audience vault through the host's own registry, and the peer transport that might have carried bytes cross-host retired with G-copy. A grant to a party whose vault lives on another gateway parks at `syncing` with the vault named — the ask stands, the vault is not here — and stays there. Stated as a current limitation wherever the docs could imply otherwise; carrying a grant across the peer plane is a follow-up under #825, not a v1 requirement.

Per-grant size ceilings carry over unchanged from the commons limits; the grant plane adds no second budget. Circle grants recompile their roster on every fulfillment pass — a party added to a granted circle is delivered on the next pass with no re-grant — while grants the #825 migration decomposed into per-party rows are literal and do not follow roster drift; reaching a later addition there takes a new grant.

## Tally's remaining engineering asks (#873)

Ruled 2026-08-26 by [#873](https://github.com/srikanth235/centraid/issues/873), against the gap register carried on [#872](https://github.com/srikanth235/centraid/issues/872). The v17 handoff drew eight surfaces against a backend that did not exist yet. These are the answers the vault now holds; every one of them keeps the app's founding rule — **no balance is stored and none is transmitted**, and every figure derives at read time through one fold.

| Id | Current decision |
| --- | --- |
| **T-method** | An expense records the **division it was entered with** (`split_method`) and that division's parameters (`split_params_json`), alongside the resolved shares it already stored. The vault still stores only resolved shares and never re-derives one from the parameters: the pair is provenance, so an edit re-opens the way the expense was entered instead of collapsing every division to exact amounts. Six methods are closed: equally, exact, percentages, shares, equally-adjusted, by line. A row entered before this reads as `exact`, because the resolved amounts are all it can honestly claim. |
| **T-lines** | Typed lines hang off the **expense**, with the receipt as a nullable decoration — they used to hang off the receipt, which made a photo the price of itemising. "By line" is therefore the same allocation table as Receipt with no capture. Three totals are re-validated server-side on every write: splits sum to the amount, lines sum to the amount, and each line's allocations sum to that line. |
| **T-payers** | `tally_expense_payer` records who actually put money down. It is written for **every** expense, the single-payer case as one degenerate row, so both balance folds read one shape; `paid_by` stays populated as the named principal and must be one of the payers, which is the compat rule that keeps a reader that only knows that column right. A participant's share is owed to each payer for the part they actually put down, matched off largest-first rather than pro-rated, because pro-rating rounds per share and the rounded portions then stop adding back to what each payer paid. |
| **T-groupless** | A 1:1 expense may stand **outside any group** (`tally_expense.group_id` is nullable), mirroring how a settlement always could. With no group there is no audience to check against, so participants are validated against the friend roster — you plus every enrolled `tally_friend` — and the commons rail resolves such an expense to **no container**, which makes it a private local write rather than an unrouted shared one. |
| **T-simplify** | Debt simplification is **opt-in per group and off by default**, because it rewires who owes whom and a member who agreed to pay Ana should not silently owe Tom. `tally_group.simplify_opt_in` is the only thing stored: the minimal payment set is derived at read time by `packages/blueprints/src/tally-simplify.ts`, the proposal always states what it rewired (debts before, payments after), it writes no debts, and an accepted proposal is recorded as ordinary settlements. |
| **T-leave** | Leaving a group is `tally.leave_group`, which is `remove_group_member` **without** the on-ledger guard: the rows stay exactly where they are and the leaver stops being a current member. "Departed" is derived, not a column — a party on the ledger who is not in the group's circle reads as departed. Archiving (`tally.archive_group`) needs **no settled balance**, keeps everything, and only drops the group from the default lists. |
| **T-nudge** | A balance nudge **parks and never fires**. `tally.nudge` carries `confirm: true`, and an app handler is by definition a non-owner caller, so a nudge raised from Tally always lands in Waiting for the owner's confirmation; executing it writes one row recording that a reminder was prepared, with the net the owner saw. There is no delivery path in this vault and this ruling does not invent one — `sent` is stated on the output and is always false. |
| **T-rate** | Currency-rate assistance is **additive and derived from the vault itself**: the most recent rate already recorded for a pair, carried with its source and date. There is no rate provider, no network call, and the manual-rate flow stays the primary path. |
| **T-export** | A group export carries expenses with their payers, splits and typed lines, the settlements, and the edit history. **Balances are excluded by design** — they are arithmetic over those rows, and shipping one would be the first stored balance in the app. The window is bounded and says whether it truncated. |
| **T-revoked** | A consent refusal an app renders as its access state carries **when** the grant went. The vault already recorded it; the app cannot read that, because losing the grant is exactly what put it there — so the host attaches `revokedAt` to the refusal (`VaultPlane.withRevocationTime`). It is absent when the refusal was never a revocation, and no caller may invent one. |

Two rulings the register carried as open questions are settled the same way: group-less 1:1 expenses ship (GAPS #4), and cross-member comments on an expense stay **out of v1** — memo covers annotation and Waiting covers coordination, and a comment thread is a second multi-writer object with its own intent lifecycle.

**Waiting draws no Approve and no Decline on the phone.** The gateway has a per-intent steward door ([`commonsIntentDecidePath`](../packages/core/src/protocol/routes.ts)) and the web seat calls it, but no mobile transport reaches it and nothing on that device reads another member's commons intents. `TALLY_CONTRIB_DOORS.decide` is therefore `false` on the origin seat: the surface says whose writes it is showing, and a steward-only act hands over to the shell's Approvals inbox. Drawing the verbs anyway and refusing on press would be a control that cannot fire, which the seat doctrine refuses; the parked rows are honest about being someone else's to answer.

**The Home tile says "spent this month", not a net balance.** SURFACES.md wants a net there. `useSpringboardTiles` fills tiles from replica rows OFFLINE and never asks a query, so deriving a net on that path would be a **second balance engine** beside `queries/dashboard.ts` — the one thing this app forbids, since the whole design rests on every figure coming from one read-time fold. The tile therefore states a figure it can compute honestly from the rows it has. Revisit only if the springboard gains a query path; a tile is not worth a second derivation of "who owes whom".

## Locker's remaining engineering asks (#873)

Ruled 2026-08-26 by [#873](https://github.com/srikanth235/centraid/issues/873), against the same gap register carried on [#872](https://github.com/srikanth235/centraid/issues/872). Every answer keeps the app's founding rule: **the list is metadata; the secret is not.** A secret value is sealed at rest, never enters a search index, a log or the durable offline queue, and reaches the screen only through an authorised reveal that writes a receipt.

| Id | Current decision |
| --- | --- |
| **L-type** | A type is a **set of sections and fields**, not a set of columns. The nine expansion types (SSH key, API credential, passport, bank account, driving licence, software licence, crypto wallet, membership, document) add **no columns at all**: each is a template minted into `locker_item_field`, so the rule for the next type is "add a template". The six original types keep their columns for compatibility. An unknown type **degrades to a note that still carries its custom fields** — a read-side rule, because the type CHECK keeps the write side honest, and because a vault restored from a newer build must render rather than throw. |
| **L-field** | An owner-defined field is `(section, label, kind, value)` with `kind` in text / sealed / url / date / otp, and it is written **one field per command**. The value column is split in two — `value_text` and the declared-sealed `value_sealed`, kept apart by a schema CHECK — because sealing is per COLUMN while a field's kind is per ROW, and a single polymorphic column would have had to seal the fields the member wants to read at a glance. One-at-a-time is not ergonomics: `sealedInput` redacts only TOP-LEVEL command inputs, so a list of fields would have carried secrets into the append-only journal in the clear. |
| **L-history** | Item and password history is a durable sidecar (`locker_item_history`), deliberately **not** `core_entity_revision` — that ledger is the 10-second undo window and its sweep prunes it, so a password rotated last March would be gone. A previous password is as much a secret as the current one, so it is a declared sealed column, resealed against the history row's own cell rather than copied as ciphertext (the AAD binds a ciphertext to its cell). **Password age is set-time** (`locker_item.password_set_at`), stamped only when the value actually changes, so a retag never makes an old password look fresh. |
| **L-address** | A login may answer to more than one address, each with **its own match policy**. The item's `url` and `url_match_policy` stay the primary address, so the Companion candidate list, the connector binding and Review's unsecured-address check are untouched; the sidecar is strictly additional. |
| **L-passkey** | The passkey slot is **storage only** — credential metadata (relying party, user handle, created) plain and browsable, key material in a declared sealed column. No WebAuthn ceremony exists in this vault and this ruling does not invent one. |
| **L-archive** | Archive is **exclusive with trash**, not orthogonal to it: an item is live, archived, or trashed, enforced by a schema CHECK. Archived means "keep forever, hide from lists" — it leaves the default window, sets no purge date, and nothing expires. |
| **L-duplicate** | A duplicate copies sealed values **inside the vault** — unsealed and rewritten so the sweep reseals them against the new row — so no secret round-trips through the client. The copy is not starred and does **not** take the original's connector alias: an alias is unique among live items, so carrying it would steal the binding from the item it was cloned from. |
| **L-export** | The plaintext export is a **command, not a query**, for two independent reasons: a query handler is read-only by directive and so cannot write the receipt a mass reveal owes, and a replica read returns sealed columns as placeholders and so could not see the plaintext anyway. It is confirm-gated (so a non-owner device parks rather than acts), online-only (a mass reveal must never be queued or replayed), receipted as an unseal of every sealed cell it opened, and `transcriptSensitive` so the journal records that an export happened without becoming a second copy of it. Previous passwords are opt-in. The **file is written client-side**; the command is the data door. |
| **L-access** | Access history reads the vault's own `access.receipt` stream — auth, reveal and fill, refusals included — under a grant whose **rowFilter pins `object_type` to Locker's own objects**. That filter is the boundary, not a convenience: the gateway's structural per-entity guard covers `consent.provenance` only. The query is **online-only by construction**, because journal.db is not in the browser replica and a cached answer would be a list of what one device happened to hold. |
| **L-alias** | The connector alias mapping is a **registered table**. It was DDL-only: written, resolvable at reveal time, and outside the canonical walk — so it never exported, got no replica change-log trigger, and no read could serve it back. Registration is the whole fix, and it closes the first paper cut in README-Locker §8. |
| **L-attach** | An attachment rides the existing content spine (`core.attachment` onto `core.content_item`), one allow-list entry rather than a second attach command. **Honest boundary:** the bytes are NOT sealed — the sealed class is a column class and there is no sealed blob today — so a locker attachment is protected by the vault file, not by the reveal gate, and the app's copy must say so rather than imply otherwise. |

Two asks the register carried as open questions are settled by **not building them**: breach checking stays out (it would mean network egress from an app excluded from enrichment, and `compromised` remains a flag with no automatic producer), and "recently used" stays out (reveal receipts could power it without new writes, but a recently-used shelf publishes reading habits on the one screen where reading is the sensitive act).

**The sealed sidecars reveal through the item's own permit.** A sealed custom value, a passkey's key material and a previous password are ciphertext at rest, reported to the app as PRESENT until revealed. `Gateway.reveal` enforces the one-shot Locker permit for the whole `locker` schema: a sidecar reveal resolves the row's **owning item** from the requested row itself — never from the caller — and spends that item's permit, so a field, revision or passkey reveal costs exactly what revealing the item costs, writes the same receipt (the requested row, with the owning item in its detail), and a missing sidecar row refuses exactly as an item without a permit does, adding no existence oracle. A trashed item's sidecars stop revealing with it. `locker-sidecar-reveal.test.ts` pins all of this.

**`locker_auth_credential` stays out of the canonical walk** (ruled with [#873](https://github.com/srikanth235/centraid/issues/873)): registering it would carry passphrase salts and verifiers into the portable export, handing an offline-guessing target to anything that reads the export file. Enrollment is per-install by design — a restored vault re-enrolls its credentials — so the export loses nothing a member could use, and the table remains deliberately unregistered.

The mutation, fuzz, join, simulation and time-zoo lanes are adversaries: they exist to produce evidence the author did not choose. Four answers were owed — what such evidence may claim before it has been measured in the lane that enforces it, where an expensive lock lives, how the matrix says "designed but not built for a reason that is not a gap", and what a lane does with a defect it finds but is not chartered to fix. The mechanics are [TESTING.md](../TESTING.md).

| Id | Current decision |
| --- | --- |
| **A-floors** | The eight mutation seeds over the blueprint app layer and the phone carry **provisional-local floors**, seeded at **(local measured − 11)** pending the first CI measurement. Seeding a floor from the author's own machine **silently** remains forbidden; what makes this admissible is that the file says so at the number. |

Nightly placement is the mutation-floors posture: the expensive adversary runs nightly, and what it recorded is what the PR path enforces. The replay step runs `if: always()`, so a new finding in the search above it cannot suppress the corpus already characterised. |
| **A-held** | `held` is a first-class cell status in `tests/claims.json`, distinct from both `gap` and `excluded`. A held cell **cites the ruling that held it** — [#831](https://github.com/srikanth235/centraid/issues/831) is the precedent and today's only citation — and that citation must be registered and followable but **not open**, because the clearing issue closes while the hold continues. The citation rides the rendered cell: a held interface reads as held, never as absent. |
| **A-pinned** | An adversary lane that finds a defect it is not chartered to fix **pins** it. A characterisation test asserts the current, wrong behaviour and names the ruling or documented sentence it contradicts, so the day the product moves — fixed or made worse — the pin goes red and the record is revisited deliberately. Tolerating the failure quietly and deleting the finding are both refused, and a register entry is never added to go green. **The ruling is proven by its exit, not only by its entries:** the ten pins the #839/#842 lanes raised were all fixed under [#846](https://github.com/srikanth235/centraid/issues/846), and each fix deleted its own pin in the same change — the three registered classes in `scripts/fuzz/known-findings.json` (now empty), the fall-back double fire against [cron-timezone.md](cron-timezone.md#dst-policy), defect D1 against [G-revoke](#sharing-v1--the-grant-plane-825), the two peer-target guard disagreements in `packages/tunnel/src/peer-target-differential.test.ts`, the owner-facing `GET /centraid/_gateway/diagnostics` bundle emitting the owner-authored vault name verbatim, and the DAST pin `header.boundary-response-nosniff` in `scripts/security/dast-known-findings.json` (now empty; three transport-boundary JSON responses that skipped `X-Content-Type-Options: nosniff`, filed as [#844](https://github.com/srikanth235/centraid/issues/844)). Each left a regression lock where its pin stood, which is what the pin was for. **No pin stands.** The last one — an automation worker started with no parent-chosen sandbox lane still reaching the filesystem, subprocesses and the environment (#842 W7.1) — is closed too. Its stated blocker was one builtin: `packages/model-runtime/src/onnx.ts` resolved `runtime/node_modules` through `node:module`'s `createRequire`, which every lane refuses because a `createRequire` in the graph resolves through Node's own loader and skips the lane's hooks entirely. That resolver was reworked, so the automation worker now installs the strict `automation-handler` floor unconditionally and a handler that needs more declares `sandbox.lane` in its manifest, where the ask is reviewable — `model-runtime` for the four ONNX bundles, and a new `media-transcode` lane for the one that decodes media by shelling out to ffmpeg. `bundle-lane-conformance.test.ts` holds every shipped bundle to the lane its own manifest declares, and refuses a declaration wider than the bundle needs. The ruling's record is therefore its exit: ten pins raised by the #839/#842 lanes, ten fixed, each deleting its own pin and leaving a lock. |

**Defect D1 qualified G-revoke; it never amended it, and it is now closed.** The commons simulator reached a schedule where `fulfillShareGrant` drops a `delivered` fulfillment row back to `syncing` because the host could not reach the peer for one pass, and `propagateShareGrantRevocation` then read that `syncing` as never-delivered: it settled `removed` — nothing had been delivered, so there was nothing to remove — while the audience vault still held the whole projection. The owner was told the share was gone and it was not. G-revoke's sentence is unchanged, because it states the intent and the intent is right: revoke is honestly best-effort against a peer's disk. What was wrong was the engine, on a reachable path, in the one direction the copy does not warn about — the admitted failure is a peer that keeps a copy it was asked to drop, not a host that never asks. [#846](https://github.com/srikanth235/centraid/issues/846) P1 made the engine remember what it delivered (`share_fulfillment.delivered_at`, migration rung four) rather than infer it from a live freshness reading, so revocation of a delivered-then-degraded grant asks for removal. The `test.fails` case in `packages/vault/src/share/commons-sim.test.ts` is now an ordinary passing test, and the grant-plane fixture's reach-lost carve-out became a non-vacuity witness instead.

## Performance and Rust byte plane

**The Atlas census counts per file, not per table.** Ruled 2026-08-27 by [#873](https://github.com/srikanth235/centraid/issues/873). `atlasCensus` issued one prepared `COUNT(*)` per registered table, so the first-paint SQL budget in [`tests/experience-budgets/client-query-counts.json`](../tests/experience-budgets/client-query-counts.json) had to be raised once per registration — [#731](https://github.com/srikanth235/centraid/issues/731) 128 → 138, [#807](https://github.com/srikanth235/centraid/issues/807) 138 → 140 — and the [#825](https://github.com/srikanth235/centraid/issues/825) grant-plane tables were excluded from the census on that budget's account. The counts are now batched into one compound `SELECT … UNION ALL` per database file ([`countRowsBatched`](../packages/vault/src/schema/atlas-graph.ts)), chunked well under SQLite's compound-select ceiling, with a `sqlite_master` pre-check so an absent table still answers 0 and a per-table fallback so one uncountable table cannot take its batch down. The arithmetic is unchanged: every registered table is still scanned, and no table left the answer. **Registering a table now costs a scan and never a statement**, and the budget is tightened 140 → **13**.

The consequence for the instrument is the part worth recording: **a statement count no longer proxies per-table scan cost**. The budget still catches a screen that starts issuing N+1 round trips, which is what it was built for, but growth in the registry — the thing it used to track by accident — is now invisible to it. If that trend ever needs guarding, the successor is a wall-clock or scanned-table instrument, not a re-raised statement count. The #825 exclusion's own rationale is retired with the budget it cited; whether the census should count the grant plane again is a payload-shape question and is deliberately left open rather than answered here.

Node remains the gateway runtime until Bun supports `node:sqlite` and passes the same durability suite. Five performance designs — dependency-aware read cache, compiled consent decisions, incremental materializations, verified boot snapshot, and lazy vault mount — are evidence-gated, not adopted; mounting stays eager because a missed automation wakeup is a correctness failure. The Rust data plane moves bounded bytes only and never owns identity, consent, journal, replica, agent, or automation decisions. Budgets, profiles, and the full boundary live in [ARCHITECTURE.md](../ARCHITECTURE.md#performance-and-byte-plane-boundary); settled in [#456](https://github.com/srikanth235/centraid/issues/456). The five evidence-gated designs take their gate from [#927](https://github.com/srikanth235/centraid/issues/927)'s journey ledger when it lands; until then the instruments [#922](https://github.com/srikanth235/centraid/issues/922) wave 1 lands (F3/F5 and #927's work counters) are the interim — see [Snappier blueprint apps](#snappier-blueprint-apps-922).

## Product grammar and block composition

The product grammar is the current design contract, not a migration plan: semantic roles, lowerings, recipes, icon/identity/formatter contracts, and reference states are enforced by [DESIGN.md](../DESIGN.md), [design machinery](design-machinery.md), and their tests. The former plan's durable outcome is that app identity and action colour remain separate, host appearance owns appearance, and mobile consumes `toNativeTheme()` without CSS parsing. See [#690](https://github.com/srikanth235/centraid/issues/690) and its review closure [#695](https://github.com/srikanth235/centraid/issues/695).

**The public web surfaces render in the product's design.** Ruled 2026-08-21: `centraid.dev` and `centraid.dev/docs/` consume the same `toCss()` lowering, the same vendored Instrument Sans, and the same app mark as the shell, emitted by [`scripts/site-tokens.mjs`](../scripts/site-tokens.mjs) into a committed `centraid-tokens.css` per surface. They had carried a design of their own — Fraunces + Newsreader + IBM Plex Mono over a cream paper palette with the teal brand hue the v8 flip retired, plus hard offset shadows, tilted cards and a grain overlay — so the first two things a visitor saw of Centraid looked like a different product from the one they then installed. The **non-goal** it names: a marketing design language separate from the product's. The site's own theme names (`paper`/`night`) are gone with it — the two themes are `light` and `dark`, and no `data-theme` means "follow the system", exactly as in the shell. The sanctioned steps beyond the ramp are in [design-divergences.md](design-divergences.md#the-public-web-surfaces); `assets/logo.svg`, `assets/app-icon*.svg` and `assets/splash.svg` still carry the retired teal and are **not** covered by this ruling.

**The nightly test report renders in the product's design too.** Ruled 2026-08-23: the third public surface — `/test-report/` on the same Pages origin as the two sites above — takes the same `toCss()` lowering, the same vendored Instrument Sans and the same `light`/`dark` contract, emitted by the SAME [`scripts/site-tokens.mjs`](../scripts/site-tokens.mjs) into a committed `scripts/test-report/report-tokens.css` and gated by the same `bun run lint:site-tokens`. It had been missed by the 2026-08-21 pass and kept a palette of its own (`--green`/`--red`/`--amber`/`--blue`/`--violet`/`--cyan`/`--grey` over a near-black ground), Inter, a type scale of its own, and no light theme at all. It differs from the two sites in exactly one way, and the reason is publication rather than taste: `generate.mjs` emits ONE self-contained file that `prepare-pages-site.mjs` publishes to both the mutable `nightly/` alias and an immutable `nightly/runs/<slug>/` archive, so no relative `url()` resolves from both depths and an archive has to keep rendering years later — the four faces are therefore inlined as `data:` URIs, and `report-theme.mjs` throws at generate time if any `@font-face` is left linked. The matrix's status ramp is named once in the emitter (`--st-*`) and registered in [design-divergences.md](design-divergences.md#the-nightly-test-report); the **non-goal**: a second design language for internal or engineering-facing surfaces. See [#853](https://github.com/srikanth235/centraid/issues/853).

**The nightly report is drawn in the Night Watch register.** Ruled 2026-08-24: `/test-report/` keeps one lowering, one face, the `light`/`dark` contract, one emitted sheet and one gate, and gains the layout the 2026-08-23 ruling froze: a masthead carrying the run's identity, a `role="status"` verdict bar with tonight's counts and last night's delta, a sticky index, and the sections in the design's order, with the infrastructure heat map demoted from the opening act to §8. The page's ground, ink, rules and tints are nineteen `--nw-*` rungs, emitted by the same [`scripts/site-tokens.mjs`](../scripts/site-tokens.mjs) into the report's sheet and nowhere else, and its type steps below the shell's smallest rung are authored beside them: a bounded reopening of that ruling's "no palette and no scale of its own", because a page read at a glance in ink that bottoms out at 10px needs tones, rule weights and steps the shell has no rung for. A matrix cell is a button carrying the state's WORD on a quiet family tint — which **supersedes** that ruling's fill-and-trough register, and leaves no fill on the page. The **honesty rule** this pass generalises from the matrix to every section: where the design shows a figure the repo cannot prove, the page renders what is real and names the gap — §6 is suite × budget because nothing maps a journey to an app, §5 prints no simulation numerics, an evidence age with no timestamp is an em dash, and the immutable-slot link is absent when CI supplies no slug. Grading and the nightly zero-grey gate are unchanged. The **non-goal**: a `--nw-*` rung on any surface but this one. What bounds each departure is registered in [design-divergences.md](design-divergences.md#the-nightly-test-report). See [#862](https://github.com/srikanth235/centraid/issues/862).

**One hue, one meaning, and one word, on the nightly report.** Ruled 2026-08-25: the Night Watch register paints **eight** tone families and each answers exactly ONE question — `ok` (evidence passed a solid claim), `partial` (passed, where the matrix claims only partial), `danger` (the run went wrong), `flaky` (green only on retry), `gap` (no test exists), `attn` (the report cannot vouch for its own evidence), `grey` (the evidence is absent), and `bug` (the product is known-broken — a declared defect, added 2026-08-25 by #864 Wave 7 so a product-bug cell cannot share the gap family's plum). It had painted twelve states with four families, so one colour carried several answers: grey meant both "the lane never reported" and "nobody has written this test", red meant both "tonight broke" and "the matrix declares a hole", amber meant four unrelated things — and the SAME fact was red in §8 and grey in §2, because the app grids kept a private alphabet. The `--seam` literal the attention rung duplicated is released with it: `--st-gap` takes `--c-rose`, so no two semantic rungs resolve to one value. Three rules carry it. **One tint, one meaning**, asserted across every grid at once, with exactly one collapse named rather than counted — `failed` and `infra-mismatch` share the consequence tint and are told apart by their words. **One word map** for the whole page, superseding the two vocabularies the 2026-08-24 ruling kept: a ledger row says `passed` and `missing` where a cell does, and **"no owner"** is the single name for "no test exists" on the matrix and the app grids alike (it states the fact where "gap" only named it). **A painted legend**, above every grid that uses the register rather than in prose below one, whose chips wear the cells' own classes — so the legend IS the treatment. The word-first rule is unchanged and is what this pass leans on: `partial passed` gains a word of its own alongside its tint, and every contrast pairing is recomputed from the ramp table by `report-theme.test.mjs` rather than recorded in prose. The **non-goal**: colour as a cell's only reading, on any grid. See [#864](https://github.com/srikanth235/centraid/issues/864).

The headless block logic lives in `@centraid/design/blocks`. React DOM composition is still split between shell and inline blueprint markup; the consolidation remains a follow-up tracked by [#765](https://github.com/srikanth235/centraid/issues/765). The DOM custom elements that used to be a third rendering technology are gone ([#799](https://github.com/srikanth235/centraid/issues/799)): `Avatar`, `Meter` and `Skeleton` are React blocks in `packages/blueprints/apps/_shared`, and the status line is plain DOM in `packages/design/src/elements/feedback.ts`.

## Night Watch v2 (#915)

**The nightly report answers three questions, in order.** Ruled 2026-09-02: `/test-report/nightly/` is one page that asks _can we ship the candidate_, _what changed since the last one_, and _who owes what by when_, and treats every later section as evidence for one of the three. This **supersedes** the evidence-archive layout of [#862](https://github.com/srikanth235/centraid/issues/862): that ruling ordered the page by the design's register — masthead, verdict bar, sticky index, then the grids in design order — which is the right order for a page somebody reads, and the wrong one for a page somebody acts on at 07:00. What #862 established and this keeps: one lowering, one face, the `light`/`dark` contract, the `--nw-*` palette emitted by [`scripts/site-tokens.mjs`](../scripts/site-tokens.mjs) into this sheet and nowhere else, the data-URI faces so an archived run keeps rendering, and the **honesty rule** — where the design shows a figure the repo cannot prove, the page renders what is real and names the gap. What changes: the page is a **pure function of `artifacts/evidence/`** plus [`tests/claims.json`](../tests/claims.json), so no section is assembled from a lane's private artifact shape; the verdict is `HOLD | DEGRADED | SHIPPABLE` over **unparked** lanes with one sentence of why and the single change that would flip it; and every delta is computed candidate-to-candidate rather than night-to-night, so an entry is a code change instead of weather. The **non-goal**: a second page for a second audience — there is one report, and §10 is where citation lives so §1 does not have to carry it. See [#915](https://github.com/srikanth235/centraid/issues/915).

**Four words, plus n/a with a reason.** Ruled 2026-09-02: a cell says `passed`, `failed`, `parked` or `no evidence`, and nothing else; `n/a` is the fifth reading and always carries the sentence that makes it one. This **supersedes** the twelve-state legend of [#864](https://github.com/srikanth235/centraid/issues/864). #864's law is not weakened — one hue, one meaning, one word, asserted across every grid at once, and still checked arithmetically off the emitted ramp by `report-theme.test.mjs` — it is applied to a shorter vocabulary: twelve states needed eight families and one named collapse, and six states need six families and none. What the states cost was the reading: `flaky`, `stale`, `partial passed`, `infra-mismatch`, `owner-silent`, `evidence-unmatched`, `lane-did-not-run` and `expected-grey` were eight different ways of saying "the run did not settle the claim", and a reader had to learn all eight to learn nothing. A run now either falsified the claim or did not; `parked` is a failure with an expiry and an issue against it, and `no evidence` is a lane that said nothing — which is a defect to fix, not a shade of grey to interpret. The plum family is renamed `flaky` → `park` in the emitter for the same reason: it means one thing. The **non-goal**: a state whose only difference from another is how sure the report is. See [#915](https://github.com/srikanth235/centraid/issues/915).

**Severity is declared, not computed.** Ruled 2026-09-02: each of the 45 claim rows in `tests/claims.json` carries its own `S1`–`S4`, and a lane inherits the worst severity among the claims that name it (an unclaimed gating lane is S2, an unclaimed advisory lane S4). The predecessor derived severity from `surfaces[].assessment` — from how COMPLETE the grid claimed to be — so an unfinished cell and a dangerous one read the same. Severity is about what is at stake: S1 sovereignty or data, S2 silent wrongness, S3 a promise degraded, S4 fidelity or blocked-external. See [#915](https://github.com/srikanth235/centraid/issues/915).

## Grants v2 — one authority plane (#883)

Ruled 2026-08-28 by [#883](https://github.com/srikanth235/centraid/issues/883). [Sharing v1](#sharing-v1--the-grant-plane-825) made a share a standing grant over one app-agnostic infrastructure. This ruling makes that infrastructure the vault's **one authority plane**: every standing answer a member gives about who may do what — to another person, a circle, a harness, or one of their own devices — is a row in one table, written by one command pack, and read from one dashboard. These rulings land ahead of #883's code waves, so no wave is built over a guess.

| Id | Current decision |
| --- | --- |
| **V-table** | One authority table holds the member's standing **answers**, and `granted` and `declined` are both rows — a refusal is an answer, not an absent grant. The key is (`principal_kind` × `principal_id` × `subject_type` × `subject_id` × `verb` × `duration`), where `principal_kind` is the closed union `person \| circle \| harness \| device` (`app` is reserved and unwritten — see V-split). Duration is `standing` or `until-date`; a one-time act leaves a receipt and never a row. Rows are immutable except `revoked_at`, so changing a verb is a revoke plus a new row rather than an UPDATE — an answer editable in place cannot be audited. |
| **V-writer** | A `share.*` vault command pack is the **only** writer of that table: journalled, receipted, and risk-annotated like every other vault write. The HTTP route becomes a thin command invoker, and the direct-store path in [`grant-routes.ts`](../packages/server/src/routes/grant-routes.ts) is **deleted** in the wave that lands the pack, never gated beside it. |
| **V-replica** | Grants are ordinary replica rows on every seat, and a grant write rides the shared pending-write overlay like any other write. The overlay declaration is **frame-level** — one shared projection owned by `_shared` — because the grant plane is app-agnostic infrastructure; eight per-app copies of one projection are eight places for it to drift. The bespoke transports (`grant-wire.ts`, `grants-transport.ts`) were deleted with the cutover; one shared wire law lives in `apps/_shared/grant-transport.ts` with a thin credential adapter per seat. |
| **V-delivery** | Delivery is per-strategy machinery keyed by `grant_id`: a background reconciliation loop over live sets, **never on the request path**. It is diff-based — an unchanged projected row writes nothing and wakes no device — doorbell-filtered, statement-cached, and computes a subject's closure size once per subject rather than once per audience. Every part of it is rebuildable except the durable delivery memory (`delivered_at`, [#846](https://github.com/srikanth235/centraid/issues/846)), which is what keeps revocation of a delivered-then-degraded grant honest. `max_size_bytes` belongs to delivery-strategy config, not to the authority row. |
| **V-phrases** | Three member-facing phrases carry a grant's life, plus the gateway's reason printed verbatim: **on its way** (with why), **shared**, and **withdrawn** (asked, then confirmed). `removed` never settles without the audience's acknowledgment — the copy may not claim a peer dropped what it holds until the peer says it did. |
| **V-locus** | Enforcement locus is **derived** from `principal_kind`, never stored: local for a harness, the boundary for a device, remote for a person or circle. Revoke copy states the promise its locus can actually keep, rather than one sentence stretched over three mechanisms. |
| **V-mask** | A per-party `declined` row is a **refusal mask**: it masks that party's roster membership during fulfillment, so refusing one person inside a granted circle does not cost the member the circle. |
| **V-split** | **Identity and authority split.** `core_party` and `access_device` remain identity. The authority they carry migrates into the one table — `access_device.trust`, `enrich_consent`'s provider-egress answers, and `share_circle_grant`'s authority role — one store per pass, with the old store and all of its readers swapped in the same wave. `consent_access_grant` + `consent_grant_scope` **stay** as app-strategy machinery beneath manifests, which is why `app` stays a reserved `principal_kind`. `devices.grant_profile_json` stays gateway-side attenuation of an enrollment, not a standing member answer. Conversation-lifecycle consent (`conversation_provider_consent`) stays runtime-owned and is shown as live activity only. **Superseded in part by [#928](https://github.com/srikanth235/centraid/issues/928)**: first-party apps are not principals; the app half moves out — see [One authority plane](#one-authority-plane-928). |
| **V-registry** | **One registry file** holds the closed unions of valid (`principal_kind` × `subject_type` × `verb`) triples, each naming its fulfillment strategy and its citation. A verb with no strategy cannot be offered — [#750](https://github.com/srikanth235/centraid/issues/750)'s rule, now plane-wide rather than subject-type-only. Structural exclusions stay type-level absences: Locker × sharing is a missing union member, not a registry row that says no. |
| **V-dashboard** | **One dashboard: Settings → Access**, on both seats, replica-backed, one row per standing answer — `[principal] may [verb] [subject] — since — because — last used` — with revoke copy per locus. The name is "Access". People's person screen stays the audience-first lens over the same rows and keeps Share and Revoke; the enrolled-devices Settings screen becomes a lens over the device-kind rows of the same table. |
| **V-policy** | The line between the two things a settings screen confuses: a **grant** extends authority to another principal; a **policy** configures the member's own machinery. A policy never enters the table and never appears on the dashboard. Named exclusions, so the next reader does not re-argue them: policies, structural first-party trust, ephemeral gestures, inbound shares, and conversation-lifecycle consent. |
| **V-receipts** | **One receipt stream** records every exercise of a grant, every roster change, and every delivery-level removal, each referencing `grant_id`. That stream is what makes the dashboard's "last used" a fact rather than a guess. Purging a **subject** or a **principal** revokes as a dated, receipted decision and is sweep-verified; the verification lands with wave 2's tests. |
| **V-notice** | A "shared with you" notice fires through `notifications.notice` **once per grant**, at its first `delivered`, naming the granter and the subject. Grant-level only: never per item, never as membership grows. An inbound-shares view stays out — the audience already reads the rows themselves, and a second list of them is a second place for the same fact to be wrong. |
| **V-census** | The Atlas census counts the grant plane again. The [#825](https://github.com/srikanth235/centraid/issues/825) exclusion's rationale was the first-paint statement budget, and [#873](https://github.com/srikanth235/centraid/issues/873) retired it by making registration cost a scan and never a statement (see [Performance and Rust byte plane](#performance-and-rust-byte-plane)). Atlas states **row counts**; the grant surfaces state **live grants**; those are different questions, and the census comment says so rather than leaving the next reader to reconcile two numbers. |

**v0 builds the ideal target directly.** A superseded store is deleted in the wave that replaces it, never carried beside its replacement — the point of a one-owner pre-1.0 product is that nothing has to be kept working twice. The only compatibility target is **member data**: each migration is one-shot, lossless, and demonstrated red before it lands.

**Cross-gateway delivery remains the [#825](https://github.com/srikanth235/centraid/issues/825) follow-up.** A grant whose audience vault lives on another gateway still parks at `syncing` with the vault named. Grants v2 changes the authority plane, not the transport's reach.

**D-order — the replica does not materialise order columns.** Ruled 2026-08-29 on the same doctrine as the vector engine below, and it supersedes [#880](https://github.com/srikanth235/centraid/issues/880)'s "a stored/indexed order column is the recorded next lever". The lever was measured and it is not one. A prototype of the strongest form of it — the ordered value **and** its `json_type` as STORED generated columns on `replica_row`, indexed — costs **+52% replica file size** (20.1 → 30.5 MiB) and **+20% bootstrap time** (4.7 → 5.7 s) at the 50,000-row year-3 volume, and buys **1.09x** on the filtered newest-first page it was proposed for (103 → 95 ms). It cannot make that page an index scan, which was the clause's stated goal: SQLite indexes `json_extract(...)` expressions perfectly well, and adding such an index to the unmodified schema changes the timing by nothing at all, because the plan never reaches any index while the order guards sit in the select list as window functions. `ORDER BY json_extract(payload_json, '$.<column>')` therefore **stays**, and the open question is the guards, not the storage — see [QUALITY.md](../QUALITY.md).

**The vector engine for photo similarity is decided by the wave-1 rig's numbers, not here.** The unbounded JS scan dies either way. SQL-side ranking through the already-loaded `sqlite-vec` extension is the floor; a `vec0` ANN index is adopted **only** if the rig shows the SQL scan at 90k embeddings missing the interactive budget. A structure that costs an index to maintain is earned by a measurement, not by a preference.

**Re-bootstrap is mitigated, then admitted.** Bulk inserts group into compactable commits, so a migration does not force a re-bootstrap it could have avoided; where one is still forced, the copy says plainly that the phone will refill itself and what that costs. There is no consent moment for it — a member cannot decline a migration of their own data that has already run, and asking would be a question with one answer.

## Ontology reconciliation (#883)

Ruled 2026-08-28 by [#883](https://github.com/srikanth235/centraid/issues/883). The v0 ontology carries seams where two tables answer one question, one table answers two, or a documented invariant holds on one branch only. These are the answers; each lands in a #883 code wave.

| Id | Current decision |
| --- | --- |
| **O-contact** | **An identifier is not a channel.** `core_party_identifier` keeps identity-key claims — `did`, `url`, `iban`, handle-as-identity, other — and reachability (phone, email, address, handle-as-reachability) lives in `social_contact_channel` alone; the `tel` and `email` identifier rows migrate to channels. Not one table with a kind axis: a key someone **is** and an address they can be **reached at** behave differently on dedupe, display and sharing, so one shape would have had to branch on the axis at every read. **One** shared dedupe module serves both, `social.contact_card` retires (`org_title` moves to `people_profile.role`), and both legacy dedupe implementations — People's `person.ts` query and `provider-writeback.ts` — are deleted with it. |
| **O-identity** | The identity fork closes: `tally.add_friend` gains an existing-party branch (resolved through `contact-reach.ts` by channel, never by name) and enrolls that `core_party` instead of always minting a second one. **One hue per party** is true: `partyHueKey`/`partyHueValue` in `packages/design/src/identity.ts` are the one resolver (stored choice wins), adopted by People web, People mobile, and both Tally sites; `identityColor` deliberately stays the vault/account wheel. |
| **O-payers** | [T-payers](#tallys-remaining-engineering-asks-873) is made true end to end: `tally.materialize_recurring_expense` writes payer rows, invariant triggers hold the shape at the schema, and the `tally-balance.ts` fallback is deleted after backfill. A fallback that quietly repairs an invariant is what let the invariant be false. |
| **O-attach** | `tally_expense_receipt` migrates onto `core_attachment` with `role='receipt'`, and the table drops — an app-local attachment table beside the content spine is a second answer to a question core already answers. `CONTENT_REFERENCES` and its serve-side twins are completed or derived, so the GC gap a hand-maintained reference list left open closes with it. |
| **O-recur** | `finance.recurring_series` joins the `schedule_recurrence_exception` target CHECK, and the override allow-list applies on **both** branches rather than one. `splits_json` is documented as the one deliberate JSON seam of a recurring template — the parameters of a division not yet materialized, not rows — rather than retired for rows it has no occurrences to hang on. **Superseded by [ONT-rows](#ontology-v0-close-916)**: the division is `tally_recurring_expense_split` rows, because party ids inside JSON are invisible to identity merge and unreachable by the purge cascade — and `finance.recurring_series` left with the finance pack (ONT-dormant), so the exception CHECK has two branches, not three. |
| **O-containers** | **Ordered containment is `core_collection`; label and audience membership is not.** A label is SKOS concept tagging (`core_tag`) and an audience is `social_circle`; neither is a collection. The DDL comment that says otherwise is corrected. The Address "Home" naming trap is flagged where it lives: Photos' private relative-phrase rung ([P-shared](#photos-place-and-cartography-816)) and a shared address row named Home are different things wearing one word. |
| **O-trash** | Tasks and Agenda gain the `deleted_at` / `purge_at` trash pair with the same ~30-day window the other apps carry. Their absence was an omission, not a deliberate divergence, and an app whose delete is final while its neighbour's is recoverable teaches two laws for one gesture. |
| **O-updated** | `touchUpdatedAt` applies to the thirteen domain tables missing it: `core_document`, `core_event`, `core_party`, `knowledge_note`, `locker_item`, `locker_item_field`, `locker_item_passkey`, `locker_auth_credential`, `schedule_project`, `schedule_section`, `schedule_recurrence_exception`, `social_contact_channel`, `tally_recurring_expense`. **Superseded by [ONT-lifecycle](#ontology-v0-close-916)**: a per-table list is the shape that drifts. Lifecycle is declared per entity and one `created_at`/`updated_at` shape holds everywhere, checked by test. |
| **O-bridge** | The dead Home→Tasks maintenance bridge (`home_maintenance_plan.current_task_id`, which nothing has ever set) is resolved by O-domains, **not** by inventing a producer for it. |
| **O-domains** | `home.*` and `business.*` have zero blueprint consumers. Both are dropped from the v0 ontology in wave 2 and their product case moves to a proposal issue: intent belongs in an issue, not in dormant DDL. **The ideal state carries no undocumented dormant domain.** |
| **O-label** | The table registry grows a per-entity `label` (and `blurb`) declaration, and the four hand-maintained name maps derive from it. A registry entity with no label declaration **fails validation**, so the next table cannot arrive nameless and be named again in four places. |

`schema/enrich.ts`'s header comment is corrected to name everything the file creates. The code fix lands in a later wave; the rule it records is the one this repo already applies to docs — a file header is a claim about the file, and a stale claim is a defect rather than a cosmetic lapse.

**O-sheet** — a band's overflow sheet is **docked and non-modal**: it extends the band it overflows, so a top-layer modal that covers that band is the wrong shape. Five of six shipped surfaces already behave this way ([#883](https://github.com/srikanth235/centraid/issues/883)). Tally's overflow control converted to the docked sheet in #883's surface wave as a deliberate behavior change; the focus trap it lost was an artifact of its `showModal()` implementation, not a requirement of the control.

**Consolidation defaults.** Three one-line answers the consolidation waves would otherwise each re-decide. **Select-all means the filtered set**, never the whole table, and a selection survives a filter change through `pruneSelection` rather than being silently widened to rows the member never saw. **`fmtDay` says "Yesterday"** wherever it says "Today", through one shared helper — the same fact told relatively on one screen and as a date on the next is two facts to a reader. **The page margin is 32px**, carried by the `--page-margin` design token; the invented 22px `--content-margin` dies with the screens that declared it.

## Mobile testing (#890)

Ruled 2026-08-30 by [#890](https://github.com/srikanth235/centraid/issues/890), which rebuilt the mobile test layer end to end. Mobile is the primary surface and its test layer was the one place the repo's quality axioms were not enforced: every CI flow drove `expo-dev-client` + Metro (so the device under test was not the product), one `testID` existed on a shared path, no mobile flow ran on any PR, and `tests/matrix.json` named journeys that nothing scheduled. Five principles bind the rebuilt layer, then the three decision points the plan could not start without.

| Id | Current decision |
| --- | --- |
| **E-artifact** | **CI tests the artifact users get.** Scheduled lanes install a **release-configuration** build with the embedded Hermes bundle — no Metro, no dev launcher, no bundle prewarm, no developer-menu explainer. The dev client remains the _local exploratory_ rig (the Maestro MCP loop) and is clearly separated from the CI path in [`tests/agent-e2e-mobile/README.md`](../tests/agent-e2e-mobile/README.md). Half the harness's caveats were infrastructure for testing the dev harness, and every perf probe was measuring a `__DEV__` Hermes build. The frame sampler is therefore compiled into a **perf-flavored release** behind `EXPO_PUBLIC_CENTRAID_FRAME_PROBE`, not behind `__DEV__`, so `scroll-frames` and `cold-start` measure a user-representative build. |
| **E-unfakeable** | **A green run must be unfakeable.** Selector binding is machine-checked (`bun run lint:mobile-testids`: every id a flow references exists in `apps/mobile` source, and every declared id is applied), and a `tests/claims.json` owner that no lane schedules is a hard failure (`bun run lint:e2e-wiring`). Both linters carry self-tests and silent-no-op guards, because a linter that quietly stops enforcing is worse than none. |
| **E-conformance-manifest** | **Every first-party app is covered identically, and by a manifest rather than by hand.** `apps/mobile/app-conformance.json` is the one source of truth for the shell↔app contract — one row per registered app carrying its launcher route, the navigator/screen its tile opens, its `centraid://` path, its tile handle, its arrival landmark, and whether it ships a demo fixture. `bun run lint:app-conformance` holds five tables against it (the registry, the launcher catalog, Home's navigate switch, the deep-link table, the testID vocabulary) in both directions, and `apps/mobile/src/screens/Home.test.tsx` generates its sweep from it, so **a new app is covered the day it registers or the PR that registers it fails**. Hand-authoring a journey per app is O(apps) to write and O(apps) to run, and app #9 arrives untested until somebody remembers it. Photos still carries extra hand-written flows — proportional to its **native/OS** surface, which is the only thing that makes it special, not its standing as a product. JSON, and under `apps/mobile/`, because the RNTL tier, a plain-node linter and the Maestro `.mjs` runners must all read it without a build step ([#905](https://github.com/srikanth235/centraid/issues/905)). |
| **E-device-only** | **The device layer owns only device-only claims, and the roster shrinks rather than fans out.** A simulator minute on macOS costs roughly 600× a vitest second on Linux. State variety — `dayone`/`pending`/`offline`/`stale`/`conflict`/`parked` — moves to the Node integration tier (`tests/integration-mobile/`), which runs a real replica session against a real gateway process; the device proves the native wiring **once** (one airplane-mode journey, not one per state). A write round-trip belongs inside the app's existing paired journey, not as a new flow file. |
| **E-latency** | **Signal latency matches surface priority.** Device signal lands **before merge** (an Android PR gate over the critical five), a canary runs the full roster **per merge** on `main`, and the nightly owns depth. The PR gate's envelope is ≤ 12 minutes wall warm; the nightly's is ≤ 45 minutes wall and ≈150 macOS-minutes. |
| **E-buildonce** | **Build once, run many.** Build jobs are separate from test jobs; artifacts are keyed by `apps/mobile/scripts/native-fingerprint.mjs` plus a toolchain hash **with `restore-keys`**, and are prebuilt on `main` so a PR restores rather than compiles. A JS-only change repackages the bundle into the cached native shell instead of rebuilding native. The former all-or-nothing key meant a cold ~32-minute iOS build on every fingerprint miss, including misses caused by a toolchain bump nobody made. |

### D1 — Android gates PRs

**The PR device gate is Android.** Economics and driver stability both say so and nothing in v0's user-base data says otherwise: Android runs on Linux with `/dev/kvm` (so a gate costs Linux minutes, not the ~10× macOS multiplier), and Maestro's UIAutomator2 driver hardens against Android API churn faster than its XCUITest driver against iOS — the iOS driver's disconnects past ~10 commands are recorded in [`tests/agent-e2e-mobile/README.md`](../tests/agent-e2e-mobile/README.md#known-caveats) and are what keeps iOS flows short. **iOS is the depth platform**, not a duplicate: the nightly runs iOS for the claims only iOS can carry, never the whole roster twice. Flip the gate only if user-base data is decisively iOS-first — a preference is not a reason, and the flip costs the PR lane its Linux economics.

### D2 — paired state is restorable in principle; the snapshot **unit** is the open question

The spike's cryptographic half is **settled from source, and the answer is no, nothing is UDID-bound**:

- The device's long-lived identity is 32 CSPRNG bytes the app generates itself (`SecRandomCopyBytes` / `SecureRandom` in the `centraid-tunnel` module) and hands across the bridge as base64 — extractable by construction, with no Secure Enclave, no StrongBox, and no attestation.
- It is written through [`secure-storage.ts`](../apps/mobile/src/lib/secure-storage.ts) with **no `SecureStoreOptions` at all** — no `THIS_DEVICE_ONLY`, no `requireAuthentication`. The hardware-gated options exist in this codebase (`app-lock.ts`, `locker-device-auth.ts`) and are deliberately not on the pairing path.
- The gateway's `devices` row binds **only** the proved iroh `EndpointId`. No UDID, install id, or vendor id is recorded or checked, so whoever holds those 32 bytes _is_ the paired device.
- The replica is unencrypted SQLite inside the app container, under a filename hashed from `(gatewayId, vaultId)` alone.

**What is not settled is the unit of restore, and the app container is the wrong one.** [`tests/onboarding-scenarios.md`](../tests/onboarding-scenarios.md) G2 records that `phoneLink.secretKey` and `phoneLink.ticket` survive app deletion on iOS and are cleared only by `simctl erase` — they live in the _simulator device's_ keychain, outside the container — and [`replica_backup_rules.xml`](../apps/mobile/android/app/src/main/res/xml/replica_backup_rules.xml) records the Android mirror: shared_prefs SecureStore blobs are Keystore-wrapped and restore as undecryptable bytes on a device whose Keystore did not wrap them. So a whole-**device** snapshot is the only shape that could work, and it must be restored in lockstep with the gateway's data dir at its **identical absolute path** (`key-store.ts` derives the external credential filename from `path.resolve(keysDir)`), or the checkpoint monotonicity guard refuses the rewound client.

**The ruling, therefore:** pair-once-per-suite remains the shape (`MAESTRO_REUSE_PAIRED_STATE`, which is a same-process relaunch and never was a snapshot), and the whole-device experiment ships as a **runnable committed script** — [`tests/agent-e2e-mobile/spike-paired-state-restore.sh`](../tests/agent-e2e-mobile/spike-paired-state-restore.sh) — rather than a paragraph describing one. A spike nobody can run is a wish. Its first step costs seconds and already answers whether the cheap container-only variant is worth attempting; from the source above, expect not.

### D3 — the no-quarantine doctrine permits a promotion pipeline, and only for new signal

**It forbids weakening _existing_ signal; it does not forbid staging _new_ signal.** A new flow enters the roster as `promoting`, runs non-blocking for five scheduled nights, and is promoted to `scheduled` on stability. The distinction is enforced, not stated: `bun run lint:e2e-wiring`'s `promoting` rule refuses a `promoting` flow on any lane declared `blocking`, refuses one no lane runs at all (parked, not staging), and refuses one with no `since` date and `nights` count — without those nothing can say when it is due.

Three things this ruling does **not** license, because each is the quarantine it is distinguished from: a `scheduled` flow may never be demoted to `promoting` to get a lane green; a `promoting` flow that never converges is deleted or fixed, never left staging indefinitely; and a flow's own retry budget is unchanged by its status — **retry is classification, not forgiveness**. One clean-state retry is allowed for an _infrastructure-classified_ failure only (driver disconnect, zero assertions run, a precondition that never came up), both attempts' evidence is kept, and a product assertion is never retried. An `assertVisible` timeout is a product failure by construction: it is the exact shape a real regression takes, and calling it infrastructure is how a suite learns to forgive itself.

### Non-goals recorded, not deferred silently

No device matrix beyond the pinned pair ([`apps/mobile/scripts/device-matrix.json`](../apps/mobile/scripts/device-matrix.json), whose Android x86_64-vs-arm64 and API-34-vs-35 divergences are recorded with reasons rather than assumed away); no per-PR iOS; no framework switch — revisit Detox only if iOS driver failures persist _after_ the release-artifact and testID waves have landed; no coverage floors on mobile screens; no backfilling the deliberate `n/a` cells; and no per-PR device farm. Real-device evidence — the battery/memory/cold-start `blocked-external` rows and the `CENTRAID_PERF_EVIDENCE` rig — is a release-cadence spend decision, deferred here rather than left to look like an oversight, and the rigs stay honest per [#790](https://github.com/srikanth235/centraid/issues/790).

## The PR gate loop (#892)

Ruled 2026-08-31 by [#892](https://github.com/srikanth235/centraid/issues/892), which audited the gate set against product risk and found it inverted: the meta layer was world-class and cheap (~30 real gates under 3 minutes), while the #1 risk for a local-first sovereign vault — data safety over time — had no owner at all, and ~25–30 runner minutes per run were recoverable waste.

| Id | Current decision |
| --- | --- |
| **G-deadline** | **A wall-clock budget is a bound, not a verdict.** `mobile-device-gate` reported 17m38s against a twelve-minute budget because the budget was scored only after every member finished. `tests/agent-e2e-mobile/lib/run-suite.mjs` now publishes an absolute deadline: a member is not started past it, a classified retry is refused when it cannot fit in what remains, and every Maestro chunk is clamped to the time left. | **G-advisory-expiry** | **A step that announces it will never fail carries an expiry.** `tests/inventory.json#advisory` gives the iroh binding-drift warning and the Expo compatibility map an owner, an issue and a date; a past date fails `bun run test:advisory-expiry`. | **G-lane-health** | _Extended 2026-09-02 by **G-lane-rules** ([#915](https://github.com/srikanth235/centraid/issues/915)), which adds the demote/promote/park/budget table and the `HOLD` verdict._ **First-attempt pass rate is measured, and chronic red is bounded.** `scripts/ci/lane-health.mjs` (nightly) reports per-lane first-attempt pass over the last 40 `main` runs and fails when a lane has been red on main for more than three days without an unexpired entry in `tests/quarantine.json#lanes` — the declared/attributed/expiring discipline `tests/quarantine.json` applies to tests, extended to lanes. The `skipped`-counts-as-a-pass hazard reached one level down, through the very control meant to defeat it. `bun run lint:path-filters` now fails on a read without the fallback, whatever construct does the reading. |
| **G-supply-chain** | **No `curl \| bash` in a required lane.** Maestro installs through `scripts/ci/install-maestro.sh`, which fetches the pinned release artifact and refuses a checksum mismatch — the shape gitleaks and osv-scanner already use. `MAESTRO_VERSION` pinned what the remote script would install and pinned nothing about the script. |

### G-device-only-gate — the PR gate's members carry only device-only claims

Ruled 2026-09-02 by [#905](https://github.com/srikanth235/centraid/issues/905). On the PR gate, `native-v0-resilience` proves two things and claims no more: Settings loads through the all-apps sheet, and on Android an offline write survives process death, reconnects and settles.

**The covers-open claim is not dropped; it is held where it is cheapest and still honest.** `apps/mobile/src/screens/Home.test.tsx` generates its sweep from `apps/mobile/app-conformance.json` (**E-conformance-manifest**), so every registered app's tile→cover pair is asserted at the rendered tier, and each cover keeps its own device journey on the candidate and nightly lanes (the `home-apps` and `photos` suites). No member left the gate and no assertion was loosened. This is **E-device-only** applied to the gate itself, and it is remedy 3 of [`pr-gate-budget.md`](../tests/agent-e2e-mobile/flows/pr-gate-budget.md) — "move a claim down a tier", which that document calls the correct first move rather than the last resort.

**Twelve minutes stands, and is now measurable.** The number was derived, never observed: it priced the four reusing journeys at ~6 minutes, and run 33573882728 measured them at ~9 — the ten-surface tour alone was 187s of it. The suite is therefore fitted to the budget rather than the budget to the suite: the tour moves down a tier, and six Maestro spawns (four reuse-mode gateway configures, two restarts) at ~9–15s each fold into their neighbours' chunks. The four device lanes now upload `ledger/durations.json` as `mobile-run-ledger-<lane>`, so the re-derivation the budget owes after three real runs reads data rather than arithmetic.

**The five ran as two parallel legs, and twelve minutes was per leg.** Ruled 2026-09-02 and **superseded the same day** by **G-merge-diet** ([#915](https://github.com/srikanth235/centraid/issues/915)), which makes the smaller cut: `native-v0-resilience` moves to rung 3 and the gate keeps three members at 8 minutes warm on one emulator. The finding below is why the split existed and is unchanged. Even fitted to the budget the five price ~795s in sequence against a 720s deadline — run 33582899886 measured `pairing-canary` 187s, `notes-library` 106s, `native-v0-resilience` 267s, `cold-start` 145s, and `photos-permissions` starved by the clamp at 24s where it needs ~90s — so the last member is starved on every run. `mobile-device-gate` is one job with a two-leg matrix — paired (`pairing-canary`, `notes-library`, `photos-permissions`) and resilience (`pairing-canary`, `native-v0-resilience`, `cold-start`) — on two emulators, each pairing itself, each under the unchanged twelve-minute deadline. The gate's wall time is its slower leg. The accepted cost is one extra pairing per run, ~190s of runner time paid twice instead of once. **This is not the budget raise `pr-gate-budget.md` forbids**: the bound a human waits on is unchanged, no member left the gate and no assertion was loosened — runner minutes are the currency the shape spends, and they are the one thing nobody is waiting on.

### The merge queue: evaluated, and NOT adopted yet

_Re-examined and re-dated 2026-09-02 — see [The merge queue: still NOT adopted](#the-merge-queue-still-not-adopted-re-dated-2026-09-02) below, which supplies the numbers this section was waiting for and a substitute (the candidate pointer) for what a queue would have bought._

PRs validate against the merge state at trigger time, so two individually-green PRs can merge into a red `main` — and a red `main` was the state that prompted this audit. A GitHub merge queue fixes that **by construction**, and it would also give the per-merge canary tier a native home (mutation full-seed, `gateway-package`, possibly the device gate, run once at queue time instead of on every push of every PR).

**It is not adopted in this change, and the reason is ordering rather than doubt.** A merge queue re-runs the required set against the queued merge commit, so its cost and its flake exposure are both a direct function of how long that set takes and how often it fails on the first attempt. Both of those numbers are what #892 just changed and neither has been measured on the new shape: `verify` was split, coverage was sharded four ways, the mutation full-seed moved off the PR loop, and `lane-health` (which reports first-attempt pass rate) has not yet run once. Enabling a queue before those numbers exist would be choosing a merge strategy from the arithmetic of a lane set that no longer exists.

**The decision this defers is bounded, not open.** Revisit once `lane-health` has three weeks of data. Adopt if the required set's p95 is under ~20 minutes and no required lane is below 95% first-attempt pass; if either is false, fix that first — a merge queue in front of a slow or flaky required set converts every red into a queue stall for everyone.

Meanwhile the gap is narrowed rather than left open: `mutation-canary` and `mobile-canary` both attribute a post-merge regression to one commit, and `lane-health`'s chronic-red rule bounds how long a red `main` can be treated as normal.

### `governance.yml` and branch protection

`governance.yml` is exempt from the only-`ci.yml`-listens-on-`pull_request` rule because it is kit-managed (`# governance-kit:managed`), which `scripts/lint-workflow-pins.mjs` skips by design — its policy lives upstream. The consequence is easy to miss and worth stating: **it is not part of the required `check` aggregate**, so unless the repository's ruleset lists `governance` as a required status check of its own, a red governance run blocks nothing.

That entry is repository configuration, not repository content, so no gate in this tree can assert it — the honest thing is to name it here rather than to pretend a linter covers it. The required set should be exactly two entries: `check` (which aggregates every `ci.yml` lane) and `governance`.

## Portable export custody (#630)

Ruled 2026-09-02. The portable vault bundle shipped `custody/seal-key.bin` — the vault's data-encryption key, in the clear, in the same unencrypted zip as the sealed ciphertext it opens — so every locker secret, connection token and passkey was one `unzip` away from anyone holding the file. The current decision, in four parts:

| Id | Current decision |
| --- | --- |
| **PX-ciphertext** | **A bundle never carries a key in the clear.** Sealed cells travel as ciphertext; the DEK leaves only inside `custody/recovery-kit.json`, password-wrapped, and only when the owner supplies a passphrase. Without one the manifest says `sealed: "ciphertext-only"` and the bundle opens no secrets anywhere. The header comment's claim that "no plaintext reaches the surface" is now literally true. |
| **PX-onewrap** | The wrap is the backup recovery kit's own scrypt(N=2¹⁷)→AES-256-GCM machinery, extracted to `@centraid/backup`'s `password-wrap.ts` and shared. **One** implementation, so there is one KDF cost, one AAD discipline, and one place the "no unwrapped acceptance path" rule of [#568](https://github.com/srikanth235/centraid/issues/568) lives. |
| **PX-reseal** | Import **re-seals** every sealed cell under the TARGET vault's own DEK; it never installs the source's. The target's key file, its custody and its rotation history stay its own, and the same sweep serves `key rotate` and portable import. |
| **PX-refuse** | An artifact carrying sealed values with no key is **refused before the first row is written** — as is a kit with no passphrase, a sealed value in a column the re-seal sweep cannot reach, and any bundle still carrying a plaintext `custody/seal-key.bin`. The source vault's `core_vault.settings_json.seal_key` stamp is never copied: the stamp a restored vault ends up with names the key it actually sealed with, which is why it now reopens instead of failing `SealKeyError('missing')` after reporting success. |

Intent belongs in an issue, never in dormant DDL. |
| **ONT-version** | **One version scheme.** The ontology version is a property of the FILE (`PRAGMA user_version`) and of the command CONTRACT (`agent_command.ontology_version`); `ONTOLOGY_VERSION` is `"1.0"`. No row carries a stamp — `core_party.ontology_version` is dropped. |
| **ONT-self** | **The vault's own party is the `self` party** (`core_vault.self_party_id`): the person as data. It confers nothing; authority stays gateway-side (owner + device + `share.authority`). The seam #726 left unnamed now has a name on the page and in the glossary. |
| **ONT-lifecycle** | **Lifecycle is declared per entity** — `append-only`, `mutable`, `trash` or `machinery` — and a test holds the schema to it. `created_at` / `updated_at` have ONE shape everywhere (`NOT NULL DEFAULT` + touch trigger), packs and machinery bands alike. The ledger band is the single exemption, with its reason (an engine epoch-ms clock) recorded in `lifecycle.test.ts`. |
| **ONT-star** | **Favorite is the flags-scheme tag, anchored on the entity the app shows.** `media_asset.favorite` is deleted; Photos' star anchors on `media.asset`, Docs' on `core.document`. **Supersedes** the single-writer mirror ruled in [#419](https://github.com/srikanth235/centraid/issues/419) / [#441](https://github.com/srikanth235/centraid/issues/441): a mirror is two truths, and a postcondition asserting they agree is a test for a problem that need not exist. |
| **ONT-purge** | **A party is trashed and purged like every other kind.** The purge is one DELETE the supertype cascades; the engine refuses it while money or authority still names the person (RESTRICT), and attribution yields (`SET NULL`). Standing authorities about a purged subject are revoked by trigger in the same statement, retained as history with `revoked_reason`. The foreign-key walk that deleted whatever it could reach — other people's expense splits included — is gone. |
| **ONT-revisions** | **One revision mechanism with per-entity retention.** `core_entity_revision` is the only history table; `locker_item_history` is dropped and the locker pack declares `retain: "forever"`. A revision records the invocation that caused it (`invocation_id`, `ON DELETE SET NULL` — the archive pass retires invocations and a revision outlives the record of it). |
| **ONT-rows** | **Structure that identity or the purge cascade must see is ROWS, not JSON.** A recurring template's division is `tally_recurring_expense_split` (**supersedes** O-recur's "`splits_json` is the one deliberate JSON seam"); an overriding occurrence's attendees are `schedule_recurrence_exception_attendee`. Party ids inside a blob are invisible to merge and unreachable by the cascade. |
| **ONT-access** | **The `consent` plane is renamed `access`.** The plane answers "may this actor reach this data"; consent is one of the answers it records. Every scope, tombstone and policy names ONE dotted entity (`media.asset`) instead of four encodings of "which entity". The rename is physical and logical: `consent_*` tables to `access_*`, `consent.*` scope strings to `access.*`, `gateway/consent.ts` to `gateway/access.ts`, `evaluateConsent` to `evaluateAccess`, `GatewayError("consent", …)` to `GatewayError("access", …)` and the wire code it derives, `VAULT_CONSENT` to `VAULT_ACCESS`. Deliberately **kept**: `providerEgressConsent*`, `enrich.record_consent`, the `consent.required` wire code and the client's own `ConsentDecision` — those name the member's act, not the plane that decides. |
| **ONT-currency** | **Money states its currency**: on `tally_group` (the ledger everyone in it reads), on `tally_expense`, and on `tally_settlement`, with triggers holding a grouped row to its group. Splits, payers and line items inherit by construction — they are shares of a stated amount. |
| **ONT-recur** | **Recurrence is honest about time.** An unsupported RRULE part is **refused** at the write and import boundary, never silently dropped (`packages/core/src/time/rrule-support.ts`). Exceptions key on the series' wall-clock start plus its `recurrence_semantics`, so moving a series' zone no longer orphans them. |
| **ONT-sql** | **One door means one door.** Raw SQL on vault tables from outside `packages/vault` fails `bun run lint:vault-sql`, whose allow-list carries a reason per entry and fails on stale entries. The three life-data readers that had grown outside the gate (daily brief, due reminders, semantic search) are behind it — the first two through `gateway.read`, semantic search through the vault's `rankLivePhotoEmbeddings` — and none of them was allow-listed. |
| **ONT-ladder** | **One baseline rung.** `VAULT_MIGRATIONS` holds a single entry; a fresh vault stamps `user_version = 1`. v0 has no files in the field, so a rung reconstructing a shape the baseline can state is compatibility code for a problem nobody has. The golden corpus is re-frozen as `tests/golden/issue-916`. The first release that must reach an existing file adds rung two. |

## The Quality Ladder (#915)

Ruled 2026-09-02 by [#915](https://github.com/srikanth235/centraid/issues/915), which audited the QA architecture against 30 days of run history and found the doctrine sound and the machinery outgrown by it: **0 of 30** scheduled nightlies green since 2026-08-03, a PR gate observed at ~26 minutes against a documented 12.3, and thirteen auto-filed nightly tracking issues closed as noise. Two variables govern every ruling below — confidence a regression cannot reach a user, and minutes between "done" and "merged".

Six rungs, one question each: 0 commit, 1 push, 2 merge (`ci.yml`), 3 candidate (`candidate.yml`), 4 nightly (`e2e.yml`), 5 weekly. Lane identity is the GitHub **job id**.

### The ladder's rungs 2-5

| Id | Current decision |
| --- | --- |
| **G-candidate** | **Post-merge produces a candidate; nightly, weekly and release consume it.** `candidate.yml` runs on every push to `main` and, on green, moves the git ref `refs/candidates/latest`, writes `artifacts/candidate.json` and publishes `test-report/candidate.json` + a 200-deep `test-report/candidates.json` history to gh-pages. On red the pointer **stays**, which is the whole value: the deep rungs keep testing the last build somebody would have handed to a device instead of following `main` into whatever broke. Every consumer opens with a `resolve-candidate` job whose fallback chain — dispatch input → the pointer → the last green `ci.yml` run on main → the run's own SHA — is printed to the step summary, so the page always says which link answered rather than quietly restoring the old behaviour. |
| **G-merge-diet** | **A check belongs on a rung only if it sharpens that rung's answer.** `client-e2e` (web + desktop Playwright), `gateway-package`, `desktop-e2e-macos` and the Android **resilience** leg all left rung 2. None was deleted or loosened: the first three run on every promotion as `web-e2e-linux`, `desktop-e2e-linux`, `lane-gateway-package` and `desktop-e2e-macos`, where they now **gate promotion** — strictly more than the advisory status `desktop-e2e-macos` had on the PR loop. What stays on the merge gate for the phone is the smallest set that can falsify "this diff broke it": pairing canary, one home-app journey, cold start, 8 minutes warm. |
| **G-cold-cache-is-a-lane-failure** | **A pipeline fact is reported as a pipeline fact, in seconds.** `mobile-device-gate` used to absorb a cold apk restore by compiling a release build inside the job — 16m21s of a 27m job on 0655a1b7 and again on 60732d30 — and every PR behind it paid the same. The apk key folds the native **and** JS fingerprints, and `candidate.yml`'s `mobile-canary-android` banks that exact key on every push to `main`, so a miss means that lane has not run for this fingerprint or did not bank. The gate now fails immediately with `::error title=mobile-device-gate cold cache::` and an evidence case id `cold-cache`, and its outer timeout falls 60 → 20 minutes. **Superseded by G-reconstruct-on-miss below**: the apk key names the CONTENT of `apps/mobile/src`, the four workspace packages and `bun.lock`, and the only lane that banks it runs post-merge — so a PR touching mobile JS produces a key no pre-merge run could have banked, and fail-on-miss was unpassable by construction for exactly the PRs it existed to check. |
| **G-reconstruct-on-miss** | **A cold apk is rebuilt, and the rebuild reuses everything a compile already produced.** `mobile-device-gate` no longer fails on an apk miss; it compiles the shell and banks it under the key the restore missed on, so the next push on the branch is warm. What made that affordable is a caching restructure across `ci.yml`, `candidate.yml` and `e2e.yml`, moved together under one `android-gradle-v2-*` key namespace because a lane that saves a shape another lane does not restore is worse than no cache. Three things were wrong at once and each alone still left a full native compile: `org.gradle.caching` was unset, so `~/.gradle/caches` held dependencies and transforms but no task **outputs**; the autolinked React Native / Expo libraries build under `node_modules/<lib>/android/build` with CMake intermediates in `node_modules/<lib>/android/.cxx` (and the app's own in `app/.cxx`), and none of it was cached — which is why a warm cache still recompiled `react-native-quick-crypto`'s C sources for twenty-five minutes on run 33405430819; and `apps/mobile/android/.gradle` was not cached either, so gradle's stale-output cleanup **deleted** the two build directories that were, because its execution history had no record vouching for them. The `restore-keys` fallback stays on this cache and stays refused on the apk cache: a partial match restores directories whose task inputs gradle re-checks, not a binary. The one task whose declared inputs do not cover everything that changes it is the JS bundle — React Native scopes `BundleHermesCTask.sources` to `apps/mobile` while the bundle also contains the workspace packages — so `android-emulator-install.sh` forces it with `--rerun` rather than trusting it, and no restored directory can smuggle another commit's Hermes bundle into a freshly packaged apk. The gradle/native save is gated on `gradle_ran`, not `built`: an apk-cache hit used to re-bank a barren directory, and because `restore-keys` resolve to the most recently created match, that entry then shadowed the warm one — which is why the cache never self-corrected. |
| **G-burn-in** | **A new test runs three times, alone, before it is trusted.** `author ≠ auditor` was enforced for the product and not at all for the tests: a newly written test ran exactly once before merging, inside a full suite sharing a worker pool with a thousand siblings. `new-test-burn-in` (in `check.needs`) runs every added or modified Vitest `*.test.*` / `*.spec.*` file three times in isolation from its own package. **Any disagreement across the three is red**, not just a failure — the file that passes twice and fails once is the expensive one and the one a single run cannot see. Playwright and Maestro specs are skipped with a printed reason rather than dropped. |
| **G-mutation-cap** | **Per-PR mutation keeps its audit and loses its tail.** The affected-seed set is a function of the diff, so one PR paid 90 seconds and the next nineteen minutes — a rung-2 lane answering a rung-3 question. `scripts/ci/mutation-cap.mjs` caps the run at 8 minutes (`MUTATION_PR_CAP_MS`), and over the cap it kills the run, writes a `deferred` evidence case, leaves **one** PR comment (rewritten in place through a hidden marker) and exits 0. Nothing is skipped: `candidate.yml`'s `mutation-full` runs every seed with floors on the merge commit. What moves is when the answer arrives, not whether. A deferral is never recorded as a pass of the seeds. |
| **G-suite-rung3** | **The serial suite is a promotion lane, not a merge lane.** The first time the rung-2 wall-clock gate actually ran it read **24.2 min against 15**, and `verify`'s `bun run test:suite` was ~19 of them — a serial, uninstrumented re-run of the same projects the four `coverage-shard` legs already run in ~7 min each. On the merge gate the shards are the pass/fail answer (a failing test fails its shard) as well as the floors, so the serial run left `verify` and became `candidate.yml`'s `suite` lane, on every push to `main`, gating `promote`. It took two things with it that only a single unsharded runner can produce honestly: the suite wall-clock ceiling — [#905](https://github.com/srikanth235/centraid/issues/905) measured the per-file span sum at 3,824 s sharded against 2,370 s serial for the same files, so scoring it on the shards would fail the runner, not the suite — and a second copy of the collection tripwire (the merge gate keeps its own on the merged report). What changes is _when_ a test flood bites: at promotion, minutes after the merge and attributed to one commit, rather than before it. What does not change is the number: `tests/budgets.json#suiteWallClock` is untouched and still tightens only. |
| **G-security-rung3** | **CodeQL and the Rust supply chain gate a promotion, not a week.** Both moved from `security.yml`'s Sunday cron into `candidate.yml`; `security.yml` is deleted because nothing remained in it. A weekly SAST run attributes a finding to a week's worth of commits and lets six days of promotions happen in front of it; on rung 3 the finding names one commit and blocks the pointer. |
| **G-parks** | **A park is a deadline, never a mute.** [`tests/quarantine.json`](../tests/quarantine.json)'s `lanes` entries carry `issue`, `expires` and `why`. A parked lane still runs and still writes evidence; the writer records `verdict: parked` instead of `failed`, the nightly verdict is computed over unparked lanes only, and the day the expiry passes the lane counts as red again. More than three parked lanes, or any park longer than 30 days, is a report-level `HOLD`. Seeded with `mobile-e2e-android` and `mobile-e2e-ios` (#870, expiring 2026-09-16) and `web-e2e-cross-browser` (#915, whose first green run on a candidate is its baseline rather than a regression). |
| **G-rolling-issues** | **One issue per lane, rewritten in place; never a comment, never a re-creation.** The nightly filed a single `[nightly] e2e lane red — tracking` issue and commented on it every morning; thirteen were closed as noise, and its `### Job results` block was a hand-maintained list of ten lanes that covered neither `fuzz-parsers` nor five others. `file-tracking-issue.mjs --update` matches by **exact title** (the fuzzy `in:title` search also matches `…-ios-smoke`, and editing the wrong lane's body destroys it) and rewrites the body, so `[nightly] lane red — <lane>` always states that lane's current condition and closing it means the lane is green. The red-lane list is `toJSON(needs)` through jq — a lane added to `needs:` is covered without a second list. Rung 3 files the same shape as `[candidate] lane red — <lane>`. |
| **G-lane-rules** | **Promotion and demotion are counted, not remembered.** `scripts/ci/lane-rules.mjs` applies the issue's table mechanically: a rung-2 lane below 99 % first-attempt pass files `[lanes] demote <lane>`; two escapes in the window file `[lanes] promote <lane>`; three consecutive reds on candidates demand a park; an expired park and a p95 over the rung budget (15 / 45 / 90 / 300 minutes) are red, the latter naming the minutes to cut. The escape count is a **stated over-approximation** — nothing in the Actions API carries case ids across workflows, so it counts a deep-rung red on a SHA whose rung-2 gate was green. It over-counts and never under-counts, which is the right direction for a signal whose action is "consider promoting"; do not tighten the rule without replacing the approximation with case ids from the evidence files. |
| **G-pr-gate-budget** | **The rung-2 budget is measured on the run that spends it.** `tests/budgets.json#suiteWallClock` gains a `pr-gate` lane at 900,000 ms, scored by `scripts/ci/pr-gate-wall-clock.mjs` inside `check` (which therefore holds `actions: read`) as `max(completed_at) − min(started_at)` across `check`'s `needs:`. The **span**, not the sum: summing the lanes would punish the parallelism that makes the gate fast. Both lanes of that file are ratcheted by `ratchet-floors.mjs`, so widening either needs a changed `approvedDeviation`. |
| **G-turbo-inputs** | **A build hashes only what a build reads.** With no `inputs:`, turbo hashed every non-ignored file in a package, so one line in `packages/core/src/blob/cbsf-properties.test.ts` moved 11 of 16 build hashes — including `@centraid/tunnel#build`, a release cargo compile measured at 278 s of a 349 s cold `build:ci`, in each of the five lanes that build. `turbo.json` now declares `$TURBO_DEFAULT$` minus test/spec modules and markdown; re-measured, a test edit and a README edit move **0** hashes and a real `packages/core/src` edit still moves the same 11. `coverage-shard` and `coverage` also gained the `cargo-cache: verify` preset `verify` already had, so an identical miss degrades to an incremental compile rather than a cold one. `bun run build:ci:floored` enforces `--min-hit-rate 0.15`: the deepest legitimate single-package change still leaves ≈ 23 % cached, so only a whole-graph miss falls below. |
| **G-turbo-floor-waiver** | **The floor's one exception is computed, not offered.** A change to a global-hash input (`bun.lock`, the **root** `package.json`, `turbo.json`, `.npmrc`, `bunfig.toml`, `Cargo.lock`, `.node-version`, `rust-toolchain*`, `.github/actions/setup/**`) misses every task by design, so enforcing the floor there would red every dependency bump — a gate that is always red on the PRs that need it least is a gate that is off (principle 2), and it would blow the scorecard's ≤ 2 % PR false-red target on its own. [`scripts/ci/turbo-floor.mjs`](../scripts/ci/turbo-floor.mjs) therefore reads the diff first and downgrades the failure to a `::warning title=Turbo cache floor waived::` that **names the file that moved the hash**, writing the reason to the Job Summary. A package-local `package.json` is deliberately not a mover — that is the case the floor exists to catch. **There is no flag and no environment variable that turns the floor off**: the waiver is derived from the diff, which is what makes it an exception rather than a hole. An unreadable diff waives loudly for the same reason it is not a red — reding a lane for its checkout depth is a false red the author cannot fix. Widen `GLOBAL_HASH_INPUTS` only against a run that proved the path moves the global hash; the `### Turbo cache` summary prints `globalCacheInputs` for exactly that. |
| **G-release-candidate** | **We ship builds somebody promoted.** Release SHA selection was implicitly "whatever `HEAD` is when `publish.mjs` runs", and every release lane **builds** the tree rather than testing it, so a tag on an unexercised commit would have been green. `release:prepare` now refuses a HEAD that is not `refs/candidates/latest`, `release:classify --require-candidate [--sha]` offers the same check to a caller that only classifies, and `release.yml`'s `require-candidate` job is the backstop — accepting the current pointer **or** an entry in the gh-pages promotion history, because cutting a release takes minutes while `main` keeps moving. `--allow-uncandidated` passes and prints the reason it was used. |

### The mobile roster and the iOS shell (Wave 2)

Ruled 2026-09-02 by [#915](https://github.com/srikanth235/centraid/issues/915) Wave 2. These extend **G-merge-diet** and **G-device-only-gate** rather than replacing either: what moves is where a mobile claim is declared and which rung answers it.

| Id | Current decision |
| --- | --- |
| **G-one-roster** | **One roster, one runner.** [`tests/agent-e2e-mobile/roster.json`](../tests/agent-e2e-mobile/roster.json) is the single source for what the phone must do: `suites` carry the ordered member list, the aggregate `budgetMs`, the rungs and the platform; `flows` carry the claim, the status and a per-journey marginal budget; `lanes` carry a `rung`. The seven `run-*-suite.mjs` files that each held a `const FLOWS` and a `const BUDGET_MS` literal are one `run-roster.mjs --rung <n> --platform <p> [--suite <s>]`, and `tests/agent-e2e-mobile/lib/roster.mjs` is its only reader — `lint-e2e-wiring`, `lint-mobile-testids`, `lint-e2e-claims`, `check-mobile-suite-budgets` and the report all go through it. **The flags are the wiring**, deliberately: `lint-e2e-wiring` derives what a lane schedules by reading the invocation the shipped YAML or shell script contains, so a runner that picked its suite from an environment variable would make every lane look identical to the gate whose `promoting` and `exploratory` rules depend on telling them apart. The six one-line shims that bridged the swap were deleted with the last workflow line that spelled their paths, so `run-roster.mjs` is the only runner on disk. |
| **G-roster-ratchet** | **A ceiling cannot be laundered by moving it or by renaming it.** Suite budgets stay TIGHTEN-ONLY across the move out of the runner files: `check-mobile-suite-budgets.mjs` reads the merge base's `roster.json` first, then the suite named by `supersedes`, then the retired `run-<id>-suite.mjs` literal, and only an exhausted ref list means "new suite, no base". The p95-slack rule (1.5x the observed p95 once three samples exist) is unchanged and still a no-op, because `ledger/durations.json` holds zero records. A flow's own `budgetMs` is a second, different ceiling — its **marginal** cost with no fresh pairing in it — which is why a suite's members may sum past the suite's own number; `validateRoster` refuses only a member that cannot fit its suite at all. |
| **G-rung-tags** | **Rung 2 keeps the smallest set that can falsify "this diff broke the phone".** `pr-gate` (pairing canary, `notes-library`, cold start; Android; 8 min warm) is the only mobile suite on the merge gate, and **zero iOS minutes** are spent there — a #915 non-goal in as many words. Rung 3 is `resilience` (the retired second leg's three members) plus `home-apps` on Android and `ios-smoke` on iOS. Rung 4 is `probes-suite`, `photos`, `home-apps` again, `sharing` and `promoting-suite` on Android and `ios-depth` on iOS. `sharing` exists because `sharing-reach` ran as a **bare** `node …/flows/sharing-reach.mjs` line with no aggregate ceiling — the one member of the roster nothing priced, which is the shape #890 W0 wrapped six other journeys to end. |
| **G-ios-shell** | **Cache the iOS shell by its NATIVE fingerprint and make the JS current.** The `.app` cache key drops its `js` component (`ios-shell-<os>-xc<toolchain>-fp<native>`), and [`apps/mobile/scripts/ios-simulator-install.sh`](../apps/mobile/scripts/ios-simulator-install.sh) re-exports the SHA's bundle into the banked `.app` instead of rebuilding it — the "pay packaging, not compilation" path Android has used since #905, worth ~32 minutes of a 51-minute job on a JS-only commit. The injection runs **both** commands the Xcode build phase runs, because `expo export:embed` emits plain JavaScript by design and Hermes will happily run it: skipping `hermesc -emit-binary` produces a green lane measuring an engine path no member has. `hermesc` is banked beside the `.app` under the same key (Pods are deliberately uncached, so it is otherwise absent on the warm path), the injected bundle is asserted to carry the Hermes magic `0xC61FBC03`, and the branch itself lives in `ios-shell-cache.mjs` with a unit suite — a wrong rebuild costs minutes, a wrong reuse reports green over another commit's JavaScript. See [docs/traps/ios-shell-injection.md](traps/ios-shell-injection.md). |
| **G-candidate-ios** | **Every candidate carries an iOS verdict, on every push to `main`.** The issue's open decision 3 asked whether the macOS minutes are worth it; they are, because the iOS `.app` is a SEPARATE ARTIFACT — a different binary, a different toolchain, a different Maestro driver — so "it paired and reached a usable Home on Android" is not evidence about it, and until this lane the first iOS answer of the day came from the nightly against a tree that had already absorbed a day of merges. `candidate.yml`'s `mobile-ios-smoke` runs the three-member `ios-smoke` suite in ten minutes WARM and gates `promote`. What makes the price payable is **G-ios-shell**: the shell is restored by native fingerprint and this SHA's bundle is injected into it, so a JS-only candidate pays packaging, not a thirty-two-minute compile. The lane is `blocking: false` in the roster because rung 3 is not a merge gate — it blocks the promotion, not the merge. |
| **G-state-variety** | **State variety never goes to a device.** The eight apps' seven canonical designed states are `tests/integration-mobile/`'s: it boots the shipped gateway and a real native replica session and arranges each state as a boot condition, on Linux, in about two minutes, covering 52 of the 56 cells. A simulator minute costs roughly 600 Vitest seconds, so the same claim on a device is the same claim at 600x. `lint-e2e-wiring`'s RULE `state-variety` refuses any `appStates` cell whose owner is under `tests/agent-e2e-mobile/`. The four uncovered cells (`docs.parked`, `notes.parked`, `photos.parked`, `tasks.parked`) are a **product** gap, not a test gap — no action those apps ship routes to a `confirm: true` command — and are recorded as deliberate n/a with that reason rather than closed by faking a park. |
| **G-launcher-await** | **A journey that opens an app waits for the launcher, not for the band.** `HOME_READY_MARKER` is the Home band's label and the band renders over `DayOne` too, so a flow that waits only for it walks into an empty-vault Home and fails on its own tile selector — which is #870: twelve journeys reporting `Element not found: Open <App>` while the app was correct and the corpus had simply arrived after the phone cloned. `AWAIT_LAUNCHER` waits for `home-grid`, which `LauncherGrid` alone publishes. `lint-e2e-flows`'s RULE `launcher-await` requires it in every chunk that reaches a launcher tile, with an `# e2e-lint-allow: launcher-await` escape hatch for the flows that deliberately face an empty vault. |
| **G-flow-crash** | **A broken journey is a third failure class.** `lib/failure-class.mjs` had two: `infrastructure` (retried once) and `product` (never retried, the default). A flow whose own script throws — `flows/share-intent-in.mjs` used `shQuote` without importing it and died with a `ReferenceError` after six assertions had passed — was neither, and defaulted to `product`, so the nightly said the app was broken when the journey was. `harness` is matched on the error type plus a stack frame inside `tests/agent-e2e-mobile/` (excluding `*.test.mjs`), is never retried because `retry-policy.mjs` retries `infrastructure` alone, and states that no claim was exercised. |
| **G-alarm-weekly** | **The E2E alarm runs weekly, from quarterly.** #915's open decision 4 reads "monthly now, weekly once the roster is single-sourced"; Wave 2 **is** that single-sourcing, so the cadence goes straight to weekly — Sunday 03:00 UTC, before the 04:00 slot, so the answer to "can this suite go red at all" arrives before the weekly lanes report. `mobile-alarm-test.yml` still runs the rung-2 suite against a build with Home blanked and still **fails on a green suite**; nothing about its inversion, its pins, its timeout or its deliberate absence of an apk cache changed. |

### The merge queue: still NOT adopted, re-dated 2026-09-02

Re-examined by [#915](https://github.com/srikanth235/centraid/issues/915) and **still deferred**, for a reason that is now stronger rather than weaker. #892 deferred it pending `lane-health`'s first numbers; those numbers arrived and say the required set was ~26 minutes with a nightly that had not been green in a month, which is precisely the state in which a merge queue converts every red into a queue stall for everyone.

What #915 changes is that the deferral now has a **substitute** rather than only a condition. A merge queue's value was that two individually-green PRs cannot merge into a red `main`; `candidate.yml` answers the same question one step later and without the stall — the pointer simply does not move, and the deep rungs keep testing the last good build. That is weaker than a queue (a red `main` still exists) and much cheaper (nobody waits).

**Revisit condition, unchanged in substance and re-dated:** adopt when the rung-2 p95 is under ~15 minutes over 20 runs (the `pr-gate` budget now measures exactly this) and no rung-2 lane is below 99 % first-attempt pass (the demote rule now files an issue when one is), **and** PR volume exceeds a handful a day. Until all three hold, a queue buys ordering nobody is waiting for.

## One authority plane (#928)

Ruled 2026-09-03 by [#928](https://github.com/srikanth235/centraid/issues/928), which re-judged the half of the consent system [Grants v2](#grants-v2--one-authority-plane-883) left alone: the app grant plane, its purposes, its policy table and the evaluator that ran on every non-owner read. A personal vault has exactly **four kinds of principal that can be told yes or no, and first-party apps are not one of them** — they are the owner's own screens, running the owner's own code, on the owner's own device. These rulings land ahead of #928's code waves, so no wave is built over a guess; where a sentence below describes a mechanism, it states the ruling in force and the wave that lands it.

| Principal | Subject | Enforced at |
| --- | --- | --- |
| the owner's device | the vault, with a trust tier | identity, one statement (already so) |
| automation or assistant | pack or entity, read or act, attenuated per run | the execution clamp, plus a standing answer row |
| person or circle | a shareable subject | delivery into their vault (already so) |
| external service | a capability and egress class | the enrichment gate (already so) |

All four fit `share_authority`. Two already live there; this ruling moves the other two in and deletes the plane they came from.

| Id | Current decision |
| --- | --- |
| **AP-principals** | The four kinds above are the whole list, and enforcement locus follows the kind (as [V-locus](#grants-v2--one-authority-plane-883) already rules). A first-party app is not a principal: it holds no credential, is told nothing, and cannot be revoked, because revoking the owner's own screen is not a thing the owner wants to do. `principal_kind` gains `automation`; `app` stays **reserved and unwritten** against a future third-party door. |
| **AP-apps-declare** | **Apps declare, they are not granted.** Each app keeps a build-time entity manifest (the existing `vault.scopes` block, minus purpose, minus row filters and field masks): the entities and columns its screens read and the commands it invokes. It is used for exactly two things — **replica shape composition**, which becomes a static function of the manifest and the sealed-column registry (no evaluator, no purpose, no grantee join, no `readGrantees`), and a **static tripwire** in the style of `one-computation.test.ts` that fails the build if an app's `queries/*`, `actions/*` or mobile hooks touch an entity the manifest does not declare. Minimisation is kept at build time, with a reviewable diff, at zero runtime cost. |
| **AP-owner-direct** | **Owner-app reads are owner-direct.** A handler invoked for an owner device reads **as that device**: the app bridge's `kind: "app"` credential and `evaluateAccess`'s app path go, and an owner-device read of the owner's own vault runs zero grant statements. `access_app` survives as the **install register** (name, label, the signing key for the replica row-key HMAC, status). `access_grant`, `access_grant_scope`, `access_policy`, `access_scope_tombstone`, `access_scope_request`, `access_seed_row`'s dependence on grants and the install top-up are deleted in wave 4. |
| **AP-automation-principal** | **Automations and the assistant are principals in the one plane.** An automation's compiled manifest mints `granted` rows per (pack or entity × read \| act), and the owner's refusals are `declined` rows; a widened manifest still parks as a decision, and both the request and the answer are rows Settings → Access shows. The per-run execution clamp is unchanged. **The assistant holds no standing grant** — its reads and writes ride the on-behalf-of identity with the acting owner's trust tier, receipted as exercises — and a scheduler-fired automation with no owner behind it acts under its own `automation` row rather than uncapped. |
| **AP-one-id-space** | **One id space, one receipt shape.** Every receipt references `authority_id` from the one authority table; `access_receipt.grant_id` — which today names four different id spaces — is renamed and typed accordingly, and `purpose_concept_id` leaves the receipt with the purpose vocabulary. Receipts record exercises of an answer, reveals, denials and the owner's own high-risk acts; **owner-device reads of the owner's own vault are not receipted**, because nothing consumes them. "Last used" on the Access dashboard becomes computable, and is implemented. |
| **AP-attenuations** | **Attenuations move to the principal they attenuate.** Companion `grant_profile_json` becomes `device`-principal rows with the surface as subject — a device answer with a device as its subject, rather than a surface mask parked on an enrollment — and `outbox_grant` becomes `automation`-principal rows. Each moves in the wave that deletes its old store, never beside it. |
| **AP-give-residue** | **The give-plane residue is deleted.** `share_edges`, `share_effects`, the coordinator, the edge store, the edge routes, the peer-plane sweep's edge half and the retire pass go. The verb retired in [#825](https://github.com/srikanth235/centraid/issues/825) and the machinery now serves only same-owner placement, which is a **command**: project then delete, one transaction. `share_access_receipts` is kept as history only. |
| **AP-locker-boundary** | **Locker's boundary is restated where it holds.** The sealed-column registry, the one-shot permit, `ONLINE_ONLY_ACTIONS` and the `reveal` verb are untouched — those are what protect a secret. The `access.receipt` **row filter** was never the boundary: it guarded a first-party screen against itself, so it becomes a `WHERE` clause in Locker's own history query, and `reveal` stays a distinct verb on the sealed registry rather than a grant scope. |

**v0 stance, unchanged from [#883](https://github.com/srikanth235/centraid/issues/883).** A superseded store is deleted in the wave that replaces it, never carried beside its replacement. The only compatibility target is member data: app grant rows are derived state and are not migrated, while automation grants and tombstones migrate one-shot into authority rows, demonstrated red before landing.

**Two of #928's open questions are answered here.** **Third-party apps**: `app` stays a reserved and unwritten `principal_kind`; the static manifest becomes the install-time consent artefact if and when a door exists, and no door is designed now. **A scheduler-fired automation's principal**: **one row per automation**, not one per pack — the pack is shared machinery and the automation is what the owner said yes or no to. Two are deliberately not decided here, each with the place that decides it: the raw SQL door (`sqlAsOwner`) is resolved in wave 3, once its callers are enumerated; whether owner-direct reads stop being receipted entirely or are sampled is decided with [#922](https://github.com/srikanth235/centraid/issues/922)'s B1.

### The rulings, re-judged (#928)

The register #928 built by applying [ONT-review](#ontology-v0-close-916) to every seam of the consent plane. A row is kept only where a concrete product or security property depends on it **for the product as it is now**; a row that survives on a citation alone is a finding.

| Seam | Ruling cited | Property that depends on it now | Verdict |
| --- | --- | --- | --- |
| "Installing IS the consent" | [#306](https://github.com/srikanth235/centraid/issues/306) | none — all eight apps are bundled and installed by default, and the owner is never asked; the only consent moment an app grant produces is a widened manifest on upgrade | **finding** — the consent is fiction; the manifest becomes a build-time declaration (AP-apps-declare) |
| App grants as app-strategy machinery beneath manifests | [#883](https://github.com/srikanth235/centraid/issues/883) V-split | none — SECURITY.md disclaims protection against an installed app with broad grants, and there is no third-party app door | **finding** — kept by citation; deleted with the evaluator (AP-owner-direct) |
| Purposes and the DPV vocabulary | [#306](https://github.com/srikanth235/centraid/issues/306) | none — 8 apps and 29 automations declare exactly one purpose, `dpv:ServiceProvision`; the second party the vocabulary was held for arrived in [#825](https://github.com/srikanth235/centraid/issues/825) and sharing did not use it | **finding** — deleted, receipt column included (AP-one-id-space) |
| `access_policy` purpose / minimization / retention | [ONT-06](#ontology-v0-close-916) kept three kinds of four | none — zero non-test writers; the table has been seeded empty since #916 and `evaluateAccess` consults it twice per non-owner read | **finding** — deleted (AP-owner-direct) |
| Row filters and field masks on app scopes | [#306](https://github.com/srikanth235/centraid/issues/306) | none — 5 of 277 manifest scopes carry one, and every one is a first-party app reading its own undo history or its own receipts | **finding** — each is re-expressed as a `WHERE` clause in the query that needed it, before the evaluator goes |
| Locker: "the rowFilter is the boundary" | [#873](https://github.com/srikanth235/centraid/issues/873) L-access | none — the filter's counterparty is Locker itself, a first-party screen; the properties that hold are the sealed-column registry and the one-shot permit, and neither is a grant | **finding** — the sentence is superseded; the boundary is restated where it holds (AP-locker-boundary) |
| Tombstones and scope requests | [#308](https://github.com/srikanth235/centraid/issues/308) | **real for automations**: an automation authors its own manifest, so an owner's "no" must survive as data or the next compile silently re-asks | **kept, re-homed** — `declined` rows in the one plane (AP-automation-principal); irrelevant for bundled apps and deleted there |
| The assistant's standing `act` over every command schema | the code's own comment — "more privileged than any app, contained only by confirm-parking" | none — on-behalf-of already carries the acting owner's trust tier, which is the cap that should apply | **finding** — the standing grant is deleted; any command that only worked under it is itself a finding |
| `sqlAsOwner` with purpose `owner-assistant` | [#306](https://github.com/srikanth235/centraid/issues/306) purpose vocabulary | none — a door outside the plane whose purpose string is decorative | **finding** — resolved in wave 3 once its callers are enumerated (deleted if only the assistant uses it) |
| Per-read receipts keyed by a polymorphic `grant_id` | [#883](https://github.com/srikanth235/centraid/issues/883) V-receipts | none as built — V-dashboard promises "last used" and four id spaces share the column, so it is uncomputable | **finding** — one id space, and the promise is implemented (AP-one-id-space) |
| The give-plane residue (`share_edges`, `share_effects`, coordinator, edge store, edge routes, sweep half, retire pass) | [#726](https://github.com/srikanth235/centraid/issues/726), retired as a verb by [#825](https://github.com/srikanth235/centraid/issues/825) | none — it now serves only same-owner placement, which is a command | **finding** — deleted; placement becomes one vault command (AP-give-residue) |
| Companion `grant_profile_json` | [#726](https://github.com/srikanth235/centraid/issues/726) device attenuation | **real**: a companion device is attenuated to a set of surfaces, and that attenuation is what keeps an autofill companion from reaching the rest of the vault | **kept, re-homed** — it is a device-principal answer wearing a surface as its subject, so it becomes rows of the one plane (AP-attenuations) |
| The spine: one owner per vault; `share_authority` with immutable `granted` / `declined` rows; the `share.*` pack as sole writer; delivery as enforcement for people; the sealed-column registry and Locker permits; the demo-seed exclusion for autonomous readers; the per-run execution clamp | [#726](https://github.com/srikanth235/centraid/issues/726), [#825](https://github.com/srikanth235/centraid/issues/825), [#883](https://github.com/srikanth235/centraid/issues/883), [#873](https://github.com/srikanth235/centraid/issues/873) | **real**: each is the only thing standing between a principal and data it was never told yes about — an auditable answer, one writer, enforcement at the boundary a principal cannot cross, and a per-run cap an autonomous reader cannot widen | **holds** — untouched by this umbrella, and the shape every ruling above is folded into |

One earlier open question closes with this ruling: `locker.item` list visibility does **not** depend on `ctx.vault.authenticate` — the list was authorised by the app grant alone (and an owner device bypasses grants), and authentication gates permits and reveal only.
