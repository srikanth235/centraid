# Trap: a guard on the generated half of a generated-and-committed pair

## What goes wrong

A file is generated from a source and **also** committed, so the tree holds both. Somebody writes a guard — a test, a spec, a lint — and points it at the file they can see failing: the generated one. It goes green. The source is still wrong, and the next regeneration puts the defect back, past a guard that was watching the wrong file.

The observed instance, paid for by [#1029](https://github.com/srikanth235/centraid/issues/1029) W18 (find 1): `mobile/iosApp/Info.plist` is generated by XcodeGen from `mobile/iosApp/project.yml` and is committed too. `BGTaskSchedulerPermittedIdentifiers` was correct in the plist and wrong in `project.yml`. The only thing that had ever compared them read the plist alone — the half that is *not* the source — so an iOS build that regenerated the project would launch a background task the system had not been told about, and iOS terminates the app for that.

`project.yml`'s own header says this repository rejected two sources of truth for `.xcodeproj`. The plist is the same shape and was never noticed.

## Why the pair exists at all

Committing the generated half is not always wrong: a reviewer can read it, a CI job that does not run the generator can still build, and a diff shows what actually changed. What is wrong is treating it as readable **state** when it is derived output.

## The rule

**A guard over a generated-and-committed pair asserts against the source, and separately asserts that the generated half matches the source.** Two assertions, not one. If only one is affordable, it is the one over the source — a wrong generated file is fixed by regenerating; a wrong source is fixed by nobody.

`mobile/iosApp` now has `BackgroundIdentifierSpec`, which closes it **for one key**. Every other generated file under `mobile/iosApp/Resources/` is still exposed the same way.

## How to find the next one

```sh
# anything a generator writes that git also tracks
grep -rn 'GENERATED\|DO NOT EDIT\|generated by' --include='*.plist' --include='*.json' --include='*.sql' --include='*.rs' . | head
git ls-files mobile/iosApp/Resources
```

For each hit, ask the two questions in order: what writes this, and what would go red if the *source* were wrong?

## How agents get it wrong

1. **Fixing the generated file and stopping.** The build goes green and the source is untouched; the next `xcodegen generate` reverts the fix.
2. **Writing the guard where the symptom was.** The symptom is in the output. The defect is in the input.
3. **Assuming "it is committed, so it is the source".** Being in git says nothing about which file a human edits.
