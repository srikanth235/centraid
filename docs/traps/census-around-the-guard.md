# A write the commit guard never saw makes every restore refuse the vault

**The symptom.** A restore from the 24 words fails with `code Internal: core invariant: the restored vault at index 0 has the wrong rows: <table>: the generation says N rows at txid T and the restored vault has M`. The phone says the restore did not pass its check. The restored file is fine; the number it is compared against is wrong. It bites only on a vault a phone kept open across the write, which is every real phone and no seeder: a process that opens a vault after the write seeds its census by scanning the file and counts the row.

**The cause.** The generation manifest carries a per-table census, and a restore refuses a file whose `count(*)` disagrees with it (`RestoredGeneration::census_matches`, #1029 §2). That census is **not a scan**: it is `RunningCensus` (`crates/vault/src/log/census.rs`), seeded once per process and then moved only by the deltas `Vault::commit`'s `update_hook` reports. So any row SQLite changes without that hook hearing it is a row the backup will later call missing or extra:

- **A write around the guard.** `Vault::locker_generation` inserted the `locker_key` row on the raw connection, outside `commit`; the census said `locker_key: 0` forever after the first unlock, and every vault that had used Locker was unrestorable (#1047 R3).
- **A fast-path `INSERT OR REPLACE`.** SQLite does not invoke `update_hook` for a row a REPLACE displaced when the table has no delete trigger and no foreign key pointing at it, so a REPLACE over an existing key is `+1` with no `−1`. `locker_item_alias` was one.
- **`DELETE FROM t` with no `WHERE`** on a table with no triggers (the truncate optimisation) and any **`WITHOUT ROWID`** table — neither reports to the hook. The only `WITHOUT ROWID` tables are FTS5's shadow tables, which the census excludes.

**The fix, and the rule.** Every vault write goes through `Vault::commit` — a door that must write outside a command still opens its own `commit` (`locker_generation` does). No vault writer resolves a conflict by REPLACE: use `ON CONFLICT (…) DO UPDATE`, which is an update and moves no count. A path that must write around the guard (`Vault::apply_replica`) calls `RunningCensus::forget`, so the next read re-seeds from the file. `crates/vault/tests/running_census.rs` holds the rule: the Locker generation is counted, SQLite's fast-path REPLACE behaviour is pinned, and a source scan refuses `OR REPLACE` anywhere in `crates/vault/src`. The end-to-end proof is `crates/centraid/tests/drain_wire.rs::a_vault_that_used_locker_restores_from_its_words_and_its_secret_reveals`.
