# The vault ontology

The ontology is the crux of Centraid: one person-owned model of a life, over which every app is a projection and through which every agent acts. This document is its **current state**: what the model is, which commitments the code enforces, and how a table is added. The published design is [centraid.dev/docs/ontology](https://centraid.dev/docs/ontology/) (`scripts/docs-site/src/content/ontology-body.html`, whose schema section is generated); vocabulary is [glossary.md](glossary.md); rulings are [decisions.md](decisions.md) ("The vault model from first principles (#1135)"). The model was rebuilt whole in [#1135](https://github.com/srikanth235/centraid/issues/1135) and carries no compatibility with the one before it (R-FP-10). History lives in receipts, not here.

The schema is one file, `contracts/migrations/001_baseline.sql`, rendered for review as `contracts/schema/vault-ddl.sql` by `export-ladder-ddl`. The Rust that reads it is `crates/vault/src/model.rs` (`Kind`, `Rel`, `Flag`, `fold_label`).

## The shape

- **`entity`** is everything with a title and a trash: `(n, id, kind, title, created_at, updated_at, deleted_at, purge_at)`. `n` is the rowid the search index keys on. The trash pair lives here and nowhere else: a Locker item's trash is its entity's, like every kind's.
- **26 kinds, 14 hosts.** Twelve kinds have a table of their own (`person`, `place`, `event`, `task`, `activity`, `note`, `document`, `photo`, `account`, `txn`, `thread`, `locker_item`); six share `concept` (`tag`, `flag`, `category`, `workout_kind`, `activity_kind`, `relation`: words the member names) and eight share `container` (`notebook`, `folder`, `album`, `list`, `project`, `section`, `area`, `calendar`: things that hold things). A kind table carries `kind GENERATED ALWAYS AS ('<k>') VIRTUAL` and a composite `FOREIGN KEY (id, kind) REFERENCES entity(id, kind) ON DELETE CASCADE`; a typed pointer into a shared host carries its own generated constant, so the engine, not a trigger, refuses a task filed under a notebook.
- **`edge`** joins two entities with one of eight relations (`contains`, `tagged`, `about`, `links`, `attached`, `attendee`, `with`, `related`). `edge_shape` names which kinds a relation may join (`*` is any); a trigger enforces it, and an edge's ends never change. Typed columns carry what only one relation has (`position`, `state`, `anchor`, `label_id`).
- **Children** that are not entities hang off their parent and cascade: contact points, measurements, workouts, occurrences, messages and attachments, checkpoints, revisions.
- **Bytes.** `blob(hash, size)` is the vault's claim on content; `derivative(blob, variant, out, ...)` is what was made from it (thumb, preview, poster, text, caption, phash, thumbhash). A hash is only ever a foreign key into `blob`.
- **Follow.** `origin` is a system the member follows; `source` is one record of it, with `stated` (what the system last said) so the next pass is a per-field three-way merge. Statement lines are `source` rows under the statement origin.
- **Action keys and the write counter** ([#1146](https://github.com/srikanth235/centraid/issues/1146)). There is no journal: the vault keeps nothing of what a member asked for. `action_key (key, asked, at)` holds the key an executed `act` carried and a digest of what it asked, written in the act's own commit, so a delivery repeated after a restart is answered `replayed` and runs nothing; both columns are opaque and the commit that writes a key forgets the keys older than thirty days. `vault.writes` and `vault.written_at` count the commits that changed something a screen reads, bumped once per such commit by the commit guard, so a takeover can tell which copy is ahead. A refused or failed command writes nothing anywhere ([R-1146-1B-1](decisions.md#the-journal-is-gone-1146) to R-1146-1B-3).
- **Format.** A file's `application_id` is `CEN2` and its schema hashes to `SCHEMA_DIGEST` (`crates/vault/src/format.rs`); open and restore refuse a file of the model before [#1135](https://github.com/srikanth235/centraid/issues/1135) and one with other tables, with a sentence. There is no compatibility with the earlier model (R-FP-10).
- **Search.** One contentless FTS5 table, `search`, keyed by `entity.n`, kept by the writer; `search_vocab` serves a word's document count, and `search_word` is the same vocabulary as a list a reader loads whole and a correction reads in memory (one edit anywhere, a first-letter change only when nothing keeps the first letter, a fragment of four letters or more inside a longer word; `crates/search`) (the writer adds a text's words with `centraid_ontology::text::index_words`, the tokenizer compared with SQLite's own; a purge drops the words no other row holds; an edit that drops a word leaves it until `index::rebuild`). `Vault::words()` serves the list from a cache that checks itself against the table on every use (`crates/vault/src/words.rs`): unchanged is one statement, appended words are read as a tail, anything else is read whole. A search answers the entities whose title holds every word first and the other matches after them in slabs of 500, newest slab first and ranked within a slab (a page that ends a slab reads the next, so an old match is reached by paging; [#1146](https://github.com/srikanth235/centraid/issues/1146)); a photograph with no title is in it under a date label (`Photo · 12 Mar 2026`, from `taken_at`) and found by its day; a telephone number (a person's contact point, a Locker item's `phone`) is also indexed as its digits alone, and with the national part after a `+` country code, and a query written as a number is also read as its digits; the index keeps two- and three-letter prefixes (`prefix = '2 3'`), and a query of one-character words is the empty query. A trashed entity is not in it (R-1135-1-4), and a trashed label (a list, album, notebook, folder, project, place …) no longer lends its words to what it held: the trash re-indexes the members in its own commit, and a restore does again. A Locker item is in it by its plain text, whether or not Locker is locked, and the word list is one list for every reader, the assistant included: it searches as the owner does, and there is no search principal ([#1135](https://github.com/srikanth235/centraid/issues/1135)). Every text column is in its entity's own text, folded into the text of what it labels (a tag or flag into what carries it, a list or album into what it holds, a notebook, folder, project, section, area, calendar, category, account or relation into what is filed under it), or argued out in the census `every_text_column_is_findable_folded_into_what_it_labels_or_argued_out` keeps.
- **Locker** is an entity kind, `locker_item`, whose five secret cells (`password`, `otp_seed`, `card_number`, `cvv`, `content`) stay `lk1:` ciphertext that no entity-wide reader carries. Its title, stamps and trash are its entity's; its tags are vault tags, its star and archive are flags; a note may link it. What Locker keeps is `locker_item`'s typed columns and the field, alias, address and passkey rows (`locker_item_field.value_sealed` and `locker_item_passkey.private_key` are sealed too), `locker_key` (the one generation id, and the count of unlocks the phone refused since the last it allowed), and, on each item, `last_used_at`: when the core last opened one of its secrets. A use is a stamp, not an edit — the item keeps its `updated_at`, makes no revision and is not re-indexed — and the Locker keeps no log of uses ([R-1146-1A-1](decisions.md#locker)). A page over `entity` or `edge` serves an item only to a read named for Locker or for the assistant (`page::reaches_locker`; the assistant's reads reach the plain rows and `page::withholds_sealed_value` keeps a sealed column out of them), the search index and `text_of` hold its plain text only (its title, username, addresses, notes, full name, email, phone, brand, memo, aliases, tags and the notes about it) and never a sealed cell, a sealed field's value or a passkey's key, a revision is never written for it. **The assistant has the owner's access to a Locker item except to a sealed value** (the owner's ruling of 2026-10-22): it finds one, reads its plain fields and runs the shared commands on it under the confirmations the owner gets, and its principal is refused any command that reveals or sets a sealed value (`locker.mark_used`, `locker.totp_code`, `locker.export`, a duplicate, a field or passkey removal, and any input carrying a sealed cell, a sealed custom field or a passkey key).
- **Not in the file**: access grants and device tables (the gateway's allowlist is not vault data, [#1080](https://github.com/srikanth235/centraid/issues/1080)), the conversation ledger, per-app decoration tables, an app roster.

## What a familiar thing becomes

A star, a pin, an archive: a `tagged` edge to `flag:starred|pinned|archived`. An album or a People list: a `container` with ordered `contains` edges. A memo, a journal entry, a People note: a `note` with an `about` edge. A task about Mum: a `task` with `about`. An anniversary: a yearly `event` with `about`. A logged call: an `activity` of an activity kind with `with` edges. A relationship: a `related` edge labelled by a `relation` concept. A wikilink: a `links` edge with an anchor. Extracted text, a caption, a thumbnail: a `derivative`. A followed contact, event, file, workout or statement line: a `source` under an `origin`. Last contacted, balances, totals: computed at read.

## How a command changes the model

- **The gate** (`Vault::execute`) validates the input against the command's schema, checks authority, runs preconditions, the handler and postconditions, and, for a keyed `act`, writes the action key, in one transaction. A refusal writes nothing.
- **`ctx.touch(id)`** is the one helper that changes an entity: it stamps `updated_at` and marks the entity for re-indexing at commit. Every command that changes an entity's row, its kind row or its child rows calls it; adding or removing an `about` or `links` edge touches the note at the edge's start. `ctx.insert_entity` is the first half of every create.
- **Re-indexing** (`crates/vault/src/index.rs`) runs inside the commit over the touched ids plus the targets of any touched note's `about` edges (and the people a touched activity is `with`), so a person is found by what was written about them and about a touch with them, plus whatever a touched entity's title labels (`DEPENDENTS`: the things a renamed tag, list, project, calendar or account holds). A link written without touching either end (a tag, a list's `contains`, a `related` label) marks the labelled end for the index itself. **A label's members are written a bounded piece at a time** ([#1146](https://github.com/srikanth235/centraid/issues/1146)): a commit re-indexes the first `INLINE_DEPENDENTS` (50) of what a touched title feeds, and a label with more is left in `search_owed` with the last member done; the core writes the rest in batches of that size (`OWED_BATCH`) when the vault is idle (`Vault::reindex_owed`, started by `with_vault` when something is owed and at open), and a rebuild empties it. An album of 5,000 photographs trashed holds the vault under 30 ms, not 1.3 s; its members show the album's old words for the seconds the batches take.
- **Notes' own verbs** (`commands/note.rs`) are the four only a note has: `note.create`, `note.edit` (title, body, format), `note.move` (into a notebook or out of one) and `note.restore_version`. An edit that changes the body writes the words it replaced as a `revision` (`seq` counts up from one; an edit or a restore that lands on the words already there writes none), and a body's `[[title]]` links compile to `links` edges in the same commit: the compile owns the edges whose anchor is `{"wikilink": "<title>"}` and no others, and resolves a title to the live note, person, event, task, document or photo that carries it, never to a memo (a note with an `about` edge) or a trashed row. A pin, a trash, a notebook, a tag and a hand-made link are the shared verbs below ([R-1135-2-1](decisions.md#notes) to R-1135-2-6).
- **People's own verbs** (`commands/person.rs`, `commands/contact_point.rs`) are what only a person has: `person.add`, `person.edit` (name, columns, cadence; a present key is set, `null` clears), `person.move` (one list at a time), `person.log_interaction` (an `activity` of an activity kind, `with` the person, and a note `about` it), `person.add_note`, `person.add_journal_entry` (a note about the owner, filed on its own day), `person.add_task` and `person.add_gift` (a `task` about them, a gift also tagged `gift`), `person.add_date` (the birthday column, else a yearly all-day `event` about them), `person.add_relationship` (a `related` edge to a person it reuses or founds), `person.save_contact_point` and `person.remove_contact_point` (one preferred per kind, a number once however it is spelled) and `person.merge` (confirmed like a purge; it re-points every foreign key into an entity, read from the file, and carries the phone link to the survivor). Last contacted is **computed at read** from the activities `with` the person. `event::found` and `task::found` are the one birth of those rows for the commands of Agenda and of People ([R-1135-3-1](decisions.md#people) to R-1135-3-14).
- **Agenda's own verbs** (`commands/event.rs`, `commands/task.rs`) are what only an event or a task has. `event.propose`, `event.edit`, `event.cancel`, `event.respond` (a guest's answer is the `attendee` edge's `state`) and `event.edit_occurrence` (`override`, `skip`, `restore` of one day of a series or of it and the days after, an `occurrence` row keyed `(series_id, original_start, scope)` by the series-local wall clock). A day carries what is its own and nothing else is copied: `starts`/`ends`, a title and description, a `timing` (and a `zone` for a zoned one) when it does not read as its series does (an all-day series' day moved to 15:00, a zoned series' day made all-day; NULL is the series') and so is refused for the days after, a `url` and a `place_id` (NULL is the series'); guests and reminders stay the series' ([#1146](https://github.com/srikanth235/centraid/issues/1146)). An event is `zoned` (a `…Z` instant and its zone), `floating` or `all-day`; a time is stated as an instant, or as a wall clock the command resolves in `zone`. `task.add`, `task.edit`, `task.organize` (project, section, position), `task.complete` (the one operation that closes a task as done, and a repeating task's successor inherits the series' filing, rule, `about` and `tagged` edges), `task.reopen` and `task.cancel`. A project, section, calendar or area is a `container` made by `container.create`; a tag, a guest list entry, an attachment and the trash are shared verbs (R-1135-4-1…4-3).
- **Docs' and Photos' own verbs** (`commands/document.rs`, `commands/photo.rs`, `commands/place.rs`) are what only a document, a photograph, a place or an album has. `document.add` files a staged blob as a document (`blob`, `media_type`, an optional folder); `document.create_text` writes words through the byte store; `document.edit` replaces the words of a text document in place; `document.replace` puts down new bytes and writes the old ones as a `revision` (`seq` counts up from one, and a file followed from the phone that changes is a replace); `document.move` files into a folder or out of one; `document.restore_version` brings a revision back as the head. `photo.add` files a photograph over its blob (a blob is one photograph: re-adding the same bytes restores it) and derives a thumbnail and a preview when none was staged; `photo.edit` sets the capture time and zone; `photo.set_place` and `place.locate` say where. `album.set_cover` chooses the key photograph (`container.cover`, a blob). A command that names a blob finds its row or takes `size` and claims it, so bytes staged and never named leave nothing behind ([R-1135-5-1](decisions.md#the-vault-model) to R-1135-5-19).
- **Money's and Health's own verbs** (`commands/money.rs`, `commands/rule.rs`, `commands/measurement.rs`, `commands/workout.rs`) are what only an account, a line, a budget or a day has. `account.add` files an account (its opening balance is as of `opening_on`, and a statement line on or before that day is already in it) and its one `statement` origin (whose `ref` is the bank's number and `config` the remembered layout); a statement line is a `source` under it, so `txn` rows enter only by `follow.statement` and a line is never edited by the member beyond `txn.categorize`, `entity.retitle` and `txn.void`. `txn.link_transfer|unlink_transfer` write `transfer_id` on both halves; `budget.set|set_carry` and `checkpoint.record` are idempotent rows, never figures; `category.add|merge` and `rule.add|edit|delete|apply` are the categories and the rules (`rule.apply` reads the bank's words from `source.stated`; a rule's optional `display_name` retitles a line it decides when the title is still the bank's words, and a line `follow.statement` adds takes it too; the bank's words are never touched). A person's `birthday_reminder` is their own switch (`person.set_birthday_reminder`). `measurement.record` writes only the `(day, metric)` values that changed, and a workout is an `activity` of a workout kind with a `workout` row, entering by `follow.health` (a record gone from a complete read keeps its row and forgets its source, only inside the window the read began at; a new phone re-finds one by kind and start minute).
- **Shared verbs** serve every kind that allows them: `entity.retitle|trash|restore|purge|empty_trash`, `tag.add|remove`, `flag.set|clear`, `edge.add|remove|move`, `container.create|move`, `blob.stage|collect`, `derivative.write|drop`, `person.merge`, `follow.<system>`, `follow.stop`. Each refuses a kind it does not serve, with a sentence. Per-kind create and edit verbs are `<kind>.<verb>` and live with their app.
- **Trash.** A holder (notebook, folder, project, account, and a person for what is written about them alone) trashes its members with the same stamp and a restore brings back only those. A purge purges its companions and what cannot outlive it (a section, a transaction) and moves the rest to the top level (R-1135-1-5). A folder's trash takes the folders and documents under it (R-1135-5-1). **A trashed row's `purge_at` says when the launch pass may take it, not when it stops being restorable**: the core opens the vault and then, on a thread of its own and in bounded batches (`Vault::empty_overdue_trash`: `entity.empty_trash {due_only, limit}`), purges what is overdue, and until a row's batch runs `entity.restore` accepts it (for the assistant too) and no read hides it. A purge also ends the follow of any origin that `fills` the purged entity, of every kind (`PURGE_RULES` names what a purge does with every pointer into an entity that deletes nothing itself), and `container.move` of a section re-files its tasks, trashed ones too, to the new project ([R-1146-3-1](decisions.md)). Kinds with no trash (tag, flag, category, workout kind, activity kind, relation, calendar) are purged directly, with a sentence when something would lose its meaning.
- **Garbage collection** asks `PRAGMA foreign_key_list` which columns reference `blob`; a reference that cascades does not keep its blob alive, a plain one does, and the pass repeats until nothing more falls. Every command that can drop the last reference to a blob (`entity.purge`, `entity.empty_trash`, `thread.save_turn`, `thread.clear`, `derivative.write`, `derivative.drop`, `blob.collect`) collects and answers `released`, the hashes whose files the gate then deletes from the byte store; a replayed answer deletes nothing. A file in the store that no `blob` row claims and that is older than the core's own launch is deleted by the launch sweep (`Vault::sweep_unclaimed_files`, bounded), never one a staging wrote since. The backup plane enumerates `blob` except what only lapsed entities (a `purge_at` that has passed) rent (`backup::files::RENTERS`). **The launch pass collects once, at its end, and in pieces**: its batches of `entity.empty_trash {due_only, limit, defer_collect}` keep the bytes, and the step after the last (`Vault::empty_overdue_trash_step`) runs `blob.collect {limit}` until a piece comes back short, because one collect walks every blob and a batch that paid it each time paid the whole library for a handful of rows.
- **Follow** (`commands/follow.rs`) merges a followed system's record with the row per field against `source.stated`: the member's edit wins on that field, the system's change lands on the rest, an absence in a complete read trashes an untouched row (the source remembers when, as `gone_at`, and the record's return restores it) and forgets the source of an edited one (a source of another phone is re-found by match key, tombstones included, or forgotten, never trashed), rows that hang off the kind row (a contact's points, a calendar series' `overrides`) are a `Child` of the system's map with their own three-way merge, and a purged row leaves a tombstone so it is not added again (it is forgotten once its record is gone from a complete read). Four guards are the engine's, not a screen's ([#1146](https://github.com/srikanth235/centraid/issues/1146)): the owner is nobody's record (never matched, never given a source, never trashed: `entity::is_self`); a complete read that no longer holds at least five of an origin's followed rows and more than half of them is **doubted** (nothing trashed or forgotten, `doubted` says how many) for contacts, events and files alike; a followed series that moves re-keys the `occurrence` rows it would strand to the one day it now has on that date, or drops them; and a followed file's bytes are claimed by `follow.files` itself (a record says its `size`). A statement is not a phone store: its origin is the account's (one per account, whatever `ref` an import names), no `device_id` rides its origin or its lines, `source.stated` keeps the bank's first words of a line whatever it is called now, and `follow.stop` refuses it. A followed phone calendar is a calendar of the vault (a `container` of kind `calendar`) founded the first time it is read and kept after, titled as the phone calls it and painted with the phone's colour as the design wheel names it (the member's own name for it stands; a calendar they trashed is left in the trash), and a followed event is filed on it, not on `calendar:default`. A phone's moved day states its own `timing`, `url` and `location` (a place found or founded by its words) when they differ from its series'. A system's map from fields to columns is data (`SYSTEMS`). The `files` system sends one record per file (`title`, `blob`, `media_type`, and a `stat` child that tells an unchanged file from a changed one), and `follow.stop {system, ref}` forgets an origin and its sources and keeps every row it brought.

## Indexes

An index is the baseline's answer to a question the code asks of a table, and two guards keep the answers honest. **The read side**: `crates/core/tests/query_plans.rs` plans every page every app reads and every hand-written `SELECT`, `WITH`, `UPDATE … SET` and `DELETE FROM` in `crates/{vault,apps/kit,search,ontology}/src` over the year-3 corpus and fails on a full scan of a table over `scanFloorRows` or a sort after the read of a paged read, unless the down-only ledger `contracts/ledgers/query-plans.json` says why. **The write side, which no plan shows**: deleting a parent row makes SQLite look up the children that name it, once per deleted row, so a foreign key whose child column leads no index turns a blob collection, a purge or an emptied trash into a scan of the child table per row. Commitment 9 requires every foreign key's first child column to lead some index (the primary key counts), with `vault.self_id` (one row) the only exemption; a column that is mostly NULL gets a partial index (`WHERE col IS NOT NULL`). A case-insensitive title match (`entity_by_title_nocase`, for a contact import and a followed record's match key) and a closed-task logbook (`task_by_done`) have the indexes their statements stream by. [#1146](https://github.com/srikanth235/centraid/issues/1146)

## Commitments the code enforces

Each is a test in `crates/vault/tests/commitments.rs` that asks the founded file, so a change that breaks one is red before it ships.

| 2 | The trash pair exists only on `entity` | `the_trash_pair_lives_on_entity_only` |
| 3 | Every column holding a hash is a foreign key into `blob(hash)`; GC finds every reference from `foreign_key_list` alone | `every_column_holding_a_hash_...` |
| 3b | Every column that rents a blob says whose the bytes are, so the backup skips what only a lapsed entity holds | `every_column_that_rents_a_blob_says_whose_...` |

| 4b | Every pointer into an entity that deletes nothing itself has a purge rule | `every_pointer_into_an_entity_that_deletes_nothing_has_a_purge_rule` |

Beside them, `format::tests::the_schema_digest_is_the_founded_files` holds `SCHEMA_DIGEST` to the founded file, and `crates/vault/tests/format_identity.rs` and `backup_snapshot.rs` hold the refusals at open and at restore. `crates/ontology`'s doctor checks the file's integrity; `crates/vault/tests/ladder_ddl.rs` holds `contracts/schema/vault-ddl.sql` equal to what the ladder builds; `crates/vault/tests/command_list.rs` holds `contracts/schema/vault-commands.txt` equal to the registry; `crates/vault/tests/ontology_page.rs` holds the published page equal to the file.

## Adding or changing a table

In the same PR:

- edit `contracts/migrations/001_baseline.sql` (the one rung, until the first release that must migrate), regenerate `contracts/schema/vault-ddl.sql` with `export-ladder-ddl`, put the value `the_schema_digest_is_the_founded_files` prints in `SCHEMA_DIGEST`, and add the table to the list in commitment 8;
- decide its place in the model first: a new kind is a row in `entity.kind`'s CHECK, in `Kind`, with a host, and nothing else; a new relation is a CHECK value, a `Rel`, and `edge_shape` rows; a table that is none of these is a child row of one kind and cascades from it;
- a hash column is a foreign key into `blob(hash)`; text a member searches goes in `text_of` and the command calls `ctx.touch`;
- the typed commands in `crates/vault/src/commands` (regenerate `contracts/schema/vault-commands.txt` with `export-commands`) and the app manifest's scopes, then the page: a sentence for the table in `ontology_doc::TABLES` and `cargo run -p centraid-vault --bin export-ontology-page`; and this document if a commitment changes.

## Drift register

Retired. The register audited the model before [#1135](https://github.com/srikanth235/centraid/issues/1135) (its `ONT-nn` rows are cited from [decisions.md](decisions.md) as history), and the model it audited is gone. A finding against this model gets a commitment test above, or is deferred in its issue and says so; it does not get a row here. The one standing gap the old register named, that nothing compared the published design with the schema (ONT-01), is closed: `crates/vault/tests/ontology_page.rs` re-renders [the page's schema section](https://centraid.dev/docs/ontology/#schema) from a founded vault and fails when they differ, when a table has no sentence on the page, and when its entity map names a kind or a relation the code does not.

## How this model is reviewed

A model review that only reads is not a review. Every "deliberate" or `#NNN`-ruled seam is re-judged on its merits for the product as it is now; mechanical sweeps (every CHECK value against its writers, every foreign key's delete rule against its siblings, every table's timestamps) and an adversarial run against the real gateway are part of it ([#916](https://github.com/srikanth235/centraid/issues/916), [AGENTS.md](../AGENTS.md)). When a finding is fixed, the fix names the mechanism, and the mechanism has a commitment test above; a finding with no mechanism is deferred, and says so.
