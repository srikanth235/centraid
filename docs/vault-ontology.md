# The vault ontology

The ontology is the crux of Centraid: one person-owned model of a life, over which every app is a projection and through which every agent acts. This document is its **current state** — what the model is today, which of its commitments are enforced by code, and the register of places where the implementation and the design disagreed. The design itself is the published page at [centraid.dev/docs/ontology](https://centraid.dev/docs/ontology/), authored in [`scripts/docs-site/src/content/ontology-body.html`](../scripts/docs-site/src/content/ontology-body.html); this file is the engineering companion that keeps that page honest.

Vocabulary is [glossary.md](glossary.md); rulings are [decisions.md](decisions.md) (search "Ontology v0 close (#916)", "Ontology reconciliation (#883)", "Grants v2", "Portable export custody"). History lives in receipts and issues, not here: the ontology package landed in [#252](https://github.com/srikanth235/centraid/issues/252), rule 10 in [#274](https://github.com/srikanth235/centraid/issues/274), the first audit in [#441](https://github.com/srikanth235/centraid/issues/441), the reconciliation in [#883](https://github.com/srikanth235/centraid/issues/883), and the v0 close in [#916](https://github.com/srikanth235/centraid/issues/916).

## One file, three bands

A vault is **one SQLite file**, `vault.db`, holding three bands ([#916](https://github.com/srikanth235/centraid/issues/916)):

- **The model** — the `core` spine, nine life-domain packs, the `access` and `command` planes, and the machinery bands (`share`, `sync`, `enrich`, `outbox`, `notifications`, `blob`).
- **The audit band** (`auditBand` in the registries; the writer is `crates/vault/src/audit.rs`) — `access_provenance`, `access_receipt`, `command_invocation`, `command_invocation_check`, `command_evidence`, `command_explanation`, and the archive manifests. Append-only **by trigger**: UPDATE and DELETE are refused by the engine, not by convention.
- **The ledger band** — the conversation transcript (`conversation ⊃ turn ⊃ item`), automation state and the archive rows that bounded it. **Dropped** (#1029 W19; a new vault never founds it): the assistant and automation planes went with the amendment, nothing wrote the band, and a table with no writer is not state. The member-facing chat history is not this band and not a return of it: it is the `chat` pack ([R-CHAT-1](decisions.md#the-on-device-chat-keeps-its-history-in-the-vault)).

The audit stream lived in a second file, `journal.db`, until #916. Splitting it was a size argument and it cost correctness: a receipt in another file is not atomic with the mutation it describes, and every pointer across the seam had to be a gateway promise instead of a foreign key. One file gives one ACID boundary — invocation, rows and receipt commit together — and makes `core_entity_revision.invocation_id` a real key. The size argument is answered where it belongs: each band declares a retention window in one place (`RETENTION_WINDOWS`: audit 365 days), and the archival pass proves custody of what it sealed before it prunes. The audit band is excluded from the portable export and the device replica **by band** (`privateTables` in the registries), so there is no second list to maintain.

One file also collapsed the backup protocol, and [#1080](https://github.com/srikanth235/centraid/issues/1080) rebuilt it from first principles. A backup of the vault is a **snapshot**: the file copied page for page by SQLite's online backup API, cut into page-aligned 64 KiB ranges each sealed as a file named from its own bytes, and described by a sealed **manifest** that also carries the census counted on that copy ([R-1080-5](decisions.md#backups-from-first-principles-1080), [R-1080-B7](decisions.md#the-sealed-format-and-the-snapshot-plane-1080-wave-1-lane-b)); the generation it supersedes was a base, its segments and a manifest carrying the dictionary they were sealed against ([R-1029-6](decisions.md#the-phone-is-the-vault--v0-1029-ruled-2026-09-21)). **There is no custody table**: an object's name and key derive from the vault's backup key and the plaintext hash the vault already stores for every content item and derivative, so the database and the 24 words are the whole index, and a vault founds none of `backup_object_range`, `backup_base_range`, `backup_blob_custody` and `backup_blob_placement` — the old plane's index tables, which the ladder dropped before the first release and `crates/vault/tests/baseline.rs` keeps from returning ([R-1080-4](decisions.md#backups-from-first-principles-1080)). The two-database coordination — the capture order, the coordinated break, the pair marker and the two-base same-tick refusal — was deleted before that, because a pair is what it existed to keep in step. The implementation is `crates/vault/src/backup/`, and its format fixture is `contracts/crypto/sealed-vectors.json`; `contracts/custody/recovery-kit.json` was deleted as a v0 kit nothing read ([R-1047-D2](decisions.md#the-sealedv1-cell-layer-and-the-retired-locker-generation-deleted-1047)), and `contracts/golden/format-golden.json` went with the TypeScript half of the product.

## The shape today

A freshly founded vault, at the ladder head (`contracts/schema/vault-ddl.sql`, regenerated by `cargo run -p centraid-vault --bin export-ladder-ddl`): **95 base tables** (plus 10 FTS virtual tables and their 50 shadow tables: 145 `CREATE TABLE` in all, and 10 `fts5vocab` virtual tables over the seven domain indexes, the three container indexes and the chat's). The ladder is four rungs. Rung one, `001_baseline.sql`, was **squashed on 2026-10-15** from the fifteen rungs that preceded it (Q-1029-1): it is the frozen v0 corpus's schema as v1 changed it, plus the rows founding seeds (the money categories). Rung two, `002_phone_link.sql`, adds `phone_link` and `phone_origin` (#1127): which phone record each followed person, event, document or workout came from, and which phone account, calendar, picked folder or health store it was read in. It is unreleased and was amended in place to admit the `health` source, which a link maps to `core.activity` (R-1129-1). Rung three, `003_health.sql`, adds the `health` pack (#1129): `health_daily` (one stated total per subject, day and metric) and `health_workout` (the health half of a `core_activity`), the `health:workout-kinds` scheme's eight kinds seeded under fixed ids, and the page index `core_activity_started_page_idx` the Workouts list pages on. It also rebuilds `core_activity` as **mutable** (`updated_at`, `row_version`, the touch trigger), so a followed workout can be corrected in place and People's logged interactions inherit the same life (the owner's answer 5, ONT-43). Rung four, `004_chat_message_version.sql`, gives `chat_message` `updated_at`, `row_version` and the touch trigger, because a proposal settles in place and a new turn dismisses it (R-1129-17); it copies the message and its two children aside, rebuilds them and restores every row at version 1. v1 **did not found** the planes it does not have — 43 tables and 119 schema objects in all (#1029), Tally's twelve tables, the expense index and the circle index (ONT-41, [#1099](https://github.com/srikanth235/centraid/issues/1099)), and the four tables the old backup plane kept, `backup_object_range`, `backup_base_range`, `backup_blob_custody` and `backup_blob_placement`, because a snapshot's ranges and the ledger of what a gateway holds live in `<stem>.backup.db` beside the vault, not in it ([#1080](https://github.com/srikanth235/centraid/issues/1080)); and it **does** add the revision guards (ONT-22), `core_collection`'s required `kind` (ONT-33), `locker_key` as one generation (ONT-34), the Locker without a match policy (ONT-35), no `notifications_notice` (ONT-36), the `chat` pack (R-CHAT-1) with a parked write's life (`chat_message.outcome` takes `proposed`, `applied`, `dismissed`, `stale` and `failed`, and two triggers state when it may change: ONT-38, [#1088](https://github.com/srikanth235/centraid/issues/1088)), the search folds that put the text a member typed into the domain indexes, seven fewer indexes and a vocabulary per index (ONT-39, [#1097](https://github.com/srikanth235/centraid/issues/1097)), and the `money` pack: six tables that hold a member's decisions about a statement, a unique index that lands a statement line once per account, and the triggers that hold a Money account to one currency and an imported line to never being edited (ONT-40, [#1099](https://github.com/srikanth235/centraid/issues/1099)). The command registry, the invocation journal and its four siblings are `command_definition`, `command_invocation`, `command_capability`, `command_invocation_check`, `command_evidence` and `command_explanation` (Q-1029-3, and the other four on 2026-10-16; despite their v0 names, `agent_*`, there is no agent left). The baseline also stopped founding `access_device` and `access_device_secret` and the columns that named them, `core_content_item.origin_device_id` and `media_asset.camera_device_id`, on 2026-10-16: nothing wrote them once the gateway's allowlist left (#1080). ## Derived data is not automatically local data

A tempting rule after [#1014](https://github.com/srikanth235/centraid/issues/1014) (B10) was "derived data does not replicate": enrichment writes 512-float vectors and a provenance stamp per derivation, and on a 50k library that is what a seat's change log fills up with.

The rule is wrong, and the reason is [R1](decisions.md#one-vault-every-seat-996): a seat holds `vault.db` WHOLE. There are no row filters and no field masks, so a table travels or it does not — and a replicated table may never reference a private one ([R4](decisions.md#one-vault-every-seat-996)), which is a constraint on the _graph_, not on how the row was produced.

So the question that decides it is not "was this derived?" but:

1. **Does a seat read it?** `media_face_cluster` is derived and the People page walks it; `media_asset_phash` is derived and the library page reads it. Both travel.
2. **Does a replicated row point at it?** `core_content_text.derivation_id` REFERENCES `enrich_derivation`, so making that stamp private would break the property the private list exists for. It travels.
3. **Neither?** Then it is gateway machinery: private, and usually unregistered too. `enrich_request` is private (the queue is work, not data) and `enrich_target_failure` is both private and unregistered — a restore re-derives one host's failure counts by simply attempting the work again.

Each derived table's answer is its membership, or not, in `privateTables`; `crates/ontology/tests/commitments.rs` (`no_replicated_table_references_a_private_one_by_name`) holds the graph half of the rule.

## Commitments the code enforces

Each row is a design commitment, where it is enforced, and the test that goes red when it is broken. A commitment with no row here is a wish, not a rule.

## The ten rules, as implemented

The page's §11 states ten hard rules. This is where each stands in code.

| Rule | Standing |
| --- | --- |
| R1 IDs immutable, meaningless | Held, and now unique across the model: every entity row is a `core_entity` row, so an id names one thing. `core.merge_party` folds one party into another: every reference re-points — the sweep is generated from `PRAGMA foreign_key_list`, never a hand-kept list — and the merged party's row is deleted (`crates/vault/src/commands/core.rs`). A cross-source match the owner has not accepted stays two rows with a `same-as` link. |
| R2 Extend, don't fork | Held for every shipped domain: `people_profile`, `media_asset`, `schedule_event_ext` anchor a core row by UNIQUE FK. **Locker is the one written exemption** — an owner-only secret anchors nothing in core by design (its DDL header). |
| R3 Relationships typed and temporal | Held for cross-entity meaning (`core.link`). Junction tables that carry state (`schedule_attendee.partstat`, `social_circle_member.capability`, `core_collection_entry.position`) are typed rows, not the boolean junctions the rule forbids. |
| R4 Writes are typed commands | Held. Every write is a registered command in `crates/vault/src/commands`, run through one gate order; there is no generic row writer. A SQL literal outside the confined crates is a `sql-confinement` failure. |
| R5 Durable facts vs rebuildable projections | Held with two registered stored projections: `social_thread.last_message_at` (healed by sweep) and `blob_custody_*` (rebuilt). Money stores no balance beyond a member's stated checkpoint. The `media_asset.favorite` mirror is gone. |
| R6 Consent travels with the data | Held; the authority answers live in one plane (`share.authority`, [#883](https://github.com/srikanth235/centraid/issues/883)), and the plane that answers "may this actor reach this data" is named `access`. The principal kinds the plane admits are `person`, `circle`, `harness`, `device` and — accepted in [#928](https://github.com/srikanth235/centraid/issues/928) wave 1, written in wave 3 — `automation`, whose id is a manifest ref (`<app_id>/<automation_id>`) and whose subject is a command pack (`agent.pack`) or an entity type (`core.entity`), read or act. `app` is not among them and is not reserved as a value: first-party apps are the owner's own screens, not principals. A portable export carries policy and ciphertext, never a key. |
| R7 Version the ontology explicitly | **Held, restated.** The version is a property of the file (`user_version`) and of the command contract (`command_definition.ontology_version`) — not of a row (ONT-04). |
| R8 Lifecycle is declared, not adopted | **Held.** This rule replaced "corrections become durable judgment", whose loop had DDL, commands and no caller (ONT-06). Each entity declares its lifecycle and a test holds the schema to it. A declaration changes only by a rung: `core.activity` went from `append-only` to `mutable` in rung three, for a followed workout that is corrected in place ([R-1129-1](decisions.md#health-follows-the-phones-health-store-1129), ONT-43). |
| R9 (rule 10) One judgment, one mechanism | **Held with no exception.** The single registered mirror (`media.asset.favorite`) was deleted; Photos' star anchors on `media.asset`, Docs' on `core.document`. |
| R10 Every app rides the paved road | Held: manifests become grants, reads are scoped, writes are commands, app-declared tables are an `ext` block in the manifest, which no bundled app uses. The registered-view half of the road left with the views nothing registered (ONT-06). |

## Drift register

The do-not-fix-quietly register for the ontology. Each row names the finding, the evidence, and its standing. A row is removed when its finding is gone from the code **and** nothing about the removal is worth remembering; it is kept as **fixed** when the mechanism that closed it is the thing a future reader needs. Nothing here is "deliberate" any more: [#916](https://github.com/srikanth235/centraid/issues/916) re-judged every deferred row on its merits and three of them — polymorphic references, the favorite mirror, the consent plane — had been filed as settled on nothing but a prior ruling.

**Rung numbers and `contracts/migrations/0NN_*.sql` names in the rows below** are the fifteen-rung ladder as it stood before the baseline was squashed on 2026-10-15 (Q-1029-1): those files are gone, their effect is in `001_baseline.sql`, and the commit before the squash holds them (`a44202fe9`). A row's standing is unchanged by that; what a row says a rung did is what a new vault now simply has.

**Reader-side drift against a landed ruling** is a category of its own, introduced by [#996](https://github.com/srikanth235/centraid/issues/996) ([R22](decisions.md#one-vault-every-seat-996)): a ruling the storage layer enforces — a column, a CHECK, a trigger, a dropped table — while a reader ignores it, reads a column the writer does not write, or aggregates away the thing the column was added to carry. It looks fixed from the DDL and from the schema tests, which is exactly what makes it drift rather than a bug: the mechanism the register asks a **fixed** row to name is present, and the property is still absent at the surface the owner sees. **A storage ruling is not enforced until a reader test holds it** — one test that writes through a real command and reads through a real app query, across two app surfaces. Three of [#916](https://github.com/srikanth235/centraid/issues/916)'s rulings were in this state when #996 audited them (ONT-22, ONT-23, ONT-25), and each row below in this category names the ruling it drifted from.

## Was the starting design right?

The spine was. Every domain that shipped anchored into it without forking identity: People is a profile on `core.party`, Docs is `core.document` over `core.content_item` filed by `core.tag`, Photos is `core.content_item` with capture context, and the one exemption (Locker) is written down. The universal joins (`tag`, `link`, `annotation`, `collection`, `attachment`) absorbed stars, memos, employment, albums, notebooks, receipts and folders, which is what they were for. The rules caught real drift four times — [#274](https://github.com/srikanth235/centraid/issues/274), [#441](https://github.com/srikanth235/centraid/issues/441), [#883](https://github.com/srikanth235/centraid/issues/883), [#916](https://github.com/srikanth235/centraid/issues/916) — and each time the fix was a mechanism, not a patch.

Four things were started wrong, and the register above is their residue:

1. **Breadth before consumers.** The foundation release modelled eight life domains at once; the page's own first-boundary advice ("do not add a third domain until export→reimport round-trips") was better than the plan that ignored it. Four domains and five mechanisms have now left for the same reason: no producer, no consumer.
2. **A consent plane borrowed from a different product.** App grants, registered views, purpose policy and export jobs were modelled Solid/ODRL-style before Centraid's real authority model existed. That model turned out to be owner + device + one authority table ([#726](https://github.com/srikanth235/centraid/issues/726), [#883](https://github.com/srikanth235/centraid/issues/883)). What survives of it is `access_app` — the install register (name, label, its signing key, status) — and the audit band's `access_receipt`. The grant tables, the policy table and the evaluator's app path are gone: a first-party app is the owner's own screen, its reach is fixed at build time by its declared entity manifest and the static tripwire over it, and an owner-device read of the owner's own vault runs zero grant statements ([#928](https://github.com/srikanth235/centraid/issues/928) AP-owner-direct).
3. **Conventions where declarations belonged.** A per-row version stamp, a soft-delete pair "adopted as tables are touched", a polymorphic pointer registry swept by hand — each was a convention, and a convention without a mechanism drifts by construction. The registry is where such things are declared, and the engine is where they are enforced: the supertype turned pointer hygiene from a sweep into a foreign key, and the lifecycle declaration turned timestamps from a habit into a test.
4. **A second file for a size problem.** `journal.db` traded atomicity and referential integrity for a smaller sovereign asset. Retention was the answer all along; the split was a cost paid every transaction for a benefit that arrived once a year.

What was missing was never a better model but a guard: nothing compared the design with the schema, so the design aged silently. The commitment tests close that for the conventions and `sql-confinement` closes it for the door; the page is open again (ONT-01).

## Adding or changing a table

The admission checklist on the page (§11, [#310](https://github.com/srikanth235/centraid/issues/310) C6) still governs. In this repo that means, in the same PR:

- a new rung under `contracts/migrations/`, appended to `LADDER` in `crates/vault/src/migrations.rs` — a released rung is never edited — with the entity's row in `core_entity` following from its membership trigger;
- the registry entry in `contracts/schema/v0-registries.json` with its label, **lifecycle** and deletion roles — or `projectionOf` if the row is a part of an entity — or an entry in `localTables` / `privateTables`;
- a composite foreign key into `core_entity` if the table carries a `(type, id)` pair;
- the `contentReferences` entry if it rents bytes; an FTS index if it has text (with a deleted-row filter if it trashes);
- the typed commands in `crates/vault/src/commands` and the app manifest's scopes;
- the §03 entry on the published page;
- and this document, if a commitment or a register row changes.

## How this model is reviewed

A model review that only reads is not a review. [#916](https://github.com/srikanth235/centraid/issues/916) established three practices, now part of the repo's conventions (see [AGENTS.md](../AGENTS.md)):

- **A citation is not a justification.** Every "deliberate", "by design" or `#NNN`-ruled seam is re-judged on its merits for the product as it is now. A ruling explains why something was chosen, never whether it should stay. An item worth keeping gets an explicit question to the owner with options and a recommendation; an item that survives only because someone ruled it, with no consumer or security property depending on it, is a finding. This wave filed polymorphic references, the favorite mirror and the consent plane as settled on exactly that deference, and had to reopen all three.
- **Mechanical sweeps are part of the review.** Every CHECK value against its writers; every FK's delete rule against its siblings; every table's timestamps against its lifecycle; every raw-SQL site outside the package. Reading found none of the dead CHECK values, none of the inconsistent delete rules, and none of the missing currency columns.
- **An adversarial run against the real gateway is part of the review.** Twelve scenarios driven through the shipping command pipeline reproduced the merge that deleted a party's expense splits, the purge sweep that wedged on one refused row, the export that shipped the data-encryption key in the clear, and the revoke a trashed projection could evade. None of those were visible by reading.

The corollary for a future wave: when a register row says **fixed**, the row names the mechanism, and the mechanism has a test in the commitments table above. A finding with no mechanism is not fixed; it is deferred, and it says so.
