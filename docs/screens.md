# Screens

Every decision a person sees is made in Rust: screen state, finished strings, counts, navigation, timers. SwiftUI and Compose draw `ViewState`, send `ScreenEvent`s and perform `Effect`s ([#1135](https://github.com/srikanth235/centraid/issues/1135)). Code: [`crates/screens`](../crates/screens); wire: [`screens.proto`](../crates/api-proto/proto/centraid/core/v1/screens.proto).

## The contract

- **A screen** implements `Screen`: `update(event, &Ctx) -> Vec<Effect>` and `view(&Ctx) -> ViewState`. It reads and writes only through `Ctx::load` / `Ctx::act` — the core's one read and one write, the same door chat and the training harness use.
- **Re-render.** Each `load` records the tables it read; when one changes the screen gets `DataChanged` and loads again. A view is pushed only if it differs from the last, so a screen's own `act` echoes no second draw.
- **Navigation** is a route stack per tab, owned by the runtime. Routes are protos. A shell draws the stack it is given and reports a tap (`NavPush`) or a back-swipe (`NavPopped`) as events; the root of a tab cannot be popped.
- **Effects** are platform work: clipboard, haptic, share, open URL, pick photos, camera, Health read, keychain, screenshot shield, notification. The shell performs one and answers with `EffectResult` carrying the same `effect_id`.
- **Timers** (undo windows, clipboard clear, reveal auto-hide) live in the runtime: `ctx.start_timer(name, after)` and the screen later gets `TimerFired`. They die with their screen.
- **Catalogue ids.** A screen never spells an app, action, query or input name: it builds `catalog::act::<app>::<Action> { .. }` or `catalog::load::<app>::<Query> { .. }` (generated from the manifests by `cargo xtask screens-catalog`; `--check` and a unit test fail on a stale file) and converts it into the request. Mint a fresh `.keyed(..)` per gesture: the core runs one `invoke_key` once.
- **Strings** come from one catalog, [`strings.rs`](../crates/screens/src/strings/mod.rs): typed functions, plural-aware, locale-ready; the locale and zone arrive in `Environment`. Native views write no copy.
- **Wire.** Requests ride `centraid_call` (`Request.screen`); pushes ride `centraid_next_event` (`Event.screen`). The ABI stays five symbols. The runtime is driven from `Handle::call`, change events and wakes inside `next_event`, so it holds no handle reference between calls.
- **A failed read is not an empty list.** A view has three states — loading, a `Failure`, data.

## Writing a screen

Agenda is the worked example: [`crates/screens/src/agenda/`](../crates/screens/src/agenda).

1. **Protos.** The app's view states and events in `<app>_screens.proto`; its route arguments in `route.proto` (with any enum a route names); one arm each in `Route.args` (`route.proto`), `ScreenEvent.kind` and `ViewState.kind` (`screens.proto`) in the app's reserved range. The shared view vocabulary (`Failure`, `Loading`, `Denied`, `EmptyState`, `StatusLine`, `Confirm`, `Autosave`, `ListRow`, the kit trash) is `kit_screens.proto`. `route.proto` and `kit_screens.proto` are leaves, so a view can hold a `Route` without an import cycle. Add the files to `build.rs`.
2. **Code.** `crates/screens/src/<app>/<name>.rs`, one folder per app, self-contained, no imports from another app. It is not in `crates/apps/<app>` because the core depends on the app crates for their readers and this crate depends on the core for `load` and `act`: a screen there would be a Cargo cycle. A piece several apps use goes in `crates/screens/src/kit/` and is shared.
3. A struct holding the loaded data and local UI state; `update` handles `Appeared` (the one load), `DataChanged` (load again), your events, `EffectResult`, `TimerFired`, `Left`; `view` makes every string through `strings::<app>::*`.
4. **Strings.** One module per app (`strings/<app>.rs`) and one per screen that needs its own (`strings/<app>_<screen>.rs`), each a `catalog!` block; the kit's are `strings::shared`.
5. Register: `<app>::registry()` returns `Registry::with("<app>.<name>", build)`; the shell composes registries with `Registry::merge`.

## Conventions every app copies

- **A tap that opens a page is a `Route` in the row** (`<app>::routes::*`). The shell sends the route back as `NavPush`; no screen names a destination in Swift or Kotlin and no screen pushes itself. A screen that is done (saved, deleted, cancelled) sets `dismissed`/`finished` in its view and the shell pops.
- **Writes are synchronous.** `ctx.act` answers with the verdict, so there is no in-flight map, pending row or held write: submit, read the verdict (`kit::act::act` → `Settled`), load again. A refusal's sentence goes in the view. Undo is the core's `inverse` for the action, sent back as an action.
- **Invoke keys: take the sequence from `kit::act::fresh()`.** The vault journals a key for good and answers a repeat "replayed" without running it, so a counter that restarts at 1 on each open turns a later tap into a silent no-op.
- **Reads are `kit::read::read`**: `Reading::{Data, Denied, Failed}`. A failed read is a `Failure` in the view, never an empty list.
- **`Left`** is sent to a screen the instant before it is popped: its last chance to `act` what the member typed (the kit's autosave flushes there). Timers die with the screen.
- **Civil time** comes from the core's answers (`today`, `local_days`) and `kit::civil`; the zone arrives in `Environment` (`ctx.zone()`).
- **Device memory** (a per-phone habit) is a Keychain effect, not a vault row; platform reads that feed an import are generic Effects the shell answers (`CalendarRead`, `PhoneWatch`, `HealthRead` answered by `HealthSnapshot`); the shell reports `locale`, `zone` and `platform` in `Environment`, so Rust picks units (from the locale's region) and the store name.
- **Secrets are `kit::secret::Secrets`.** A revealed value lives in the screen, never in a route or a view that was not asked to draw it: show, copy (`ClipboardSet{sensitive, clear_after_ms}`; Rust owns the clear timer and the shell persists the deadline so a killed process clears the stale clip on next launch), hide on a timer, on conceal, on a relock and on `Left`. `view_shielded()` is for a screen whose own `secure` flag already shields capture.
- **A wall is a per-screen piece over the core's one session** (`locker::wall::Wall`, `Ctx::locker`). A view with `wall` set is drawn instead of the screen. The owner check is the generic `OwnerCheck`/`OwnerChecked` effect; a core without keys, a lockout and a cancel are outcomes the wall words. The Home screen asks on `Appeared`; others probe and wait for the tap. The shell reports `AppLifecycle{foreground}` and the core relocks on background; every open screen hears it as `Lifecycle`.
- **Files and announcements are generic effects**: `PickFile`/`FilePicked` (bytes held only as long as the asking screen), `SaveFile` (the only place a file is written; a dismissed sheet is `EffectFailed.cancelled`), `Announce{topic}` (`locker.unlocked` files a vault's own key in the shell).
- **A value that must not ride a route is a process-local take-once slot** (`locker::handoff`): the generator's candidate reaches the editor that way.
- **A file the member picks is a generic Effect that answers more than once** (`PickFile`, #1135). The shell copies the choice to a file, streams it through the stage door and answers `FileProgress` any number of times under the one effect id, then `FilePicked{blob, byte_size, name, media_type}`; Rust files it with an `act` (`document.upload`, whose `size` the stage door cannot know). `FollowFolder`/`StopFollowing` keep the OS grant in the shell, the vault's links in Rust. `OpenRoute` lets Rust ask the shell to push a page when no tap caused it (a filed document).
- **A code is read by a generic effect** (`ScanCode{photo_label}` -> `CodeScanned{text}`, #1135): the shell raises its camera (a photo picker on a phone with none), asks for the camera grant at that moment, and answers the text; empty text is a photo with no square, an outcome and not a failure; backing out and a refused grant are `EffectFailed.cancelled`. `pair.laptop` and the restore's code field both use it.
- **A browse of the local network is a generic effect that answers more than once** (`BrowseGateways{on, window_ms, repeat_ms}` -> `GatewaysSighted` per window, #1135): outbound only, for as long as the screen that asked wants it (`on: false`, or the screen closing). The match (`pairing::matching`: by the TXT `gw` id, never the instance name) and the check (`refresh_destination`) are Rust's; a screen that wants a gateway followed holds a `pairing::discovery::Rediscovery`.
- **A path is computed once, in Rust.** Docs' folder walk is `centraid_apps_docs::folder_path`, shared by the core's answer and the screens; the shells draw the crumbs' `Route`s.
- **The 24 words are sagas over the shell's secret stores** (`custody::enrollment`): a flow is a `Job` that asks the shell for one thing at a time (a `SecretBatch`, the `SyncedSecretsProbe`, a restore on a worker thread via `Ctx::vault_async`) and takes the answer as input, so the order the words are kept in is a state machine. Every job begins by reading both stores again into the one `VaultSecrets` cache. The multi-vault shelf is the `custody::keeper::Keeper` trait (`KeeperSlot`, `registry_with`); a screen is never given a secret except where it draws it (`secure` views the shell shields).
- **An `Announce` is relayed to every open screen** (`ScreenEvent::Announced`), services included, in the same call: the shell performs its half and sends nothing back. `custody.filing` files a vault's own recovery key in Locker when it hears `locker.unlocked`.
- The kit's generic screens (`kit::trash`, parameterised by a spec; `kit::autosave`) are built once. A new app supplies a spec.

## The vaults, and the vault in front

A phone holds several vaults, and **Rust holds them** ([`crates/screens/src/vault`](../crates/screens/src/vault)). The shell opens ONE core over a directory (`{"shelf": dir}`; `CoreConfig::fronting`), the _front_, which holds no vault: the shelf opens every vault under the directory itself (one directory each: `<dir>/<opaque>/vault.db`), keys each from the phone's secrets (`custody::secrets`, filled by `SecretBatch`), rests, wakes, freezes, renames, forgets and founds them, and forwards the vault in front's events to the front's queue.

- **The front routes.** Every `call`, `load`, `act` and Locker step that is about a vault goes to `Vaults::foreground_core` (`centraid_core::vaults`); the screen runtime, the words, a restore and the handshake are the front's own. A screen changes nothing to read through "the vault in front". `Ctx::vault_async` binds its door to the vault in front when it is asked (the words and a restore are the front's own: a restore lays vaults down beside the front's file), so a pairing finishes on the vault it began on after a switch; a job from `Ctx::off_thread` gets the front, and one that must finish on a vault binds `ctx.vaults()`'s `foreground_core()` or `core_of(id)` when it is asked.
- **A switch is the runtime closing and reopening the tabs.** `Ctx::switch_vault(id)` (Home's `VaultCommand.switch_to` becomes one): every screen in a tab hears `Left` first, so what was typed is written to the vault it was typed in; then the vault comes to the front and each tab root is opened again. A foreground that changes any other way (a vault founded, the one in front forgotten, the first launch) closes the roots WITHOUT `Left`. Both are ordinary `ScreenUpdate`s. Services are not closed.
- **`shell.holdings`** is the shelf's read (`vault_screens.proto`: `Holdings`, `HeldVault`): the vault in front first, resting, keyed, own-words and frozen (date and the count of changes no gateway acknowledged). It is announced under the table `shelf`, so a screen that read it hears `DataChanged`. Home is _told_ the same facts as events by the shelf's service (`vault::service`), which also performs Home's `VaultCommand` (switch, make, restore, forget, rename; `Open` stays the platform's). While the core is not a shelf's door, those commands reach the shell as before.
- **The shelf talks to nobody.** Its methods are synchronous, read the secrets cache and return the `SecretOp` writes the shell must perform (`Effected`); the caller sends them. A found spends its derivation index before the core makes the file, recorded in a `found.pending` marker in the new vault's directory (`vault::files::Marker`) until the secret store is seen to hold it; a launch finishes or deletes what a killed process left.
- **The shell tells Rust three things about the shelf:** the directory (open config), a debug build's demo seed (`devSeed`), and the operating system's memory warning (`ScreenRequest.memory_warning`; the shelf closes every core but the one in front).

## The shell's catalogue and the chat

- **The shell has a catalogue too.** What is not one app's (the chat's history, Home, search, the vault's plumbing) is named in ONE manifest, [`crates/core/src/shell/manifest.json`](../crates/core/src/shell/manifest.json) (app id `shell`, `catalog::SHELL`, rows in `shell::ACTIONS`). It is parsed like an app manifest and is not one of the eight apps: the assistant's catalogue and the training export carry the eight only. A screen builds `catalog::load::shell::..` / `catalog::act::shell::..` like any other.
- **Chat is a Rust screen** (`chat.home`, the `chat` tab; `chat.ask` is a search's Ask as a page; [`crates/screens/src/chat`](../crates/screens/src/chat)). The turn is the core's (`assist.proto`): the screen never re-implements a decision the assistant makes. A bounded assistant call (status, start, suggest, cancel, clear, confirm, dismiss, documents) is `Ctx::assist`. The two that block for seconds, a model load and a turn, run from `Ctx::off_thread(tag, job)`: the job runs on its own thread, off the runtime lock, with a handle to the core, and what it returns comes back to the screen that asked as `ScreenEvent.off_thread_done{tag, bytes}`. The shell carries none of it. While a turn runs the core routes each `AssistEvent` to the screens that opt in (`Screen::hears_assist`) as `ScreenEvent.assist`; `Handle::next_event` hands them to the runtime and on to the shell, which ignores them.
- **`Ctx::post(name, event)` is the one way a screen reaches another**, services included: it delivers the event to every open instance registered under that name, after the current update and in the same re-render; an instance cannot post to itself. Photos' picker with purpose `attach` returns its pick to the chat this way, a service tells Home what the shelf holds, and the Backup screen wakes the pass service.
- **The model files are Rust's facts** (`chat/asset.rs`: URL, name, SHA-256, size) and ride the `ModelDownload` effect; the shell downloads and verifies, then reports `ChatEvent.download_progress` / `download_finished`. The library photo is `PickLibraryPhoto` (the system picker, HEIC converted, a thumbnail written by the shell). A confirm that seals a typed secret while Locker is shut asks `OwnerCheck` and opens the Locker session itself.
- **A reference to a row opens through one table**, [`shell/row_routes.rs`](../crates/screens/src/shell/row_routes.rs): chat cards and Home's search both use `row_routes::route`; a conversation opens as `chat.thread`.
- **A search's Ask** (`SearchAsk{scope, question}` in any view state) is handled by the shell as: select the `chat` tab, send `ChatEvent.asked{scope, question}` to its root instance.

## Testing

`centraid_screens::testing::Driver` goes through the door a shell uses: `start()`, `send(instance, event)`, `nav(..)`, `answer_effect(..)`, `pump(wait)` (the shell's event thread, for timers and change pushes), then assert on `driver.views`, `driver.effects`, `driver.navigation`. `crates/screens/tests/proof.rs` is the model; `Driver::keyed(runtime)` seeds a core with keys so sealed secrets can be written (`crates/screens/tests/locker_support`).

## Home, the band and the shell's facts

- **Home is the root of the `home` tab** (`home.springboard`, [`shell/`](../crates/screens/src/shell)); an app opens as a page pushed on that tab and back returns to Home. A tile and a search row carry the `Route` to push, so a shell never names a destination. The tabs are `home`, `chat` and `backup`, plus the hidden roots of the phone imports, which the band leaves out; the pass, custody and vault services are not tabs.
- **The band is `Navigation.band`** (`shell/band.rs`): Rust words it, lights the place the member is in, and draws only the places whose tab exists. A shell draws it under a tab's root and sends `NavSelectTab` for a press. The `SelectTab` effect is how a screen selects a tab: the runtime performs it itself and the shell hears the new `Navigation`.
- **The shell tells Home facts as events** (`HomeEvent`: the phone's scheme, the vaults and the backup line the shelf and the pass service hold, an outside entry such as a key slot or a system rationale link) and Home answers with routes and views. Home's `VaultCommand` effect (switch, make, restore, forget, rename) is performed by the vault service (`vault::service`) and never reaches a shell; `Open` stays the platform's. Home carries its own `first_launch` view while the phone holds no vault, and its `transfer_sheet` (the transfer rule), which writes the device-store key `transfer-rule` and asks `RuleChanged` of the pass conductor; the Backup screen does the same, with no native step.
- **The shell's reads are `load::shell::*`** (`catalog::load::shell::..`, the shell manifest above): `holdings`, `search`, `backup-status`, `files-followed`, the chat's history.

## Drawing

Rust holds every route stack; a shell mirrors the stack it is given and reports taps and pops.

- **iOS**: `Sources/Core.swift` (`actor Core`) is the Swift binding of the five symbols. `Sources/ShellModel.swift` opens the process's one core over the shelf directory (`{"shelf": dir}`) and reports the platform's facts. `Sources/ScreenStore.swift` holds navigation, views and the generic effect performers, and `Sources/RustScreenHost.swift` is the one place that maps `ViewState.kind` to a view. Platform work behind the effects (secret stores, the photo library, the stage door, the background windows and `URLSession`, the phone's contacts, calendars and folders) is listed in [mobile/README.md](../mobile/README.md#what-ios-performs).
- **Android**: `session/AppSession.kt` opens the process's one core over `filesDir` and its one `dev.centraid.core.Screens` (`mobile/core`), counted so an activity and a WorkManager window share it. `session/ShellEffects.kt` performs every effect that needs only a context, once, in the order asked per screen; `kit/ScreenEffects.kt` performs the ones that need the activity (a haptic, a prompt, a picker, the owner check, a scan, a sheet, a page pushed) while it is composed. `session/LibraryRoll.kt` answers the camera roll from MediaStore, `session/Stage.kt` is the streaming stage door, `session/ImportsRelay.kt` sends the imports' two facts, and `screens/RustRoot.kt` draws the route stack. `MainActivity` names no screen and no destination.
- Both draw by switching on `ViewState.kind`; no screen is named in Swift or Kotlin, and a route is whatever the row carries.

## Phone imports

[`crates/screens/src/imports`](../crates/screens/src/imports) holds three **headless services**: screens that are never drawn, opened once per foreground vault. A core is one vault (a vault switch is a new runtime), so each is the root of a hidden tab: the navigation root appends [`imports::roots()`](../crates/screens/src/imports/mod.rs) to its tabs (`imports-camera-roll`, `imports-files`, `imports-made`) and keeps them out of the band. Every decision is Rust's; the shell performs the effects below, **answers them in the order they were asked** (a cursor write is answered `EffectDone` and a later wait must not mistake it), and sends two events only.

**The shell sends** `ImportsCameraRollEvent.LibraryChanged` (the OS photo library changed while the app is on screen) and `ImportsMadeEvent.Made{reminders}` (a vault was just made; `reminders` is false on Android). **The shell draws** the `imports.made` line (`summary`, `open_label`, `open_route`). Everything else reaches the services by name (`Ctx::post`):

| Service | Decides | Reached by |
| --- | --- | --- |
| `imports.camera_roll` | the walk, the grant and its words, the per-vault cursor, what may cross which link, an edit beside its original, the derivatives, the bytes the core asks for again | Photos' home (`Requested{ASK_PERMISSION, IMPORT_NOW, READ_PERMISSION}`, and its view back to every open Photos home as `PhotosPermissionChanged` / `PhotosBackupChanged`); the pass service hands it `Walk` and the feed (`BytesNeeded`), and it posts `RollReported` back and asks `ImportFinished` of the conductor; `imports.made` asks `LibraryPermission{ask}` itself and its grant posts `ImportNow` to the roll |
| `imports.files` | a followed folder: what the vault knows, what to stage, what a file gone from a complete read becomes | the drive posts `FolderFollowed` / `FolderStopped` (the answers of Docs' `FollowFolder` / `StopFollowing`); the drive reads `shell.files-followed`; the service hears `Lifecycle` |
| `imports.made` | what a made vault brings in, as one line; it hosts People's `ContactsFollow` and Agenda's `CalendarFollow`, so what a made vault imports is followed from then on exactly as one imported from the app | `Made{reminders}` from the shell |

Effects (`screens.proto`, 1700-1899), each answered under the effect's `effect_id`:

- `LibraryPermission{ask}` → `LibraryPermissionRead`. `ask` false reads the grant and never prompts; `ask` true shows the OS prompt.
- `Keychain` holds the per-vault cursor `camera-roll.cursor.<vault>` as UTF-8 bytes.
- `RollPage{cursor, limit}` → `RollPaged`: assets after the cursor with their resources (`ORIGINAL`, `CAMERA_ORIGINAL`, `PAIRED_VIDEO`), each `after` cursor, the capture group and `changed_in_place`.
- `LinkRead` → `LinkReading{online, metered, platform_refused}`. The shell reports the link; the transfer rule is Rust's (`camera_roll::may_fetch`).
- `LibraryStage{ref, allow_network, changed_in_place, media_type, byte_size}` → `LibraryStaged`. The shell opens the resource and streams it through the stage door with `source = OS_LIBRARY` and the ref as `os_ref`, and answers the core's handle (`content_hash`, `byte_size`, `already_held`, `derivatives_held`) or `IN_CLOUD` / `GONE` / `FAILED`. With `changed_in_place` it first asks `library_assets` for the ref and answers `prior_asset_id` / `prior_content_hash`.
- `LibraryDerivatives{ref, for_hash, tiers}` → `EffectDone`: render those tiers as the platform draws them and stage each against the original (`for_hash`, `tier`).
- `LibraryDelete{items}` → `LibraryDeleted`: delete the named originals behind the system's own confirmation and answer the hashes that went. Rust runs the census, `releasable` and `released` flow around it; `Environment.library_deletes` says whether the platform can, and a phone that cannot is offered no "Free up space" row.
- `CameraRoll{OPEN_SETTINGS | MANAGE_SELECTION}` opens this app's page in Settings or iOS's limited-selection editor; the prompt and the walk are the camera roll's.
- `FoldersRead{origins}` → `FoldersListing` (a listing only; a folder with no access is left out; `complete` false for a partial listing; the install's `device_id`), then `StageFolderFile{origin, path, media_type}` → `FolderFileStaged{ok, content_hash, byte_size}` for each file the vault has not seen as stated.
- `RemindersRead{ask_permission}` → `RemindersSnapshot` of the **open** reminders (iOS EventKit).
- The calendar and contacts reads of a made vault are the apps' own (`CalendarRead`, `ContactsRead`, `PhoneWatch`, `Keychain`).
- The pass service's own effects: `ScheduleWindows` / `PassWindowDone`, `UploadsOp`, and `LongRun{start, title, channel_name}` (the notification's title and channel name, finished in the device's locale).

The shell keeps no list of followed folders beyond the access it holds to each (a security-scoped bookmark, a persisted tree URI) keyed by the origin Rust minted.
