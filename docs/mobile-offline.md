# Mobile offline data

Centraid's native Photos and Docs surfaces read the phone's own copy of the active vault. A vault is a world, so the vault a read draws from and the vault a write targets are the same one, and switching vaults IS the remount ([#996](https://github.com/srikanth235/centraid/issues/996) R12). The vault-free view assembled from every enrolled vault is superseded: it needed the mount plane, and the mount plane is gone.

Docs is back on the phone (rebuilt on the v12 handoff) and reads that same file. Its origin acts — scan, bulk upload, and offline pins — address the open vault, exactly as its reads do.

## The seat's read plane

The phone keeps one replica SQLite file per vault and opens exactly ONE of them — the active vault's ([#996](https://github.com/srikanth235/centraid/issues/996) R12). Every row a read returns is stamped with that vault's id, its label, and whether the current owner may write there.

The mount is keyed on the (gateway, vault) pair, so switching vaults IS the remount: the previous file's session closes and the chosen vault's opens. Nothing is evicted and nothing is capped — every vault the gateway granted is one tap away in the switcher, and a vault that is not open keeps its replica file untouched. Only revocation deletes bytes.

The multi-vault mount plane is gone with the questions it answered. There is no `ATTACH DATABASE` union, no cross-vault SHA dedupe, no source-badge collapse, no provenance ordering and no four-scope cap disclosure: one open file cannot produce two answers to "which vault is this from". A share is a projection into the audience's own vault ([#929](https://github.com/srikanth235/centraid/issues/929)), so the household case the plane was built for has no consumer left.

One number survives it, and only for the radio: `MAX_REPLICA_FEED_MOUNTS` in `packages/core/src/protocol/routes.ts` bounds the mounts one change-feed subscription carries, which is what keeps the phone's other replica files in step in the background. The gateway's multiplex route and the mobile background budget both read that one constant; neither re-declares it.

A bounded read costs what it returns. A read is an app's own statement-as-data page, run by the seat against its open file with the ordering and the window inside SQLite (`packages/client/src/replica/seat/paged-handler.ts`, `seat-page-reader.ts`). There is no JS re-sort and no silent fallback. The declarative read grammar and its compiler are superseded: an app handler's `queries/*.ts` runs the same statement on every seat and on the gateway over the vault's real tables ([#996](https://github.com/srikanth235/centraid/issues/996) R9, W4-D2).

## Bootstrap and freshness

Bootstrap is a file copy, not a walk ([#996](https://github.com/srikanth235/centraid/issues/996) R4). The seat downloads the gateway's `VACUUM INTO` snapshot — a compressed artifact whose strong ETag is a pure function of the log position it stands at — expands it, and tails the change log from the cursor the artifact carries. The windowed newest-first walk, its page-one preview and its shape catalog are superseded with the shaped store: there is no window to negotiate, because the seat receives the vault's own file.

The download is resumable across process death, and the resume is by BYTE RANGE (`packages/client/src/replica/seat/bootstrap.ts`). A resume asks for `bytes=N-` and pins the ETag, so "the same artifact" is a checkable claim: an artifact that moved underneath restarts at zero rather than splicing two files into one that gunzips to garbage. The seat also checks it has room for BOTH files — its current one, the staged artifact and the expanded new one — before the first byte, against the platform's own estimate, and refuses by name when it does not fit; discovering that halfway through would leave a phone with a corrupt seat and no space to repair it.

A phone whose cursor falls below the change log's collected floor cannot be caught up — the deltas are gone — so it re-bootstraps in full, and since [#883](https://github.com/srikanth235/centraid/issues/883) C6 it says so: the gateway's rebootstrap frame carries a closed verdict vocabulary plus the retention window it actually keeps, `packages/client/src/replica/rebootstrap-copy.ts` is the one place that turns a verdict into a member sentence, and the frame surfaces it. Retention pinning is implemented ([#1014](https://github.com/srikanth235/centraid/issues/1014) V1/T9): the seat-log door records each device's acknowledged `seq` into `access_device_secret.sync_cursor` with the time it asked, and the sweep's `pruneReplicaLog` holds the floor at or below the lowest cursor any device has moved inside `REPLICA_SEAT_HOLD_DAYS`. The bound is the other half of the pin — a phone that is lost, wiped or never opened again stops holding the log after it, and re-bootstraps once when it comes back. Compactable commit grouping remains open (#883 question 13).

**A gap is a batch that starts AHEAD of the cursor, and only that** ([#922](https://github.com/srikanth235/centraid/issues/922) E3). Two catch-up paths legitimately hold the same cursor at once — the bootstrap's convergence replay and the change feed's own sync — so the slower one arrives with a `from` the faster one has already passed. That batch skipped nothing: it OVERLAPS, and every change in it is an idempotent upsert or delete under the same server-version guard. The transport's mismatch classifier (`packages/client/src/replica/shell-transport.ts`) therefore raises `cursor-gap` only for `batch.from.seq > cursor_seq` (or a batch whose `to` precedes its `from`); protocol, schema-epoch and cursor-epoch mismatches are unchanged. Treating an overlap as a gap wiped the store and demanded a re-bootstrap that raced the same way — a loop, not a repair.

### The seat is stale: how to tell

Ask the two numbers, in this order, before anything else ([#1011](https://github.com/srikanth235/centraid/issues/1011)):

| Question | Where to read it |
| --- | --- |
| How far is the gateway? | `sqlite3 <vault dir>/vault.db 'SELECT commit_seq, floor_seq, epoch, schema_epoch, ddl_version FROM replica_meta'`, and `SELECT max(seq), count(*) FROM replica_log` |
| How far is the phone? | `seat_state` in `<app data container>/Library/Application Support/CentraidReplica/centraid-seat-*.sqlite3` — `applied_seq`, `applied_commit_seq`, `gateway_watermark`, `epoch`, `contents` (copy the file with its `-wal`) |

`applied_commit_seq` well below the gateway's `commit_seq` with `gateway_watermark 0` means **no log page has ever been applied** — the snapshot landed and nothing after it did. A `gateway_watermark` that matches while `applied_seq` lags means pages arrived and the applier refused them; a mismatched `epoch` or `schema_epoch` means a re-bootstrap is owed, not a catch-up.

Then ask whether the phone ever knocked. The gateway logs one line per seat door answer into its log ring ([logs.md](logs.md)):

- `seat log page for <vaultId>: since <seq>, <n> rows, next <seq>, watermark <seq>, hasMore <bool>`
- `seat snapshot for <vaultId>: seq <seq>, <bytes> bytes, GET|HEAD`

No `seat log page` lines at all means the phone is not asking, and the device console says why:

- `[centraid] replica: no gateway base — device=<bool>` — nothing resolved a gateway to ask.
- `[centraid] replica: pull did not land — blocked=<bool>[, reason=…]` — `blocked=true` is the member's own transfer rules (`never`); a `reason` is the catch-up's own failure, also kept on the session as `lastSyncError`.
- `[centraid] replica: seat catch-up failed — <error>` — the seat loop's failure, from the door or the applier.

A write this phone makes through a door that is not the session — the camera-roll Import stages and publishes on the gateway, which commits the rows — **nudges the seat once when the batch lands** (`kit/replica/seat-nudge.ts`, called by `runImportBatchWithNudge`), so the owner's own import appears in their library in seconds instead of waiting for the next foreground pull; a batch that published nothing asks for nothing, and this is a single catch-up, never a poll.

A catch-up refused because the mount believes it is offline **schedules a retry**; the connectivity oracle is never set from the pull's own verdict, which is how one transient failure used to latch a phone's copy shut for the life of the mount.

Pairing can grant several vaults through one short-lived ticket. The gateway redeems that ticket atomically, while the phone records one `VaultLink` and one replica lifecycle per returned vault. The first grant is only the initial focus; all other granted vaults remain independently mountable and retain their own cursor, freshness, intent outbox, and revocation state.

## Replica correctness and durability

The replica wire has five invariants that every client observes:

- A canonical SQLite write transaction gets one `commitId`. Delta pages extend through the end of that commit group, so a page boundary never exposes half of one transaction. Retention cutoffs use the same boundary rule. Under count pressure the log folds fully superseded commit groups into their survivors (each survivor inheriting the folded prior state) and does **not** move the resumable floor; only the age window and the residual count trim collect history.
- Projected changes carry the row's canonical `rowVersion` when it is nonzero; an omitted version means version zero. Local application ignores an older upsert or delete when a newer version is already stored, which makes overlapping bootstrap convergence and reconnect replay safe.
- Offline intents may carry `baseVersions`. The gateway compares those preconditions before dispatch and returns a structured conflict with expected and actual versions. The client retains the projected row, reason, and both versions until the member edits/retries or discards it.
- Every replicated column arrives whole. A seat holds `vault.db` itself ([#996](https://github.com/srikanth235/centraid/issues/996) R1), so nothing is stripped by size and nothing is fetched back on demand; what a seat does not hold is decided per table and per column by R3's private list, not per value. The per-value text ceilings and lazy/deferred fields of the shaped store — [#922](https://github.com/srikanth235/centraid/issues/922)'s SB-text — are superseded with it.
- `coverage` and `durability` are explicit status/result fields. A partial preview is readable and searchable, but it is labeled partial and is never treated as a completed cold start. The native seat has no memory fallback to fall back to: a replica that cannot open its durable database is an error, not an unremembered in-memory session.

Both seats keep one outbox contract, and since [#996](https://github.com/srikanth235/centraid/issues/996) it is one store: `SeatIntentStore` over the seat's own vault file (`packages/client/src/replica/seat/seat-intent-store.ts`), reached in process on the phone and through the worker's `outbox` op in the browser. The browser's IndexedDB outbox and the phone's second SQLite database beside the replica are superseded — the queue is a table in the same file as the rows it is about, which is what lets an executed answer clear its overlay in the transaction that carries its commit (R24). Executed intents use the existing settlement path, which removes input and journals the outcome. Denied/conflict/failed results instead use the existing atomic transition primitive to remain unsettled with their input and row projection. Edit/retry mints a fresh immutable intent id and payload hash, adds its projection first, then truthfully journals the old terminal result; an engine-private supersession marker lets startup finish that handoff if the process stops between those existing store operations. That marker never enters query validation: both seats share one presentation function that strips engine-private fields before applying the projected row. The presentation/revision clone follows the replica's JSON-shaped value grammar and does not require the browser-only `structuredClone` global; the native restart regression runs with that global absent to match Hermes. Revision identity also comes from the blueprint's declared edit-action projection, not by scanning arbitrary `*_id` inputs, so a child write may safely reference a pending parent. A filtered or limited read keeps its canonical page and adds only canonical row ids addressed by pending mutations before composition (`packages/client/src/replica/seat/read-overlay.ts`); one outbox row therefore cannot turn a bounded Home read into a vault-sized scan. Discard journals the last real non-executed result rather than inventing execution. Locker add/edit secrets are explicit online-only actions: browser inline, served, and native callers never present secret plaintext to a durable session. Ordinary non-secret Locker item actions remain outbox-visible through metadata-only row patches. Foreground and background catch-up follow `hasMore` with a bounded sequential loop; an interrupted loop resumes from the last committed cursor.

One gateway SSE connection multiplexes independent vault cursors. A frame never combines cursors or data across vaults. A frame is also the unit of cursor cost: both feeds coalesce a page's advances and debounce the durable cursor write by one second, flushing on background and teardown, so a thousand-change page costs one write and one freshness signal rather than a thousand of each. Foreground UI reports human states (`Offline on this phone`, `Gateway asleep`, `Syncing recent changes`, `Sync paused by transfer rules`, and `Updated …`) plus a timestamp for every source. Those states are learned from ANSWERS, never from configuration: `resolveGatewayBase()` only resolves an address, so a pass that has not yet asked the gateway anything may lower reachability and never raise it, and every gateway request runs under a time-to-first-byte deadline (`apps/mobile/src/lib/replica/gateway-deadline.ts`) because the tunnel listener keeps accepting after its peer is gone. The change feed and the write drain report each outcome, so a vault that dies under a still-connected phone is noticed without waiting for a radio event, and a vault that returns is picked up the same way. See [traps/unreachable-vault.md](traps/unreachable-vault.md). Revocation produces a scoped tombstone: the local cursor and rows for that vault are purged without affecting the other vaults this phone is enrolled in, and a durable member-facing notice is left behind because the purge takes every other trace with it (see below).

A restored device is treated as a cold start, not a resume. The replica databases live in the module-owned durable directory and never ride Auto Backup, device-to-device transfer, or an iCloud restore, but the SSE resume cursors and freshness stamps beside them are ordinary app storage. When a scope's replica file is absent or empty while its cached cursor and stamps are present, both are discarded before bootstrap, so the feed cannot resume at a sequence for rows this device never had. A first launch after pairing has no database and no cache either; that stays silent, because it is a cold start rather than a restore.

Freshness is stored independently per `(gateway, vault)` and advances only after that source successfully pulls or produces a cursor frame. Pulling rows is not moving bytes (#905 O): a foreground read obeys only the `never` floor, so a phone on cellular still pulls its deltas while the Wi-Fi-only/metered/roaming/charger rules keep governing blobs, the write drain and the unprompted background pass. Reads once shared `canTransfer()`, and since `wifiOnly` is the default a cellular phone pulled nothing at all — silently, which Home could not tell from an empty vault. A pull the `never` floor refuses is still neither a landed pull nor a sleeping gateway: nothing was asked, no stamp advances, and the phone says `Sync paused by transfer rules` instead of claiming freshness it never obtained. Offline startup restores those values rather than stamping every source with launch time. Scoped revocation purges that replica's rows and intents, removes its pinned thumbnail pack, and deletes only that scope from the cached mount/freshness manifests. It also closes the driver handle and deletes the replica SQLite file family — the main file plus its WAL, SHM, and rollback-journal sidecars — because an emptied database keeps its full size for a vault this phone may never see again; a vault that is merely not open is still enrolled and keeps its file. The revocation leaves one durable, dismissible audience notice behind (“No longer shared with you — {label} was removed from this phone”), surfaced through the status bar, because the purge takes every other trace with it. The headless background pass reclaims a revoked scope the same way the foreground does. Delivery of that notice is on reconnect, so the window a revoked phone stays dark is unbounded while it is off.

Coverage is the open vault's own: a file with no completed bootstrap is partial, and no other file can make it look complete. That coverage is read from durable status at mount and after every pull, and carried through the replica context into every query result, so an app killed mid-download and relaunched offline still labels its incomplete library partial — the in-process bootstrap that would have reported progress died with the old process.

Mobile reads `/centraid/_gateway/info` before constructing either foreground or background sessions. `seatReplica` — the snapshot and log-tail doors — must be advertised; the key is optional on the wire, and its absence is what a gateway older than the doors says, which reads as off. A missing or false flag produces one update wall instead of a phone that mounts and then finds no file to fetch. The judgment is asked fresh each time and is not cached: an offline start skips the probe entirely and fails open rather than replaying a remembered verdict, so a gateway that was upgraded — or downgraded — between launches is judged on what it answers now.

## Offline search

Search on the phone answers out of the seat's own file, and it has three lanes.

**Keyword (fts5) — exists.** The snapshot arrives with the gateway's fts5 shadow tables, and the bootstrap re-derives every one of them, found from `sqlite_schema` rather than a registry (`rebuildSeatFtsIndexes`, `packages/client/src/replica/seat/bootstrap.ts`). Coverage is therefore the gateway's `SPECS` (`packages/vault/src/schema/fts.ts`) exactly, with no phone-side index to drift from it — including the derivative-aware document body, so extracted OCR/scan text is searchable offline under `core.document` the same way it is on the gateway. `core.content_item` indexes the owned title alone on both planes.

**People and similar faces (sqlite-vec) — exists.** Face vectors replicate in `enrich_embedding`, and the phone ranks them with `vec_distance_cosine` under the row's own `dim` guard, the way `packages/vault/src/enrich/similarity.ts` does. The vector WIDTH is the gateway's to decide and the phone hard-codes none of it: whatever dimension replicates is what a query carries.

**Semantic (CLIP) — not in v0.** The phone does not run a text or image encoder and does not query semantic embeddings; a member's phone answers keyword and face queries offline and nothing else.

Both existing lanes depend on a native extension the build has to have compiled in, so `ExpoSeatDriver.open` probes both and refuses by name (`ReplicaFts5UnavailableError`, `ReplicaSqliteVecUnavailableError`) rather than letting a shell open and fail inside a member's search.

fts5 is compiled into the SQLite the app links, so it is simply there. sqlite-vec is not: `withSQLiteVecExtension: true` only puts the artifact in the bundle and publishes its path as expo-sqlite's `bundledExtensions["sqlite-vec"]`, and **every connection that wants `vec0` must load it itself** — `ExpoSeatDriver.open` does, once per handle, before it probes. A driver that skips the load gets `no such function: vec_version` from a build that is entirely correct, and the probe then condemns the shell ([#1011](https://github.com/srikanth235/centraid/issues/1011)).

### The sqlite-vec pins

The two planes are on different sqlite-vec versions, deliberately.

| Plane | Version | Pinned in |
| --- | --- | --- |
| Gateway | `0.1.9` | the `sqlite-vec` npm dependency in `packages/server/package.json`, loaded by `packages/server/src/enrich/sqlite-vec.ts` |
| Phone (Android) | `v0.1.7-alpha.2` | expo-sqlite `~57.0.2`'s bundled `android/vec/<abi>/vec.so` |
| Phone (iOS) | `v0.1.7-alpha.2` | `TAG` in `apps/mobile/scripts/build-sqlite-vec-ios.sh`, which builds `vec.xcframework` from source |

The phone's two artifacts must agree, and they are checked against one constant — `EXPECTED_SQLITE_VEC_VERSION` in `apps/mobile/src/lib/replica/sqlite-vec-version.ts` — at build time by `apps/mobile/scripts/sqlite-vec-version.test.mjs` and at open by the seat driver, which asks the extension that actually loaded for `vec_version()`. The gateway's version is not part of that agreement: the planes compare vectors, not extensions, and `vec_distance_cosine` over the same bytes at the same `dim` is the same answer on both. Raising the phone's pin moves a native artifact on both platforms and is a reported change, never a side effect.

## Offline changes and cross-vault placement

Ordinary writes stay in each replica's durable intent outbox. A first-open write made before any bootstrap is also admitted there: the action input is durable immediately, the write reports itself as saved-on-this-phone pending first sync (never a bare "waiting for a connection"), and its optimistic row projection is reconstructed from that durable input — when the first copy of the vault lands, and again on every relaunch, never held only in component state ([#883](https://github.com/srikanth235/centraid/issues/883) D1, restated by [#996](https://github.com/srikanth235/centraid/issues/996) R23). Add/Move uses a separate device outbox keyed by a durable link token. Reconciliation always:

1. commits or confirms the target projection;
2. records that target receipt in the gateway database;
3. for Move only, deletes the source item; and
4. records completion.

Replay is idempotent. A crash can leave a completed target and pending source removal, but cannot delete the source before the target exists. Queued changes may be cancelled. Permission denial, terminal failure, and parked retries remain visible until dismissed.

### The phone renders the display rungs the gateway cannot decode

Both device ingress paths — the upload queue and the first-run camera-roll **Import** — contribute the preview ladder's `thumb` and `preview` rungs, plus `phash` and `thumbhash`, from bytes the phone decoded itself. For HEIC/HEIF that is not an optimisation but the only source: the gateway's preview codec is sharp, and the `@img/sharp-libvips-darwin-arm64` build this repo pins ships libheif **without an HEVC decoder** (HEVC patent licensing), so the HEIC an iPhone actually captures declines on the gateway and earns the durable `preview-codec@1` "unsupported" stamp that makes recognition skip it ([#1011](https://github.com/srikanth235/centraid/issues/1011)). iOS decodes it natively.

The rungs go through the ledger's variant door (`POST /centraid/_vault/blobs?variant=…&variant_of=<sha>`), at the ladder's own edges — imported from `@centraid/core/blob`, never mirrored — fitted to the long side and never upscaled. **Order is the contract**: `variant_of` must identify staged or claimed content, so Import stages the original, contributes the rungs, and only then publishes; a rung on the row before the claim means recognition never sees the asset without one. A rung that fails to render or contribute is never fatal — the item stays exactly as backfillable as it was. See [the derived ledger](photos/derived-ledger.md).

### An absent writability answer is not a refusal

A row on the phone says which vault it came from and whether the member may write there (`kit/replica/row-provenance.ts`). **A row with no such stamp is writable**: a locally projected pending row, a camera-roll photograph that is not in the vault yet, and a session whose scope has not landed all carry no answer, and none of them is the vault saying no. Only an explicit `canWrite: false` — the scope the gateway actually answered for a container the member may only read — draws the read-only sentence. Photos' timeline stamped its rows the other way round until [#1011](https://github.com/srikanth235/centraid/issues/1011): a camera-roll row carried no answer at all and a replica row defaulted an unknown scope to `false`, so the owner's own vault rendered every lightbox as read-only.

### A re-bootstrap keeps the queue, and holds it

A re-bootstrap replaces what the gateway gave this seat. The queued intents, their order and the bytes they need are the three things the gateway has never heard of, so they survive it: the outbox is its own table in the shared file, `created_order` is carried verbatim (renumbering the queue would reorder the member's work), and the overlay is rebuilt from that outbox rather than from component state.

While the repair runs, a write is **admitted and held** ([#996](https://github.com/srikanth235/centraid/issues/996) R23): refusing would make "saved" untrue during a repair nobody asked for and nobody can see, and sending would let an outcome be reconciled against a copy that is about to be replaced. The member is told the change is saved and will send after; the drain resumes from the outbox the moment the new copy is in place.

Bytes a queued intent still needs are not evictable (R25). The seat publishes the content ids its unsettled outbox names to the offline byte store on every move of the queue, and the LRU sweep reads that answer alongside the pins — so the one copy of what a pending write is waiting on cannot be deleted to make room for a cache. A closed seat withdraws its answer; nothing is inferred from a filename.

### Shared-container writes and cursors

A shared container is not a special borrowed scope. Its domain rows and blobs are real residents of each joined member vault, so the ordinary per-vault replica, backup, search, and attachment paths cover them. The phone still has exactly one physical replica cursor for that vault even when the vault subscribes to many shapes.

Offline writes into a shared container use the ordinary durable replica outbox — the same one every other write uses ([#929](https://github.com/srikanth235/centraid/issues/929) retired the separate `share_commons_intent` rail). What travels is a **signed replica intent** the ORIGIN executes: the phone's vault signs the canonical envelope, the origin verifies it and invokes, and the receipt names the member. The pending row is an honest UI overlay, not an optimistic domain record; when it parks it carries a structured `waitingOn` of kind `owner`, `origin` or `gateway` with the label from the link, so the phone can say who it is waiting for in the same words the web seat uses. Revoking the share settles that shape's queued intents as `expired` with "no longer shared with you".

Minting a share is not one of those offline writes. `tally.group` is v1's one edit-capable subject, so the phone's single producer is the share row on a Tally group: it opens the share sheet when the gateway is reachable and WITHHOLDS the verb with its own sentence when it is not — an unreachable gateway is a different screen from a refused grant, and neither is an empty ledger.

`share_subscription.cursor_seq`, keyed `(shape_id, audience_vault_id)`, is how far this vault has ingested one shape, alongside the physical replica cursor. Ten shared Tally groups in one vault therefore mean one vault cursor plus ten shape cursors, not eleven sync engines. The vault cursor transports the resulting row changes; each origin orders its own shape independently. A late join or a restore starts from a bootstrap at the origin's current epoch and follows changes from there; a changed `cursor_epoch` is a re-bootstrap, never a silently extended floor.

### The chain, and where its numbers come from

Five changes made offline against one row execute in order, once each, when the radio returns ([#996](https://github.com/srikanth235/centraid/issues/996) R23). The edges are derived on the seat from what the outbox minted, the held dependents say "Waiting on an earlier change" rather than "failed", and a conflict raised by a second writer stops the head of the chain with both versions on the row and Retry/Discard beside it.

Four intervals of that arc are measured on node against the production session and a real file — `mobile/durable-save`, `mobile/pending-render`, `mobile/restart-recovery` and `mobile/reconnect-drain` in `tests/journeys.json`, all at `none/ci-linux-x64-4c`. Every one is a LOWER BOUND on the phone: no network RTT, no flash, no render. The phone's own numbers are the `device-fixture/ci-android-emu` rows, which are `unmeasured` and name the Android airplane flow as their probe.

## Background work and push privacy

The Expo background task maps to BGTaskScheduler on iOS and WorkManager on Android. It runs the same pull, intent, placement, and upload queues as the foreground and calls the same metered/battery upload policy. Platform timing is opportunistic; correctness always comes from the durable outboxes and the next foreground pull.

One pass owns a fixed 20 s budget (iOS grants a background refresh task about 30 s; the remainder is teardown headroom), checked between stages and also driven by the platform's own expiration listener. A pass that runs out of budget stops at a stage boundary instead of being killed mid-stage, and reports what it managed. Scopes are isolated from each other: one scope whose pull or bootstrap fails never cancels the remaining scopes, and the device outboxes — placements, then uploads — still drain afterwards, because their rows are durable and target their own vault. The pass also asks the platform for the real connectivity answer rather than assuming a radio, and it reclaims a revoked scope's files exactly as the foreground does.

Registration is observable rather than assumed. Whether the background task and the push task registered, why one refused, and the platform's own availability verdict are recorded durably and rendered on the storage screen, so “Background App Refresh is off” is a sentence the member can read instead of a sync that silently never runs.

The active vault is ordered before the other cached scopes before the background feed's mount bound is applied. Upload rows persist that target vault, and headless reconciliation replays the canonical follow-up through the session it holds open; transferred bytes therefore cannot settle without their app mutation merely because the app was backgrounded.

The pass is also where diagnostics traces land. Spans (#927) buffer in a bounded in-memory ring while the app runs — a phone doing disk I/O on a scroll is exactly the cost the traces exist to find — and are written to `<replicaStorage>/diagnostics/traces.jsonl` in the pass's `finally`, so a pass that timed out still lands what it recorded. The write swallows its own failures and the ring is dropped if the OS kills the app first: a diagnostics buffer, not evidence. Tracing is OFF unless `EXPO_PUBLIC_CENTRAID_TRACE=1`; the work counters underneath are always on and are integers. See [logs.md](logs.md).

The gateway push relay is wake-only. Its payload contains no vault id, item id, title, content, cursor, or owner data. Push delivery can make a background pull happen earlier, but loss or throttling cannot lose data. iOS background push is therefore treated as an optimization, in line with Expo's delivery guidance.

## Thumbnail packs and budgets

Each source gets a pinned thumbnail pack containing the recent 90 days plus favorites, with an independent 128 MiB budget and oldest-first eviction. Displayed rows prefer those local pixels. One source cannot evict another source's offline pack. The Phone storage screen reports, per vault:

- replica database bytes;
- pinned thumbnail bytes; and
- pending upload bytes.

Database bytes mean the complete live SQLite family: the main file plus WAL, SHM, or rollback-journal sidecars. Pending bytes come from each upload row's durable target vault, never from whichever Space happens to be focused when the screen opens. Legacy pre-target rows are reported honestly as unassigned instead of being fabricated into a vault total. Tapping a vault total expands its database, thumbnail, and pending-upload components.

Per-vault cards reach only the open vault, so the screen adds an `Other Centraid data on this phone` section for what they cannot see: the upload queue's own database family, and replica databases on disk that no open vault claims (an unopened or revoked vault's files, plus any near-empty reader host database left behind by the superseded mount plane, which the screen has no gateway id to name separately). That section reports; it never deletes.

Neither the screen nor the budget check may cost the size of what it measures. Pending bytes, counts, and the unassigned bucket come from one `GROUP BY target_vault_id` aggregate over the upload queue rather than from its rows; queue rows are read in bounded pages with a `created_order` keyset cursor, which is also how one upload drain pass walks a deep backlog. Pack totals come from the native module's single-crossing `directorySize`, and eviction pays for a per-file listing only once that total says a source is over budget. Pack downloads take the same durable transfer policy as uploads — Wi-Fi-only, metered, roaming, and charger rules govern thumbnail bytes exactly as they govern originals.

`Free thumbnail cache` removes only reproducible thumbnails. Replica rows and pending changes are not cache and are never removed by that action.

Low disk fails closed and preserves the last readable projection, and it does so mid-session rather than only at start-up. op-sqlite's `SQLITE_FULL`/errcode 13 and OS `ENOSPC` variants are normalized into one actionable screen error wherever they surface. A delta that cannot be applied for want of room PARKS the change feed: the one-second retry cadence stops instead of re-applying the same failing batch forever, the cursor and rows stay exactly as they were, a later feed frame does not restart the loop, and the surface says the phone is out of room. Freeing space resumes the parked feed from its durable cursor. Replica rows and pending intents remain untouched throughout, and the person can free the reproducible thumbnail cache or other phone storage before retrying. Centraid never evicts canonical replica rows or queued writes to manufacture free space. The device contract test pins that classification and copy; the vault custody test fault-injects the same SQLite-full condition during `wal_checkpoint(TRUNCATE)` and requires the gateway disk-health tracker to turn red.

## Durable path and at-rest decision

Replica databases, pending intents, upload queues, and thumbnail packs live in a native module-owned durable directory:

- iOS: `Application Support/CentraidReplica`, excluded from iCloud backup and protected with `completeUntilFirstUserAuthentication`;
- Android: credential-encrypted `noBackupFilesDir/CentraidReplica`. The app excludes ALL of its data from Auto Backup and device-to-device transfer, not just this path: the manifest sets `allowBackup="false"` with backup and data-extraction rules that exclude every domain (cloud and device transfer alike). `android/` is generated ([#996](https://github.com/srikanth235/centraid/issues/996)), so config is the only source: `app.config.ts` sets `android.allowBackup`, and `apps/mobile/plugins/withCentraidAndroidPrivacy.cjs` writes the two rule files and points the manifest at them in place of the narrower `@xml/secure_store_*` pair expo-secure-store would otherwise leave there. The AsyncStorage backend moves with a build flag, so a path-level exclude would be the fragile version of this rule.

These files survive OS cache eviction and disappear on uninstall. Centraid does not add SQLCipher or field encryption to the local projection in this version. That decision preserves the seat's own SQLite/FTS read plane and the cold/search budgets, while relying on iOS Data Protection and Android credential encryption for at-rest protection. Phone at-rest encryption is expo-sqlite's `useSQLCipher` flag ([#996](https://github.com/srikanth235/centraid/issues/996) R14), and desktop and web file encryption is a later driver swap over the same file format. The seat's copy is backup-excluded and contains no blob originals; a future stronger app-layer scheme must preserve seat-local search and publish measured cold/search costs before replacing this decision.

An optional biometric app lock adds a user-presence layer before the seat's file is opened. Its gate is stored with SecureStore `requireAuthentication`; moving the app out of the foreground clears the decrypted credential cache, unmounts replica sessions, and paints an opaque switcher mask. This complements the OS at-rest controls above—it does not turn the replica into an independently encrypted database.

Locker is stricter than the ordinary replica plane in ONE direction: the secret half. The browsable half is not. `locker.item` visibility is not a grant question at all — listing an item is not unlocking it, and since [#996](https://github.com/srikanth235/centraid/issues/996) wave 6 (W6-D2) the unlock boundary is the shell's, which holds the vault's key `K` and hands an app one row's plaintext per receipt through `window.centraid.locker.reveal`. The permit tier, the `authenticate` op and the gateway's Locker reveal arm are deleted with it ([#928](https://github.com/srikanth235/centraid/issues/928) AP-locker-boundary superseded). So the window, the archived and trash shelves and the search run the app's own `packages/blueprints/apps/locker/queries/{items,search,trash}.ts` against the seat's own file, through `apps/mobile/src/apps/locker/locker-reads.ts`. No sealed column can ride those rows: `packages/vault/src/replica/locker-sealed-columns.test.ts` asserts every sealed column of every sealed entity is structurally unavailable to the replica lane, by name rather than blanked. The Watchtower decoration (weak/reused/last4) is derived inside the sealed boundary, so a local read asks for it as an `optional` invocation and answers UNDECORATED when it cannot be reached: the two row keys and the payload's `watchtower` summary are then ABSENT, and `review-model.ts`'s register says those checks did not run rather than clearing every password. `apps/mobile/src/apps/locker/locker-airplane.test.ts` holds the three reads with every `lib/gateway` door throwing, and `tests/integration-mobile/locker-rows-parity.integration.test.ts` holds the phone and the web seat to identical payloads over the same rows. The seat still boots locked and drops its rows on a lock — a locker that drew its own list behind its lock screen has not locked anything — and unlocking remains online.

Its native cover performs authentication and reveal through online-only app queries, and its two secret-bearing WRITES take an online-only transport door of their own: `NativeWriteInput.onlineOnly` posts the action straight to the app's handler and never enqueues, mirroring the browser bridge's `opts.onlineOnly`. A gateway it cannot reach is a failure, never a queued row — falling back to the outbox is exactly what the flag forbids. The action list is `packages/blueprints/apps/locker/writes.ts`'s `ONLINE_ONLY_ACTIONS`; `apps/mobile/src/lib/replica/locker-online-only.test.ts` pins the seat's half. Passphrases, biometric device secrets, memory-session tokens, one-shot item permits, and revealed fields never enter replica rows or durable intents. The local biometric secret is random, device-only SecureStore material; only a vault-key-peppered verifier reaches the gateway database. Locker's memory-only session lives in one process-level store (`apps/mobile/src/apps/locker/locker-store.ts`) rather than a React context, so no remount can reconstruct a session the boundary ended.

Tally is ordinary in both directions now — its writes queue and its derived reads run locally. Every Tally act carries an optimistic pending projection (`packages/blueprints/apps/tally/pending-projection.ts`), so the native cover issues all of them through `session.write` and they queue in the durable outbox when the gateway is out of reach — that is what "record-only and fully offline-capable" means on a phone. The one exception is `materialize-recurring-expense`, whose occurrence id is minted by the canonical recurrence engine: the projection excludes it by construction, so the seat WITHHOLDS the verb while offline rather than queueing a copy of an expense nobody issued. Reads run the app's ONE balance engine ON THE PHONE: `apps/mobile/src/apps/tally/tally-reads.ts` imports the seven `packages/blueprints/apps/tally/queries/*.ts` modules the web seat imports and runs them against the seat's own file through `apps/mobile/src/lib/replica/inline-query-ctx.native.ts`. There is still exactly one derivation of "who owes whom"; it simply no longer needs a network to reach it, so a member on a plane sees complete balances rather than a spinner. A refused read and a seat with no copy yet are different screens, and `apps/mobile/src/apps/tally/tally-store.test.ts` pins that a failed read never reads as an empty ledger.

**That read carve-out is gone.** SB-tally ([#922](https://github.com/srikanth235/centraid/issues/922)) reverted it in wave 4 (E7): the phone runs the same `queries/*.ts` modules the web seat runs, over the same rows, and `tests/integration-mobile/tally-balance-parity.integration.test.ts` holds the two seats to the identical dashboard. The seat's `__centraid*` provenance is stripped before a handler sees a row, so neither seat's payload carries the other's bookkeeping. Tally's ten-minute stale clock went with the RPCs — a read of this device's own replica is as current as the device is, and a replica behind the vault is the frame's own line, not a verdict about the ledger. See [decisions.md](decisions.md#snappier-blueprint-apps-922).

## Performance guardrails

The ceilings below are the current contract; the measurements under them were taken against the superseded shaped store and are kept as the provenance of the numbers, not as a description of how a read works now. `tests/journeys.json` is the enforced ledger either way.

The checked 50,000-row fixture spans 2016–2025 across four household sources. Its current pending-write variant adds 200 durable SQLite outbox mutations (50 per vault) before starting either timer. On the 2026-08-11 macOS arm64 development host it measured a 778.4 ms cold 5,000-row merged/sorted read, a 4.5 ms FTS lookup, and 22,622,208 projection bytes. At that observed density the 5,000-row bootstrap window is 2,262,221 bytes. The browser perf lane separately opens IndexedDB, enqueues 200 intents, and budgets their full overlay enumeration/composition at one tenth of its registered 2,500 ms real-I/O ceiling. The same native evidence lane encodes twelve reproducible 256px/82%-quality thumbnail samples: the 13,726-byte p95 projects a 12,820,084-byte recent-90-day plus 5%-favorite pack for each 12,500-item source, within its 128 MiB ceiling. The lane enforces the 1,000 ms cold, 100 ms search, 4 MiB bootstrap-page, and 128 MiB thumbnail ceilings; `tests/journeys.json` records the volume, probe, observation, and headroom. Native build/install/launch checks prove the modules load on both platforms; the Android mobile journey owns the airplane-mode UI/process proof, with the rendered SQLite restart companion — `apps/mobile/src/apps/tally/PendingRestartJourney.test.tsx`, which drives the Tally cover through a real process restart over the same production reader — covering it on iOS-compatible infrastructure.

### Where 50,000 rows came from, and where it stops (#659)

50,000 is a measured fixture, not a product ceiling. A household that keeps a phone camera for a decade plausibly reaches 90,000 items by year three of using Centraid, so the envelope has to say what happens there rather than imply the number cannot be exceeded.

Scaling the 2026-07-29 measurement linearly — a projection from that run, **not** a new measurement — a 90,000-row set is about 39.9 MB and about 1,013 ms of cold read. That was over the 1,000 ms ceiling, and it was over it for a structural reason since removed: the reader answered every request by selecting every row of the entity, parsing each JSON payload in JavaScript, and only then applying the caller's filters and limit. Cost tracked the size of the library instead of the size of the answer.

Two changes retired that shape. #659 pushed the filters and the limit into SQLite and ran the statement off the JS thread; [#996](https://github.com/srikanth235/centraid/issues/996) removed the JSON payload the parse was for — a seat reads the vault's own typed columns. What that leaves as the envelope:

- **A bounded read costs what it returns.** A filtered lookup and a keyed fetch do not scale with the library, so they hold at 90,000 rows and beyond.
- **An unbounded read still costs the whole entity.** Photos deliberately reads its full asset set to merge the camera roll against it. That path scales linearly and is the one that leaves the 1,000 ms budget somewhere between 50,000 and 90,000 rows on the reference host.
- **The cross-source page refusal is superseded.** [#883](https://github.com/srikanth235/centraid/issues/883) D1 exempted content-hashed entities from the pushed limit because equal bytes in two attached vaults collapsed into one badge-carrying row. One open file cannot produce two answers to "which vault is this from" (R12), so the case it guarded no longer exists.

**What an ordered read costs** ([#996](https://github.com/srikanth235/centraid/issues/996) W5). A seat holds the vault's own file, so an ordered read is a keyset statement over the canonical table and its ordering is served by a composite index stated in the baseline DDL — `(equality predicate columns, sort column, primary key)`, in `packages/vault/src/schema/read-path-indexes.ts`. The plan snapshot in `packages/server/src/serve/app-query-plans.snapshot.md` is the assertion: it went from 36 `USE TEMP B-TREE FOR ORDER BY` steps to 0 when those indexes landed, and it is regenerated with the schema. **What this replaced:** the shaped store kept two EXPRESSION indexes per ordered column over `replica_row` — `replica_row_ord_*` and `replica_row_cen_*` over a fixed 0–5 `censusClass` ladder — with a census probe per guard, a per-session `ORDER_INDEX_MAX` cap, and a spelling rule that made a renamed helper silently un-index a read. The census, the ladder and the cap are gone with `replica_row`; a stated index over a real column has no second spelling to drift from.

**No read truncates silently, on any seat** ([#922](https://github.com/srikanth235/centraid/issues/922) 0a), and since [#996](https://github.com/srikanth235/centraid/issues/996) wave 4 no app read leaves its window unspoken at all:

- Every screen read is a page a handler wrote. A read that is a whole set walks it (`readPages` in `apps/mobile/src/kit/hooks/useSeatPages.ts`) and THROWS at its stated fan-out bound, so a set that turned out to be unbounded is a failure naming the handler rather than a short list that reads as a complete one. A read that is genuinely a window takes `useSeatWindow`, which names its own size.
- The page fetches `limit + 1`. The probe row never reaches a caller; it is what tells a window that FILLED apart from a set that merely ends there, which a row count alone cannot. It costs exactly one row per read.
- A page that hid rows carries `truncated: true` and `appliedLimit` on the read result, and the kit turns that into one status line — `Showing the newest 1,000; more not loaded` (`truncatedListNotice`, `packages/blueprints/apps/_shared/shared-copy.ts`), said the same way on the phone and on the web.
- `truncated` is not `coverage`. Coverage is how much of the library this device holds; truncation is what this read's window did. A fully bootstrapped phone still truncates a 5,000-contact roster at 1,000.
- **The `acceptTruncation` flag and `ctx.vault.read` are superseded, and a grep keeps them gone.** The flag meant "give me the default window", which nobody chose and no screen said out loud; both words now fail a tripwire over the two trees an app's reads live in (`packages/blueprints/src/paged-read-tripwire.test.ts`, `apps/mobile/src/kit/hooks/replica-read-windows.test.ts`), including in a comment. The generic read survives on the gateway for automations and the server's own callers under `GATEWAY_DEFAULT_READ_ROWS` — a different door with a different caller.

The honest ceiling today is therefore: **bounded reads are unbounded in library size; the full-projection Photos read is measured to 50,000 rows and projected to leave budget near 90,000.** Closing that gap means giving the timeline a windowed read rather than raising the number here. Storage scales without a cliff — projection bytes are linear, and the per-source 128 MiB thumbnail budget is unchanged because the pack is a 90-day-plus-favorites window, not a fraction of the library.

- merged cold view: under 1 second after page one is locally available;
- local search: under 100 ms over the open vault's FTS tables;
- scrolling: reads bounded by the query, not by the library, and no 10k truncation;
- newest-first bootstrap page: 5,000 rows;
- FTS results: 1,000;
- pinned thumbnails: 128 MiB per source;
- measured library: 50,000 rows; projected budget edge for a full-projection read: ~90,000 rows.

Device/simulator runs remain the release evidence for 60 fps and the end-to-end time budgets; unit tests pin query behavior, provenance dedupe, cursor convergence, and outbox durability.
