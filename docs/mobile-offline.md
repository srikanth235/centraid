# Mobile offline data

> **What is current, and what is a record.** The phone is the vault ([#1029](https://github.com/srikanth235/centraid/issues/1029)) and its backup is the plane [#1080](https://github.com/srikanth235/centraid/issues/1080) rebuilt: everything above the rule below is current — where the phone's files live, what a pass does in the foreground and the background, the member's transfer rule, the phone's disk, and what Centraid may tell a member per app state. Everything below the rule is the design of the **seat plane** that #1029 deleted — a replica per device, its log tail, its outbox and its bootstrap, with the `crates/seat` and `crates/seat-link` it described — kept as that record because older documents link into it. Nothing below the rule describes the product. How the phone's screens read is [mobile/README.md](../mobile/README.md#the-kit-the-app-queries-and-adding-an-app-screen).

**The phone works offline because there is nothing to be offline from.** It holds `vault.db` and is its only writer; every read and every write is local, and no screen waits on a network. What needs a network is the **backup**: sealed copies of the vault and of every original and derivative it knows, uploaded to the gateways the member paired, by a **pass** that the shell runs in the foreground and in the windows the platform grants ([docs/gateway.md](gateway.md), [docs/recovery/backup-restore.md](recovery/backup-restore.md)).

## Durable path and at-rest decision

A device's vault files live in the app's own data directory — Android's `filesDir`, iOS's Documents directory (`ShellModel.vaultDirectory`) — and the directory is the roster: every `<name>/vault.db` in it is a vault this device holds, one directory per vault so each has its own backup home ([R-1047-E8](decisions.md#the-24-words-on-the-phone-1047-e1)); a new one is founded in `centraid-vault-<random>/vault.db` (`Shelf`, `mobile/shared/.../shell/Shelf.kt`). Beside each `vault.db`:

| Path | What it holds | Lose it and |
| --- | --- | --- |
| `vault.bytes/` | The content store: files named by their BLAKE3 — every derivative, and every original with no home in the operating system's library (an edit, a document, a download, an original fetched back from a gateway) | the originals only it held are gone unless a gateway confirmed them |
| `vault.backup.db` | The **ledger**: the paired gateways (addresses, pinned certificate, token, epoch), the queue of parts to move, every name each gateway confirmed, the snapshots this phone took, and where each content hash's bytes are on this phone — the operating system's library, the content store, or nowhere | the phone pairs again and reconciles; nothing a gateway holds is lost |
| `vault.spool/` | **Sealed parts waiting to move**, one file per name, at most 2 GiB or a tenth of the free space, whichever is smaller | the next pass seals again |
| `vault.keep-originals.json` | The albums kept out of **Free up space** ([R-1029-PH-2](decisions.md#photos-kept-originals-and-freeing-space-1029)) | every album reads as not kept |

**The phone does not copy its photo library in.** A photograph or a video in the operating system's library is read where it lives and streamed once through hash and seal into the spool; the ledger records that its bytes are the library's, and the grid draws its thumbnail from the content store ([R-1080-6](decisions.md#backups-from-first-principles-1080)). An original larger than the room the spool has is hashed on that first read and sealed on later ones, a window of parts per read, under the names the first read made known ([R-1080-C39](decisions.md#the-phone-core-and-the-cut-over-1080-lane-c)): one more read per window, instead of an original that never backs up.

The ledger, the spool and the keep list are **device-local and derived, never inside the vault**: a snapshot of the vault never carries the state of its own upload, and a restored phone must not inherit a dead phone's facts about its own disk. Android excludes all of the app's data from Auto Backup and device-to-device transfer (`android:allowBackup="false"` plus the data-extraction rules in `mobile/androidApp/src/main/AndroidManifest.xml`); iOS excludes every vault-derived path from the OS backup by name, because exclusion does not inherit ([R-1029-8](decisions.md#the-phone-is-the-vault--v0-1029-ruled-2026-09-21)).

These files survive OS cache eviction and disappear on uninstall. Centraid does not add SQLCipher or field encryption to the vault file beyond its declared sealed columns: that keeps the phone's own SQLite/FTS read plane and its cold/search budgets, and relies on the platform's at-rest encryption. A future stronger scheme must preserve on-device search and publish measured costs before replacing this decision.

Locker is stricter in ONE direction: the secret half. The phone is the unlock boundary and the only place the vault's Locker key becomes plaintext ([`crates/core/src/locker`](../crates/core/src/locker/mod.rs)), behind the phone's own biometric or passcode ([D-5](decisions.md#the-owners-rulings-of-2026-09-25-1047)); in the file a secret value is `lk1:` ciphertext under `K` ([ARCHITECTURE.md](../ARCHITECTURE.md#at-rest-formats)).

## Background work and push privacy

### The pass

**One mechanism backs a vault up: the pass** — `drain` in the core, `DrainPass` and `ShelfDrain.run(deadlineMs, reason)` in the shared module. It runs in three steps, each one durable before the next, so a pass cut off at any point resumes from the ledger and the spool rather than from the beginning:

1. **Prepare.** Take a snapshot if one is due — hourly while a gateway is reachable on an unmetered link, and whenever the pass's reason wants one (**Back up now**, the app leaving the screen, a restore that just finished) — then ask `exists` and seal into the spool only what no gateway has confirmed: the snapshot's changed ranges and its manifest, and every original and derivative the vault knows by hash, newest first, under the member's rule and up to the spool's budget. The core seals what its own store holds; for an original that lives in the operating system's library it answers `need_bytes`, and the shell streams those bytes through the stage door, which hashes and seals in the same stream. The hash of an item a pass asks for is already known, so the pass plans which of its parts the spool has room for — every item that fits whole, then as many parts of the first larger one as the rest leave — and the stage door seals those under their names, keeping them only if what streamed hashes to the item; a read of an item edited since its first is dropped. A pass that moved a window asks for the next one before it answers.
2. **Move.** Upload the spool to the preferred reachable gateway — the LAN one when home — checking the deadline between parts. Android moves every part inside the pass. iOS moves what it can while the app is alive and **hands the rest to the system's background `URLSession`**: `handoff` gives the shell a batch of spool files with their URLs and headers, the operating system uploads them while the app is suspended, and each part carries whether it may cross a metered link, so the member's rule holds for uploads the OS runs on its own ([R-1080-2](decisions.md#backups-from-first-principles-1080)). Before a batch is handed off the shell asks `reconcile`, and nothing is handed to a gateway that did not answer.
3. **Settle.** Record each acknowledgement in the ledger, delete its spool file, and move the gateway's head once every range of the newest snapshot is confirmed. On iOS each finished upload is reported back through `settle`, from the delegate the system relaunches the app into.

A pass stops for one of a small set of reasons, and **`DEADLINE` is not an error and does not say so**: a window that ran out with bytes left is the ordinary case for a first backup of a camera roll, and a phone that reported it as a failure would train members to distrust a product that is working. `UNREACHABLE` is a gateway that did not answer; nothing is lost and the next pass resumes. `UNTRUSTED` is a machine at the gateway's address that is not the pinned gateway: the pass stops, takes nothing from it, and the status says so rather than calling the gateway absent. `MOVED` is a vault another phone claimed: this one freezes read-only. The member-facing sentences for each are `DrainCopy`'s ([`mobile/shared/.../sync/DrainCopy.kt`](../mobile/shared/src/commonMain/kotlin/dev/centraid/shared/sync/DrainCopy.kt)), not sentences this document re-spells.

**Acknowledgement is the `PUT`'s success** ([R-1080-7](decisions.md#backups-from-first-principles-1080)), and the ledger is reconciled against every gateway's `exists` answer on every launch, so it is a cache of the gateways' truth and cannot drift. The backup line on Home and the Backup screen read the core's backup status — when the last snapshot was taken, when a gateway last acknowledged the head, how many content items are confirmed of how many, and what waits and why — and **never say more than a gateway acknowledged** ([`BackupLines`](../mobile/shared/src/commonMain/kotlin/dev/centraid/shared/sync/BackupLines.kt)).

**When a pass runs.** Every pass names its reason (`WakeReason`): the session opening, the app becoming active, a commit or a camera-roll import (debounced), the link changing, a window the operating system granted, **Back up now**, the app leaving the screen, and a restore finishing; the last three force a snapshot. A foreground pass survives backgrounding by finishing its current part under the platform's grace. The background windows are registered at launch on both platforms — iOS's processing task asks for external power and a network, and is asked for again at every background entry and after every pass; Android's are periodic WorkManager windows under constraints derived from the member's rule, one on a charger and an unmetered link for the long work, and an expedited one-off after a capture ([`BackgroundWindows`](../mobile/shared/src/commonMain/kotlin/dev/centraid/shared/sync/BackgroundWindows.kt)). Platform timing is opportunistic; correctness comes from the ledger and the spool.

### The member's transfer rule

**The member's transfer rule is the pass's input, and it is the member's own** ([D-1025-S7-60](decisions.md#slice-s4s5--the-members-transfer-rule-and-fetch-this-one-now-1025)). The gateway does not know which SIM is in the phone, whether the member is abroad or what they agreed to, so the phone decides what it pays for. One rule per **device** — what it governs is a data plan, and a phone has one however many vaults it holds — kept in the shell's secure store (`TransferRule`, `mobile/shared/src/commonMain/kotlin/dev/centraid/shared/sync/TransferRule.kt`) and read before every pass, with the platform's answers to "is this link metered" and "is the phone charging" beside it — never cached across passes.

| rule | on Wi-Fi | on a metered link |
| --- | --- | --- |
| `wifi-only` (**default**) | every original | no originals |
| `wifi-and-cellular-photos` | every original | a photograph's original; **a video's never** |
| `manual` | no originals | no originals |

Thumbnails and previews always cross, on any link and ahead of everything, because they are kilobytes and they are the grid. **A snapshot is not taken on a metered link** unless the rule lets photographs cross cellular or the member tapped Back up now ([R-1080-C38](decisions.md#backups-from-first-principles-1080): the records are a few megabytes, and a tap is the member asking). Only the originals are a member's decision, which is why the enum has no other cases. **Videos never on cellular is a fixed rule**, not a fourth setting: the two differ by three orders of magnitude, and a member who said "photos on cellular" did not say "a 900 MB video on cellular". **Include videos** is the member's other control, on the Backup screen: off, no video's original is backed up at all. `manual` withholds originals on every link, which is not the same as Wi-Fi off. **No shell computes any part of the table**: the core decides every item, and the same decision travels with each part the iOS background session carries. The Home header's rule sheet and the Backup screen draw the same sentences and write the same key ([R-1080-E9](decisions.md#the-native-shells-backup-half-1080)).

### No push wake

**There is no push wake, and that is a recorded non-goal** ([D-1025-S7-41](decisions.md#slice-s2--the-tail-stream-1025), and out of [#1080](https://github.com/srikanth235/centraid/issues/1080)'s scope). `WakeReason` has no push case: what is missing is a way to deliver a wake that does not put a third party between a member and their own vault. A phone that is not in the foreground backs up in the next window its platform grants, and on iOS the uploads it already handed off move without one.

## Byte budget and low disk

**The spool is bounded**: at most 2 GiB or a tenth of the free space, whichever is smaller. Preparing stops when it is full and resumes once moving has drained it, so a backlog never fills the phone. The bound is on what waits, not on what can back up: an original larger than the room is sealed a window at a time, each window moved before the next is sealed ([R-1080-C39](decisions.md#the-phone-core-and-the-cut-over-1080-lane-c)), never half-sealed and never skipped. **The content store evicts nothing a gateway has not confirmed**: an original this phone owns may be evicted only once a gateway acknowledged it and it is not in a kept album, and an original fetched back from a gateway is a cache. Out of room is a wait, never a wipe: the vault's rows and the member's own bytes are never evicted to manufacture space.

## Performance guardrails

The absolute targets for a phone are in [`tests/journeys.json`](../tests/journeys.json), stated on the two reference devices ([glossary.md](glossary.md#hosts-and-clients)). A bounded read costs what it returns, and every read states its window: there is no unpaged read, and a whole-set read walks its pages and fails at its stated bound rather than returning a short list that reads as complete (`read_pages` in `crates/apps/kit/src/reads.rs`). A snapshot is hashed and sealed off the request path; the only step that holds the vault is the page copy, which cannot interleave with a commit ([R-1080-B6](decisions.md#the-sealed-format-and-the-snapshot-plane-1080-wave-1-lane-b)).

## The per-state promise — the backup on iOS

What Centraid may tell a member about when their data will be safe, per app state. **The transport is settled and the timing is measured, not promised.** HTTPS to the member's own gateway is what lets iOS carry the bytes while the app is closed ([R-1080-2](decisions.md#backups-from-first-principles-1080)): the pass prepares sealed files while the app is alive, the operating system uploads them while it is suspended, and the app settles when it wakes. The sentences a member reads are `DrainCopy`'s and `BackupLines`', not this table's.

| App state | What Centraid does |
| --- | --- |
| **Open, on screen** | Passes run at open, on resume, after a commit or an import, and when the link changes; each part moves inside the app. The backup line shows what is confirmed and what waits. |
| **Leaving the screen** | A pass takes a snapshot and finishes its current part under the platform's grace, then hands the prepared spool to the background session. |
| **Suspended, iOS** | **The operating system uploads the handed-off parts** while Centraid is not running, each under its own cellular allowance, and relaunches the app to settle them. The processing window — on a charger, with a network — prepares and seals the next batch; a refresh window settles. Progress is the ledger and the spool, never the task. |
| **Backgrounded, Android** | The periodic and charging windows run the whole pass in the process, under constraints derived from the member's rule; **Back up now** is a user-initiated data transfer job on API 34 and later and a `dataSync` foreground service below it, with a notification. |
| **Force-quit, iOS** | The platform cancels the app's background uploads and grants no windows until Centraid is opened again. Nothing is lost: the spool and the ledger resume from where they stopped (`DrainCopy.FORCE_QUIT_SENTENCE`). |
| **Low Power Mode, or Background App Refresh off** | The platform pauses background work, so nothing new is prepared until Centraid is opened. |
| **A gateway asleep or out of reach** | The pass stops `UNREACHABLE`; what waits is counted as waiting for the gateway, with when it was last seen, and the next pass resumes from the same place. A laptop that sleeps is a gateway that is waited for, not a failure. |
| **On a metered link** | No snapshot unless the member taps Back up now, and no original the rule withholds; thumbnails and previews still move. What waits is counted as waiting for Wi-Fi. |
| **An original only in iCloud** | Counted as waiting for iCloud; downloaded to be backed up only under the rule and inside a window. |
| **Everything confirmed** | Idle. "Backed up" with no qualifier needs the records acknowledged **and** every content item confirmed. |
| **Photo access denied** | The camera-roll walk is idle; **the grid is unaffected**, because it reads the vault and not the camera roll. |

**What is not yet known is how much gets through**, which the platform's scheduling decides and which a measurement on a **named reference device** settles — never a simulator ([R-1020-20](decisions.md#v1-platform--rust-core-kmp-shell-electron-seat-gateway-anywhere-1020)). [`mobile/maestro/backup-measurement.md`](../mobile/maestro/backup-measurement.md) is the protocol, with three claims and fixed thresholds: the first backup of a 2,000-asset library finishes in one evening; a night's photographs are confirmed by morning with the app closed on iOS; a fresh phone shows the whole grid within minutes of the words. A missed threshold is reported as missed, never moved.

**HEIC originals upload untouched**, as the camera wrote them; their thumbnails and previews are rendered on the phone by the platform's own decoder and staged as derivatives of the original, so an iPhone's grid no longer falls back to a multi-megabyte original ([docs/photos/README.md](photos/README.md#derivatives)).

## The seat's read plane

The phone keeps one replica SQLite file per vault and opens exactly ONE of them — the active vault's ([#996](https://github.com/srikanth235/centraid/issues/996) R12). A vault is a world, so the vault a read draws from and the vault a write targets are the same one, and switching vaults IS the remount.

The mount is keyed on the **vault** — one pairing, one gateway address, one replica file, one cursor, one outbox, one byte store and one endpoint key per vault ([#1025](https://github.com/srikanth235/centraid/issues/1025) S1) — and the SET of vaults a device holds is owned by one object, `Shelf` (`mobile/shared/.../shell/Shelf.kt`, [D-1025-S7-10](decisions.md#slice-s7--one-loop-one-file-one-page-one-report-1025)): it reads the three stores together at launch, it is the only thing that adds or removes a holding afterwards, and it publishes the roster as a stream. So switching vaults IS the remount: the previous file's session closes and the chosen vault's opens. Nothing is evicted and nothing is capped — every vault the gateway granted is one tap away in the switcher, and a vault that is not open keeps its replica file untouched. Only revocation deletes bytes.

There is no cross-vault union: one open file cannot produce two answers to "which vault is this from".

A bounded read costs what it returns. A read is an app crate's own statement-as-data page (`crates/apps/kit/src/page.rs`), run by the seat against its open file with the ordering and the window inside SQLite; the same statement runs on every seat and on the gateway over the vault's real tables.

## One stream, three occasions

**There is ONE mechanism for a seat to become current: connect, tail the log from the durable cursor, and stay open as long as the OS allows** ([#1025](https://github.com/srikanth235/centraid/issues/1025) S2, [D-1025-S7-40](decisions.md#slice-s2--the-tail-stream-1025)). Polling and foreground timers are deleted concepts; nothing in the shell or the core holds an interval. "Up to date" means **current within one round trip whenever this device is connected, and caught up the moment a connection opens**.

The occasions are three, and they are all the same mechanism with a different bound:

| Occasion | What opens, and what closes it |
| --- | --- |
| **Foreground** | A round catches every holding up, then the foreground holding's log stream stays open. It closes when the foreground is lost — iOS `inactive`/`background`, Android `onPause` — or when the device locks. **Airplane mode is this occasion interrupted, not a fourth one** (R-SHELL-4): a path that stops being satisfied lowers reachability and closes the tail so the header cannot keep "synced"; a path that becomes satisfied again _while the member is still looking_ is the same catch-up-then-tail as arriving. `WakeReason.CONNECTIVITY` is that event. **A dead tail while the member is still looking, with the radio still up, is the same occasion** (R-SHELL-5): gateway restart does not move the path, so the stream that ended is reopened on a 1s…30s backoff. That is not a poll — a live tail still has no interval. The backoff is cancelled on leave, on our own stop, and on radio-down. |
| **Background pass** | The tail is closed first, then one bounded round runs inside the deadline the platform stated. A stream parked on a quiet gateway would spend the whole window waiting for a commit nobody is making. |
| **Relaunch** | The same as a foreground, resuming from the durable cursor. A relaunch is not a re-bootstrap. |

`LogRequest.tail` is the whole of the protocol change. A gateway answering a tail serves the catch-up pages from `since` exactly as it serves a one-shot request — following `has_more` — and then keeps the stream open, writing a further `LogPage` every time the vault's watermark moves past what it last sent. **One page per commit batch and never one per row**: the gateway's wake carries no payload, so the reader asks the log door where the watermark is and writes whatever is there. `RebootstrapRequired` ends the stream as it ends any request. There are no new message types, because a tail is the same answer more than once.

**There is one log per vault, and a seat never subscribes to a table.** Every table's changes are rows in that one log, named by `LogRow.table`. A seat holds a COPY of the vault, not a view of part of it, so a request that could ask for less would be a request that could produce a copy which is silently not one.

On the gateway, a tailing stream is one task parked on a per-vault commit wake that the core rings after every request that may have written. A seat holds **at most one tail per vault**, and a second tail from the same device replaces the first — the second is what that device believes, and a gateway writing pages into a socket nobody will read is a task held by a phone that has moved on. **Presence falls out of the registry**: the gateway can enumerate the devices with a tail open, and for now that goes to a log line and nothing else. A presence protocol is a decision about what members may learn about each other's devices, and this slice needed none.

`Sync now` is **"reconnect the tail"**. When one is open over a reachable last pass the button is a no-op with a sentence, because the device is already current within one round trip and a second dial could only learn what the open stream already knows. The header reads the derived lockup state: `STATE_SYNCING` while catch-up pages are flowing or the first copy is landing, `STATE_ONLINE` while a receiving tail is open over a reachable last pass or the last pass completed, `STATE_OFFLINE` when the dial failed. **A receiving tail over a reachable last pass IS a gateway that is reached** — a caught-up device on a quiet vault moves nothing for hours and is not offline for a second of it. **Marking `tailing` true when the stream is merely asked for must not outrank a just-recorded unreachable**: after a failed pass or a dead tail the lockup published to Home is OFFLINE / not "synced", and `tailClosed` republishes that lockup so the header cannot keep a stale ONLINE line for the whole outage.

## Bootstrap and freshness

**A seat with no file is refused rather than founded, and that is a state and not a failure** ([#1025](https://github.com/srikanth235/centraid/issues/1025) S1). `Core::open` on a seat path that does not exist answers a handle; every read refuses `CoreError::Unpaired`, nothing founds an empty vault behind the member's back, and **pairing creates the replica** by taking the first copy. `Unpaired` is the CORE's refusal on a file with no vault in it; it is not a vault's state in the header. **Unpaired is a state of the DEVICE** — a device holding zero vaults shows the pair flow — and never of a vault, because a vault the device holds has by definition been admitted ([D-1025-S7-9](decisions.md#slice-s7--one-loop-one-file-one-page-one-report-1025)). A held vault has one of exactly three states, all derived from the last pass's outcome and whether a pass is in flight: `STATE_SYNCING`, `STATE_ONLINE`, `STATE_OFFLINE`.

**Bootstrap is a blob** ([#1025](https://github.com/srikanth235/centraid/issues/1025) S1, [D-1025-S1-2](decisions.md#the-sync-model--one-authority-many-copies-1025)). It is a file copy and not a walk ([#996](https://github.com/srikanth235/centraid/issues/996) R4): the log has a floor, so "replay from seq 0" is a cursor the gateway refuses to serve from on any vault with history. The gateway keeps a current replica-shaped snapshot per vault — the replicated tables with every private one dropped, built by the same pipeline the backup plane and the pre-migration copy use (`build_replica_snapshot` in `crates/vault/src/snapshot.rs`) — hashed with BLAKE3 and placed in that vault's byte store. The head (`snapshot_hash`, `snapshot_seq`, `snapshot_bytes`) rides `PairOk` and `RebootstrapRequired`, the only two answers that tell a device to take a copy, and the bytes move on a `blob` stream of the seat's one connection like any other blob (protocol.md's bootstrap section, deleted with the seat plane). **The snapshot is rebuilt when a seat asks and the current one is older than the log floor, or there is none** — nothing else is a reason, because a snapshot at or above the floor can still be tailed from and one below it cannot.

The transfer is resumable by **verified chunk group**, not by byte range. Every 16 KiB group arriving is checked against the root hash through its bao outboard, so a window that ends mid-download leaves chunks _proven_ to belong to this artifact and the next window is set subtraction over the ranges still missing (`crates/blobs/src/lane.rs`). A content address cannot move underneath a download, so there is nothing to re-HEAD and nothing to splice. The artifact is `forget`-ed from the seat's byte store once it has been expanded — a seat holding its own vault twice is a phone out of space.

**A bootstrap is ADOPTED, not installed** ([#1025](https://github.com/srikanth235/centraid/issues/1025) S7, [D-1025-S7-2](decisions.md#slice-s7--one-loop-one-file-one-page-one-report-1025)). The gateway builds the blob **replica-shaped**: the same sanitisation pipeline, uncompressed, with `centraid_seat::seat_own_ddl()` run on the copy so the artifact already IS a replica. The seat fetches it as any other blob, **hard-links the verified bytes to the replica's name**, and writes the cursor and the pairing record in one small transaction; the blob is then forgotten, so the store's name goes and the file stays. A re-bootstrap attaches the old file and copies the seat-own tables in that same transaction. The rename is the publication and it is last.

That replaces three full-size files on a phone at once — the blob, a gzip and an expanded database — to produce one. The **room check** is before the first byte: one copy of the artifact for a first bootstrap, two for a re-bootstrap (the old file is there until the rename), refused by name, because checking afterwards is checking after a phone has filled its own disk. A background window may continue the FETCH and never adopts: adoption closes the vault, renames a file into place and reopens it, and a thirty-second refresh cut halfway through that is a member watching their device go blank and come back.

**Paired, with no file yet, is a real state — and it is spelled `STATE_SYNCING`** ([D-1025-S7-6](decisions.md#slice-s7--one-loop-one-file-one-page-one-report-1025), [D-1025-S7-9](decisions.md#slice-s7--one-loop-one-file-one-page-one-report-1025)). The fact is unchanged; what it is called is not. There is no `paired` case in the lockup, because "admitted, nothing has reported yet" and "the copy is 40% here" are the same sentence to a member: Centraid is working on it. A gateway is often reachable long enough to redeem a ticket and not long enough to move a 300 MB artifact. Until the copy lands there is no replica to write the pairing record into, so it lives in the shell's secure store beside the endpoint key — `PairOk` carries the gateway's address and its dialling hints for exactly that — and the member reads "Copying your vault", not "Synced: 0 changes, 0 files".

**A seat file has an identity, and it is the VAULT's** ([#1025](https://github.com/srikanth235/centraid/issues/1025) S1, [D-1025-S1-1](decisions.md#the-sync-model--one-authority-many-copies-1025)). The replica, its outbox, its cursor and its byte store are named by `vault_id` and by nothing else. Naming a file after the gateway as well would make a vault RESTORED onto a second machine a different file, orphaning every replica on every phone along with the queue inside it. A gateway's endpoint id is now a replaceable property of the pairing record: _where to reach this vault right now_, never part of a name or a key.

The artifact is still checked against that identity before the destination is touched ([#1014](https://github.com/srikanth235/centraid/issues/1014) C16/C17, ruling R-1014-11). bao proves the bytes are the hash the gateway named; it cannot prove the hash names this vault's snapshot. So the adopted file is asked through its own `core_vault` row against the vault this seat paired for, and a mismatch refuses with the old replica and its outbox untouched (`crates/seat/src/adopt.rs`). A file cannot be replaced underneath an open SQLite connection, so the **core** closes its vault around the swap and opens the new file after (`centraid_core::Handle`); that is why the lifecycle lives on the handle and not in a sync pass.

**A repair that cannot repair anything stops.** Under the floor is the same path again — take the current copy — and that is right exactly once per cause and wrong forever: a gateway committing faster than a device can download leaves every fresh copy stale before it lands, so the retry timer re-enters the repair on every pass. **Three re-bootstraps in a row park the seat instead of a fourth** (`centraid_core::REPAIRS_BEFORE_PARKING`, [D-1025-S2-4](decisions.md#slice-s2--one-protocol-1025)), counted on CONSECUTIVE passes and reset by any pass that does not ask for one — a seat that repairs once a week is never parked by three repairs three weeks apart. An artifact served for the wrong vault parks at once, because the answer will be the same in six seconds. Out of room parks it the same way. **Parked means parked: nothing is wiped**, the file and its outbox stay, every screen still reads, and the reason reaches the status line in the member's own words.

A phone whose cursor falls below the log's collected floor cannot be caught up — the deltas are gone — so it re-bootstraps in full. Retention pinning holds that floor for a live phone: the log door records each device's acknowledged position in `access_device_secret.sync_cursor` with the time it asked, and `lowest_seat_cursor` (`crates/vault/src/log/door.rs`) holds the floor at or below the lowest cursor any device has moved inside the seat hold (14 days, `seatHoldDays` in the registries). The bound is the other half of the pin — a phone that is lost, wiped or never opened again stops holding the log after it, and re-bootstraps once when it comes back. There is ONE log and one floor ([#1014](https://github.com/srikanth235/centraid/issues/1014) R-1014-1), and no compaction: a log row is a full row image, so folding buys nothing a truncation does not.

**Redelivery is harmless by construction.** The applier drops a row at or below `applied_seq` before it is bound (rule 5 in `crates/seat`'s README, deleted with the crate), so two paths holding the same cursor — a catch-up and a tail — cannot walk a value backwards, and an overlapping page is not a gap.

### The seat is stale: how to tell

Ask the two numbers, in this order, before anything else ([#1011](https://github.com/srikanth235/centraid/issues/1011)):

| Question | Where to read it |
| --- | --- |
| How far is the gateway? | `sqlite3 <data-dir>/vault/<vaultId>/vault.db 'SELECT commit_seq, floor_seq, epoch, schema_epoch, ddl_version FROM replica_meta'`, and `SELECT max(seq), count(*) FROM replica_log` |
| How far is the phone? | `seat_state` in `centraid-replica-<vaultId>.sqlite3` in the app's replica directory (Android `filesDir`, iOS the app's Documents directory) — `applied_seq`, `applied_commit_seq`, `gateway_watermark`, `epoch`, `schema_epoch`, `deferred_from`, `contents` (copy the file with its `-wal`) |

`applied_commit_seq` well below the gateway's `commit_seq` with `gateway_watermark 0` means **no log page has ever been applied** — the snapshot landed and nothing after it did. A `gateway_watermark` that matches while `applied_seq` lags means pages arrived and the applier refused them; a mismatched `epoch` or `schema_epoch` means a re-bootstrap is owed, not a catch-up.

A non-null `deferred_from` with `applied_seq` sitting just below it is neither: it is a metered seat **parked in front of** a commit that crossed the deferral threshold. The applier stops at that commit and leaves the cursor before it, so nothing behind the span is applied either and `gateway_watermark - applied_seq` counts real unapplied work. The span is taken by the next pull the seat makes without the metered flag, and `deferred_from` clears in the transaction that applies it. A commit that carries a `ddl` row is never deferred — the column it adds is what every later row binds against.

Then ask whether the phone ever knocked. Run the gateway with `CENTRAID_LOG=centraid=debug` (or `--log`); the seat lane logs each page it serves a tailing seat (`a tailing seat was served a page`, with the device, the row count and the next position) and each wake (`a tail woke`), in `crates/centraid/src/seat_lane.rs`. No such lines for a device means the phone is not asking.

**One ticket admits exactly one vault.** `Shelf.admit` redeems a ticket into a fresh core at `Replicas.PAIRING_FILE` and takes the single vault `PairOk.vault_id` names; there is no multi-grant and no `VaultLink` per returned vault. A device that holds several vaults holds them because it redeemed several tickets, and each one is independent — its own replica file, cursor, freshness, intent outbox, byte store, endpoint key and revocation state, keyed by vault id and by nothing else. A ticket naming a vault this device already holds is refused with `ERROR_CODE_VAULT_ALREADY_HELD`, checked before the redemption so nothing is burned, and nothing is merged: two vaults with the same display name are two vaults ([D-1025-S7-10](decisions.md#slice-s7--one-loop-one-file-one-page-one-report-1025), [D-1025-S7-11](decisions.md#slice-s7--one-loop-one-file-one-page-one-report-1025)).

**`forget` is local, and the gateway keeps the device enrolled.** `Shelf.forget` is the exact inverse of `admit` — the open core closes, the holding drops off the shelf, and the replica, its byte store, its pairing record and this device's endpoint key are all deleted together, because a half-forget leaves a file with no identity to dial with. It says nothing to the gateway: enrolment ends when someone with the vault revokes this device there. A phone that could revoke itself could lock a member out of their own vault, and a device that has forgotten a vault can be handed a new ticket for it and pair again from scratch.

## Replica correctness and durability

- **One commit, one transaction.** The applier applies a gateway commit in one transaction with the cursor in it, so a page boundary never exposes half of one commit (`crates/seat`).
- **The epoch gate is per row.** A row from another epoch is refused where it is bound; the page header is only what the gateway believes.
- **Every replicated column arrives whole.** A seat holds the vault's replicated tables themselves ([#996](https://github.com/srikanth235/centraid/issues/996) R1), so nothing is stripped by size and nothing is fetched back on demand; what a seat does not hold is decided per table by the private list.
- **The queue is in the same file as the rows.** `seat_outbox` and `seat_outbox_settled` live in the replica, which is what lets an executed answer clear its pending state in the transaction that carries its commit (R24).
- **A durable file or nothing.** A replica that cannot open its database is an error, never an in-memory session.

## Offline search

Search on the phone answers out of the seat's own file, through the one FTS door, [`crates/search`](../crates/search/README.md). The snapshot carries the gateway's FTS5 indexes, so coverage is the gateway's exactly, with no phone-side index to drift from it; `seat_state.contents` says `rows-minus-fts` when a seat holds the rows without the index. No sealed column can be projected by that door. The phone runs no semantic or vector search.

## Offline changes

Every write goes into the open vault's durable outbox, including one made before the first copy has landed: the input is durable immediately and the write says it is saved on this device and waiting for the first sync ([#883](https://github.com/srikanth235/centraid/issues/883) D1, restated by [#996](https://github.com/srikanth235/centraid/issues/996) R23).

### How an intent settles

An intent travels on an `intent` stream of the seat's one connection and the gateway runs it **under the enrolled device this connection was admitted as**, answering with the commit position the effect landed in ([#1025](https://github.com/srikanth235/centraid/issues/1025) S2, [D-1025-S2-2](decisions.md#slice-s2--one-protocol-1025)). Identity is `(vaultId, intentId, payloadHash)` and never the device, so a restored phone re-enrolling under a new endpoint id replays an outbox the vault answers from its ledger rather than executing twice.

An `executed` answer is the gateway's fact, not the phone's: it says the commit happened, not that this seat holds the rows it wrote. So the answer's **commit position** goes onto the outbox record and the intent waits at `awaiting-change`, and the applier clears the overlay in the transaction that carries that commit — the pending row and the canonical row it was drawn over become visible in the same instant. Where the answer arrives AFTER the seat already applied that commit, the drain settles it against the seat's applied commit position instead, because the applier's hook has been and gone. An answer that names no position waits on `answeredVersions` instead; one that names **neither** is refused loudly rather than parked, because nothing could ever settle it.

**A member's own queued write is on their screen, not only in a badge — and it is IN THE REPLICA** ([#1025](https://github.com/srikanth235/centraid/issues/1025) S7, [D-1025-S7-3](decisions.md#slice-s7--one-loop-one-file-one-page-one-report-1025)). There is no overlay and no composition. `Request::Intent` on a seat validates the command against the registry — an unknown command is REFUSED and never queued — runs the real handler in a transaction against the replica, captures the row images it produced in the shape `replica_log` carries them, rolls back, and **applies them through the same applier the gateway's own pages go through**. Reads are plain reads.

What makes that take-backable is `seat_pending_rows`: every row the predicted apply touches has its PRIOR image journalled there first, keyed by the intent. Three things consume it, and between them a pending write can always be undone or superseded:

- **the answer lands** — the applier upserts the gateway's canonical row and drops the entry in the same transaction (R24);
- **a canonical page touches the row first** — TRUTH WINS: the same call drops the entry, because a prior image from before a commit the gateway has since made is not a state this device may return to;
- **the write is refused** — the prior images go back, newest first, and the entries go. A row a LATER intent also wrote is not restored; that intent's own journalled prior is rewritten to this one's, which is the only answer that is right for both orders.

The invariant is one sentence and the walking skeleton asserts it: **an empty outbox means an empty journal means a replica that is byte-for-byte the gateway's replicated tables.** The predicted apply emits a `RowsChanged` like any page, so a member's own write moves their screen through the one change-stream consumer every other change moves it through — there is no pending-write event kind and no screen has to learn one.

One gesture mints one intent id. Idempotency across RETRIES comes from the outbox row — a retry re-sends the id the gesture minted and the gateway answers from its retained outcome — never from hashing the payload, which collapsed two legitimate identical writes ("+1" twice) into one. An id supplied by the caller (the upload queue keys on the file's digest) is passed through untouched.

A successful send retires the transport reason an earlier attempt wrote, so a `fetch failed` line is never shown under an intent that has since executed.

### A re-bootstrap keeps the queue, and holds it

A seat under the floor takes the **same path** a seat with no copy takes: there is no repair branch and no partial catch-up, because the deltas between its cursor and the floor are collected and no amount of asking brings them back ([#1025](https://github.com/srikanth235/centraid/issues/1025) S1). A re-bootstrap replaces what the gateway gave this seat. The queued intents, their order and the bytes they need are the three things the gateway has never heard of, so they survive it: the outbox is its own table in the shared file, `created_order` is carried verbatim (renumbering the queue would reorder the member's work).

**The queue is on disk for the whole swap, and it never leaves a database.** The outbox and the settled journal are carried from the live replica onto the staged one with `created_order` **verbatim** — renumbering the queue reorders the member's work — and the rename publishes both at once, so there is no window in which the intents are nowhere. A retried install is idempotent on the intent id.

While the repair runs, a write is **admitted and held** ([#996](https://github.com/srikanth235/centraid/issues/996) R23): refusing would make "saved" untrue during a repair nobody asked for and nobody can see, and sending would let an outcome be reconciled against a copy that is about to be replaced. The member is told the change is saved and will send after; the drain resumes from the outbox the moment the new copy is in place.

**Bytes a queued intent still needs are not evictable** (R25, [#1025](https://github.com/srikanth235/centraid/issues/1025) S3, [D-1025-S3-7](decisions.md#slice-s3--bytes-both-ways-one-store-1025)). An intent names the blobs it cannot run without in its own record (`IntentRecord.needs_blobs`, and on the wire `Intent.needs`), and `outbox::pinned_blobs` reads them off every unsettled row. `ByteStore::sweep` subtracts those pins **before it orders anything**, so a pin is never an eviction candidate structurally rather than by a filter at the end: a store over budget _because of_ pins reports `over_budget_by` instead of breaking the promise. Those bytes are the one copy of a write the member has already made — the gateway does not have them, which is why the intent is still queued — so evicting them loses the photograph and no later window can recover it.

The pin list is read from the durable column, not from an in-flight report, so a phone killed mid-pass still knows what not to take at next launch; an outbox that cannot be READ means the sweep does not run at all, because an empty pin list and an unreadable one are not the same fact. Order is oldest-first by the data file's own mtime — there is no access time to read and a phone is usually mounted `noatime` — which is the right order for a cache the planner fills newest-first. Nothing is inferred from a filename.

### Bytes both ways, one store

**A device holds one content store per vault** — iroh's, at `<stem>.bytes`, read by the grid and written by the window alike ([#1025](https://github.com/srikanth235/centraid/issues/1025) S3, [D-1025-S3-1](decisions.md#slice-s3--bytes-both-ways-one-store-1025)). One store is what lets a photograph a seat FETCHED be displayed and one a window MINTED be served, on the same device, for the same vault. `content_location` now answers with iroh's own data file, read in place — a phone that exported every cell of a camera roll would hold the roll twice — and the store inlines nothing, so every complete blob has a file to answer with ([D-1025-S3-2](decisions.md#slice-s3--bytes-both-ways-one-store-1025)).

**A photograph taken on the phone goes UP, and the gateway pulls it.** The bytes land in this seat's own store first; the intent that files them names them; and the gateway fetches them over the connection _the seat opened_ — it cannot dial a phone — verifies them against the hash bao proves, and commits the content row only then. Bytes commit after rows, and never only on a phone. A pull the window cuts leaves the write **queued**, not failed: the member's train went into a tunnel, which is not a rejection ([D-1025-S3-5](decisions.md#slice-s3--bytes-both-ways-one-store-1025), [D-1025-S3-6](decisions.md#slice-s3--bytes-both-ways-one-store-1025)).

A byte pass plans over the rows **that pass** applied, not the ones it started with, so a photograph whose row arrives in this window has its bytes asked for in the same window rather than the next ([D-1025-S3-8](decisions.md#slice-s3--bytes-both-ways-one-store-1025)).

**A landed byte is a row** ([D-1025-S7-20](decisions.md#slice-s7--one-loop-one-file-one-page-one-report-1025)). "Does this device hold these bytes?" is a question a page read has to be able to ask, so the byte pass keeps `seat_blob_held`, a seat-own table beside the outbox and the cursor: written in the window a blob completes, released in the window the sweep forgets one, carried across a re-bootstrap, and **rebuilt in full from the store at every core open and after every adoption**, because a projection only ever written incrementally drifts and drift here renders exactly like a photograph that has not arrived. A page read asks for `with_held_thumbnail` and the door appends a `thumbnail_path` per row, resolved thumbnail-tier-first with the original as the fallback; the byte door's embed refusal is decided where the path is produced and stored as one `drawable` column, so a read cannot hand out a path for bytes the door would refuse and cannot express the unsafe question either.

**And a blob landing wakes a screen through the ordinary change stream** ([D-1025-S7-21](decisions.md#slice-s7--one-loop-one-file-one-page-one-report-1025)): the seat joins a completed hash back to `media_asset.asset_id`, the core emits one `RowsChanged` over `media_asset` with `commit_seq: 0` — bytes arriving is not a commit — and the `BytesArrived` event is deleted. It only ever existed because the ids the core had were content ids, which matched nothing any screen was showing.

### The chain, and where its numbers come from

Five changes made offline against one row execute in order, once each, when the radio returns ([#996](https://github.com/srikanth235/centraid/issues/996) R23). The edges are derived on the seat from what the outbox minted, the held dependents say "Waiting on an earlier change" rather than "failed", and a conflict raised by a second writer stops the head of the chain with both versions on the row and Retry/Discard beside it.

**Every write states a base version, including the chained ones and the destructive ones** ([#1014](https://github.com/srikanth235/centraid/issues/1014) R18/R23/R24). The chain's _dependency_ and the write's _base_ are different facts and are derived separately:

- `dependsOn` says this write may not run before that one. It comes from the ids the input names against the ids the outbox has minted.
- The base version is the `row_version` the seat OBSERVED on the row, taken from the canonical image — a predicted write's prior is journalled in `seat_pending_rows`, so a queued edit never becomes its own base and a retry observes the row that rejected it.

The one case with nothing to observe is a row only a queued predecessor will mint: the gateway has never seen it and never will, so the write names the predecessor (`{"$intent": …}`) instead of a version. Every other row — an existing photograph edited twice, a row being trashed — carries the number.

The gateway then REBASES a chained write before checking it: the predecessors executed first and moved the row, so the child is compared against the version its parent produced (read out of the parent's durable outcome, ordered by commit position). A third party's edit landing between parent and child is still a conflict, which is the point.

A base version is a `row_version`, never a log position. The two are different numbers in different units,, and comparing one against the other reads a much-touched row as a conflict it is not.
