# Mobile offline data

Centraid's native Photos and Docs surfaces are vault-free views: they read one device-local projection assembled from every enrolled vault on the current gateway. A focused vault is only the default write target. It is not a read filter and switching it does not tear down or reopen the read plane.

Docs is back on the phone (rebuilt on the v12 handoff) and reads that same mounted plane — its rows carry source labels and the one read-only sentence above the route where the canonical source cannot be written. Its origin acts are the narrow half: scan, bulk upload, and offline pins address the focused vault alone, so a Docs write is single-vault even though a Docs read is not.

## Mounted read plane

The phone keeps one replica SQLite file per vault and mounts at most four into one read-only op-sqlite connection with `ATTACH DATABASE`. Each result carries its source vault, source label, and whether the current owner may write there. Content rows with the same SHA are displayed once with all source badges. Search runs the same bounded FTS query in every attached database, then merges ranked results locally.

SHA dedupe never separates authority from identity. The canonical row retains one source vault and that source's item id as a pair; a writable source wins when the same bytes also exist in a read-only source. Other sources are badges, not candidate write targets. Favorite/star/archive/trash/move affordances use that canonical role and degrade together when it is read-only; Add may still copy a readable item into another writable target.

The four-scope cap is deliberate. It bounds file descriptors, query fan-out, radio fan-out, and frame work for the 10-year/50k-item performance envelope. The gateway exposes additional enrolled scopes, but the active vault and the first three remaining scopes in stable registry order are the mounted set. The cap is one constant, `MAX_MULTIPLEX_REPLICA_SCOPES` in `packages/core/src/protocol/routes.ts`, which the mobile budget and the gateway's multiplex route both read; neither re-declares it.

Past four enrolled vaults the cap is disclosed rather than silent: the vaults switcher names which saved vaults are resident on this phone and which are over the four-vault limit. Activating an unmounted vault re-plans the mounted set and remounts live — the read plane is torn down and rebuilt in place, with a one-attempt anti-spin guard and no outbox purge — so a member never has to relaunch to read a vault they just chose. A vault the cap evicts stays enrolled and keeps its replica file; only revocation deletes bytes.

A bounded read costs what it returns. The mounted reader compiles the whole read grammar — filters, in-lists, order, limit, and every refusal — into one SQL statement whose `UNION ALL` arms are the attached databases and whose `ORDER BY` is the cross-vault merge, so SQLite orders vaults against each other exactly as it orders rows inside one ([#883](https://github.com/srikanth235/centraid/issues/883) D1; the shared compiler lives in `packages/client/src/replica/read-plan.ts`). Set-wide refusal guards ride the same statement as window aggregates, so a cross-vault order straddle refuses rather than approximates. There is no JS re-sort and no silent fallback: the four shapes that cannot take the full pushdown are a pinned register (`mounted-read-scoping.ts`) — content-hash badge collapse and same-vault dedupe degrade visibly on `result.degraded`; provenance ordering and provenance range comparison escalate as online-only. Provenance equality selects which databases join the union instead of filtering rows.

## Bootstrap and freshness

Bootstrap asks for newest items first. Page one is committed as a crash-safe partial preview so the grid can paint while the canonical walk continues. The complete walk still commits at page one's cursor and replays the change log from there; this closes insert/delete holes created by reading different pages from different SQLite snapshots.

The walk is resumable across process death. The store persists the continuation token, the page-one commit cursor, and the page count inside the same transaction that writes the rows they describe, so a bootstrap killed by the OS resumes at the page it reached instead of starting over — and still commits, and still replays, at the ORIGINAL page-one cursor, because committing at the newer cursor a resumed fetch reports would skip the very deltas the replay exists to apply. A continuation the gateway will no longer serve (epoch, schema, or shape drift, or a collected delta floor) restarts the walk exactly once from a fresh page one; a second refusal is raised, not retried.

A phone whose cursor falls below the change log's collected floor cannot be caught up — the deltas are gone — so it re-bootstraps in full, and since [#883](https://github.com/srikanth235/centraid/issues/883) C6 it says so: the gateway's rebootstrap frame carries a closed verdict vocabulary plus the retention window it actually keeps, `packages/client/src/replica/rebootstrap-copy.ts` is the one place that turns a verdict into a member sentence, and the frame surfaces it. No mitigation is claimed: retention pinning and compactable commit grouping remain open (#883 question 13).

**A gap is a batch that starts AHEAD of the cursor, and only that** ([#922](https://github.com/srikanth235/centraid/issues/922) E3). Two catch-up paths legitimately hold the same cursor at once — the bootstrap's convergence replay and the change feed's own sync — so the slower one arrives with a `from` the faster one has already passed. That batch skipped nothing: it OVERLAPS, and every change in it is an idempotent upsert or delete under the same server-version guard. `changeMismatch` (`packages/client/src/replica/store-core.ts`) therefore raises `cursor-gap` only for `batch.from.seq > cursor_seq` (or a batch whose `to` precedes its `from`); protocol, schema-epoch and cursor-epoch mismatches are unchanged. Treating an overlap as a gap wiped the store and demanded a re-bootstrap that raced the same way — a loop, not a repair.

Pairing can grant several vaults through one short-lived ticket. The gateway redeems that ticket atomically, while the phone records one `VaultLink` and one replica lifecycle per returned vault. The first grant is only the initial focus; all other granted vaults remain independently mountable and retain their own cursor, freshness, intent outbox, and revocation state.

## Replica correctness and durability

The replica wire has five invariants that every client observes:

- A canonical SQLite write transaction gets one `commitId`. Delta pages extend through the end of that commit group, so a page boundary never exposes half of one transaction. Retention cutoffs use the same boundary rule. Under count pressure the log folds fully superseded commit groups into their survivors (each survivor inheriting the folded prior state) and does **not** move the resumable floor; only the age window and the residual count trim collect history.
- Projected changes carry the row's canonical `rowVersion` when it is nonzero; an omitted version means version zero. Local application ignores an older upsert or delete when a newer version is already stored, which makes overlapping bootstrap convergence and reconnect replay safe.
- Offline intents may carry `baseVersions`. The gateway compares those preconditions before dispatch and returns a structured conflict with expected and actual versions. The client retains the projected row, reason, and both versions until the member edits/retries or discards it.
- Text a screen renders arrives in FULL, up to a ceiling its entity declares (`packages/vault/src/schema/entity-catalog.ts`; `core.content_item` and `core.content_derivative` declare 1 MiB, everything else takes the 64 KiB default). Only values a column declares LAZY — `enrich.embedding.vector` is the one today — are deferred, and a deferred field is never silently `undefined`: reading it raises an online-only refusal carrying `fieldNotOnThisDevice`, the sentence both clients print. There is no fetch-on-demand route, because nothing renders the one lazy column ([#922](https://github.com/srikanth235/centraid/issues/922), ruling SB-text). Before this a note body over roughly 48 KiB of prose was stripped from every bootstrap page and no client fetched it back.
- `coverage` and `durability` are explicit status/result fields. A partial preview is readable and searchable, but it is labeled partial and is never treated as a completed cold start. The native seat has no memory fallback to fall back to: a replica that cannot open its durable database is an error, not an unremembered in-memory session.

The browser and native outbox storage contracts are unchanged. Executed intents use the existing settlement path, which removes input and journals the outcome. Denied/conflict/failed results instead use the existing atomic transition primitive to remain unsettled with their input and row projection. Edit/retry mints a fresh immutable intent id and payload hash, adds its projection first, then truthfully journals the old terminal result; an engine-private supersession marker lets startup finish that handoff if the process stops between those existing store operations. That marker never enters query validation: browser and multi-vault native reads share one presentation function that strips engine-private fields before applying the projected row. The presentation/revision clone follows the replica's JSON-shaped value grammar and does not require the browser-only `structuredClone` global; the native restart regression runs with that global absent to match Hermes. Revision identity also comes from the blueprint's declared edit-action projection, not by scanning arbitrary `*_id` inputs, so a child write may safely reference a pending parent. A mounted filtered/limited read keeps its SQL-pushed canonical page and adds only canonical row ids addressed by pending mutations before composition; one outbox row therefore cannot turn a bounded Home read into a vault-sized scan. Discard journals the last real non-executed result rather than inventing execution. No IndexedDB version, SQLite table, serialized `IntentState`, or `IntentRecordStore` method changes for this overlay. Locker add/edit secrets are explicit online-only actions: browser inline, served, and native callers never present secret plaintext to a durable session. Ordinary non-secret Locker item actions remain outbox-visible through metadata-only row patches. Foreground and background catch-up follow `hasMore` with a bounded sequential loop; an interrupted loop resumes from the last committed cursor.

One gateway SSE connection multiplexes independent vault cursors. A frame never combines cursors or data across vaults. A frame is also the unit of cursor cost: both feeds coalesce a page's advances and debounce the durable cursor write by one second, flushing on background and teardown, so a thousand-change page costs one write and one freshness signal rather than a thousand of each. Foreground UI reports human states (`Offline on this phone`, `Gateway asleep`, `Syncing recent changes`, `Sync paused by transfer rules`, and `Updated …`) plus a timestamp for every source. Those states are learned from ANSWERS, never from configuration: `resolveGatewayBase()` only resolves an address, so a pass that has not yet asked the gateway anything may lower reachability and never raise it, and every gateway request runs under a time-to-first-byte deadline (`apps/mobile/src/lib/replica/gateway-deadline.ts`) because the tunnel listener keeps accepting after its peer is gone. The change feed and the write drain report each outcome, so a vault that dies under a still-connected phone is noticed without waiting for a radio event, and a vault that returns is picked up the same way. See [traps/unreachable-vault.md](traps/unreachable-vault.md). Revocation produces a scoped tombstone: the local cursor and rows for that source are purged without affecting other mounted vaults, and a durable member-facing notice is left behind because the purge takes every other trace with it (see below).

A restored device is treated as a cold start, not a resume. The replica databases live in the module-owned durable directory and never ride Auto Backup, device-to-device transfer, or an iCloud restore, but the SSE resume cursors and freshness stamps beside them are ordinary app storage. When a scope's replica file is absent or empty while its cached cursor and stamps are present, both are discarded before bootstrap, so the feed cannot resume at a sequence for rows this device never had. A first launch after pairing has no database and no cache either; that stays silent, because it is a cold start rather than a restore.

Freshness is stored independently per `(gateway, vault)` and advances only after that source successfully pulls or produces a cursor frame. Pulling rows is not moving bytes (#905 O): a foreground read obeys only the `never` floor, so a phone on cellular still pulls its deltas while the Wi-Fi-only/metered/roaming/charger rules keep governing blobs, the write drain and the unprompted background pass. Reads once shared `canTransfer()`, and since `wifiOnly` is the default a cellular phone pulled nothing at all — silently, which Home could not tell from an empty vault. A pull the `never` floor refuses is still neither a landed pull nor a sleeping gateway: nothing was asked, no stamp advances, and the phone says `Sync paused by transfer rules` instead of claiming freshness it never obtained. Offline startup restores those values rather than stamping every source with launch time. Scoped revocation detaches the mounted database, purges that replica's rows/intents and cross-scope placement work, removes its pinned thumbnail pack, and deletes only that scope from the cached mount/freshness manifests. It also closes the driver handle and deletes the replica SQLite file family — the main file plus its WAL, SHM, and rollback-journal sidecars — because an emptied database keeps its full size for a vault this phone may never see again; a vault the four-scope cap merely evicted is still enrolled and keeps its file. The revocation leaves one durable, dismissible audience notice behind (“No longer shared with you — {label} was removed from this phone”), surfaced through the status bar, because the purge takes every other trace with it. The headless background pass reclaims a revoked scope the same way the foreground does. Delivery of that notice is on reconnect, so the window a revoked phone stays dark is unbounded while it is off.

The aggregate multi-vault cursor is conservative: it is the minimum sequence across every mounted source, including a source that has no completed bootstrap yet. Any missing or partial source therefore keeps the aggregate result partial instead of allowing a fast source to make the mounted read plane look complete. That coverage is read from durable status at mount and after every pull, and carried through the replica context into every query result, so an app killed mid-backfill and relaunched offline still labels its truncated library partial — the in-process bootstrap that would have reported pages died with the old process.

Mobile reads `/centraid/_gateway/info` before constructing either foreground or background sessions. Both `multiVaultReplica` and `crossVaultPlacements` must be advertised. Missing flags produce one update wall instead of repeated multiplex/placement 404s. The judgment is asked fresh each time and is not cached: an offline start skips the probe entirely and fails open rather than replaying a remembered verdict, so a gateway that was upgraded — or downgraded — between launches is judged on what it answers now.

## Offline changes and cross-vault placement

Ordinary writes stay in each replica's durable intent outbox. A first-open write made before any bootstrap is also admitted there: the action input is durable immediately, the write reports itself as saved-on-this-phone pending first sync (never a bare "waiting for a connection"), and its optimistic row projection backfills from the durable input as soon as bootstrap supplies the shape catalog — at the first bootstrap page, at completion, and on relaunch ([#883](https://github.com/srikanth235/centraid/issues/883) D1). Add/Move uses a separate device outbox keyed by a durable link token. Reconciliation always:

1. commits or confirms the target projection;
2. records that target receipt in the gateway database;
3. for Move only, deletes the source item; and
4. records completion.

Replay is idempotent. A crash can leave a completed target and pending source removal, but cannot delete the source before the target exists. Queued changes may be cancelled. Permission denial, terminal failure, and parked retries remain visible until dismissed.

### Commons writes and cursors

A circle-backed commons is not mounted as a special borrowed scope. Its domain rows and blobs are real residents of each joined member vault, so the ordinary per-vault replica, backup, search, and attachment paths cover them. The phone still has exactly one physical replica cursor for that vault even when the vault participates in many commons.

Offline commons writes use the durable `share_commons_intent` rail. A pending row is an honest UI overlay, not an optimistic domain record; it can say “waiting for Alice's device” when the grant's steward is unavailable. After the steward verifies capability, container allowlist, member-vault signature, and replay nonce, the executed/refused outcome receives the next per-grant sequence and the member catches up normally.

Minting a commons is not one of those offline writes. `tally.group` is v1's one edit-capable subject, so the phone's single commons producer is the share row on a Tally group: it opens the share sheet when the gateway is reachable and WITHHOLDS the verb with its own sentence when it is not — an unreachable gateway is a different screen from a refused grant, and neither is an empty ledger. The first compile of that commons binds it to the group circle's stored roster: the sheet is handed the group's `circle_id` as its preferred circle, so the audience is the roster the vault already holds rather than one assembled on the device. The audience itself is the LINKED roster and nothing else — a share is delivered into the receiver's own vault, so a party with no approved vault link has nowhere to receive one and is not offered. Making someone reachable is likewise online, and is the link ceremony on the Sharing screen; v1 shares are same-gateway only.

`share_commons_cursor(grant_id, member_vault_id)` is a logical operation offset alongside the physical replica cursor. Ten Tally groups in one vault therefore mean one vault cursor plus ten grant offsets, not eleven sync engines. The vault cursor transports resulting row changes; each grant's steward sequence independently orders that group's writes. Late join and restore begin from a closure checkpoint at sequence N, then consume the tail. Removal or revocation detaches and scrubs only that grant's lineage; other vault rows, outboxes, grants, and cursors remain intact.

## Background work and push privacy

The Expo background task maps to BGTaskScheduler on iOS and WorkManager on Android. It runs the same pull, intent, placement, and upload queues as the foreground and calls the same metered/battery upload policy. Platform timing is opportunistic; correctness always comes from the durable outboxes and the next foreground pull.

One pass owns a fixed 20 s budget (iOS grants a background refresh task about 30 s; the remainder is teardown headroom), checked between stages and also driven by the platform's own expiration listener. A pass that runs out of budget stops at a stage boundary instead of being killed mid-stage, and reports what it managed. Scopes are isolated from each other: one scope whose pull or bootstrap fails never cancels the remaining scopes, and the device outboxes — placements, then uploads — still drain afterwards, because their rows are durable and target their own vault. The pass also asks the platform for the real connectivity answer rather than assuming a radio, and it reclaims a revoked scope's files exactly as the foreground does.

Registration is observable rather than assumed. Whether the background task and the push task registered, why one refused, and the platform's own availability verdict are recorded durably and rendered on the storage screen, so “Background App Refresh is off” is a sentence the member can read instead of a sync that silently never runs.

The focused write target is ordered before the other cached scopes before the four-scope cap is applied. Upload rows persist that target vault, and headless reconciliation keeps the corresponding mounted sessions alive through canonical follow-up replay; transferred bytes therefore cannot settle without their app mutation merely because the app was backgrounded.

The pass is also where diagnostics traces land. Spans (#927) buffer in a bounded in-memory ring while the app runs — a phone doing disk I/O on a scroll is exactly the cost the traces exist to find — and are written to `<replicaStorage>/diagnostics/traces.jsonl` in the pass's `finally`, so a pass that timed out still lands what it recorded. The write swallows its own failures and the ring is dropped if the OS kills the app first: a diagnostics buffer, not evidence. Tracing is OFF unless `EXPO_PUBLIC_CENTRAID_TRACE=1`; the work counters underneath are always on and are integers. See [logs.md](logs.md).

The gateway push relay is wake-only. Its payload contains no vault id, item id, title, content, cursor, or owner data. Push delivery can make a background pull happen earlier, but loss or throttling cannot lose data. iOS background push is therefore treated as an optimization, in line with Expo's delivery guidance.

## Thumbnail packs and budgets

Each source gets a pinned thumbnail pack containing the recent 90 days plus favorites, with an independent 128 MiB budget and oldest-first eviction. Displayed rows prefer those local pixels. One source cannot evict another source's offline pack. The Phone storage screen reports, per vault:

- replica database bytes;
- pinned thumbnail bytes; and
- pending upload bytes.

Database bytes mean the complete live SQLite family: the main file plus WAL, SHM, or rollback-journal sidecars. Pending bytes come from each upload row's durable target vault, never from whichever Space happens to be focused when the screen opens. Legacy pre-target rows are reported honestly as unassigned instead of being fabricated into a vault total. Tapping a vault total expands its database, thumbnail, and pending-upload components.

Per-vault cards reach only the mounted scopes, so the screen adds an `Other Centraid data on this phone` section for what they cannot see: the upload queue's own database family, and replica databases on disk that no mounted scope claims (an unmounted or revoked vault's files, plus the near-empty per-gateway mounted-reader host database, which the screen has no gateway id to name separately). That section reports; it never deletes.

Neither the screen nor the budget check may cost the size of what it measures. Pending bytes, counts, and the unassigned bucket come from one `GROUP BY target_vault_id` aggregate over the upload queue rather than from its rows; queue rows are read in bounded pages with a `created_order` keyset cursor, which is also how one upload drain pass walks a deep backlog. Pack totals come from the native module's single-crossing `directorySize`, and eviction pays for a per-file listing only once that total says a source is over budget. Pack downloads take the same durable transfer policy as uploads — Wi-Fi-only, metered, roaming, and charger rules govern thumbnail bytes exactly as they govern originals.

`Free thumbnail cache` removes only reproducible thumbnails. Replica rows and pending changes are not cache and are never removed by that action.

Low disk fails closed and preserves the last readable projection, and it does so mid-session rather than only at start-up. op-sqlite's `SQLITE_FULL`/errcode 13 and OS `ENOSPC` variants are normalized into one actionable screen error wherever they surface. A delta that cannot be applied for want of room PARKS the change feed: the one-second retry cadence stops instead of re-applying the same failing batch forever, the cursor and rows stay exactly as they were, a later feed frame does not restart the loop, and the surface says the phone is out of room. Freeing space resumes the parked feed from its durable cursor. Replica rows and pending intents remain untouched throughout, and the person can free the reproducible thumbnail cache or other phone storage before retrying. Centraid never evicts canonical replica rows or queued writes to manufacture free space. The device contract test pins that classification and copy; the vault custody test fault-injects the same SQLite-full condition during `wal_checkpoint(TRUNCATE)` and requires the gateway disk-health tracker to turn red.

## Durable path and at-rest decision

Replica databases, pending intents, upload queues, and thumbnail packs live in a native module-owned durable directory:

- iOS: `Application Support/CentraidReplica`, excluded from iCloud backup and protected with `completeUntilFirstUserAuthentication`;
- Android: credential-encrypted `noBackupFilesDir/CentraidReplica`. The app excludes ALL of its data from Auto Backup and device-to-device transfer, not just this path: the manifest sets `allowBackup="false"` with backup and data-extraction rules that exclude every domain (cloud and device transfer alike), and `app.config.ts` mirrors it so a later `expo prebuild` cannot regenerate the manifest without it. The AsyncStorage backend moves with a build flag, so a path-level exclude would be the fragile version of this rule.

These files survive OS cache eviction and disappear on uninstall. Centraid does not add SQLCipher or field encryption to the local projection in this version. That decision preserves one attached SQLite/FTS read plane and the cold/search budgets, while relying on iOS Data Protection and Android credential encryption for at-rest protection. The projection is consent-minimal, backup-excluded, and contains no blob originals; a future stronger app-layer scheme must preserve cross-database search and publish measured cold/search costs before replacing this decision.

An optional biometric app lock adds a user-presence layer before this read plane is mounted. Its gate is stored with SecureStore `requireAuthentication`; moving the app out of the foreground clears the decrypted credential cache, unmounts replica sessions, and paints an opaque switcher mask. This complements the OS at-rest controls above—it does not turn the replica into an independently encrypted database.

Locker is stricter than the ordinary replica plane in ONE direction: the secret half. The browsable half is not. `locker.item` visibility is authorised by the app grant alone — listing an item is not unlocking it, and authentication gates permits and `reveal` ([#928](https://github.com/srikanth235/centraid/issues/928)) — so the window, the archived and trash shelves and the search run the app's own `packages/blueprints/apps/locker/queries/{items,search,trash}.ts` against the mounted replica, through `apps/mobile/src/apps/locker/locker-reads.ts`. No sealed column can ride those rows: `packages/vault/src/replica/locker-sealed-columns.test.ts` asserts every sealed column of every sealed entity is structurally unavailable to the replica lane, by name rather than blanked. The Watchtower decoration (weak/reused/last4) is derived inside the sealed boundary, so a local read asks for it as an `optional` invocation and answers UNDECORATED when it cannot be reached: the two row keys and the payload's `watchtower` summary are then ABSENT, and `review-model.ts`'s register says those checks did not run rather than clearing every password. `apps/mobile/src/apps/locker/locker-airplane.test.ts` holds the three reads with every `lib/gateway` door throwing, and `tests/integration-mobile/locker-rows-parity.integration.test.ts` holds the phone and the web seat to identical payloads over the same rows. The seat still boots locked and drops its rows on a lock — a locker that drew its own list behind its lock screen has not locked anything — and unlocking remains online.

Its native cover performs authentication and reveal through online-only app queries, and its two secret-bearing WRITES take an online-only transport door of their own: `NativeWriteInput.onlineOnly` posts the action straight to the app's handler and never enqueues, mirroring the browser bridge's `opts.onlineOnly`. A gateway it cannot reach is a failure, never a queued row — falling back to the outbox is exactly what the flag forbids. The action list is `packages/blueprints/apps/locker/writes.ts`'s `ONLINE_ONLY_ACTIONS`; `apps/mobile/src/lib/replica/locker-online-only.test.ts` pins the seat's half. Passphrases, biometric device secrets, memory-session tokens, one-shot item permits, and revealed fields never enter replica rows or durable intents. The local biometric secret is random, device-only SecureStore material; only a vault-key-peppered verifier reaches the gateway database. Locker's memory-only session lives in one process-level store (`apps/mobile/src/apps/locker/locker-store.ts`) rather than a React context, so no remount can reconstruct a session the boundary ended.

Tally is ordinary in both directions now — its writes queue and its derived reads run locally. Every Tally act carries an optimistic pending projection (`packages/blueprints/apps/tally/pending-projection.ts`), so the native cover issues all of them through `session.write` and they queue in the durable outbox when the gateway is out of reach — that is what "record-only and fully offline-capable" means on a phone. The one exception is `materialize-recurring-expense`, whose occurrence id is minted by the canonical recurrence engine: the projection excludes it by construction, so the seat WITHHOLDS the verb while offline rather than queueing a copy of an expense nobody issued. Reads run the app's ONE balance engine ON THE PHONE: `apps/mobile/src/apps/tally/tally-reads.ts` imports the seven `packages/blueprints/apps/tally/queries/*.ts` modules the web seat imports and runs them against the mounted replica through `apps/mobile/src/lib/replica/inline-query-ctx.native.ts`. There is still exactly one derivation of "who owes whom"; it simply no longer needs a network to reach it, so a member on a plane sees complete balances rather than a spinner. A refused grant and an unmounted replica are different screens, and `apps/mobile/src/apps/tally/tally-store.test.ts` pins that a failed read never reads as an empty ledger.

**That read carve-out is gone.** SB-tally ([#922](https://github.com/srikanth235/centraid/issues/922)) reverted it in wave 4 (E7): the phone runs the same `queries/*.ts` modules the web seat runs, over the same rows, and `tests/integration-mobile/tally-balance-parity.integration.test.ts` holds the two seats to the identical dashboard. The mounted plane's `__centraid*` provenance is stripped before a handler sees a row, so neither seat's payload carries the other's bookkeeping. Tally's ten-minute stale clock went with the RPCs — a read of this device's own replica is as current as the device is, and a replica behind the vault is the frame's own line, not a verdict about the ledger. See [decisions.md](decisions.md#snappier-blueprint-apps-922).

## Performance guardrails

The checked 50,000-row fixture spans 2016–2025 across four mounted household sources. Its current pending-write variant adds 200 durable SQLite outbox mutations (50 per vault) before starting either timer. On the 2026-08-11 macOS arm64 development host it measured a 778.4 ms cold 5,000-row merged/sorted read, a 4.5 ms federated FTS lookup, and 22,622,208 projection bytes. At that observed density the 5,000-row bootstrap window is 2,262,221 bytes. The browser perf lane separately opens IndexedDB, enqueues 200 intents, and budgets their full overlay enumeration/composition at one tenth of its registered 2,500 ms real-I/O ceiling. The same native evidence lane encodes twelve reproducible 256px/82%-quality thumbnail samples: the 13,726-byte p95 projects a 12,820,084-byte recent-90-day plus 5%-favorite pack for each 12,500-item source, within its 128 MiB ceiling. The lane enforces the 1,000 ms cold, 100 ms search, 4 MiB bootstrap-page, and 128 MiB thumbnail ceilings; `tests/journeys.json` records the volume, probe, observation, and headroom. Native build/install/launch checks prove the modules load on both platforms; the Android mobile journey owns the airplane-mode UI/process proof, with the rendered SQLite restart companion — `apps/mobile/src/apps/tally/PendingRestartJourney.test.tsx`, which drives the Tally cover through a real process restart over the same production reader — covering it on iOS-compatible infrastructure.

### Where 50,000 rows came from, and where it stops (#659)

50,000 is a measured fixture, not a product ceiling. A household that keeps a phone camera for a decade plausibly reaches 90,000 items by year three of using Centraid, so the envelope has to say what happens there rather than imply the number cannot be exceeded.

Scaling the 2026-07-29 measurement linearly — a projection from that run, **not** a new measurement — a 90,000-row set is about 39.9 MB of projection across four sources and about 1,013 ms of cold merged read. That is over the 1,000 ms ceiling, and it was over it for a structural reason: the mounted reader answered every request by selecting every row of the entity from every attached source, parsing each payload in JavaScript, and only then applying the caller's filters and limit. Cost tracked the size of the library instead of the size of the answer.

Since #659 the reader pushes the read grammar's filters, and the caller's limit where truncation is provably safe, into the attached SQLite databases, and runs the statement off the JS thread. What that changes about this envelope:

- **A bounded read costs what it returns.** The 5,000-row bootstrap window, a filtered lookup, and a keyed fetch no longer scale with the projection, so they hold at 90,000 rows and beyond.
- **An unbounded read still costs the whole entity.** Photos deliberately reads its full asset set to merge the camera roll against it. That path scales linearly and is the one that leaves the 1,000 ms budget somewhere between 50,000 and 90,000 rows on the reference host.
- **The limit is not pushed for content-hashed entities across several sources.** Equal bytes in two vaults collapse into one row carrying both source badges, and a pushed page could drop the duplicate that supplies a badge. Those entities read the whole filtered set by design and say so on `result.degraded`; the cheaper path is not worth a missing badge. This is the only surviving page refusal ([#883](https://github.com/srikanth235/centraid/issues/883) D1).

**What an ordered read costs, and what a write pays for it** ([#922](https://github.com/srikanth235/centraid/issues/922) C3). An ordered read asks its order guards as **index seeks**, not as a scan: the store keeps two expression indexes per ordered column — `replica_row_ord_*` over the ordering value and `replica_row_cen_*` over `censusClass(column)`, a fixed 0–5 ladder — and each guard asks `class >= N ORDER BY class ASC LIMIT 1`. One statement per read either way; the difference is the plan. Measured on this container over 50,000 `knowledge.note` rows: an ordered read taken **after a write**, when the census must be re-asked, **37.9 ms → 1.03 ms**; the warm read (census cached) is unchanged at ~0.4 ms. The cost lands on the write instead: a one-row write batch goes **0.36 ms → 0.55 ms** for the extra b-tree per ordered column, paid once against 37 ms saved on the next ordered read. Both indexes are capped by `ORDER_INDEX_MAX` per session; past the cap the read falls back to a scan. The index expression and the probe expression must be spelled identically or SQLite uses neither — [traps/expression-index-spelling.md](traps/expression-index-spelling.md).

**No read truncates silently, on any seat** ([#922](https://github.com/srikanth235/centraid/issues/922) 0a). A read that declares no `limit` still gets the 1,000-row default window (`REPLICA_DEFAULT_LOCAL_ROWS` on the replica, `GATEWAY_DEFAULT_READ_ROWS` on the gateway) — bounding is the point ([#262](https://github.com/srikanth235/centraid/issues/262)) — but the bound is now spoken:

- The compiled plan fetches `limit + 1`. The probe row never reaches a caller; it is what tells a window that FILLED apart from a set that merely ends there, which a row count alone cannot. It costs exactly one row per read.
- A page that hid rows carries `truncated: true` and `appliedLimit` on the read result, and the kit turns that into one status line — `Showing the newest 1,000; more not loaded` (`truncatedListNotice`, `packages/blueprints/apps/_shared/shared-copy.ts`), said the same way on the phone and on the web.
- `truncated` is not `coverage`. Coverage is how much of the library this device holds; truncation is what this read's window did. A fully bootstrapped phone still truncates a 5,000-contact roster at 1,000.
- The kit REFUSES a read that declares neither `limit` nor `acceptTruncation: true` — `useReplicaQuery` on the phone, `ctx.vault.read` inside the inline query host on the web — with a typed `UNBOUNDED_READ` error naming the entity and both fixes. The refusal does not fall back online: the gateway would cap it the same way. Call sites that have not yet declared a window carry `acceptTruncation: true`, so the debt is greppable rather than invisible.

The honest ceiling today is therefore: **bounded reads are unbounded in library size; the full-projection Photos read is measured to 50,000 rows and projected to leave budget near 90,000.** Closing that gap means giving the timeline a windowed read rather than raising the number here. Storage scales without a cliff — projection bytes are linear, and the per-source 128 MiB thumbnail budget is unchanged because the pack is a 90-day-plus-favorites window, not a fraction of the library.

- merged cold view: under 1 second after page one is locally available;
- federated local search: under 100 ms for the supported mounted set;
- scrolling: reads bounded by the query, not by the library, and no 10k truncation;
- newest-first bootstrap page: 5,000 rows;
- attached sources: 4;
- FTS results: 1,000;
- pinned thumbnails: 128 MiB per source;
- measured library: 50,000 rows; projected budget edge for a full-projection read: ~90,000 rows.

Device/simulator runs remain the release evidence for 60 fps and the end-to-end time budgets; unit tests pin query behavior, provenance dedupe, cursor convergence, and outbox durability.
