# Mobile offline data

Centraid's native Photos and Docs surfaces read the phone's own copy of the active vault. A vault is a world, so the vault a read draws from and the vault a write targets are the same one, and switching vaults IS the remount ([#996](https://github.com/srikanth235/centraid/issues/996) R12). The vault-free view assembled from every enrolled vault is superseded: it needed the mount plane, and the mount plane is gone.

Docs is back on the phone (rebuilt on the v12 handoff) and reads that same file. Its origin acts — scan, bulk upload, and offline pins — address the open vault, exactly as its reads do.

## The seat's read plane

The phone keeps one replica SQLite file per vault and opens exactly ONE of them — the active vault's ([#996](https://github.com/srikanth235/centraid/issues/996) R12). Every row a read returns is stamped with that vault's id, its label, and whether the current owner may write there.

The mount is keyed on the **vault** — one pairing, one gateway address, one replica file, one cursor, one outbox, one byte store and one endpoint key per vault ([#1025](https://github.com/srikanth235/centraid/issues/1025) S1) — and the SET of vaults a device holds is owned by one object, `Shelf` (`mobile/shared/.../shell/Shelf.kt`, [D-1025-S7-10](decisions.md#slice-s7--one-loop-one-file-one-page-one-report-1025)): it reads the three stores together at launch, it is the only thing that adds or removes a holding afterwards, and it publishes the roster as a stream. So switching vaults IS the remount: the previous file's session closes and the chosen vault's opens. Nothing is evicted and nothing is capped — every vault the gateway granted is one tap away in the switcher, and a vault that is not open keeps its replica file untouched. Only revocation deletes bytes.

The multi-vault mount plane is gone with the questions it answered. There is no `ATTACH DATABASE` union, no cross-vault SHA dedupe, no source-badge collapse, no provenance ordering and no four-scope cap disclosure: one open file cannot produce two answers to "which vault is this from". A share is a projection into the audience's own vault ([#929](https://github.com/srikanth235/centraid/issues/929)), so the household case the plane was built for has no consumer left.

One number survives it, and only for the radio: `MAX_REPLICA_FEED_MOUNTS` in `packages/core/src/protocol/routes.ts` bounds the mounts one change-feed subscription carries, which is what keeps the phone's other replica files in step in the background. The gateway's multiplex route and the mobile background budget both read that one constant; neither re-declares it.

A bounded read costs what it returns. A read is an app's own statement-as-data page, run by the seat against its open file with the ordering and the window inside SQLite (`packages/client/src/replica/seat/paged-handler.ts`, `seat-page-reader.ts`). There is no JS re-sort and no silent fallback. The declarative read grammar and its compiler are superseded: an app handler's `queries/*.ts` runs the same statement on every seat and on the gateway over the vault's real tables ([#996](https://github.com/srikanth235/centraid/issues/996) R9, W4-D2).

## One stream, three occasions

**There is ONE mechanism for a seat to become current: connect, tail the log from the durable cursor, and stay open as long as the OS allows** ([#1025](https://github.com/srikanth235/centraid/issues/1025) S2, [D-1025-S7-40](decisions.md#slice-s2--the-tail-stream-1025)). Polling and foreground timers are deleted concepts; nothing in the shell or the core holds an interval. "Up to date" means **current within one round trip whenever this device is connected, and caught up the moment a connection opens**.

The occasions are three, and they are all the same mechanism with a different bound:

| Occasion | What opens, and what closes it |
| --- | --- |
| **Foreground** | A round catches every holding up, then the foreground holding's log stream stays open. It closes when the foreground is lost — iOS `inactive`/`background`, Android `onPause` — or when the device locks. |
| **Background pass** | The tail is closed first, then one bounded round runs inside the deadline the platform stated. A stream parked on a quiet gateway would spend the whole window waiting for a commit nobody is making. |
| **Relaunch** | The same as a foreground, resuming from the durable cursor. A relaunch is not a re-bootstrap. |

`LogRequest.tail` is the whole of the protocol change. A gateway answering a tail serves the catch-up pages from `since` exactly as it serves a one-shot request — following `has_more` — and then keeps the stream open, writing a further `LogPage` every time the vault's watermark moves past what it last sent. **One page per commit batch and never one per row**: the gateway's wake carries no payload, so the reader asks the log door where the watermark is and writes whatever is there. `RebootstrapRequired` ends the stream as it ends any request. There are no new message types, because a tail is the same answer more than once.

**There is one log per vault, and a seat never subscribes to a table.** Every table's changes are rows in that one log, named by `LogRow.table`. A seat holds a COPY of the vault, not a view of part of it, so a request that could ask for less would be a request that could produce a copy which is silently not one.

On the gateway, a tailing stream is one task parked on a per-vault commit wake that the core rings after every request that may have written. A seat holds **at most one tail per vault**, and a second tail from the same device replaces the first — the second is what that device believes, and a gateway writing pages into a socket nobody will read is a task held by a phone that has moved on. **Presence falls out of the registry**: the gateway can enumerate the devices with a tail open, and for now that goes to a log line and nothing else. A presence protocol is a decision about what members may learn about each other's devices, and this slice needed none.

`Sync now` is **"reconnect the tail"**. When one is open over a reachable last pass the button is a no-op with a sentence, because the device is already current within one round trip and a second dial could only learn what the open stream already knows. The header reads the derived lockup state: `STATE_SYNCING` while catch-up pages are flowing or the first copy is landing, `STATE_ONLINE` while a receiving tail is open over a reachable last pass or the last pass completed, `STATE_OFFLINE` when the dial failed. **A receiving tail over a reachable last pass IS a gateway that is reached** — a caught-up device on a quiet vault moves nothing for hours and is not offline for a second of it. **Marking `tailing` true when the stream is merely asked for must not outrank a just-recorded unreachable** (R-SHELL-1, trap [unreachable-vault](traps/unreachable-vault.md)): after a failed pass or a dead tail the lockup published to Home is OFFLINE / not "synced", and `tailClosed` republishes that lockup so the header cannot keep a stale ONLINE line for the whole outage.

## Bootstrap and freshness

**A seat with no file is refused rather than founded, and that is a state and not a failure** ([#1025](https://github.com/srikanth235/centraid/issues/1025) S1). `Core::open` on a seat path that does not exist answers a handle; every read refuses `CoreError::Unpaired`, nothing founds an empty vault behind the member's back, and **pairing creates the replica** by taking the first copy. `Unpaired` is the CORE's refusal on a file with no vault in it; it is not a vault's state in the header. **Unpaired is a state of the DEVICE** — a device holding zero vaults shows the pair flow — and never of a vault, because a vault the device holds has by definition been admitted ([D-1025-S7-9](decisions.md#slice-s7--one-loop-one-file-one-page-one-report-1025)). A held vault has one of exactly three states, all derived from the last pass's outcome and whether a pass is in flight: `STATE_SYNCING`, `STATE_ONLINE`, `STATE_OFFLINE`. Until #1025 the open failed outright, so the only way a phone had a replica at all was a script copying a gateway-role artifact into its container.

**Bootstrap is a blob** ([#1025](https://github.com/srikanth235/centraid/issues/1025) S1, [D-1025-S1-2](decisions.md#the-sync-model--one-authority-many-copies-1025)). It is a file copy and not a walk ([#996](https://github.com/srikanth235/centraid/issues/996) R4): the log has a floor, so "replay from seq 0" is a cursor the gateway refuses to serve from on any vault with history. The gateway keeps a current snapshot per vault — `VACUUM INTO` of the replicated tables with every private one dropped, the same artifact the backup plane and the pre-migration copy use (`crates/vault/src/snapshot.rs`) — hashed with BLAKE3 and placed in that vault's byte store. A seat asks `SnapshotHeadRequest` on a stream of its one connection and is answered `{hash, seq}`; the bytes move on a `blob` stream of that same connection, like any other blob ([#1025](https://github.com/srikanth235/centraid/issues/1025) S2, [D-1025-S2-1](decisions.md#slice-s2--one-protocol-1025)). **The snapshot is rebuilt when a seat asks and the current one is older than the log floor, or there is none** — nothing else is a reason, because a snapshot at or above the floor can still be tailed from and one below it cannot.

The request rides the seat lane's **one** stream. `seat_lane::serve` calls `accept_bi` once per connection and loops on that stream, so a second `open_bi` waits for an accept that never comes ([D-1020-B6](decisions.md#the-byte-plane-and-the-seats-half-1020)); a bootstrap is therefore a message, never a stream of its own.

The transfer is resumable by **verified chunk group**, not by byte range. Every 16 KiB group arriving is checked against the root hash through its bao outboard, so a window that ends mid-download leaves chunks _proven_ to belong to this artifact and the next window is set subtraction over the ranges still missing (`crates/blobs/src/lane.rs`). v0's `bytes=N-` plus `If-Range` ETag pin is superseded with the HTTP door it belonged to, and so is its "moved artifact" retry: a content address cannot move underneath a download, so there is nothing to re-HEAD and nothing to splice. The artifact is `forget`-ed from the seat's byte store once it has been expanded — a seat holding its own vault twice is a phone out of space.

**A bootstrap is ADOPTED, not installed** ([#1025](https://github.com/srikanth235/centraid/issues/1025) S7, [D-1025-S7-2](decisions.md#slice-s7--one-loop-one-file-one-page-one-report-1025)). The gateway builds the blob **replica-shaped**: the same sanitisation pipeline, uncompressed, with `centraid_seat::seat_own_ddl()` run on the copy so the artifact already IS a replica. The seat fetches it as any other blob, **hard-links the verified bytes to the replica's name**, and writes the cursor and the pairing record in one small transaction; the blob is then forgotten, so the store's name goes and the file stays. A re-bootstrap attaches the old file and copies the seat-own tables in that same transaction. The rename is the publication and it is last.

That replaces three full-size files on a phone at once — the blob, a gzip and an expanded database — to produce one. The **room check** is before the first byte: one copy of the artifact for a first bootstrap, two for a re-bootstrap (the old file is there until the rename), refused by name, because checking afterwards is checking after a phone has filled its own disk. A background window may continue the FETCH and never adopts: adoption closes the vault, renames a file into place and reopens it, and a thirty-second refresh cut halfway through that is a member watching their device go blank and come back.

**Paired, with no file yet, is a real state — and it is spelled `STATE_SYNCING`** ([D-1025-S7-6](decisions.md#slice-s7--one-loop-one-file-one-page-one-report-1025), [D-1025-S7-9](decisions.md#slice-s7--one-loop-one-file-one-page-one-report-1025)). The fact is unchanged; what it is called is not. There is no `paired` case in the lockup, because "admitted, nothing has reported yet" and "the copy is 40% here" are the same sentence to a member: Centraid is working on it. A gateway is often reachable long enough to redeem a ticket and not long enough to move a 300 MB artifact. Until the copy lands there is no replica to write the pairing record into, so it lives in the shell's secure store beside the endpoint key — `PairOk` carries the gateway's address and its dialling hints for exactly that — and the member reads "Copying your vault", not "Synced: 0 changes, 0 files".

**A download does not close the seat; only the install does** ([#1014](https://github.com/srikanth235/centraid/issues/1014), lane H). A file cannot be replaced underneath an open SQLite connection, so the seat releases its handle for the swap — but it used to release it before the transport was even built. On a phone that is the whole of a multi-minute download during which every read, every `state()` and every `outbox()` call answered `SeatWorkerNotOpenError`: the member's queued writes unreachable, and `NativeReplicaSession.close()` itself throwing. The handle now goes down in `beforeInstall`, after the last byte has arrived, and the carry-over is read at that moment too — so an intent queued DURING the download travels across the swap with the rest. A bootstrap refused before a byte moves (no room, a mis-addressed artifact) never closes anything at all.

**A seat file has an identity, and it is the VAULT's** ([#1025](https://github.com/srikanth235/centraid/issues/1025) S1, [D-1025-S1-1](decisions.md#the-sync-model--one-authority-many-copies-1025)). The replica, its outbox, its cursor and its byte store are named by `vault_id` and by nothing else. The `(gatewayId, vaultId)` digest v0 and the first v1 wave used was a workaround for a loopback port re-picked each launch, and it made a vault RESTORED onto a second machine a different file — orphaning every replica on every phone along with the queue inside it. A gateway's endpoint id is now a replaceable property of the pairing record: _where to reach this vault right now_, never part of a name or a key.

The artifact is still checked against that identity, and before the destination is touched ([#1014](https://github.com/srikanth235/centraid/issues/1014) C16/C17, ruling R-1014-11). bao proves the bytes are the hash the gateway named; it cannot prove the hash names this vault's snapshot. So the expanded file is asked through its own `core_vault` row, on the STAGED copy, and a mismatch refuses with the old replica and its outbox untouched (`centraid_seat::install::prepare_replica`). Until #1014 the seat wrote its own id over whatever arrived, which left a `Personal` seat holding `Family`'s epoch and rows with no `seat_state`, `seat_outbox` or `seat_outbox_settled` at all.

**Install and naming are one step, and the swap is a rename.** The seat's own tables — `seat_state`, the carried-over outbox and its settled journal — are written on the EXPANDED artifact before it is moved into place, so a kill leaves either the old replica, whole, or the new one, whole. They used to be written after the swap, and a kill in that window left the gateway's file under this seat's name with `seat_state` absent, which reads as "this seat has no copy" and costs the whole artifact again. A file cannot be replaced underneath an open SQLite connection, so the **core** closes its vault around a bootstrap and opens the new file after (`centraid_core::Handle::bootstrap`); that is why the lifecycle lives on the handle and not in a sync pass.

**A repair that cannot repair anything stops.** Under the floor is the same path again — take the current copy — and that is right exactly once per cause and wrong forever: a gateway committing faster than a device can download leaves every fresh copy stale before it lands, so the retry timer re-enters the repair on every pass. **Three re-bootstraps in a row park the seat instead of a fourth** (`centraid_core::REPAIRS_BEFORE_PARKING`, [D-1025-S2-4](decisions.md#slice-s2--one-protocol-1025)), counted on CONSECUTIVE passes and reset by any pass that does not ask for one — a seat that repairs once a week is never parked by three repairs three weeks apart. An artifact served for the wrong vault parks at once, because the answer will be the same in six seconds. Out of room parks it the same way. **Parked means parked: nothing is wiped**, the file and its outbox stay, every screen still reads, and the reason reaches the status line in the member's own words. Before this, a drift the gateway could not resolve was one full artifact download every five minutes on cellular with no user-visible cause.

A phone whose cursor falls below the log's collected floor cannot be caught up — the deltas are gone — so it re-bootstraps in full, and since [#883](https://github.com/srikanth235/centraid/issues/883) C6 it says so: the gateway's rebootstrap frame carries a closed verdict vocabulary plus the retention window it actually keeps, `packages/client/src/replica/rebootstrap-copy.ts` is the one place that turns a verdict into a member sentence, and the frame surfaces it. Retention pinning is implemented ([#1014](https://github.com/srikanth235/centraid/issues/1014) V1/T9): the seat-log door records each device's acknowledged `seq` into `access_device_secret.sync_cursor` with the time it asked, and the sweep's `pruneReplicaLog` holds the floor at or below the lowest cursor any device has moved inside `REPLICA_SEAT_HOLD_DAYS`. The bound is the other half of the pin — a phone that is lost, wiped or never opened again stops holding the log after it, and re-bootstraps once when it comes back. There is ONE log and one floor since [#1014](https://github.com/srikanth235/centraid/issues/1014) R-1014-1, and no compaction: a log row is a full row image, so folding buys nothing a truncation does not. Per-commit row coalescing remains open (#883 question 13, re-scoped by R-1014-5).

**A gap is a batch that starts AHEAD of the cursor, and only that** ([#922](https://github.com/srikanth235/centraid/issues/922) E3). Two catch-up paths legitimately hold the same cursor at once — the bootstrap's convergence replay and the change feed's own sync — so the slower one arrives with a `from` the faster one has already passed. That batch skipped nothing: it OVERLAPS, and every change in it is an idempotent upsert or delete under the same server-version guard. The transport's mismatch classifier (`packages/client/src/replica/shell-transport.ts`) therefore raises `cursor-gap` only for `batch.from.seq > cursor_seq` (or a batch whose `to` precedes its `from`); protocol, schema-epoch and cursor-epoch mismatches are unchanged. Treating an overlap as a gap wiped the store and demanded a re-bootstrap that raced the same way — a loop, not a repair.

### The seat is stale: how to tell

Ask the two numbers, in this order, before anything else ([#1011](https://github.com/srikanth235/centraid/issues/1011)):

| Question | Where to read it |
| --- | --- |
| How far is the gateway? | `sqlite3 <vault dir>/vault.db 'SELECT commit_seq, floor_seq, epoch, schema_epoch, ddl_version FROM replica_meta'`, and `SELECT max(seq), count(*) FROM replica_log` |
| How far is the phone? | `seat_state` in `<app data container>/Library/Application Support/CentraidReplica/centraid-seat-*.sqlite3` — `applied_seq`, `applied_commit_seq`, `gateway_watermark`, `epoch`, `contents` (copy the file with its `-wal`) |

`applied_commit_seq` well below the gateway's `commit_seq` with `gateway_watermark 0` means **no log page has ever been applied** — the snapshot landed and nothing after it did. A `gateway_watermark` that matches while `applied_seq` lags means pages arrived and the applier refused them; a mismatched `epoch` or `schema_epoch` means a re-bootstrap is owed, not a catch-up.

A non-null `deferred_from` with `applied_seq` sitting just below it is neither: it is a metered seat **parked in front of** a commit that crossed the deferral threshold. The applier stops at that commit and leaves the cursor before it, so nothing behind the span is applied either and `gateway_watermark - applied_seq` counts real unapplied work — the watermark line says both, `"1,204 changes behind — a large update is waiting for wifi"`. The span is taken by the next pull the seat makes without the metered flag, and `deferred_from` clears in the transaction that applies it. Stepping over the span and recording only the position lost it permanently: rule 3 dropped those rows on every later delivery while the seat reported `behind: 0` ([#1014](https://github.com/srikanth235/centraid/issues/1014)). A commit that carries a `ddl` row is never deferred — the column it adds is what every later row binds against.

Then ask whether the phone ever knocked. The gateway logs one line per seat door answer into its log ring ([logs.md](logs.md)):

- `seat log page for <vaultId>: since <seq>, <n> rows, next <seq>, watermark <seq>, hasMore <bool>`
- `seat snapshot for <vaultId>: seq <seq>, <bytes> bytes, GET|HEAD`

No `seat log page` lines at all means the phone is not asking, and the device console says why:

- `[centraid] replica: no gateway base — device=<bool>` — nothing resolved a gateway to ask.
- `[centraid] replica: pull did not land — blocked=<bool>[, reason=…]` — `blocked=true` is the member's own transfer rules (`never`); a `reason` is the catch-up's own failure, also kept on the session as `lastSyncError`.
- `[centraid] replica: seat catch-up failed — <error>` — the seat loop's failure, from the door or the applier.

A write this phone makes through a door that is not the session — the camera-roll Import stages and publishes on the gateway, which commits the rows — **nudges the seat once when the batch lands** (`kit/replica/seat-nudge.ts`, called by `runImportBatchWithNudge`), so the owner's own import appears in their library in seconds instead of waiting for the next foreground pull; a batch that published nothing asks for nothing, and this is a single catch-up, never a poll.

A catch-up refused because the mount believes it is offline **schedules a retry**; the connectivity oracle is never set from the pull's own verdict, which is how one transient failure used to latch a phone's copy shut for the life of the mount.

**What actually delivers a gateway write to a phone** ([#1014](https://github.com/srikanth235/centraid/issues/1014) R15/R22/C3/C4/C21). Four triggers, and no one of them is load-bearing on its own:

| Trigger | What it is |
| --- | --- |
| The wake feed | The multiplex SSE radio (`apps/mobile/src/lib/replica/native-multiplex-change-feed.ts`). A frame is a WAKE — the seat pulls its own pages — so a lost frame costs latency, never rows. |
| The feed's own reconnect | Every way a stream ends other than a deliberate `stop()` schedules a reconnect on the existing backoff, the platform cancelling the request included. A stream that delivers no byte for twice the gateway's heartbeat is treated as dead and re-issued: the keep-alive is an SSE comment, so silence is the only symptom a dropped socket has. |
| The foreground clock | While the app is foregrounded and believes it is connected, `NativeReplicaSession` catches up every `REPLICA_PULL_INTERVAL_MS` (a minute). Over a level seat that is one log-page request answering zero rows. |
| A foreground transition | Unchanged, and no longer the only one. |

Until #1014 the feed was the only trigger besides a foreground transition, and it could be muted permanently: one rebootstrap frame latched that scope off and `resume()` — the only reset — had no production caller, so a single verdict took the vault's feed out for the life of the process. The session now resumes the feed when its re-bootstrap finishes, whatever that re-bootstrap reached; a catch-up that did not land still unmutes, or the failure is permanent rather than the next attempt's problem. The live trace this fixes: a foregrounded phone 43 minutes behind a reachable gateway, with `lsof` showing zero connections from either simulator.

**Rows landing produce the invalidation, on the phone too.** The applier's change sink names the TABLES a batch wrote; the browser has wired it since #996 W5 and the phone built its seat core with no sink at all, so another device's rows landed in the file and no screen re-read them. `NativeSeat` carries the sink through a holder — the file is opened before the session that reads it — and the session attaches on `start()`. The same sink carries R24's other half: the intents whose overlay the applier cleared inside the commit's transaction, told after it committed. The phone consumes those now — the pending badge goes and the outbox mirror is invalidated by the store the queue was built over — where before an executed write's badge sat over the very rows that settled it until something else happened to move the queue ([#1014](https://github.com/srikanth235/centraid/issues/1014), C10/C11). The freshness position a screen reads is the applied cursor from that notice, never the cursor a frame predicted.

**One ticket admits exactly one vault.** `Shelf.admit` redeems a ticket into a fresh core at `Replicas.PAIRING_FILE` and takes the single vault `PairOk.vault_id` names; there is no multi-grant and no `VaultLink` per returned vault. A device that holds several vaults holds them because it redeemed several tickets, and each one is independent — its own replica file, cursor, freshness, intent outbox, byte store, endpoint key and revocation state, keyed by vault id and by nothing else. A ticket naming a vault this device already holds is refused with `ERROR_CODE_VAULT_ALREADY_HELD`, checked before the redemption so nothing is burned, and nothing is merged: two vaults with the same display name are two vaults ([D-1025-S7-10](decisions.md#slice-s7--one-loop-one-file-one-page-one-report-1025), [D-1025-S7-11](decisions.md#slice-s7--one-loop-one-file-one-page-one-report-1025)).

**`forget` is local, and the gateway keeps the device enrolled.** `Shelf.forget` is the exact inverse of `admit` — the open core closes, the holding drops off the shelf, and the replica, its byte store, its pairing record and this device's endpoint key are all deleted together, because a half-forget leaves a file with no identity to dial with. It says nothing to the gateway: enrolment ends when someone with the vault revokes this device there. A phone that could revoke itself could lock a member out of their own vault, and a device that has forgotten a vault can be handed a new ticket for it and pair again from scratch.

## Replica correctness and durability

The replica wire has five invariants that every client observes:

- A canonical SQLite write transaction gets one `commitId`. Delta pages extend through the end of that commit group, so a page boundary never exposes half of one transaction. Retention cutoffs use the same boundary rule. Under count pressure the log folds fully superseded commit groups into their survivors (each survivor inheriting the folded prior state) and does **not** move the resumable floor; only the age window and the residual count trim collect history.
- Projected changes carry the row's canonical `rowVersion` when it is nonzero; an omitted version means version zero. Local application ignores an older upsert or delete when a newer version is already stored, which makes overlapping bootstrap convergence and reconnect replay safe.
- Offline intents may carry `baseVersions`. The gateway compares those preconditions before dispatch and returns a structured conflict with expected and actual versions. The client retains the projected row, reason, and both versions until the member edits/retries or discards it. What it SHOWS is not the retained reason: the states the kit has words for say them (a conflict prints both versions, a parked change names the steward), and every other non-accepted state says "Your vault did not accept this change. Try again." — [#1015](https://github.com/srikanth235/centraid/issues/1015) R-SH-7, because the gateway's own `reason` is an exception string wearing a sentence's clothes.
- Every replicated column arrives whole. A seat holds `vault.db` itself ([#996](https://github.com/srikanth235/centraid/issues/996) R1), so nothing is stripped by size and nothing is fetched back on demand; what a seat does not hold is decided per table and per column by R3's private list, not per value. The per-value text ceilings and lazy/deferred fields of the shaped store — [#922](https://github.com/srikanth235/centraid/issues/922)'s SB-text — are superseded with it.
- `coverage` and `durability` are explicit status/result fields. A partial preview is readable and searchable, but it is labeled partial and is never treated as a completed cold start. The native seat has no memory fallback to fall back to: a replica that cannot open its durable database is an error, not an unremembered in-memory session.

Both seats keep one outbox contract, and since [#996](https://github.com/srikanth235/centraid/issues/996) it is one store: `SeatIntentStore` over the seat's own vault file (`packages/client/src/replica/seat/seat-intent-store.ts`), reached in process on the phone and through the worker's `outbox` op in the browser. The browser's IndexedDB outbox and the phone's second SQLite database beside the replica are superseded — the queue is a table in the same file as the rows it is about, which is what lets an executed answer clear its overlay in the transaction that carries its commit (R24). Executed intents use the existing settlement path, which removes input and journals the outcome. Denied/conflict/failed results instead use the existing atomic transition primitive to remain unsettled with their input and row projection. Edit/retry mints a fresh immutable intent id and payload hash, adds its projection first, then truthfully journals the old terminal result; an engine-private supersession marker lets startup finish that handoff if the process stops between those existing store operations. That marker never enters query validation: both seats share one presentation function that strips engine-private fields before applying the projected row. The presentation/revision clone follows the replica's JSON-shaped value grammar and does not require the browser-only `structuredClone` global; the native restart regression runs with that global absent to match Hermes. Revision identity also comes from the blueprint's declared edit-action projection, not by scanning arbitrary `*_id` inputs, so a child write may safely reference a pending parent. A filtered or limited read keeps its canonical page and adds only canonical row ids addressed by pending mutations before composition (`packages/client/src/replica/seat/read-overlay.ts`); one outbox row therefore cannot turn a bounded Home read into a vault-sized scan. Discard journals the last real non-executed result rather than inventing execution. Locker add/edit secrets are explicit online-only actions: browser inline, served, and native callers never present secret plaintext to a durable session. Ordinary non-secret Locker item actions remain outbox-visible through metadata-only row patches. Foreground and background catch-up follow `hasMore` with a bounded sequential loop; an interrupted loop resumes from the last committed cursor.

One gateway SSE connection multiplexes independent vault cursors. A frame never combines cursors or data across vaults. A frame is also the unit of cursor cost: both feeds coalesce a page's advances and debounce the durable cursor write by one second, flushing on background and teardown, so a thousand-change page costs one write and one freshness signal rather than a thousand of each. Foreground UI reports human states (`Offline on this phone`, `Gateway asleep`, `Syncing recent changes`, `Sync paused by transfer rules`, and `Updated …`) plus a timestamp for every source. Those states are learned from ANSWERS, never from configuration: `resolveGatewayBase()` only resolves an address, so a pass that has not yet asked the gateway anything may lower reachability and never raise it, and every gateway request runs under a time-to-first-byte deadline (`apps/mobile/src/lib/replica/gateway-deadline.ts`) because the tunnel listener keeps accepting after its peer is gone. The change feed and the write drain report each outcome, so a vault that dies under a still-connected phone is noticed without waiting for a radio event, and a vault that returns is picked up the same way. See [traps/unreachable-vault.md](traps/unreachable-vault.md). Revocation produces a scoped tombstone: the local cursor and rows for that vault are purged without affecting the other vaults this phone is enrolled in, and a durable member-facing notice is left behind because the purge takes every other trace with it (see below).

A restored device is treated as a cold start, not a resume. The replica databases live in the module-owned durable directory and never ride Auto Backup, device-to-device transfer, or an iCloud restore, but the SSE resume cursors and freshness stamps beside them are ordinary app storage. When a scope's replica file is absent or empty while its cached cursor and stamps are present, both are discarded before bootstrap, so the feed cannot resume at a sequence for rows this device never had. A first launch after pairing has no database and no cache either; that stays silent, because it is a cold start rather than a restore.

Freshness is stored independently per `(gateway, vault)` and advances only after that source successfully pulls or produces a cursor frame. Pulling rows is not moving bytes (#905 O): a foreground read obeys only the `never` floor, so a phone on cellular still pulls its deltas while the Wi-Fi-only/metered/roaming/charger rules keep governing blobs, the write drain and the unprompted background pass. Reads once shared `canTransfer()`, and since `wifiOnly` is the default a cellular phone pulled nothing at all — silently, which Home could not tell from an empty vault. A pull the `never` floor refuses is still neither a landed pull nor a sleeping gateway: nothing was asked, no stamp advances, and the phone says `Sync paused by transfer rules` instead of claiming freshness it never obtained. Offline startup restores those values rather than stamping every source with launch time. Scoped revocation quiesces the drain, exports whatever the gateway never durably took to `revoked-outbox-<vaultId>.json` in the module's durable directory, purges that replica's rows and intents, removes its pinned thumbnail pack, and deletes only that scope from the cached mount/freshness manifests. The revoked notice carries the count — "N unsent changes were saved to this phone" — because "removed" alone was untrue whenever queued edits went with the file ([#1014](https://github.com/srikanth235/centraid/issues/1014), R-1014-12). Every way a revocation reaches the mount converges on `kit/replica/revoke-scope.ts`: the change feed's revoked frame, the seat log door's 401/403, and the intent drain's — the last two used to re-bootstrap against the gateway that had just revoked the device. It also closes the driver handle and deletes the replica SQLite file family — the main file plus its WAL, SHM, and rollback-journal sidecars — because an emptied database keeps its full size for a vault this phone may never see again; a vault that is merely not open is still enrolled and keeps its file. The revocation leaves one durable, dismissible audience notice behind (“No longer shared with you — {label} was removed from this phone”), surfaced through the status bar, because the purge takes every other trace with it. The headless background pass reclaims a revoked scope the same way the foreground does. A revocation reaches a RUNNING phone within one `REPLICA_PULL_INTERVAL_MS` foreground pass even with the wake feed dead, because the foreground clock's own log-page request is one of the doors that converges on `revoke-scope.ts` (the 401/403 lane); the feed's revoked frame is usually faster. A phone that is off or offline learns on its next successful reach, and that window is unbounded by construction — nothing on the gateway can shorten it, so the revocation's security value is what it takes AWAY on the gateway, not when the phone hears.

Coverage is the open vault's own: a file with no completed bootstrap is partial, and no other file can make it look complete. That coverage is read from durable status at mount and after every pull, and carried through the replica context into every query result, so an app killed mid-download and relaunched offline still labels its incomplete library partial — the in-process bootstrap that would have reported progress died with the old process.

Mobile reads `/centraid/_gateway/info` before constructing either foreground or background sessions. `seatReplica` — the snapshot and log-tail doors — must be advertised; the key is optional on the wire, and its absence is what a gateway older than the doors says, which reads as off. A missing or false flag produces one update wall instead of a phone that mounts and then finds no file to fetch. The judgment is asked fresh each time and is not cached: an offline start skips the probe entirely and fails open rather than replaying a remembered verdict, so a gateway that was upgraded — or downgraded — between launches is judged on what it answers now.

## Offline search

Search on the phone answers out of the seat's own file, and it has three lanes.

**Keyword (fts5) — exists.** The snapshot arrives with the gateway's fts5 shadow tables, and the bootstrap re-derives every one of them, found from `sqlite_schema` rather than a registry (`rebuildSeatFtsIndexes`, `packages/client/src/replica/seat/bootstrap.ts`). Coverage is therefore the gateway's `SPECS` (`packages/vault/src/schema/fts.ts`) exactly, with no phone-side index to drift from it — including the derivative-aware document body, so extracted OCR/scan text is searchable offline under `core.document` the same way it is on the gateway. `core.content_item` indexes the owned title alone on both planes.

**People and similar faces (sqlite-vec) — exists.** Face vectors replicate in `enrich_embedding`, and the phone ranks them with `vec_distance_cosine` under the row's own `dim` guard, the way `packages/vault/src/enrich/similarity.ts` does. The vector WIDTH is the gateway's to decide and the phone hard-codes none of it: whatever dimension replicates is what a query carries.

**Semantic (CLIP) — not in v0.** The phone does not run a text or image encoder and does not query semantic embeddings; a member's phone answers keyword and face queries offline and nothing else.

Both existing lanes depend on a native extension the build has to have compiled in, so `ExpoSeatDriver.open` probes both and refuses by name (`ReplicaFts5UnavailableError`, `ReplicaSqliteVecUnavailableError`) rather than letting a shell open and fail inside a member's search.

fts5 is compiled into the SQLite the app links, so it is simply there. sqlite-vec is not: `withSQLiteVecExtension: true` only puts the artifact in the bundle and publishes its path as expo-sqlite's `bundledExtensions["sqlite-vec"]`, and **every connection that wants `vec0` must load it itself** — `ExpoSeatDriver.open` does, once per handle, before it probes. A driver that skips the load gets `no such function: vec_version` from a build that is entirely correct, and the probe then condemns the shell ([#1011](https://github.com/srikanth235/centraid/issues/1011)).

### The sqlite-vec pins

The two planes are on different sqlite-vec versions, deliberately.

| Plane | Version | Pinned in |
| --- | --- | --- |
| Gateway | `0.1.9` | the `sqlite-vec` npm dependency in `packages/server/package.json`, loaded by `packages/server/src/enrich/sqlite-vec.ts` |
| Phone (Android) | `v0.1.7-alpha.2` | expo-sqlite `~57.0.2`'s bundled `android/vec/<abi>/vec.so` |
| Phone (iOS) | `v0.1.7-alpha.2` | `TAG` in `apps/mobile/scripts/build-sqlite-vec-ios.sh`, which builds `vec.xcframework` from source |

The phone's two artifacts must agree, and they are checked against one constant — `EXPECTED_SQLITE_VEC_VERSION` in `apps/mobile/src/lib/replica/sqlite-vec-version.ts` — at build time by `apps/mobile/scripts/sqlite-vec-version.test.mjs` and at open by the seat driver, which asks the extension that actually loaded for `vec_version()`. The gateway's version is not part of that agreement: the planes compare vectors, not extensions, and `vec_distance_cosine` over the same bytes at the same `dim` is the same answer on both. Raising the phone's pin moves a native artifact on both platforms and is a reported change, never a side effect.

## Offline changes and cross-vault placement

Ordinary writes stay in each replica's durable intent outbox. A first-open write made before any bootstrap is also admitted there: the action input is durable immediately, the write reports itself as saved-on-this-phone pending first sync (never a bare "waiting for a connection"), and its optimistic row projection is reconstructed from that durable input — when the first copy of the vault lands, and again on every relaunch, never held only in component state ([#883](https://github.com/srikanth235/centraid/issues/883) D1, restated by [#996](https://github.com/srikanth235/centraid/issues/996) R23). Add/Move uses a separate device outbox keyed by a durable link token. Reconciliation always:

1. commits or confirms the target projection;
2. records that target receipt in the gateway database;
3. for Move only, deletes the source item; and
4. records completion.

Replay is idempotent. A crash can leave a completed target and pending source removal, but cannot delete the source before the target exists. Queued changes may be cancelled. Permission denial, terminal failure, and parked retries remain visible until dismissed.

### Photographs queued for two vaults

One phone holds one upload queue and, at times, several vaults, so a queued item carries the vault it was queued FOR and the queue is keyed by `(content, vault)` — the same photograph offered to two vaults is two rows, two uploads, two writes ([#1014](https://github.com/srikanth235/centraid/issues/1014)). Every gateway call an item makes is addressed per REQUEST (`x-centraid-vault`), never once per client, and a settled follow-up is written only through a session that holds the vault the row names; one addressed elsewhere waits, and the pending surface reports it as waiting for that vault. The first-run camera-roll **Import** goes through this same durable queue rather than posting originals at the gateway itself, so an import survives a kill, obeys the transfer policy, and gives each imported photograph the `upload_item` its device row joins the vault row by.

A retryable failure takes an exponential backoff with jitter between attempts, and an attempt against a gateway the transport never reached spends no attempt at all. Terminally failed rows stay listed with their reason and a Retry; settled rows are pruned once their canonical write has landed, and dismissed failures with them.

A caption typed on a photograph no vault holds yet is merged into that upload's own unreplayed follow-up and travels with it ("Saved with the upload") — it is not a permissions refusal, and the member is never told to ask themselves for write access.

### How an intent settles

An intent travels on a `submit` stream of the seat's one connection and the gateway runs it **under the enrolled device this connection was admitted as**, answering with the commit position the effect landed in ([#1025](https://github.com/srikanth235/centraid/issues/1025) S2, [D-1025-S2-2](decisions.md#slice-s2--one-protocol-1025)). Identity is `(vaultId, intentId, payloadHash)` and never the device, so a restored phone re-enrolling under a new endpoint id replays an outbox the vault answers from its ledger rather than executing twice.

An `executed` answer is the gateway's fact, not the phone's: it says the commit happened, not that this seat holds the rows it wrote. So the answer's **commit position** goes onto the outbox record and the intent waits at `awaiting-change`, and the applier clears the overlay in the transaction that carries that commit — the pending row and the canonical row it was drawn over become visible in the same instant. Where the answer arrives AFTER the seat already applied that commit, the drain settles it against the seat's applied commit position instead, because the applier's hook has been and gone. An answer that names no position waits on `answeredVersions` instead; one that names **neither** is refused loudly rather than parked, because nothing could ever settle it — the deterministic simulation found exactly that on its first run.

Until [#1014](https://github.com/srikanth235/centraid/issues/1014) the drain discarded that number, so every executed intent parked at `awaiting-change` for the life of the install and the pending badge never cleared. And until [#1025](https://github.com/srikanth235/centraid/issues/1025) S2 the v1 sink was `ShutSink`, which reported itself permanently down — so every write a phone made stayed in the outbox forever while the badge honestly said "queued". The cause was one `accept_bi` per connection on the gateway, and the fix was to accept more than one stream rather than to keep the sink shut.

**A member's own queued write is on their screen, not only in a badge — and it is IN THE REPLICA** ([#1025](https://github.com/srikanth235/centraid/issues/1025) S7, [D-1025-S7-3](decisions.md#slice-s7--one-loop-one-file-one-page-one-report-1025)). There is no overlay and no composition. `Request::Intent` on a seat validates the command against the registry — an unknown command is REFUSED and never queued — runs the real handler in a transaction against the replica, captures the row images it produced in the shape `replica_log` carries them, rolls back, and **applies them through the same applier the gateway's own pages go through**. Reads are plain reads.

What makes that take-backable is `seat_pending_rows`: every row the predicted apply touches has its PRIOR image journalled there first, keyed by the intent. Three things consume it, and between them a pending write can always be undone or superseded:

- **the answer lands** — the applier upserts the gateway's canonical row and drops the entry in the same transaction (R24);
- **a canonical page touches the row first** — TRUTH WINS: the same call drops the entry, because a prior image from before a commit the gateway has since made is not a state this device may return to;
- **the write is refused** — the prior images go back, newest first, and the entries go. A row a LATER intent also wrote is not restored; that intent's own journalled prior is rewritten to this one's, which is the only answer that is right for both orders.

The invariant is one sentence and the walking skeleton asserts it: **an empty outbox means an empty journal means a replica that is byte-for-byte the gateway's replicated tables.** The predicted apply emits a `RowsChanged` like any page, so a member's own write moves their screen through the one change-stream consumer every other change moves it through — there is no pending-write event kind and no screen has to learn one.

The old paint could not add a row, remove one, or add a column, and each limitation was written down honestly because there was nothing behind the paint that knew any better. An apply has no such limitations, and `crates/apps/kit/src/overlay.rs` is deleted.

One gesture mints one intent id. Idempotency across RETRIES comes from the outbox row — a retry re-sends the id the gesture minted and the gateway answers from its retained outcome — never from hashing the payload, which collapsed two legitimate identical writes ("+1" twice) into one. An id supplied by the caller (the upload queue keys on the file's digest) is passed through untouched.

A successful send retires the transport reason an earlier attempt wrote, so a `fetch failed` line is never shown under an intent that has since executed.

### The phone renders the display rungs the gateway cannot decode

Both device ingress paths — the upload queue and the first-run camera-roll **Import** — contribute the preview ladder's `thumb` and `preview` rungs, plus `phash` and `thumbhash`, from bytes the phone decoded itself. For HEIC/HEIF that is not an optimisation but the only source: the gateway's preview codec is sharp, and the `@img/sharp-libvips-darwin-arm64` build this repo pins ships libheif **without an HEVC decoder** (HEVC patent licensing), so the HEIC an iPhone actually captures declines on the gateway and earns the durable `preview-codec@1` "unsupported" stamp that makes recognition skip it ([#1011](https://github.com/srikanth235/centraid/issues/1011)). iOS decodes it natively.

The rungs go through the ledger's variant door (`POST /centraid/_vault/blobs?variant=…&variant_of=<sha>`), at the ladder's own edges — imported from `@centraid/core/blob`, never mirrored — fitted to the long side and never upscaled. **Order is the contract**: `variant_of` must identify staged or claimed content, so Import stages the original, contributes the rungs, and only then publishes; a rung on the row before the claim means recognition never sees the asset without one. A rung that fails to render or contribute is never fatal — the item stays exactly as backfillable as it was. See [the derived ledger](photos/derived-ledger.md).

### An absent writability answer is not a refusal

A row on the phone says which vault it came from and whether the member may write there (`kit/replica/row-provenance.ts`). **A row with no such stamp is writable**: a locally projected pending row, a camera-roll photograph that is not in the vault yet, and a session whose scope has not landed all carry no answer, and none of them is the vault saying no. Only an explicit `canWrite: false` — the scope the gateway actually answered for a container the member may only read — draws the read-only sentence. Photos' timeline stamped its rows the other way round until [#1011](https://github.com/srikanth235/centraid/issues/1011): a camera-roll row carried no answer at all and a replica row defaulted an unknown scope to `false`, so the owner's own vault rendered every lightbox as read-only.

### A re-bootstrap keeps the queue, and holds it

A seat under the floor takes the **same path** a seat with no copy takes: there is no repair branch and no partial catch-up, because the deltas between its cursor and the floor are collected and no amount of asking brings them back ([#1025](https://github.com/srikanth235/centraid/issues/1025) S1). A re-bootstrap replaces what the gateway gave this seat. The queued intents, their order and the bytes they need are the three things the gateway has never heard of, so they survive it: the outbox is its own table in the shared file, `created_order` is carried verbatim (renumbering the queue would reorder the member's work), and the overlay is rebuilt from that outbox rather than from component state.

**The queue is on disk for the whole swap, and it never leaves a database.** The outbox and the settled journal are carried from the live replica onto the staged one with `created_order` **verbatim** — renumbering the queue reorders the member's work — and the rename publishes both at once, so there is no window in which the intents are nowhere. v0's `<seat>.carry-over.json` sidecar existed to survive a platform whose install deleted the destination before moving the new file in ([#1014](https://github.com/srikanth235/centraid/issues/1014)); a rename has no such window, so the sidecar, its token in `seat_carry_over` and its replay are superseded. A retried install is idempotent on the intent id.

While the repair runs, a write is **admitted and held** ([#996](https://github.com/srikanth235/centraid/issues/996) R23): refusing would make "saved" untrue during a repair nobody asked for and nobody can see, and sending would let an outcome be reconciled against a copy that is about to be replaced. The member is told the change is saved and will send after; the drain resumes from the outbox the moment the new copy is in place.

**Bytes a queued intent still needs are not evictable** (R25, [#1025](https://github.com/srikanth235/centraid/issues/1025) S3, [D-1025-S3-7](decisions.md#slice-s3--bytes-both-ways-one-store-1025)). An intent names the blobs it cannot run without in its own record (`IntentRecord.needs_blobs`, and on the wire `Intent.needs`), and `outbox::pinned_blobs` reads them off every unsettled row. `ByteStore::sweep` subtracts those pins **before it orders anything**, so a pin is never an eviction candidate structurally rather than by a filter at the end: a store over budget _because of_ pins reports `over_budget_by` instead of breaking the promise. Those bytes are the one copy of a write the member has already made — the gateway does not have them, which is why the intent is still queued — so evicting them loses the photograph and no later window can recover it.

The pin list is read from the durable column, not from an in-flight report, so a phone killed mid-pass still knows what not to take at next launch; an outbox that cannot be READ means the sweep does not run at all, because an empty pin list and an unreadable one are not the same fact. Order is oldest-first by the data file's own mtime — there is no access time to read and a phone is usually mounted `noatime` — which is the right order for a cache the planner fills newest-first. Nothing is inferred from a filename.

### Bytes both ways, one store

**A device holds one content store per vault** — iroh's, at `<stem>.bytes`, read by the grid and written by the window alike ([D-1025-S3-1](decisions.md#slice-s3--bytes-both-ways-one-store-1025)). It used to hold two: a flat `<vault>.blobs/` CAS the vault's byte door wrote and `content_location` read, and the byte plane's store every transfer wrote. A photograph a seat FETCHED could not be displayed and one a window MINTED could not be served, on the same device, for the same vault. `content_location` now answers with iroh's own data file, read in place — a phone that exported every cell of a camera roll would hold the roll twice — and the store inlines nothing, so every complete blob has a file to answer with ([D-1025-S3-2](decisions.md#slice-s3--bytes-both-ways-one-store-1025)).

**A photograph taken on the phone goes UP, and the gateway pulls it.** The bytes land in this seat's own store first; the intent that files them names them; and the gateway fetches them over the connection _the seat opened_ — it cannot dial a phone — verifies them against the hash bao proves, and commits the content row only then. Bytes commit after rows, and never only on a phone. A pull the window cuts leaves the write **queued**, not failed: the member's train went into a tunnel, which is not a rejection ([D-1025-S3-5](decisions.md#slice-s3--bytes-both-ways-one-store-1025), [D-1025-S3-6](decisions.md#slice-s3--bytes-both-ways-one-store-1025)).

A byte pass plans over the rows **that pass** applied, not the ones it started with, so a photograph whose row arrives in this window has its bytes asked for in the same window rather than the next ([D-1025-S3-8](decisions.md#slice-s3--bytes-both-ways-one-store-1025)).

**A landed byte is a row** ([D-1025-S7-20](decisions.md#slice-s7--one-loop-one-file-one-page-one-report-1025)). "Does this device hold these bytes?" used to live only in the byte store's actor, so a blob completing was not a row change and a page read could not ask the question at all — a grid drew a hundred and twenty placeholders over a device holding nineteen photographs, and the only surface that ever showed one was Home's four-cell mosaic, which made a `content_urls` trip nothing else made. The byte pass now keeps `seat_blob_held`, a seat-own table beside the outbox and the cursor: written in the window a blob completes, released in the window the sweep forgets one, carried across a re-bootstrap, and **rebuilt in full from the store at every core open and after every adoption**, because a projection only ever written incrementally drifts and drift here renders exactly like a photograph that has not arrived. A page read asks for `with_held_thumbnail` and the door appends a `thumbnail_path` per row, resolved thumbnail-tier-first with the original as the fallback; the byte door's embed refusal is decided where the path is produced and stored as one `drawable` column, so a read cannot hand out a path for bytes the door would refuse and cannot express the unsafe question either.

**And a blob landing wakes a screen through the ordinary change stream** ([D-1025-S7-21](decisions.md#slice-s7--one-loop-one-file-one-page-one-report-1025)): the seat joins a completed hash back to `media_asset.asset_id`, the core emits one `RowsChanged` over `media_asset` with `commit_seq: 0` — bytes arriving is not a commit — and the `BytesArrived` event is deleted. It only ever existed because the ids the core had were content ids, which matched nothing any screen was showing.

### Shared-container writes and cursors

A shared container is not a special borrowed scope. Its domain rows and blobs are real residents of each joined member vault, so the ordinary per-vault replica, backup, search, and attachment paths cover them. The phone still has exactly one physical replica cursor for that vault even when the vault subscribes to many shapes.

Offline writes into a shared container use the ordinary durable replica outbox — the same one every other write uses ([#929](https://github.com/srikanth235/centraid/issues/929) retired the separate `share_commons_intent` rail). What travels is a **signed replica intent** the ORIGIN executes: the phone's vault signs the canonical envelope, the origin verifies it and invokes, and the receipt names the member. The pending row is an honest UI overlay, not an optimistic domain record; when it parks it carries a structured `waitingOn` of kind `owner`, `origin` or `gateway` with the label from the link, so the phone can say who it is waiting for in the same words the web seat uses. Revoking the share settles that shape's queued intents as `expired` with "no longer shared with you".

Minting a share is not one of those offline writes. `tally.group` is v1's one edit-capable subject, so the phone's single producer is the share row on a Tally group: it opens the share sheet when the gateway is reachable and WITHHOLDS the verb with its own sentence when it is not — an unreachable gateway is a different screen from a refused grant, and neither is an empty ledger.

`share_subscription.cursor_seq`, keyed `(shape_id, audience_vault_id)`, is how far this vault has ingested one shape, alongside the physical replica cursor. Ten shared Tally groups in one vault therefore mean one vault cursor plus ten shape cursors, not eleven sync engines. The vault cursor transports the resulting row changes; each origin orders its own shape independently. A late join or a restore starts from a bootstrap at the origin's current epoch and follows changes from there; a changed `cursor_epoch` is a re-bootstrap, never a silently extended floor.

### The chain, and where its numbers come from

Five changes made offline against one row execute in order, once each, when the radio returns ([#996](https://github.com/srikanth235/centraid/issues/996) R23). The edges are derived on the seat from what the outbox minted, the held dependents say "Waiting on an earlier change" rather than "failed", and a conflict raised by a second writer stops the head of the chain with both versions on the row and Retry/Discard beside it.

**Every write states a base version, including the chained ones and the destructive ones** ([#1014](https://github.com/srikanth235/centraid/issues/1014) R18/R23/R24). The chain's _dependency_ and the write's _base_ are different facts and are derived separately:

- `dependsOn` says this write may not run before that one. It comes from the ids the input names against the ids the outbox has minted.
- The base version is the `row_version` the seat OBSERVED on the row, read from canonical rows only — the overlay is bypassed, so a queued edit never becomes its own base and a retry observes the row that rejected it.

The one case with nothing to observe is a row only a queued predecessor will mint: the gateway has never seen it and never will, so the write names the predecessor (`{"$intent": …}`) instead of a version. Every other row — an existing photograph edited twice, a row being trashed — carries the number.

The gateway then REBASES a chained write before checking it: the predecessors executed first and moved the row, so the child is compared against the version its parent produced (read out of the parent's durable outcome, ordered by commit position). A third party's edit landing between parent and child is still a conflict, which is the point.

A base version is a `row_version`, never a log position. The two are different numbers in different units, and comparing one against the other is how an offline edit of a much-touched row used to come back "expected 432, found 2".

Four intervals of that arc are measured on node against the production session and a real file — `mobile/durable-save`, `mobile/pending-render`, `mobile/restart-recovery` and `mobile/reconnect-drain` in `tests/journeys.json`, all at `none/ci-linux-x64-4c`. Every one is a LOWER BOUND on the phone: no network RTT, no flash, no render. The phone's own numbers are the `device-fixture/ci-android-emu` rows, which are `unmeasured` and name the Android airplane flow as their probe.

## Background work and push privacy

The Expo background task maps to BGTaskScheduler on iOS and WorkManager on Android. It runs the same pull, intent, placement, and upload queues as the foreground and calls the same metered/battery upload policy. Platform timing is opportunistic; correctness always comes from the durable outboxes and the next foreground pull.

**The pass never opens a seat the foreground holds.** A seat file is opened under a lease — a `<seat>.lease.json` sidecar naming an owner (`foreground`, `background`) and an expiry, read before SQLite is touched at all — and the headless pass asks for it with `useNewConnection: true`. If a live lease names another owner, `NativeSeat.open` refuses with `SeatLeaseHeldError` and the pass counts that vault as `skippedLive`, not as a failure: a live mount is already doing this pass's work. The lease is renewed on each `sync()` and released on close or purge, and it expires so a process the OS killed mid-pass never strands a vault. Both halves are needed and neither is enough: expo-sqlite caches connections by database name, so without `useNewConnection` the two handles are the same object and the pass's `finally` closed the foreground's ([#1014](https://github.com/srikanth235/centraid/issues/1014)); and without the lease they are two writers over one outbox, which the queue's ordering and R24's in-transaction clear both assume they are not. The phone's upload database is shared the same way, by one reference-counted handle in `native-queue.ts`: five entry points used to open and close it independently and the first one out closed it under the rest.

One pass owns **the platform's own deadline** ([#1025](https://github.com/srikanth235/centraid/issues/1025) S5, [D-1025-S5-4](decisions.md#slice-s5--the-shells-half-1025)), checked between stages and also driven by the platform's own expiration listener. It was a fixed 20 s for one wave, with the remainder of Apple's ~30 s called teardown headroom — a constant standing in for a number only the OS knows, and a third of the window thrown away for headroom the expiration handler already provides for free. `BackgroundTasks.window(wake)` states it per platform and per wake reason; **iOS publishes no API for a `BGAppRefreshTask`'s remaining time**, so what it states is Apple's documented window and it says so in those words rather than as a measurement. The expiration handler stays the second, independent trigger, because it is the half that is actually the OS speaking. A pass that runs out of budget stops at a stage boundary instead of being killed mid-stage, and reports what it managed. Scopes are isolated from each other: one scope whose pull or bootstrap fails never cancels the remaining scopes, and the device outboxes — placements, then uploads — still drain afterwards, because their rows are durable and target their own vault. The pass also asks the platform for the real connectivity answer rather than assuming a radio, and it reclaims a revoked scope's files exactly as the foreground does.

**The Wi-Fi and charger rules are a SELECTOR, not a number the shell computes** ([#1025](https://github.com/srikanth235/centraid/issues/1025) S5, [D-1025-S5-4](decisions.md#slice-s5--the-shells-half-1025)). A foreground wake asks for a foreground window; a background wake on a charger and an unmetered link asks for the night shift; every other background wake asks for a short refresh. `crates/blobs` owns what each of those costs in bytes and items, and the window names the plan rather than restating the sizes — a Kotlin and a Swift copy of that arithmetic would drift from the Rust the moment either number changed. `metered` rides beside the selector because it is a separate fact (a night shift on a tethered phone is a night shift, metered) and it changes WHAT crosses rather than only how much: **no originals at all**, thumbnails and previews still. A ceiling could not have expressed that — the planner admits an item larger than the whole budget on purpose, because that is the only way a 900 MB video ever crosses, so a metered window bounded only by bytes would start the video and resume it every window until the bill arrived.

**The member's transfer rule is the third input, and it is the member's own** ([#1025](https://github.com/srikanth235/centraid/issues/1025) S4, [D-1025-S7-60](decisions.md#slice-s4s5--the-members-transfer-rule-and-fetch-this-one-now-1025)). Bytes are never pushed; they are PLANNED, and the plan is a setting: the gateway does not know which SIM is in the phone, whether the member is abroad, or what they agreed to, so the phone decides what it pays for. One rule per **device** — what it governs is a data plan, and a phone has one however many vaults it holds — kept in the shell's secure store (`TransferRule`, superseding `TransferPreference`) and passed as part of the window.

| rule | on Wi-Fi | on a metered link |
| --- | --- | --- |
| `wifi-only` (**default**) | every original | no originals |
| `wifi-and-cellular-photos` | every original | a photograph's original; **a video's never** |
| `manual` | no originals | no originals |

Thumbnails always cross, on any link and ahead of everything, because they are kilobytes and they are the grid; previews cross on any link bounded by the short-refresh budget. Only the originals are a member's decision, which is why the enum has no other cases. **Videos never on cellular is a fixed rule**, not a fourth setting: the two differ by three orders of magnitude and a member who said "photos on cellular" did not say "a 900 MB video on cellular". `manual` is not "Wi-Fi off" — a member on unlimited fibre may want a phone that holds thumbnails and fetches a full-size photograph only when asked, because the constraint being spent is the device's disk.

The rule and `metered` are two fields and not one, because they are separately true: `manual` withholds on an unmetered link too, which no spelling of a metered flag could say. **No shell computes any part of the table** — `centraid_blobs::Budget::admits_original` is all of it, in Rust, in one place; a Kotlin or Swift copy of the rule that decides a member's bill is the worst candidate for a second copy. The sheet that sets it is reached from the header's own "N originals waiting for Wi-Fi" line ([D-1025-S7-61](decisions.md#slice-s4s5--the-members-transfer-rule-and-fetch-this-one-now-1025)): a grid of thumbnails with no full-size files is a DECISION and not a failure, and a header that says nothing is how a working byte plane looks broken. A member who wants one photograph now taps it and gets it — `seat.bytes.fetch` overrides the rule for that one item ([D-1025-S7-63](decisions.md#slice-s4s5--the-members-transfer-rule-and-fetch-this-one-now-1025)), and the upload half obeys the same rule, because a sheet governing one direction lies by omission.

Registration is observable rather than assumed. Whether the background task and the push task registered, why one refused, and the platform's own availability verdict are recorded durably and rendered on the storage screen, so “Background App Refresh is off” is a sentence the member can read instead of a sync that silently never runs.

The active vault is ordered before the other cached scopes before the background feed's mount bound is applied. Upload rows persist that target vault, and headless reconciliation replays the canonical follow-up through the session it holds open; transferred bytes therefore cannot settle without their app mutation merely because the app was backgrounded.

The pass is also where diagnostics traces land. Spans (#927) buffer in a bounded in-memory ring while the app runs — a phone doing disk I/O on a scroll is exactly the cost the traces exist to find — and are written to `<replicaStorage>/diagnostics/traces.jsonl` in the pass's `finally`, so a pass that timed out still lands what it recorded. The write swallows its own failures and the ring is dropped if the OS kills the app first: a diagnostics buffer, not evidence. Tracing is OFF unless `EXPO_PUBLIC_CENTRAID_TRACE=1`; the work counters underneath are always on and are integers. See [logs.md](logs.md).

The gateway push relay is wake-only. Its payload contains no vault id, item id, title, content, cursor, or owner data. Push delivery can make a background pull happen earlier, but loss or throttling cannot lose data. iOS background push is therefore treated as an optimization, in line with Expo's delivery guidance.

**There is no push wake in v1, and that is a recorded non-goal** ([D-1025-S7-41](decisions.md#slice-s2--the-tail-stream-1025)). `WakeReason.PUSH` keeps its slot because the enum is the whole payload and a broker would fill in nothing; what is missing is a way to deliver the wake that does not put a third party between a member and their own vault. Three options were considered and the decision is written down in `decisions.md`. Until one is taken, a phone that is not in the foreground learns about a change on its next background window or its next foreground — which is the same guarantee this product has always made, because correctness comes from the durable outboxes and the cursor, never from timing.

## Thumbnail packs and budgets

Each source gets a pinned thumbnail pack containing the recent 90 days plus favorites, with an independent 128 MiB budget and oldest-first eviction. Displayed rows prefer those local pixels, and a surface that has to explain an empty cell says which of the two things is true: with no pack for that vault the photographs are on the gateway, and with a pack in place these particular ones are not in it. One source cannot evict another source's offline pack. The Phone storage screen reports, per vault:

- replica database bytes;
- pinned thumbnail bytes; and
- pending upload bytes.

Database bytes mean the complete live SQLite family: the main file plus WAL, SHM, or rollback-journal sidecars. Pending bytes come from each upload row's durable target vault, never from whichever Space happens to be focused when the screen opens. Legacy pre-target rows are reported honestly as unassigned instead of being fabricated into a vault total. Tapping a vault total expands its database, thumbnail, and pending-upload components.

Per-vault cards reach only the open vault, so the screen adds an `Other Centraid data on this phone` section for what they cannot see: the upload queue's own database family, and replica databases on disk that no open vault claims (an unopened or revoked vault's files, plus any near-empty reader host database left behind by the superseded mount plane, which the screen has no gateway id to name separately). That section reports; it never deletes.

Neither the screen nor the budget check may cost the size of what it measures. Pending bytes, counts, and the unassigned bucket come from one `GROUP BY target_vault_id` aggregate over the upload queue rather than from its rows; queue rows are read in bounded pages with a `created_order` keyset cursor, which is also how one upload drain pass walks a deep backlog. Pack totals come from the native module's single-crossing `directorySize`, and eviction pays for a per-file listing only once that total says a source is over budget. Pack downloads take the same durable transfer policy as uploads — Wi-Fi-only, metered, roaming, and charger rules govern thumbnail bytes exactly as they govern originals.

`Free thumbnail cache` removes only reproducible thumbnails. Replica rows and pending changes are not cache and are never removed by that action.

Low disk fails closed and preserves the last readable projection, and it does so mid-session rather than only at start-up. op-sqlite's `SQLITE_FULL`/errcode 13 and OS `ENOSPC` variants are normalized into one actionable screen error wherever they surface. A delta that cannot be applied for want of room PARKS the change feed: the one-second retry cadence stops instead of re-applying the same failing batch forever, the cursor and rows stay exactly as they were, a later feed frame does not restart the loop, and the surface says the phone is out of room. Freeing space resumes the parked feed from its durable cursor. Replica rows and pending intents remain untouched throughout, and the person can free the reproducible thumbnail cache or other phone storage before retrying. Centraid never evicts canonical replica rows or queued writes to manufacture free space. The device contract test pins that classification and copy; the vault custody test fault-injects the same SQLite-full condition during `wal_checkpoint(TRUNCATE)` and requires the gateway disk-health tracker to turn red.

## Durable path and at-rest decision

Replica databases, pending intents, upload queues, and thumbnail packs live in a native module-owned durable directory:

- iOS: `Application Support/CentraidReplica`, excluded from iCloud backup and protected with `completeUntilFirstUserAuthentication`;
- Android: credential-encrypted `noBackupFilesDir/CentraidReplica`. The app excludes ALL of its data from Auto Backup and device-to-device transfer, not just this path: the manifest sets `allowBackup="false"` with backup and data-extraction rules that exclude every domain (cloud and device transfer alike). `android/` is generated ([#996](https://github.com/srikanth235/centraid/issues/996)), so config is the only source: `app.config.ts` sets `android.allowBackup`, and `apps/mobile/plugins/withCentraidAndroidPrivacy.cjs` writes the two rule files and points the manifest at them in place of the narrower `@xml/secure_store_*` pair expo-secure-store would otherwise leave there. The AsyncStorage backend moves with a build flag, so a path-level exclude would be the fragile version of this rule.

One vault's seat file is named after the pair `(gatewayId, vaultId)`, so two vaults on one gateway are two files and one vault on two gateways is two files. There is no stand-in for a gateway id: a mount either resolves one before it names a file or refuses with a waiting state the next reachability wake retries ([#1014](https://github.com/srikanth235/centraid/issues/1014), P14, ruling R-1014-11). The literal `"manual"` that used to fill the gap named a file whose path MOVED the moment a real endpoint id arrived, orphaning every write queued in it; a phone that already ran it has that file renamed onto the resolved name once, and never over a live seat. The "last reachable base" is likewise per gateway rather than one global value, so a phone paired with two desktops does not open one vault's seat against the other's port ([#1014](https://github.com/srikanth235/centraid/issues/1014), P13). Storage accounting counts these files by the name they actually have (`centraid-seat-`), so an unmounted or orphaned seat is visible rather than silently held.

These files survive OS cache eviction and disappear on uninstall. Centraid does not add SQLCipher or field encryption to the local projection in this version. That decision preserves the seat's own SQLite/FTS read plane and the cold/search budgets, while relying on iOS Data Protection and Android credential encryption for at-rest protection. Phone at-rest encryption is expo-sqlite's `useSQLCipher` flag ([#996](https://github.com/srikanth235/centraid/issues/996) R14), and desktop and web file encryption is a later driver swap over the same file format. The seat's copy is backup-excluded and contains no blob originals; a future stronger app-layer scheme must preserve seat-local search and publish measured cold/search costs before replacing this decision.

An optional biometric app lock adds a user-presence layer before the seat's file is opened. Its gate is stored with SecureStore `requireAuthentication`; moving the app out of the foreground clears the decrypted credential cache, unmounts replica sessions, and paints an opaque switcher mask. This complements the OS at-rest controls above—it does not turn the replica into an independently encrypted database.

Locker is stricter than the ordinary replica plane in ONE direction: the secret half. The browsable half is not. `locker.item` visibility is not a grant question at all — listing an item is not unlocking it, and since [#996](https://github.com/srikanth235/centraid/issues/996) wave 6 (W6-D2) the unlock boundary is the shell's, which holds the vault's key `K` and hands an app one row's plaintext per receipt through `window.centraid.locker.reveal`. The permit tier, the `authenticate` op and the gateway's Locker reveal arm are deleted with it ([#928](https://github.com/srikanth235/centraid/issues/928) AP-locker-boundary superseded). So the window, the archived and trash shelves and the search run the app's own `packages/blueprints/apps/locker/queries/{items,search,trash}.ts` against the seat's own file, through `apps/mobile/src/apps/locker/locker-reads.ts`. No sealed column can ride those rows: `packages/vault/src/replica/locker-sealed-columns.test.ts` asserts every sealed column of every sealed entity is structurally unavailable to the replica lane, by name rather than blanked. The Watchtower decoration (weak/reused/last4) is derived inside the sealed boundary, so a local read asks for it as an `optional` invocation and answers UNDECORATED when it cannot be reached: the two row keys and the payload's `watchtower` summary are then ABSENT, and `review-model.ts`'s register says those checks did not run rather than clearing every password. `apps/mobile/src/apps/locker/locker-airplane.test.ts` holds the three reads with every `lib/gateway` door throwing, and `tests/integration-mobile/locker-rows-parity.integration.test.ts` holds the phone and the web seat to identical payloads over the same rows. The seat still boots locked and drops its rows on a lock — a locker that drew its own list behind its lock screen has not locked anything — and unlocking remains online.

Its native cover performs authentication and reveal through online-only app queries, and its two secret-bearing WRITES take an online-only transport door of their own: `NativeWriteInput.onlineOnly` posts the action straight to the app's handler and never enqueues, mirroring the browser bridge's `opts.onlineOnly`. A gateway it cannot reach is a failure, never a queued row — falling back to the outbox is exactly what the flag forbids. The action list is `packages/blueprints/apps/locker/writes.ts`'s `ONLINE_ONLY_ACTIONS`; `apps/mobile/src/lib/replica/locker-online-only.test.ts` pins the seat's half. Passphrases, biometric device secrets, memory-session tokens, one-shot item permits, and revealed fields never enter replica rows or durable intents. The local biometric secret is random, device-only SecureStore material; only a vault-key-peppered verifier reaches the gateway database. Locker's memory-only session lives in one process-level store (`apps/mobile/src/apps/locker/locker-store.ts`) rather than a React context, so no remount can reconstruct a session the boundary ended.

Tally is ordinary in both directions now — its writes queue and its derived reads run locally. Every Tally act carries an optimistic pending projection (`packages/blueprints/apps/tally/pending-projection.ts`), so the native cover issues all of them through `session.write` and they queue in the durable outbox when the gateway is out of reach — that is what "record-only and fully offline-capable" means on a phone. The one exception is `materialize-recurring-expense`, whose occurrence id is minted by the canonical recurrence engine: the projection excludes it by construction, so the seat WITHHOLDS the verb while offline rather than queueing a copy of an expense nobody issued. Reads run the app's ONE balance engine ON THE PHONE: `apps/mobile/src/apps/tally/tally-reads.ts` imports the seven `packages/blueprints/apps/tally/queries/*.ts` modules the web seat imports and runs them against the seat's own file through `apps/mobile/src/lib/replica/inline-query-ctx.native.ts`. There is still exactly one derivation of "who owes whom"; it simply no longer needs a network to reach it, so a member on a plane sees complete balances rather than a spinner. A refused read and a seat with no copy yet are different screens, and `apps/mobile/src/apps/tally/tally-store.test.ts` pins that a failed read never reads as an empty ledger.

**That read carve-out is gone.** SB-tally ([#922](https://github.com/srikanth235/centraid/issues/922)) reverted it in wave 4 (E7): the phone runs the same `queries/*.ts` modules the web seat runs, over the same rows, and `tests/integration-mobile/tally-balance-parity.integration.test.ts` holds the two seats to the identical dashboard. The seat's `__centraid*` provenance is stripped before a handler sees a row, so neither seat's payload carries the other's bookkeeping. Tally's ten-minute stale clock went with the RPCs — a read of this device's own replica is as current as the device is, and a replica behind the vault is the frame's own line, not a verdict about the ledger. See [decisions.md](decisions.md#snappier-blueprint-apps-922).

## Performance guardrails

The ceilings below are the current contract; the measurements under them were taken against the superseded shaped store and are kept as the provenance of the numbers, not as a description of how a read works now. `tests/journeys.json` is the enforced ledger either way.

The checked 50,000-row fixture spans 2016–2025 across four household sources. Its current pending-write variant adds 200 durable SQLite outbox mutations (50 per vault) before starting either timer. On the 2026-08-11 macOS arm64 development host it measured a 778.4 ms cold 5,000-row merged/sorted read, a 4.5 ms FTS lookup, and 22,622,208 projection bytes. At that observed density the 5,000-row bootstrap window is 2,262,221 bytes. The browser perf lane separately opens IndexedDB, enqueues 200 intents, and budgets their full overlay enumeration/composition at one tenth of its registered 2,500 ms real-I/O ceiling. The same native evidence lane encodes twelve reproducible 256px/82%-quality thumbnail samples: the 13,726-byte p95 projects a 12,820,084-byte recent-90-day plus 5%-favorite pack for each 12,500-item source, within its 128 MiB ceiling. The lane enforces the 1,000 ms cold, 100 ms search, 4 MiB bootstrap-page, and 128 MiB thumbnail ceilings; `tests/journeys.json` records the volume, probe, observation, and headroom. Native build/install/launch checks prove the modules load on both platforms; the Android mobile journey owns the airplane-mode UI/process proof, with the rendered SQLite restart companion — `apps/mobile/src/apps/tally/PendingRestartJourney.test.tsx`, which drives the Tally cover through a real process restart over the same production reader — covering it on iOS-compatible infrastructure.

### Where 50,000 rows came from, and where it stops (#659)

50,000 is a measured fixture, not a product ceiling. A household that keeps a phone camera for a decade plausibly reaches 90,000 items by year three of using Centraid, so the envelope has to say what happens there rather than imply the number cannot be exceeded.

Scaling the 2026-07-29 measurement linearly — a projection from that run, **not** a new measurement — a 90,000-row set is about 39.9 MB and about 1,013 ms of cold read. That was over the 1,000 ms ceiling, and it was over it for a structural reason since removed: the reader answered every request by selecting every row of the entity, parsing each JSON payload in JavaScript, and only then applying the caller's filters and limit. Cost tracked the size of the library instead of the size of the answer.

Two changes retired that shape. #659 pushed the filters and the limit into SQLite and ran the statement off the JS thread; [#996](https://github.com/srikanth235/centraid/issues/996) removed the JSON payload the parse was for — a seat reads the vault's own typed columns. What that leaves as the envelope:

- **A bounded read costs what it returns.** A filtered lookup and a keyed fetch do not scale with the library, so they hold at 90,000 rows and beyond.
- **An unbounded read still costs the whole entity.** Photos deliberately reads its full asset set to merge the camera roll against it. That path scales linearly and is the one that leaves the 1,000 ms budget somewhere between 50,000 and 90,000 rows on the reference host.
- **The cross-source page refusal is superseded.** [#883](https://github.com/srikanth235/centraid/issues/883) D1 exempted content-hashed entities from the pushed limit because equal bytes in two attached vaults collapsed into one badge-carrying row. One open file cannot produce two answers to "which vault is this from" (R12), so the case it guarded no longer exists.

**What an ordered read costs** ([#996](https://github.com/srikanth235/centraid/issues/996) W5). A seat holds the vault's own file, so an ordered read is a keyset statement over the canonical table and its ordering is served by a composite index stated in the baseline DDL — `(equality predicate columns, sort column, primary key)`, in `packages/vault/src/schema/read-path-indexes.ts`. The plan snapshot in `packages/server/src/serve/app-query-plans.snapshot.md` is the assertion: it went from 36 `USE TEMP B-TREE FOR ORDER BY` steps to 0 when those indexes landed, and it is regenerated with the schema. **What this replaced:** the shaped store kept two EXPRESSION indexes per ordered column over `replica_row` — `replica_row_ord_*` and `replica_row_cen_*` over a fixed 0–5 `censusClass` ladder — with a census probe per guard, a per-session `ORDER_INDEX_MAX` cap, and a spelling rule that made a renamed helper silently un-index a read. The census, the ladder and the cap are gone with `replica_row`; a stated index over a real column has no second spelling to drift from.

**No read truncates silently, on any seat** ([#922](https://github.com/srikanth235/centraid/issues/922) 0a), and since [#996](https://github.com/srikanth235/centraid/issues/996) wave 4 no app read leaves its window unspoken at all:

- Every screen read is a page a handler wrote. A read that is a whole set walks it (`readPages` in `apps/mobile/src/kit/hooks/useSeatPages.ts`) and THROWS at its stated fan-out bound, so a set that turned out to be unbounded is a failure naming the handler rather than a short list that reads as a complete one. A read that is genuinely a window takes `useSeatWindow`, which names its own size.
- The page fetches `limit + 1`. The probe row never reaches a caller; it is what tells a window that FILLED apart from a set that merely ends there, which a row count alone cannot. It costs exactly one row per read.
- A page that hid rows carries `truncated: true` and `appliedLimit` on the read result, and the kit turns that into one status line — `Showing the newest 1,000; more not loaded` (`truncatedListNotice`, `packages/blueprints/apps/_shared/shared-copy.ts`), said the same way on the phone and on the web.
- `truncated` is not `coverage`. Coverage is how much of the library this device holds; truncation is what this read's window did. A fully bootstrapped phone still truncates a 5,000-contact roster at 1,000.
- **The `acceptTruncation` flag and `ctx.vault.read` are superseded, and a grep keeps them gone.** The flag meant "give me the default window", which nobody chose and no screen said out loud; both words now fail a tripwire over the two trees an app's reads live in (`packages/blueprints/src/paged-read-tripwire.test.ts`, `apps/mobile/src/kit/hooks/replica-read-windows.test.ts`), including in a comment. The generic read survives on the gateway for automations and the server's own callers under `GATEWAY_DEFAULT_READ_ROWS` — a different door with a different caller.

The honest ceiling today is therefore: **bounded reads are unbounded in library size; the full-projection Photos read is measured to 50,000 rows and projected to leave budget near 90,000.** Closing that gap means giving the timeline a windowed read rather than raising the number here. Storage scales without a cliff — projection bytes are linear, and the per-source 128 MiB thumbnail budget is unchanged because the pack is a 90-day-plus-favorites window, not a fraction of the library.

- merged cold view: under 1 second after page one is locally available;
- local search: under 100 ms over the open vault's FTS tables;
- scrolling: reads bounded by the query, not by the library, and no 10k truncation;
- newest-first bootstrap page: 5,000 rows;
- FTS results: 1,000;
- pinned thumbnails: 128 MiB per source;
- measured library: 50,000 rows; projected budget edge for a full-projection read: ~90,000 rows.

Device/simulator runs remain the release evidence for 60 fps and the end-to-end time budgets; unit tests pin query behavior, provenance dedupe, cursor convergence, and outbox durability.

## The per-state promise — the camera-roll backup on iOS (PROVISIONAL)

What Centraid may tell a member about when their photos will be safe, per app state ([#1020](https://github.com/srikanth235/centraid/issues/1020) wave 3 lane E, D-1020-E5; open question 3).

**This section is provisional and marked as such deliberately.** iOS does not let an app transfer a large number of files in the background on its own schedule: `BGProcessingTask` runs when the system decides and for as long as the system decides, and `URLSession` background transfers continue outside the app but only over HTTP(S) to a URL — which iroh-blobs, a QUIC transport, is not. So the promise depends on a measurement nobody has taken.

The experiment that takes it is written in full at [`mobile/maestro/ios-transfer-experiment.md`](../mobile/maestro/ios-transfer-experiment.md): five app states × two transports (iroh-blobs, and an HTTPS blob door behind the `blob-door` feature), four measurements per cell, a 2,000-asset corpus on a **named reference device** (R-1020-20 — never a simulator), and a decision table with one already-written sentence per outcome. The threshold is **500 assets per night, charging, on Wi-Fi**.

**The pass that fills this table now exists** ([#1025](https://github.com/srikanth235/centraid/issues/1025) S6, [D-1025-S7-73](decisions.md#slice-s6--the-camera-roll-goes-up-1025)). Until that slice there was no code anywhere that turned a photograph on a phone into a row in a vault: `MediaLibrary` could describe a roll, `Staging` could hand bytes to the core, `BackupState` could be drawn — and nothing joined them, so every row below described a thing the product could not do. `CameraRoll` is the join. One pass enumerates from a **durable per-vault cursor**, streams each original into the core through the staging door so THE CORE names the bytes (BLAKE3; the phone computes no digest), and queues an ordinary `media.add_asset` intent declaring `needs`, which is what makes the gateway pull and verify the bytes over this seat's own connection **before** it commits the content row. Progress is the cursor plus the hash-keyed intent id, so a re-enumeration after a relaunch queues nothing and a restored phone — whose `PHAsset` identifiers are all new — does not re-upload a library. Wi-Fi and charger rules are the member's one `TransferRule`, read **before each item**.

**HEIC is the standing gap** ([D-1025-S7-76](decisions.md#slice-s6--the-camera-roll-goes-up-1025)): an iPhone's originals upload untouched and the gateway derives no `thumb` or `preview` for them, so those cells fall back to the original until the deferral in [D-1025-S7-52](decisions.md#slice-s3--derivatives-at-the-gateway-1025) is closed.

Until the transfer experiment runs, this is what the product may say, and the state machine in `mobile/shared` reports each row as a `BackupState.Phase` rather than as a claim:

| App state | What Centraid does | What a member is told |
| --- | --- | --- |
| **Open, on screen** | enumerates and transfers continuously; Wi-Fi and charger rules are queried **before each item**, not once per pass | "Backing up: 38 done, 12 to go" |
| **Open, phone locked** | continues while the app is foreground-but-obscured; the decrypted cache is cleared and the replica unmounted the moment it truly backgrounds | "Backing up" until the state changes, then the background row below |
| **Backgrounded, recent** | one pass on a **20-second budget**, checked at stage boundaries, with the platform's expiration handler as a second independent trigger | "Backing up when your phone lets Centraid run" |
| **Backgrounded, scheduled task** | `BGProcessingTask` with `requiresExternalPower`; **opportunistic timing, durable correctness** — progress is the sha-addressed upload ledger, not the task | _the sentence the experiment picks_ |
| **Force-quit** | nothing until a task or a launch wakes it; **no progress is lost** — every drain resumes the same ledger from its durable cursor | "Centraid picks up where it stopped" |
| **Out of disk** | the feed is **parked**: the retry cadence stops, the cursor and the rows stay, and nothing is evicted to manufacture space | "This device is out of space, so Centraid has paused" + "Free up space and Centraid picks up where it stopped" |
| **Photo access denied** | the backup is idle; **the grid is unaffected**, because it reads the vault and not the camera roll | "Photo access is off. Turn it on in Settings to back up your camera roll." |
| **Background App Refresh off** | no scheduled passes at all; registration is **observable rather than assumed** | "Background App Refresh is off, so Centraid only catches up when you open it." |

### The sentence that changes, and what it changes to

One row above is blank on purpose. The experiment's decision table fills it, and these are the only four things it may say:

1. **iroh-blobs clears ≥ 500 assets/night** — _"Backed up overnight: plug the phone in on Wi-Fi and Centraid finishes the night's photos before morning."_ The `blob-door` feature is then deleted and `no-listening-socket` loses its exception.
2. **iroh-blobs clears 100–499** — _"Backed up over a few nights: Centraid moves your photos while the phone is charging on Wi-Fi, oldest first, and tells you how many are left."_
3. **iroh-blobs clears < 100 and the HTTPS door clears ≥ 500** — _"Backed up overnight… On iPhone, Centraid uses a direct connection to your gateway for photo files."_ The door ships on iOS only, behind `blob-door`.
4. **Neither clears 100** — _"Backed up while Centraid is open: leave it on screen while the phone charges."_ The worst outcome, and it has to be sayable: the alternative is a promise the product cannot keep.

**Android is not in this table.** WorkManager's periodic work with a `NetworkType.UNMETERED` + charging constraint runs long enough for a night's camera roll, and v0 already shipped that path; the open question is iOS's alone.
