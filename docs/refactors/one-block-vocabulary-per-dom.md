# One block vocabulary per DOM — a single implementation for the shell and blueprint apps

**Issue:** #765 **Status:** proposed **Owner session:** claude/design-system-migration-hzvmsb

## Goal

The v9 block vocabulary (section, rows, panel, chips, note, empty, doc table, bars, skeleton) is implemented **once per rendering technology**, not once per surface. React Native already has exactly one implementation (`apps/mobile/src/kit/components`). React DOM has three:

| # | Implementation | Home | Consumers | Technology |
| --- | --- | --- | --- | --- |
| 1 | Shell blocks | `packages/client/src/react/ui/*.tsx` + `*.module.css` | the six operational routes, screens | React + CSS modules, bundled into the shell |
| 2 | Blueprint app blocks | `packages/blueprints/apps/_shared/*.tsx` (`LoadingSkeleton`, `ScopeChips`, `SearchScaffold`, `ConsentGate`, …) | the eight system apps | React + CSS modules, bundled inline into the shell |
| 3 | Served kit elements | `packages/design/kit/kit-*.js` (`kit-skeleton`, `kit-bar-chart`, `kit-meter`, `kit-status-line`, …) + `kit.css` | builder / code-store apps served over HTTP | custom elements, no framework runtime |

**Correction (#765, after the consolidation pass): #2 is much smaller than this table implies, and the scope of this plan shrinks accordingly.** The blueprint apps do not reimplement the block vocabulary. They consume the design kit through a _different mechanism_ — global CSS recipes and served custom elements. `LoadingSkeleton` is a seven-line wrapper around `<kit-skeleton>`; `ScopeChips` is `className="kit-chip"` across twelve files. Both lower from the same `packages/design`.

Counting only recipes that genuinely exist in **both** mechanisms:

| Block | Shell | Blueprint apps | Doubled? |
| --- | --- | --- | --- |
| chips | `ChipsBlock.module.css` | `.kit-chip` in `kit.css` (12 files) | **yes** |
| skeleton | `pageSkeleton.module.css` | `<kit-skeleton>` custom element | **yes** |
| panel, rows, empty, section, note, doc table, bars | shell only | no equivalent — blueprint apps do not draw these | no |

So the work is **two recipes, not nine components**. Everything below still applies to those two; the per-block slicing plan is correspondingly shorter, and the "nine slices" framing in the safety argument overstates it.

"Done" means the chip and skeleton recipes have one definition that both the shell and the blueprint apps resolve, and any block a blueprint app grows later is added once rather than twice; #3 is either fed from the same headless model or explicitly declared a different rendering technology with its own implementation (it is not React, so it is not a duplicate of the same technology — see "Rejected alternatives").

The headless half of this is **already done** (#765, this session): `@centraid/design/blocks` holds the bars arithmetic, the skeleton sequence and breath, the doc-table snip line and row-menu model, and the five-state ladder. All three DOM implementations plus the React Native one can consume it today; #1, #2 and the RN kit already do. What remains is the _markup and stylesheet_, which is what this plan is about.

## Safety argument

- Pure code motion: no runtime, protocol, storage, or wire change. Every intermediate state renders the same DOM.
- The move is per-block and each block ships alone (nine slices), so a regression is bisectable to one component.
- The tokens are already compatible (audit below), so no block changes colour or geometry when it is imported by a blueprint app rather than the shell.
- Nothing about the served path (#3) changes: served apps keep `kit.css` and the custom elements they resolve today.
- Rollback is a revert of one slice.

## The real blocker (why this is not a one-session change)

1. **The dependency arrow.** `packages/client` depends on `packages/blueprints`, not the reverse. Blocks living in `packages/client/src/react/ui` can never be imported by a blueprint app. The home must therefore be `packages/blueprints` (which only depends on `@centraid/design`) or a **new workspace package** below both.
2. **`packages/design` cannot be that home as it stands.** It is renderer-free and is consumed by the Expo app through Metro and by the gateway through Node. Adding React + `.module.css` files to it puts a JSX runtime and a CSS-module loader in the dependency path of every one of those consumers.
3. **Three build paths must compile the new home.** The client's vite/vitest (shell), the blueprints inline bundle, and `app-engine`'s served `esbuild` bundling with its `*.module.css` `onLoad` hook. The third one is the hard one: served apps resolve **relative specifiers inside the app dir** plus a root-level allowlist (`SHARED_ASSET_FILES` in `packages/app-engine/src/http/security.ts`) — a bare `@centraid/blocks` specifier does not resolve there at all. So the served path (#3) cannot consume a package no matter where it lives; it can only consume a file added to that allowlist.
4. **Four path-scoped gates enumerate directories.** `scripts/lint-design-tokens.mjs` (`packages/client/src`, `packages/blueprints/apps`, `packages/design/kit`, …), `scripts/lint-css-classes.mjs` (`packages/client/src/react`, `packages/blueprints/apps`), `scripts/design-gallery.mjs`, and `knip.json`'s per-workspace entries all name paths. A new home is invisible to every one of them until it is added.
5. **The move touches files this session does not own** — every shell route and screen that imports a block, plus `packages/blueprints`, which another agent owns.

Realistic size: nine component slices plus package/build/gate wiring, well past a single session. Deferred deliberately, with the headless layer landed first so the _logic_ stops being duplicated while the _markup_ waits.

## Plan

1. **Create `packages/blocks`** (`@centraid/blocks`): React + CSS modules, dependencies `@centraid/design` and `react` only. Wire `tsconfig`, `vitest`, `turbo` build, `knip.json` entry, and add its `src` to `lint-design-tokens.mjs` and `lint-css-classes.mjs` target lists. No components yet — an empty package that builds green.
2. **Lower `--w-key-col` for the blueprint profile** in `packages/design/src/roles.ts` (+ `blueprint.ts`, DESIGN.md, `design-md.test.ts`). One value, one commit, no consumers yet.
3. **Move the five blocks with no open questions** — Section, Note, Empty, Rows, Chips — one commit each: component + `.module.css` + test into `packages/blocks`, re-export from `packages/client/src/react/ui/index.ts` so no screen import changes in the same commit.
4. **Move Panel and DocTable** (they depend on step 2 and on the shell's `contextMenu`/`useCompactLayout` — extract those two as injected props or a tiny context so the block does not import shell).
5. **Move Bars** (already headless-model-backed; only the stylesheet moves).
6. **Move Button** minus its `chrome` size, which stays shell-side as a size variant applied to the moved component.
7. **Adopt in `packages/blueprints/apps/_shared`**: delete `LoadingSkeleton`, fold `ScopeChips` onto ChipsBlock and `SearchScaffold`'s list onto RowsBlock, one app at a time.
8. **Rewrite the shell imports** from the re-export to the package specifier, and delete the re-export shim.
9. **Decide the served surface (#3)**: either add a bundled `kit-blocks.js` to `SHARED_ASSET_FILES` that renders the same markup as custom elements over the shared headless model, or record that the served surface is a distinct rendering technology whose duplication is intended. Do NOT leave it undecided.

## Rejected alternatives

| Idea | Why rejected |
| --- | --- |
| Put the blocks in `packages/design` beside the tokens | Design is renderer-free and is consumed by Metro (Expo) and Node (gateway). React + CSS modules there is a runtime dependency for consumers that render neither |
| Put them in `packages/client` and have blueprints import the client | Inverts the dependency arrow — the client already depends on blueprints |
| Put them in `packages/blueprints/apps/_shared` and import from the shell | Works today and needs no new package, but makes the shell's operational routes depend on a **blueprint app's** shared directory, and that directory is served/bundled under the blueprint token layer. The vocabulary would be owned by the surface that consumes it least |
| Make the served custom elements (`kit-*.js`) the one DOM implementation and have the shell use them | Custom elements inside React means manual prop plumbing and no typed props; it also drags the shell onto a delivery model built for the no-bare-specifier served graph. Different technology, not a duplicate |
| Ship the blocks as a `SHARED_ASSET_FILES` React bundle so served apps get them too | Served apps are given no framework runtime by the platform; adding one is a much larger decision than block sharing |

## Out of scope

- The React Native kit (`apps/mobile/src/kit/components`): a native view is a different rendering technology and keeps its own implementation, as `docs/design-machinery.md` states.
- Token VALUES: one lowering per renderer stays. This plan moves markup, not values.
- The screens and routes that consume the blocks: their imports change mechanically in steps 3–8, their composition does not.
