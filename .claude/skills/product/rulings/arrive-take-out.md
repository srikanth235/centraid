# Arrive and take out

How things get into the vault (the phone's stores, imports, the byte plane) and how they leave (export, share).

## Sync, following and the byte plane

- **There is no sync between devices.** One authoritative file, sealed backups, restore whole. Do not add a replica log, outbox, conflict-resolution UI or "last device wins" semantics.
- **The phone's own stores stay the source and are followed one way, into the vault.** Contacts, Calendar, Reminders (iOS; Android has no system Reminders store and says so), the camera roll, a picked folder and the health store are read; nothing is ever written back. Health asks for read permission only.
- **Following is foreground work plus the windows the OS grants, never continuous.** One coordinator in Rust (`crates/screens/src/follow`) runs a pass for each store the member connected when the app comes forward, when the OS says the store changed while the app runs (contacts, calendar and reminders), when a screen that shows it appears or is pulled, and once in a granted background window after the camera roll and the backup. A pass never asks the OS for a permission, and no copy claims the phone is followed all the time.
- **Background Health reading is Android only, by the owner's decision.** Android asks Health Connect for its background-read permission and says when it is refused. iOS does not wire HealthKit background delivery and has no entitlement for it: iOS Health follows when the app comes forward and in the windows the OS grants, and nothing a member reads on iOS says or implies Health is read while Centraid is closed.
- **A follower reports what it read, and the vault merges.** One three-way rule (what the source stated, what the vault holds, what is new) serves every source: a member's own edit always wins over a refresh, and the source's words are kept as evidence.
- **A member's edit wins field by field, not record by record.** Fixing a contact's name does not stop their phone number following the phone, and a list (a contact's numbers, an event's guests) is compared item by item, so adding one number does not freeze the rest. Whether a field was edited is worked out by comparing what the vault holds with what the source last stated, never from a stored flag, so a field follows again by itself once the two agree.
- **Only the detail screen says a field differs from the phone.** It shows a line such as "Phone says X" with one tap to take the phone's value back. Lists, tiles and search show the member's value and no mark. The line is worked out each time it is shown, never stored.
- **Every item that did not come from typing records where it came from.** A photo from the camera roll or the picker, a vCard, a Markdown file, a Locker CSV, a scan or an upload each name their arrival (`arrived_system` and `arrived_label`: a system and a file or device name, never content) and the vault keeps one origin per system and name and one source per item (`crates/vault/src/commands/arrival.rs`). A typed item has no source row, and nothing re-reads an arrival: it is not followed. The phone's Reminders are not an arrival: they are followed (`follow.reminders`, origin system `phone_reminders`, one origin per phone list), a reminder the phone completes completes the task, and one deleted on the phone goes to trash unless the member touched the task.
- **A store's read position is a cursor in the vault, on its origin row, beside the install that wrote it** (#1183). It moves in the same commit as the records it covers, so a crash resumes exactly where it stopped, and a cursor another install wrote is not trusted: that read is a complete one. The phone's keychain and the shells hold none (Health's keychain habit holds only this install's id, so the pass can ask for the cursor that is its own). Health's shell answers a delta from it: the days its changes touched, the workouts added and the ids deleted, and a workout deleted on the phone keeps its row and forgets its source; a cursor the shell cannot use is answered with a complete read. A missing cursor is a complete read, never an error, and there is no "every Nth read is complete" fallback.
- **Stop following retires; it never erases.** The origin keeps its row, the home it filled and its sources, is marked retired (`origin.retired_at`) and loses its cursor. Nothing the member kept is touched. A retired store counts as not followed everywhere that is asked (whether a record is still followed, what a source stated); following the same store again revives the same origin, so no second calendar, folder or project is made and no record is added twice.
- **An incomplete read trashes nothing.** A refused permission, limited access or failed query is "doubted": it reports and changes nothing. A complete read that loses most of what it followed is also doubted and does not ask the member. A doubted or partial pass is said on the screen that shows the store, as one plain status line in the same words for every store ("Only part of your phone’s contacts was readable, so this shows what was read."): what was read stays, and it is not a failure. A row gone from a complete read goes to trash if the member never touched it, otherwise only its link is forgotten.
- **A record is linked by the most durable id the phone offers and says which kind it is,** so a new phone re-finds a record instead of duplicating it. The member is told what to do (add the account in the phone's Settings), never a platform path.
- **Photos keeps what the camera roll deletes.** The vault is the photograph's backup. Camera-roll import is automatic once access is granted: no first-run offer, no per-selection "Back up". Importing is "import"; only a gateway acknowledgement is "backed up".
- **Free up space is offered only where the system confirms the deletion,** and frees only what a gateway acknowledged and no kept album holds. Bytes no gateway has acknowledged are never evictable.
- **An edited photograph is a new photograph** with the original named as its source, carrying the original's moment. The original is never touched. A re-offered photograph commits once.
- **Bytes never cross the shell boundary as payloads.** The core materialises a blob to a path; a shell never declares a digest, it streams bytes and the core names them.

## Taking data out

- **Taking data out is one rule in every app.** Every app exports its data as a file on the kit's one export screen (More, "Export"), and a primary record can be handed, one item at a time, to the OS share sheet from its detail screen ("Share"). Both ask the owner check first (a phone with no passcode goes ahead with a warning, except Locker's export, which refuses), and an import is never checked. A Locker item cannot be shared: its contents leave only through its own export. A large export is written as a streamed file, never built in memory (Docs' archive of its originals). Settings carries one more, "Export everything": every app's export in one streamed archive with a folder per app, Locker left out (its contents leave only through its own export). Docs shares the stored file and Photos the originals; every other app shares the item as a small file (a note as Markdown, a person as a vCard).
