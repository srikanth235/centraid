# Keep and protect

The vault, Locker, who may open what, and what never leaves the phone.

## The vault

- **A first-party app is the owner's own screen, not a principal.** It declares what it reads and invokes at build time and a tripwire fails the build when it strays. Do not add grants, scopes a member can revoke, or an "app permissions" plane.
- **Every writer goes through the same domain operations.** Commands, imports, the assistant, a phone follower: one door, one set of invariants. If a rule lives only in one screen, it is not a rule.
- **A mechanism with no producer and no consumer leaves the schema.** Intent belongs in an issue, not in dormant DDL, a reserved column or a flag nothing reads. A wire field no table can fill is reserved or deleted.
- **Identity is never taken from a value.** Two documents with identical bytes are two documents with independent histories. A drive row is the document wrapper, never the content hash. A merchant is not a person.
- **The vault keeps no record of what the member asked for.** No activity feed, no journal of typed words that survives "Delete forever". It keeps only what it needs to avoid doing a thing twice and to tell which copy is ahead.

## Locker

Locker is an ordinary app whose sensitive values are sealed. An item has a title, links, attachments, tags, trash and earlier versions like any item; what differs follows only from sealing, and from the wall that guards opening it.

- **Nothing inside Locker is read while it is locked, and a relock is a wipe.** Every Locker machine reads only while the gate is open, answers that land after a relock are dropped, and closing drops every revealed value and typed draft. Leaving Locker before answering the phone's prompt (back to Home, another tab, a relock) drops the pending unlock and asks the shell to take the prompt down (`OwnerCheck.cancel`: `LAContext.invalidate()`, `BiometricPrompt.cancelAuthentication()`), so Face ID never stays over Home; the answer that lands afterwards is ignored. The core's metadata list is plaintext by design (listing is not unlocking), so the wall is the shell's and it must hold.
- **The list is plain; the secret is sealed.** Sealed values (password, one-time-code seed, card number, CVV, secure-note content, sealed custom fields, sealed files, passkey keys) are encrypted under the Locker key at rest and never enter a search index, a derived file, a log, a queue, a backup in the clear, or the assistant's reach. They reach the screen only through an authorised reveal, a one-time-code seed included. The item's title, names, addresses, labels and dates are plain.
- **A changed secret keeps its earlier value, sealed.** Locker's Earlier versions lists a changed password, card number, CVV, note or sealed field as a masked row ("Password changed", dots) with a Reveal behind the same owner check the live reveal asks for, and restoring that version restores the sealed value. The full preview of such a version shows each secret as dots with no Reveal (the list has it), and a shut wall draws the gate and reads nothing. The vault keeps only the `lk1:` ciphertext, never a plaintext. A one-time-code seed comes back with a restore and is revealed behind the owner check like any sealed value, so it can move to another authenticator; a passkey's key is never revealed, copied or exported.
- **A Locker item is linked, attached to and mentioned like any item.** It can be at either end of a link, `[[title]]` resolves to it, and other items list it by its title; its links are read through the same doors as every kind's. A link's label and anchor carry no sealed value (the command refuses one). A document or photograph attached to a Locker item is an ordinary item, not sealed: it is indexed, previewed and listed in Docs or Photos, and the attach sheet says so and offers the sealed file field for anything that must stay secret. A **sealed file** is bytes encrypted under the Locker key before they enter the blob store; no thumbnail, preview or text is ever made from it, it is always sent with the backup whatever the member's exclusions, and it is never freed from the phone. A photograph or scan captured inside a Locker item is a sealed file, never a photograph in the library.
- **Search finds a Locker item by its plain fields whether or not Locker is locked; opening the result goes behind the wall.** The Home tile counts items and shows none, and reads "Locked" or "Open". A dated plain field can notify, masked ([be told](be-told-glance.md)).
- **The assistant works on Locker like the owner, and a secret never passes through the model on its way out** (owner, 2026-11-12: everything is on the phone, so the member's convenience wins). A request to see a secret ends in a card with a Reveal: the member taps it, the phone asks its owner check, and the value shows on the card, read by the core and never by the model. The revealed value is dropped when Locker relocks or the chat is left, and it is never kept in the chat. A secret the member types into Chat ("change my password to …") is written behind a confirm card that shows the value masked, and it is sealed when it is saved. With no value typed, the card opens Locker's editor. It may also help with what a login is called and where it is filed.
- **The phone is the unlock boundary.** Biometric with the passcode as fallback, relock when Centraid leaves the foreground, no separate Locker passphrase. Only the phone refusing the member counts as a failed unlock; a cancel does not. The wall says how many failed and when.
- **The key lives only in memory.** It derives from the 24 words, is zeroed on relock and is written nowhere. No gateway holds, mints or hands out a member key, and a "reveal" request is unrepresentable on that path rather than checked.
- **No history of reads, no recently-used shelf.** The only trace is each item's "Last used" stamp. A shelf of recent items would publish reading habits on the screen where reading is sensitive.
- **Never an invented all-clear.** Locker shows no verdict it did not compute: no Review screen, no weak or reused scoring, no generator (the boards for Review and Generate are retired, owner plan 2026-11-26). Compromised is a flag the member sets.
- **Nothing leaves silently.** Export is plaintext to the OS save sheet only, after a confirm and a fresh owner check, receipted before any secret opens. Every Locker copy, including one made from a chat card, remains on the clipboard when its view closes or Centraid backgrounds. iOS clears it at the original expiry; Android clears at expiry while Centraid is active, or on return if it expired while closed. An explicit Locker Lock and a vault switch clear the latest owned copy immediately, even if its view was popped or Centraid restarted first. Rust keeps the latest secret only in volatile, redacted memory; the shell may persist only a nonsecret opaque item marker, owning vault id, digest and expiry, never the text. Controller cleanup cannot clear a newer copy, and shells clear only when the current clipboard still matches the owned lease. Background still relocks Locker and wipes its keys and revealed values (owner, 2026-11-22). An open Locker is shielded from capture.
- **A secret saved mid-typing is a wrong secret.** Locker's editor saves on an explicit Save, and leaving with changes asks first. A Locker editor keeps no draft, because its unsealed values must never reach disk. An item's type can be changed; fields the new type does not define stay on the item as extra fields.
- **The passkey slot is storage.** It is shown, renamed and removed; its key is never revealed, copied or exported.

## Identity and enrollment

- **One owner per vault, no roles, no password, no session.** A device is proved by its key. Enrollment is full trust: no companion tier or per-device attenuation.
- **The 24 words are the only recovery.** A fresh phone mints them in the core and keeps them without showing them; on both platforms the first backup asks for them (`RecoveryKeyPrompt`), and only a vault on its own key shows them at creation (owner, 2026-11-18). The shell has no word list or checksum. A restore takes the words or the seed, exactly one. A comparison number (safety number), never a hex id, is what the member verifies at pairing.
- **A member can read their words again on this phone,** and can keep a vault on its own words by opting in. Refusals never quote a word.
- **Keys cross the boundary borrowed and are written nowhere by the core.** The seed lives in the platform's secure store; absent seed is a state, not a fault.
