# Changing the vault model

The vault is one SQLite file on the phone. The Rust core is its only writer. Every app is a projection of it, and every write is a typed command that goes through one commit guard. A model change touches many layers that must agree, and most of the agreement is held by tests that fail until you update the matching generated file. Use [stack/sqlite](../stack/sqlite/centraid.md) for SQL, DDL and transaction craft; this skill is about the repo's shape and what bites.

## 1. What a change touches, in order

1. **The model**: [crates/vault/src/model.rs](../../../crates/vault/src/model.rs) (`Kind`, `Rel`, `Kind::host()`, `Kind::CONCEPTS`, `Kind::CONTAINERS`) and [crates/vault/src/lookups.rs](../../../crates/vault/src/lookups.rs) (`LOOKUP_TABLES`, the fixed vocabularies) and [crates/ontology](../../../crates/ontology) (the `Vault` type, DDL helpers, the text tokenizer `text::index_words`).
2. **The baseline DDL**: [contracts/migrations/001_baseline.sql](../../../contracts/migrations/001_baseline.sql), a hand-written file that founds a new vault and seeds its rows. It is reached with `include_str!` by [crates/vault/src/migrations.rs](../../../crates/vault/src/migrations.rs).
3. **The format identity**: [crates/vault/src/format.rs](../../../crates/vault/src/format.rs) `SCHEMA_DIGEST`, a BLAKE3 over `sqlite_schema`. Open and restore refuse a file whose digest differs.
4. **Generated contracts**: [contracts/schema/vault-ddl.sql](../../../contracts/schema/vault-ddl.sql) (`export-ladder-ddl`), [contracts/schema/vault-commands.txt](../../../contracts/schema/vault-commands.txt) (`export-commands`), and the published ontology page's schema section (`export-ontology-page`, with a sentence per table in `ontology_doc::TABLES`).
5. **Commands**: [`crates/vault/src/commands/`](../../../crates/vault/src/commands), registered in [crates/vault/src/commands/mod.rs](../../../crates/vault/src/commands/mod.rs). A command runs inside `Vault::execute`, which runs the commit guard in [crates/vault/src/log/guard.rs](../../../crates/vault/src/log/guard.rs).
6. **Search**: [crates/vault/src/index.rs](../../../crates/vault/src/index.rs) (the commit's side of the index: `search_owed`, `DEPENDENTS`; `index/text.rs` `text_of`), which writes the attached index file (`<stem>.index.db`, its own ladder `contracts/migrations/index/001_index.sql`: search, `alert`, `geo`), [crates/search](../../../crates/search) (reading, matching).
7. **The app plane**: `crates/domain` **(target)**: the kind's `KINDS` row, its reads and its actions ([app-plane](app-plane.md)).
8. **Backup**: the snapshot census in [crates/vault/src/backup/snapshot.rs](../../../crates/vault/src/backup/snapshot.rs). It is derived from the file, so it rarely needs editing, but a restore compares it table by table.

## 2. The steps, in order

1. **Decide the table's place in the model first.** A new thing with a title and a trash is a new _kind_: a seed row in `entity_kind` (with its `linkable`, `may_be_top`, `may_be_named` and `may_be_unnamed` attributes), its `home_shape` rows, one value in `Kind`, a host table (its own, `concept` or `container`), and nothing else. A new relation between entities is a `Rel` and `edge_shape` rows saying which kinds it may join (the relation is the rows; there is no CHECK list). A thing that is none of these is a _child row_ of one kind and cascades from it. A star, a pin or an archive is a column of `entity` (`starred_at`, `pinned_at`, `archived_at`), never an edge. A thing's one home is `entity.parent_id`, never a column of its own table. Why: the model has one supertype and one cascade; a parallel mechanism is a second truth.
2. **Edit the baseline.** `001_baseline.sql` is the schema a new vault founds and the only rung; this is v0 and until the first release you change it directly. From the first release on it is frozen: append `002_<name>.sql` as [crates/vault/src/migrations.rs](../../../crates/vault/src/migrations.rs) describes, and prove it against a file wound back to rung one.
3. **Write the DDL to the doctrine** (section 3): generated `kind` column and composite `(id, kind)` foreign key for a kind row, an explicit `ON DELETE` on every foreign key, every FK's first child column leading an index (a partial index `WHERE col IS NOT NULL` when mostly NULL), `STRICT` where the neighbours are. **A list that can grow is a lookup table with a foreign key, never a CHECK list or a Rust match**: a new value is a seed row, written only by a migration, and a Rust enum that mirrors one is held equal to its rows by `tests/lookups.rs` and `tests/commitments.rs`; no CHECK or trigger names a value a lookup table holds (`commitments.rs` reads every CHECK and trigger to prove it). A CHECK keeps only a closed state machine or a shape that cannot grow.
4. **Run the digest test and paste the value.** `cargo test -p centraid-vault the_schema_digest_is_the_founded_files` fails printing `found: <hex>`; put it in `SCHEMA_DIGEST`. Any baseline change, even a column comment that changes a statement, needs this. Comments and whitespace do not change the digest; statements do.
5. **Regenerate the generated files.** Run `cargo run -p centraid-vault --bin export-ladder-ddl > contracts/schema/vault-ddl.sql` and, when commands change, `cargo run -p centraid-vault --bin export-commands > contracts/schema/vault-commands.txt`. Run `cargo run -p centraid-vault --bin export-ontology-page` for the page after adding a sentence for the table in `ontology_doc::TABLES`. Never hand-edit them. A table the page does not name, a foreign key that delete nothing and has no purge rule, a blob column that is not a history slot and a renter, and a foreign key with no index are each red in [crates/vault/tests/commitments.rs](../../../crates/vault/tests/commitments.rs), `purge_rules.rs`, `history.rs` and `blob_release.rs` until classified. A rule the schema holds gets a raw-SQL row in `tests/schema_rules.rs`.
6. **Write the commands.** One typed command per verb, named `<kind>.<verb>`, in the owning app's file. A per-kind verb that duplicates a shared verb (`entity.*`, `tag.*`, `flag.*`, `edge.*`, `container.*`, `blob.*`, `derivative.*`) is not written. A write to an entity's row, its kind row (host) or its child rows stamps `updated_at` and queues the re-index by itself: commit-time TEMP triggers record the entity and `Vault::commit` drains them (section 5). A command calls `ctx.touch(id)` only for what the triggers do not see (below). A create uses `insert_entity` and `born`. Refuse with a sentence, not a SQL error.
7. **Make search see it.** Text a member searches goes in `text_of`; an edge re-indexes the end whose text reads it automatically (`contains`, `about`, `with`: the `to` end; `tagged`: the `from` end; `related`: both), and never stamps `updated_at`; a link whose text lives on an end the triggers skip calls `mark_for_index` on it; a title that labels other things (a tag, list, project, calendar, account) belongs in `DEPENDENTS`. A command never writes the index file: the commit writes `search_owed` in its own transaction and the index file is written right after. The incremental-index-equals-rebuild commitment (`index_owed.rs`, `index_past.rs`, `index_geo.rs`: `assert_equals_a_rebuild`) must stay green for your command.
8. **Teach the plane.** Register the read (shape, keyset, bounded) and the action (inverse, confirm class, chat surface) in `crates/domain` **(target)** ([app-plane](app-plane.md)). Add a year-3 scale test if the read is hot (section 5).
9. **Update the shell contracts if the wire changes** (`room.proto` fields, never a command name in a shell). Read [crates/core-ffi/CONTRACT.md](../../../crates/core-ffi/CONTRACT.md) before touching an ABI or wire field; removed wire fields are `reserved` by number and name, never reused.

## 3. What must stay true

- **The commit guard is the only writer.** `Vault::commit` is `BEGIN IMMEDIATE`, body, `COMMIT`, one transaction. The read connection is `query_only`. Nothing writes outside it; nesting is a no-op inside the outer pair.
- **Upsert, never REPLACE.** No command writer resolves a conflict with `INSERT OR REPLACE` or `REPLACE INTO`. SQLite's REPLACE fast path does not report the displaced row to the update hook and fires no delete trigger, so the commit census would disagree with the file (a restore refuses a file whose counts disagree) and the displaced row's entity would be orphaned. Write `INSERT ... ON CONFLICT (...) DO UPDATE`.
- **A refused or failed command writes nothing anywhere.** Gate order: schema validation (errors scrubbed of sealed values), authority, preconditions, the handler in the commit, postconditions (a failure rolls the commit back), then the action key in the same transaction. There is no journal and no replay ledger; an `act` carrying a key is answered `replayed` and runs nothing, a command without one that arrives twice runs twice. A write a shell may re-offer must be idempotent by its own content or by an id the phone minted.
- **The write counter.** The guard bumps `vault.writes` / `vault.written_at` once per commit that changed something a screen reads, in the same transaction, muted in the census. Takeover compares it. Do not bump it yourself.
- **Delete rules are decisions.** Kind rows, child rows, edge and link ends, `revision.entity_id` and a category's budgets and rules cascade; a few pointers set NULL (`source.entity_id`, `mention.to_id`, `message_attachment.entity_id`, `event_guest.person_id`, `entity.trashed_by`); every other pointer into an entity has no action and needs a purge rule (`PURGE_RULES`: `Detach`, `Purge`, `Refuse`, `Forget`, `Home`, `Drop`) saying what a purge does with it, held equal to the file's own pointers by `tests/purge_rules.rs`. A purge is one DELETE of the entity row plus those rules, never a foreign-key walk that deletes whatever it reaches.
- **Trash lives on `entity` only** (`deleted_at`, `purge_at`, and `trashed_by`, the holder that took a row). A holder (notebook, folder, task list, account, task, event or any item a photo or document was captured inside, and a person for their touches only) trashes what it holds, and a restore brings back the rows that name it in `trashed_by` and theirs, no timestamp compared; a row trashed on its own stays, and a Trash list shows only those (`trashed_by IS NULL`): a capture comes back with its item, never alone. `purge_at` says when the launch pass may empty a row, not when it stops being restorable.
- **Hashes are BLAKE3 and only ever a foreign key into `blob(hash)`.** Garbage collection finds references from `PRAGMA foreign_key_list` alone. A column that rents a blob says whose the bytes are (the backup skips what only a lapsed entity holds). Any command that can drop the last reference to a blob collects and returns `released`; the gate deletes those files after commit.
- **Sealed cells stay sealed.** Locker's secret cells are `lk1:` ciphertext no entity-wide reader serves (the history keeps them only as that ciphertext and masks them on read); never add a column that copies, indexes or logs one, and never write a plaintext. Search and `text_of` hold plain text only. A custom field's secret kinds are `sealed` and `otp` (a seed): both live only in `value_sealed`, and a new secret kind needs the same CHECKs on `locker_item_field`, the sealing in the core's `seal_field`, and a planted row in the plaintext gate.
- **Home, capture and library reads.** One home column: `entity.parent_id`, shaped by `home_shape`; albums and lists are `contains` edges, since an item can be in several. A photo or document captured inside a payment, event, workout, note, task or person takes it as its home (never inside a Locker item, whose capture is a sealed field, or a reading). Every Photos read (library, videos, scans, places, search scopes) and Docs' top level filters `parent_id IS NULL`; every Trash list shows only `trashed_by IS NULL`. Moving a capture to the top level or into a folder promotes it. A merge (`person.merge`, `concept.merge`, `place.merge`) re-points `parent_id` before it purges the loser.
- **A currency change is one command and its own inverse.** `account.edit` with `currency` rescales every figure kept in the account's currency (opening balance, lines, splits, checkpoints) and refuses if one would lose a fraction. Undo is the inverse `account.edit` carrying the old currency; restoring an earlier version of the account that changes the currency goes through the same rescale.
- **Edges are shaped.** An edge joins only the kinds `edge_shape` allows, and an edge's ends never change. A star is a column of `entity`, not a mirror. Every record's earlier values are the one `revision` table, written at the commit door by `crates/vault/src/history` and not by a command: a new kind needs a row in `history::TABLES`, a new owned child table a `Role::Child` entry, a column that must not be kept (a sealed cell, a stamp, an immutable file) an entry in `history::OMITTED` with its reason, and a column that references `blob(hash)` a row in `history::BLOB_SLOTS` (a version names it through `revision_blob`; no hash is ever inside a state); edges, links, budgets, rules and occurrences are outside a snapshot (B1). The caller that opens a commit says who acted (`Command::as_actor`, `CommitTx::set_actor`), and a followed store's commit names its origin. `tests/history.rs` fails until each is classified.
- **No dormant schema.** A table, column or wire field with no producer and no consumer leaves; intent lives in an issue. A wire field no table can fill is `reserved`.
- **Time and identity.** Ids are UUIDv7 minted from the injected clock, so fixtures stay deterministic. Civil time is the vault's zone, never the host's. Money keeps its currency (minor units plus a code); a bare amount is not a balance.
- **One checked format for instants.** Every time column is checked: an instant is `YYYY-MM-DDTHH:MM:SS.mmmZ` and nothing else, a date is `date(c) IS c`, a floating wall clock has no zone designator, and an event's `starts`/`ends` read under its `timing`. A command that is handed an instant in another spelling writes `temporal::canonical(..)` of it; a follow canonicalises what a phone stated before it merges (so `source.stated` and the row agree).
- **A rule a command enforces is a constraint too.** No container or concept loop, `series_id <> id`, a concept's parent of its own kind, an origin's `fills` of its system's kind, a colour that is a palette key and worn only by a tag, a revision's actor and origin, one transfer per line, a line's parts that sum to its amount (the command's and a commitment test's: a trigger would fail mid-commit): the command refuses with its sentence and the database refuses the same row. `crates/vault/tests/schema_rules.rs` writes each with raw SQL.
- **A transfer is one row**, `transfer(a, b)` with `a < b`, which cascades with either line (a txn is in at most one). A derived table (`alert`) stays derived. **Every alert comes from a `reminder` row** (its own id, its entity, a lead in minutes, and a dated child row where the kind needs one: `reminder_target` says which), never JSON in a column; `alert` in the index file is keyed by the reminder's id and is rebuilt from the rows; a set of leads is presented longest first through `alerts::longest_first`. **Locker** keeps the vault's clock like every table (its commands stamp `created_at`/`updated_at`; no default, no touch trigger, no `row_version`), every type's fields — built-in (`field_key IS NOT NULL`), template, and custom — live uniformly in `locker_item_field` with `CHECK`s enforcing the secret/plain boundary, and `locker_key` is a singleton `id = 1`. Locker is an app like every other: its item is an entity of its own kind and the one difference is that sensitive field values are sealed.
- **A list is kept once.** A value two sides must agree on is written where it is decided and generated everywhere else: `cargo xtask lists` writes the `edge_shape` seed a test holds the trigger against (`crates/vault/tests/common/edge_shapes.rs`), and `generated-lists-are-fresh` in `cargo xtask rules` fails when it is not what the generator writes. The gateway's limits are not mirrored: the vault depends on `centraid-gateway`'s `rules` and reads them there. Never hand-edit a generated file; never keep a second copy of a list beside it.
- **Atomic founding, a quick check at open, and an honest delete.** `Vault::create_with` founds into `<name>.founding` and renames; `Vault::open_with` removes a stale side file, runs `PRAGMA quick_check` (a damaged file is `VaultError::Damaged`, `ERROR_CODE_VAULT_DAMAGED`) and migrates on its own connection. `secure_delete` is on, and a purge merges the search indexes and prunes `search_word`, so a purged item's text is not in the file or its WAL (`tests/secure_delete.rs`). A pass that deletes by the clock (the launch purge, the action-key prune) trusts it only within `CLOCK_BOUND_DAYS` of `vault.written_at`.
- **The DDL rules** (`cargo xtask rules`): `no-host-clock-in-ddl` refuses `'now'`, `CURRENT_TIMESTAMP`, `CURRENT_DATE`, `CURRENT_TIME`, `unixepoch()` and `julianday()` in any ladder (`strftime(<format>, <column>)` is a shape check, not a clock read); `every-database-has-an-id-and-a-ladder` wants every ladder numbered and its founder stamping an `application_id` and a `user_version`; `no-key-value-state-table` refuses a `meta`-shaped table, so every fact of a ladder is a column with its type and its CHECK; `phone-authority-needs-verify` keeps the proof of a gateway's word in its two places. **Every index has a reader**: `every_index_has_a_reader` in the read registry's plan gate **(target)** fails on an index no plan reads and no foreign key needs, so an index lands with the read that wants it.
- **`blob.seq`** numbers claims in the order they were made and is never reused; `backup::naming::claims_after` is the keyset read a per-gateway cursor walks.
- **Reads paginate by keyset** (`(sort_key, pk)`), never `OFFSET`, and always take a window. A keyset cannot continue over a NULLABLE sort column; the kit refuses it.
- **A child read's keyset is unique per row.** A read of the rows of a window of parents (`Read::within`, `by_ids`) orders on a pair that names one row, never `(parent_id, parent_id)`: a page that ends inside one parent's rows would drop the rest. Order on the parent and the child's own key (`(from_id, to_id)` for the edges of one relation, `(parent_id, id)` for subtasks); read one relation or one scope at a time where the key needs a third part. Where the second part is an integer (`reminder(entity_id, offset_min)`), use `Read::within_integer_key` (`PageOrder::asc_integer_pk`): only an order that says so may carry an integer cursor key, every other order still refuses one. A nullable key column (a subtask's `parent_id`) is refused as a sort key, except where the read's own predicate pins it to the bound list: `Read::within_pinned` declares that (`PageOrder::pinned_to_bound_list`), and the door checks the predicate says `column IN (`.
- **Follow is a three-way merge** against `source.stated`: the member's edit wins per field (and per item for a child such as contact points, guests or workout measures), the system's change lands on the rest. "Edited" is never stored: it is held != stated, so a field re-attaches by itself when they are equal. A new followed field needs its map entry; a new child needs `items` and `take` beside its `merge`. `follow::differences` reads the fields that differ and `follow.take_stated` copies the stated value back.
- **Stop following retires an origin; it deletes nothing.** `follow.stop` sets `origin.retired_at` and clears the cursor, and keeps the row, the home it filled (`fills`) and its sources. Every read of "is it followed" (whether a record is followed, what a source stated, what the pass reconciles) joins `origin` and filters `retired_at IS NULL`; a new such read must too. A follow of the same `ref` revives the retired origin (no second home, no record added twice). `retired_at` is set only where `origin_system.can_retire` says so (the file's key). `crates/vault/tests/follow_retire.rs` is the model.
- **There is no backwards compatibility with a file before v0** (#1214): `001_baseline.sql` is the only rung, and a file whose digest differs is refused with a sentence at open and restore, never migrated.

## 4. What an app declares

An app is a first-party module of `crates/domain` **(target)**, not a principal: it holds no credential. It declares, as Rust `const`s and checked by tests: its `KINDS` rows, its registered `READS` (the tables each may read, held by SQLite's authorizer; sealed Locker columns denied to every module) and its `ACTIONS` (each wrapping one vault command, with its inverse, confirm class and chat surface). There is no `manifest.json` and no free SQL: [app-plane](app-plane.md) states each declaration and the tests that hold it. Every invocation carries an `invoke_key`. A refusal is a sentence, not an error.

## 5. Pitfalls

- **Editing `001_baseline.sql` and forgetting the digest.** Three tests go red at once (`format_identity`, `ladder_ddl`, `ontology_page`); fix the digest first, then regenerate.
- **A foreign key with no index on its child column.** Deleting a parent then scans the child once per deleted row. A purge or an emptied trash turns quadratic. The commitment test catches it; the query-plan test catches the read-side twin.
- **A new read that scans or sorts a big table.** The read registry's plan gate **(target)** plans every registered read over the year-3 corpus. The fix is an index in the baseline, not a row in [contracts/ledgers/query-plans.json](../../../contracts/ledgers/query-plans.json).
- **A write the commit triggers do not see.** `history::install` puts TEMP triggers on the connection that record touched entities in `temp.centraid_commit_touched`; `Vault::commit` drains it, stamps `updated_at` (with the instant the command's first `touch` or `insert_entity` used, else the commit's) and queues the re-index. Covered: an `entity` change to `title`, `deleted_at` or `purge_at`; an update to any column of a host table or a child table that really changed (`OLD IS NOT NEW`, so an upsert that writes the same values does nothing), except those in `NEVER_TOUCHES` (`history/shape.rs`: today `locker_item.last_used_at`, a use is not an edit; this list is separate from the history's `OMITTED`, so an immutable or bank-stated column a command moves still touches); an insert or delete of a child row or host row. Edges only re-index, never stamp, and only the end whose text reads the relation: `contains`, `about`, `with` the `to` end, `tagged` the `from` end, `related` both (and a `related` label change). Not covered, so the command still calls `ctx.touch(id)` / `ctx.mark_for_index(id)`: a note's `about` edge (the one `edge_shape` row that is `anchored`) touches the note at its start (`edge.rs`), and no other edge touches; a purge re-indexes what a purged note was `about` and what the purged entity labelled (`entity.rs`); cross-entity writes the triggers have no table for (`measurement`, `message`, `derivative`, `origin`); a `link` and a `mention` are outside a snapshot and are written by their own commands.
- **A command that works on the wrong kind.** Notes and Photos both hold containers; every command states its kind and refuses the other's id with a sentence, and every reader filters on kind.
- **Adding a CHECK value without its writers.** Sweep mechanically (below); a CHECK value nothing writes is dormant schema.
- **Never weaken a test, budget, ledger or allowlist to go green.** (Wall-clock budgets were removed, owner ruling 2026-11-04; what remains are counts and sizes.) Fix the code.

### The mechanical sweeps (part of the review, not extras)

Reading alone found none of the reproduced purge and merge bugs. For any model change run these with grep or a throwaway query against a founded vault:

1. **Every CHECK value against its writers**: each value of each CHECK list has at least one command that writes it and a reader that filters on it, and Rust enums equal the SQL list.
2. **Every FK's delete rule against its siblings**: list `PRAGMA foreign_key_list` for the tables around yours; a sibling with a different rule needs a reason. New pointers into `entity` that delete nothing need a purge rule.
3. **Every table's timestamps**: each mutable table has `created_at` / `updated_at` as its neighbours do, and the command sets them (an entity's `updated_at` is stamped by the commit triggers, or by `touch` where they do not reach). A child row's changes stamp its parent.
4. **A citation is not a justification.** If a rule or comment cites a past ruling, re-judge it on its merits for the product now; surface what survives only because someone ruled it.

## 6. Year-3 scale tests

Every app module of `crates/domain` **(target)** keeps a year-3 test: a hot read is proven on a seeded year-3 corpus. Each builds a deterministic corpus (a `Year3...Shape` struct whose fields are all named, so a new field fails the literal), runs the module's registered reads, and asserts what a count cannot: windows are walked and bounded, truncation is reported, pinned or special rows outlive the window. When your change adds a hot read or grows a table that scales with years of use (notes, transactions, photos, events), extend the fixture shape and the test in the same change. Timings are reported as provenance, never as ceilings.

## 7. How to check it

```sh
cargo test -p centraid-vault the_schema_digest_is_the_founded_files   # prints the new SCHEMA_DIGEST
cargo run -p centraid-vault --bin export-ladder-ddl > contracts/schema/vault-ddl.sql
cargo run -p centraid-vault --bin export-commands > contracts/schema/vault-commands.txt
cargo run -p centraid-vault --bin export-ontology-page
cargo test -p centraid-vault            # commitments, lookups, schema_rules, ladder_ddl, command_list, ontology_page, format_identity, restore_drill, backup_snapshot
cargo test -p centraid-apps-<app>       # the app's tests, year3 included
cargo xtask gate --profile pr           # the real gate; one crate green is not enough
```

`export-ddl` in [crates/ontology](../../../crates/ontology) prints a vault file's schema; point it at a copy, never a live file. The `mobile-jvm` profile runs on Linux with the repository's Cargo and Bun tooling plus JDK 21; it does not need the Android SDK. CI runs it on Ubuntu. Android and iOS device or native framework builds have separate platform requirements. The search budget and restore drill run in the gate; if you cannot run the full gate, name which profile steps you ran.

## 8. Final checklist

- [ ] Place in the model decided (kind, relation or child row); the baseline edited directly.
- [ ] `SCHEMA_DIGEST` updated; `vault-ddl.sql`, `vault-commands.txt` and the ontology page regenerated, not hand-edited; the table has its sentence in `ontology_doc::TABLES`.
- [ ] Every FK has an explicit delete rule and an index on its first child column; any no-action pointer has a purge rule.
- [ ] Commands upsert (no REPLACE), call `ctx.touch` only where the commit triggers do not reach, refuse with sentences, collect blobs and return `released` where they can drop one.
- [ ] Search text in `text_of`; `DEPENDENTS` covers labelling rows; `mark_for_index` only for a link the edge triggers skip; incremental index equals rebuild.
- [ ] Sealed cells never indexed, logged or copied.
- [ ] The kind's `KINDS` row, its reads and its actions are registered in `crates/domain` **(target)**; no SQL outside the confined crates.
- [ ] Year-3 test extended for any hot or growing read; query-plan test green without a new ledger row; every new index has a reader.
- [ ] No list kept twice: a generated file regenerated with `cargo xtask lists`, never hand-edited.
- [ ] CHECK, delete-rule and timestamp sweeps done.
- [ ] Gate profile run (or the part that cannot run on Linux named).
- [ ] If a commitment changed, the vault-ontology doc updated in the same PR.
