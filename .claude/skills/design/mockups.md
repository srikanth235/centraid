# Mockups first

A visual or UX change starts in `design/mockups/`. The same change updates the light boards and, when a value moves, `design/tokens.toml`. The generator then writes everything derived. How screens should behave is in [behaviour](behaviour.md); this page is the flow and the checks. The folder's own map is [`design/mockups/README.md`](../../../design/mockups/README.md).

## What is authored, what is generated

| Authored (edit these) | Generated by `cargo xtask design` (never edit) |
| --- | --- |
| `design/mockups/MoneyRecurring.dc.html`, one light board per screen, outside the part regions | `design/mockups/MoneyRecurringDark.dc.html`, the same board with `data-theme="dark"` |
| `design/mockups/Part<Block>.dc.html`, one part board per block, room slot and canvas | the part regions inside a board (between `<!-- part:… -->` and `<!-- /part -->`) |
| `design/mockups/canvas.json`, the pages and each light board's place and title | the dark entries of `canvas.json` |
| `design/tokens.toml`, the values (the redesign sections and `[board]`) | `design/mockups/tokens.css`: light on `:root`, dark on `[data-theme="dark"]` |
| `design/icons.toml`, the icon silhouettes; `design/fonts/` | the shells' `Theme`, `Catalog`, `Words`, `Tokens` and colour sets, both sites' `centraid-tokens.css`, `design/icon/*.svg` and the app icon sets |

The kit's fixed words are not authored here. The generator reads them from `crates/screens/src/strings/shared.rs` (and one word from `home.rs`), so change the word in Rust.

## Colour: roles, never values

- A board writes every colour as `var(--role)`: CSS `color`, `background`, `border`, `box-shadow`, gradient stops, and SVG `fill`, `stroke` and `stop-color`. A hex, an `rgb()`, an `hsl()` or a colour name is a check failure.
- The roles are in `design/tokens.toml`: the redesign sections (`--surface-page`, `--text-ink`, `--shell`, `--app-calendar`, `--state-red`, `--list-blue`, `--brand-teal`; an app's `-fill` is its dark fill, `-tint` its chip ground) and `[board]` (glass, scrim and shadow, the washes, the colours that keep their value in dark). Each has a light and a dark value, and **dark is designed**: you choose it, the generator never derives it.
- A new colour is a role first: add it to `tokens.toml` with both values, then use it. A photograph or a third-party mark has no role; its element carries `data-keep`, which exempts that element and its children.
- To change how something looks in dark, change the role's dark value. Never edit a dark board.

## Parts

A block (a row, a facts list, a status line) is drawn once, as a part board `Part<Block>.dc.html` on the Parts page. A part board shows the block's states for people to read, and marks each insertable piece:

```html
<!-- variant:pending -->
<div …><span data-slot="t0">Ana Díaz</span> …</div>
<!-- /variant -->
```

A screen board uses it with a marker on its own line:

```html
<!-- part:Row variant="pending" t0="Ana Díaz" -->
<!-- /part -->
```

`cargo xtask design` fills the region between the markers with the variant, indented to the marker, and puts each `tN="…"` into the element with `data-slot="tN"`. A part with one variant needs no `variant`. Parts may nest; a cycle is an error. The text of a slot has no `"` and no line break.

- Change a block by editing its variant in the part file, then run the generator. A region edited inside a board fails the check, and the message names the part file.
- A block gets a part board when it is a `RoomBlock`, a room slot (header, band, status line, filter, search, selection) or one of the four canvases ([app-plane](../change/app-plane.md)). A block no board draws is drawn on its part board first.
- Whitespace inside a variant is content when the text wraps (`white-space: pre-wrap`); such a block is left in its board.

## Links

- A control that leads to another board is `<a href="X.dc.html">`; a control for a board not drawn yet is marked `data-next="X"`.
- The check fails on a link that names no board, on `data-next="X"` once `X` exists (make it a link), and on a `<button>` inside a board link.
- A dark twin links to the dark twin of its target.

## Words

The check fails, in any light or part board except `Decisions.dc.html`, on: Agenda, Todo, Flag, Flagged, Invites, Favorite, Favorites, a "What … may read" row, and every word in the Never column of [wording](wording.md) (the literal command `centraid-gateway` is exempt). Star is the one mark of importance. A board holds no HTML comments: history belongs in git.

## The flow

1. Edit the light board, or its part board, and the tokens if a value moves.
2. A new screen gets an entry in `canvas.json` on the `light` page; a new part board on the `parts` page.
3. Android gets its own `Android*.dc.html` board only where it draws a screen differently from iOS.
4. A new icon is a path list in `design/icons.toml`, never in a shell.
5. Run `cargo xtask design`. Commit the boards, the dark twins and every generated file together.

## The checks

- `cargo xtask design --check` regenerates into memory and fails listing every file that is changed, missing or stray, and every finding in the boards: a raw colour, an unknown or unclosed part marker, a part region that is not what the generator writes, a link that names no board, a `<button>` in a link, a retired or Never word, an HTML comment, a board without `./tokens.css`, a board and its entry in `canvas.json` that do not match, and a `DesignRules.dc.html` whose swatches do not match `tokens.toml`. It also lints what the two sites author on top of their sheet: a font CDN, a literal `font-family`, a retired theme name, or a `var(--x)` that names nothing declared.
- The gate runs that check as the `design` step in `pr` and above, and `mobile-jvm` runs it after its Gradle suite. See [gate](../land/gate.md).
- `crates/xtask/src/design_boards_tests.rs` tests the board checks, and `design_checks.rs` holds the guarantees the generator does not give by construction (both schemes carry every colour role, the type styles are concrete, the shells' sources carry no path data outside the catalogue, an app's icon stays at most 24 path commands). `crates/design/src/tokens.rs` validates the token file, including the contrast floors, and a value that fails a floor is a failing test.
- `crates/screens/tests/icon_keys.rs` fails when a screen names an icon key that is not in `design/icons.toml`.
- `design_words.rs` reads the Rust string catalogues strictly. A row it cannot parse, or a missing word, is an error and not an empty label.

## Not here

- Sizes and motion belong in the boards; colour values in the tokens. Behaviour and wording rules are in [behaviour](behaviour.md) and [wording](wording.md).
- The shells' design tables are never hand-edited, and a shell that needs a value takes it from the generated tables.
