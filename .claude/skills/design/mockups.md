# Mockups first

A visual or UX change starts in `design/mockups/`. The same change updates the light boards and, when a value moves, `design/tokens.toml`. The generator then writes everything derived. How screens should behave is in [behaviour](behaviour.md); this page is the flow and the checks.

## What is authored, what is generated

| Authored (edit these) | Generated by `cargo xtask design` (never edit) |
| --- | --- |
| `design/mockups/X.dc.html`, one light board per screen | `design/mockups/XDark.dc.html`, the dark twin of each light board |
| `design/mockups/canvas.json`, the pages and each board's place and title | `mobile/iosApp/Design/*.swift` and the `Assets.xcassets` colour sets and fonts |
| `design/tokens.toml`, the values | `mobile/androidApp/.../design/{Tokens,Catalog,Words}.kt` and `res/values*`, `res/font` |
| `design/icons.toml`, the icon silhouettes | both sites' `centraid-tokens.css` and `fonts/` under `scripts/{home,docs}-site/public/assets` |
| `design/fonts/`, the font files | `design/icon/*.svg` and the app icon sets |

The kit's fixed words are not authored here. The generator reads them from `crates/screens/src/strings/shared.rs` (and one word from `home.rs`), so change the word in Rust.

## The flow

1. Edit the light board. The boards are written by a design tool, so `oxfmt.config.ts` leaves `design/mockups/*.dc.html` and `canvas.json` unformatted.
2. A new screen gets an entry in `canvas.json` on the `light` page. The generator reads that page to know which boards are light screens, and it does not write `canvas.json`.
3. Android gets its own `Android*.dc.html` board only where it draws a screen differently from iOS. Otherwise the iOS board is the reference for both.
4. Change `design/tokens.toml` only when a value changes. Roles, spacing, radii and type are the shells' `[native.*]`; the sites take `[site.*]` beside them.
5. A new colour in a light board has no dark value, and the generator stops on it. Add it to `[mockups.dark]` as a `colors` entry (the dark value depends on the role: text, ink, fill, line or shadow), or list it under `keep` if it is content that does not change. Change how a colour looks in dark by editing the table, not a dark board.
6. A new icon is a path list in `design/icons.toml`, never in a shell.
7. Run `cargo xtask design`. Commit the light boards, the dark twins and every generated file together.

## The checks

- `cargo xtask design --check` regenerates into memory and fails listing every file that is changed, missing or stray in a directory the generator owns. It also lints what the two sites author on top of their sheet: a font CDN, a literal `font-family`, a retired theme name, or a `var(--x)` that names nothing declared.
- The gate runs that check as the `design` step in `pr` and above, and `mobile-jvm` runs it after its Gradle suite. It also fails on a generated file that git does not track. See [gate](../land/gate.md).
- `crates/xtask/src/design_checks.rs` is test code. It holds guarantees the generator does not give by construction: both schemes carry every colour role, the type styles are concrete, the shells' sources carry no path data outside the catalogue, and an app's icon stays under 24 path commands.
- `crates/xtask/src/design_dark_tests.rs` checks the dark conversion. `crates/design/src/tokens.rs` validates the token file, including the contrast floors, and a value that fails a floor is a failing test.
- `crates/screens/tests/icon_keys.rs` fails when a screen names an icon key that is not in `design/icons.toml`.
- `design_words.rs` and `design_glance.rs` read the Rust string catalogues strictly. A row they cannot parse, or a missing word, is an error and not an empty label.

## Not here

- Colours, sizes and motion belong in the boards and tokens. Behaviour and wording rules are in [behaviour](behaviour.md) and [wording](wording.md).
- The shells' design tables are never hand-edited, and a shell that needs a value takes it from the generated tables.
