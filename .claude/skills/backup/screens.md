# The Backup screens

What the Rust screens draw, and the code that keeps them honest. The wording rule for "backed up" lives in [product.md](./product.md). Code: [`crates/screens/src/backup/`](../../../crates/screens/src/backup/mod.rs) and the room-based Backup and Pair screens in [`crates/screens/src/room/shell.rs`](../../../crates/screens/src/room/shell.rs). Tests: [`tests.rs`](../../../crates/screens/src/backup/tests.rs) and [`room_shell.rs`](../../../crates/screens/tests/room_shell.rs).

## Where the numbers come from

- The room-based Backup screen (`backup`) and Home's subtitle (`shell::backup_line_status`) call `BackupStatusRequest` directly through `Door::call` and parse `BackupStatusResponse` with `reading::Reading::from_wire`; the legacy `backup.home` screen reads `shell.backup-status` through `reading::load`. Both run the same `reading::Reading` and `line::line`. The core answers from the device state and dials nobody. A failed read is a `Failed` room (or `Reading::Failed`), never an empty reading. A refresh that fails keeps what was drawn, under one sentence.
- Every time that is a gateway's (acknowledgements, last answered) is the gateway's clock. The phone's clock (`now_ms`) is used only for "2 minutes ago" and for dating notices.
- `Destination::footing` ranks a device worst-first: rolled back, refusing, too large, full, behind, current. Anything but current names the device by the label the member gave it.

## The line (`line.rs`)

- `line()` is a pure function of the reading, whether the vault moved, whether a pass is running and `now_ms`. Home draws the same value, and `tests.rs` proves every sentence without a core.
- It is chosen in this order: vault moved (urgent), no gateway paired, every gateway refusing this phone's token, never acknowledged, then done or records-acknowledged-with-N-waiting.
- "Done" needs the records acknowledged and `unconfirmed() == 0`. "Backing up" is said only while a pass runs. Otherwise the status says what a gateway acknowledged and how many wait.
- Tone is attention when `warns()` finds anything: no acknowledgement, one older than 3 days, a future-dated one, no gateway answering in 3 days, an untrusted gateway, a device told to pair again, any device not current, or an old backlog. The status card's condition uses the same `warns()`, so the card cannot be calm beside a warning line.
- When one device is behind, its name replaces the headline, and `behind_last_good` says what the current devices hold.
- The second clause (`detail`) is the backup's bytes (`total_bytes`, `confirmed_bytes`): decimal units, rounded down, with videos left out stated ("All 5.0 GB is backed up."). A core that names no bytes falls back to item counts. There is no per-app holding any more: the proto's `AppHolding` and `Destination.waiting_apps` stay, deprecated and never filled.
- **Records are held or they are not** (`Reading::records_held`, the records class's `backed_up`): a snapshot taken and not yet held by every device keeps the line at "Records backed up 2 minutes ago." and the tone at attention, whatever the photos say. There is no count of edits waiting, because a status cannot see an edit made since the last snapshot.
- **The card and Home say the same thing in two lengths.** The card's `sentence` is "Backed up 2 minutes ago." and its waiting rows say what waits and why ("120 photos waiting for Wi-Fi", the card's own words, `backup_photos_*`); Home's `status` is one line, "Backed up 2 min ago. 120 photos waiting for Wi-Fi." (`line::short_ago`). A backlog that has stood three days leads with "12 photos not backed up. The oldest was added 4 days ago."

## In this backup (`classes.rs`)

- Three rows, always in this order: Records, Photo previews, Photos and files (`wire::BackupAppRow`: the proto kept its old name, `app_id` carries `records`, `previews` or `originals` for the selector `backup-class-<id>`, `icon_key` the mark: `FileText`, `Grid`, `Image`). None while nothing is paired, the vault moved or the core named no classes.
- A class is **"Backed up"** when every paired device holds all of it, **"{k} of {n} devices"** when only some do, **"Waiting"** when none does. The second line says what the class holds: "Last backup 2 minutes ago" for records, "1,240 photos" for previews, "1,282 photos and files · 5.0 GB" for originals; "All 1,240 on Office NAS" when a device holds all and another does not; "1,056 of 1,240 photos" when none does. The core counts the files (`ClassStatus.total` and `held`, from the vault's content rows against each device's confirmed tree), never the Photos app.
- What waits is the row's `note`: with several devices and only some behind, one line per device that is ("184 waiting for Office NAS"); otherwise the core's reasons for that class (`ClassStatus.waiting`: "120 waiting for Wi-Fi", "184 waiting for your backup device", "212 waiting for space on this phone"). Videos left out are the originals row's last note.
- The old second list, "Not backed up yet", and its per-app rows are gone: `BackupHomeData.waiting_heading` and `apps_waiting` stay in the proto, deprecated, and are always empty.
- `contracts/backup/states.json` holds each reading and the rows it draws (`classes`, `photos_waiting`); `crates/screens/tests/backup_page.rs` reads them.

## One vault, delete warning, restore (#1209)

- **One vault per phone** (R1). Home has no vault sheet, switch, picker, rename or forget; the lockup is not a control; Settings has no Vault section and no "Make a vault" row. The shelf stays underneath for launch and restore. Rust: `HomeEvent` lost its vault arms (reserved in the proto), `VaultCommand` keeps only make, restore and open, `Ctx::switch_vault` is gone.
- **Delete warning** (R4, `room/photos.rs`): before Delete forever on one photo and on Empty trash, Photos' confirm rooms (`PurgeConfirm`, `EmptyTrashConfirm`) check `BackupStatusRequest` via `originals_unbacked_up` (reads the device state, dials nobody; the core also exposes `HeldWholeRequest.content_hashes`, answered `not_held`, for per-hash checks), and `Confirm.warning` carries one amber line ("This photo isn’t backed up yet. No backup device can bring it back." / "Some of these photos aren’t backed up yet. No backup device can bring them back."). The read happens when the confirm is raised, not on every draw. A failed read counts as unbacked up. The member can still delete.
- **Restore** (R3): the words page's working phase lists Records, Photo previews, Photos and files in order (`WordsEnterState.restore_rows`: "Restoring", "Next", "Then"). Once the vault opens, `BackupStatusResponse.restoring` (present only while the restore's originals marker exists) gives previews and originals back of total, counted from the vault's content rows against the content store; Home's line, the Photos library's scope line and the viewer say it ("Restoring previews. 312 of 1,240 back.", then "Restoring photos. 410 of 1,282 back."), a photo whose original has not come back wears a down arrow (`HELD_COMING_BACK`), and its viewer says "This photo is still coming back. Showing its preview." beside the existing "Load the original". Counts only, never a time.

- **Pair again on the status card (ruling 28, #1202).** While any backup device no longer knows this phone (`pair_again`), the top status card that says "Pair it again" carries a "Pair again" button: `pair_again_label` and `pair_again` on `BackupHomeData`, empty/absent otherwise and on a moved vault. Its route is `add_destination`'s, the pairing page; the device's row keeps its own "Pair it again". Both shells draw it with their kit button under the id `backup-card-pair-again`. Board: `BackupPairAgain`.

## Reasons

- `REASONS` lists the 13 `WaitReason`s in the order the line shows them. One row per reason with a count above zero, each worded by `strings::backup`.
- The reasons come from the core (`phone/status.rs`). A screen never decides one. Add a reason in `phone.proto`, the core, `REASONS`, `waiting_words`, `row_reason` and the strings together.
- While items wait on `Gateway`, Home browses the local network for the gateway's new address. It runs only with the page and the app in front.

## The pass conductor (`crates/screens/src/passes/`)

`conductor.rs` is the state machine for when a pass runs and what the shell is asked to do around it; `service.rs` performs its actions; `conditions.rs` and `rule.rs` carry the member's rule and the link; `windows.rs` the OS windows. Keep true: one vault (the first held vault that can be drained; a resting or moved holding is skipped); a second pass on a running vault is refused, not queued, except one that is owed a snapshot; the next OS window is asked for on every path, refusals included; a pass that names originals only the OS library holds (`need_bytes`) is followed by a round that streams them — `"Back up now"` loops across advancing `need_bytes` batches past `MAX_ROUNDS`, capping only identical stalled asks at `MAX_ROUNDS`, while scheduled/background windows remain bounded at `MAX_ROUNDS`. When a pass answers `os_bundles`, the conductor asks the OS how many upload tasks it holds (`Action::UploadsPending`) and enqueues the files only when it holds none. What the OS reports (`UploadSettled`, `UploadsDrained`, a burst of them being `Reason::UploadsReported`, one pass, only where the OS carries files) is a wake and nothing else: only the engine confirms.

## Home (`room/shell.rs`, `backup/home.rs`)

- The room-based Backup screen (`backup` in [`crates/screens/src/room/shell.rs`](../../../crates/screens/src/room/shell.rs)) is a `SYSTEM_PLACE` room of `section` and `row` blocks: status line, waiting rows, paired devices, "Back up now" (`DrainRequest`) when paired and not frozen, and "Add backup device" opening `backup/pair` (`BackupPair`, `PairPhone`).
- In `backup/home.rs`, rows per gateway lead with how it stands. "Back up now" asks the pass conductor, which runs every pass. The control is enabled only with a gateway paired, a vault that has not moved and no run going. While it runs the reading is re-read every 2 seconds.
- Forget runs off-thread, drops the pairing and revokes this phone's token there. It is refused on a vault that moved.

## Notices (`stale.rs`, `alerts.rs`)

- `backup.alerts` is a view-less service started with the app. It re-reads the device state on appear, lifecycle, data change and every 6 hours, and offers notices to the one notification service. A failed read leaves the last offer. A moved vault offers nothing.
- Notices are scheduled ahead, from the reading and the clock only. The first is due 3 days after the oldest device's last acknowledgement (or pairing, if it never had one), then at 10 days, then weekly. At most two are offered: the latest due and the next.
- Ids are `backup-stale:<T>:<n>` for that acknowledgement `T`, so a new acknowledgement changes them all. Text claims no reason. A tap opens Backup. The Android channel is its own, `backup`.
- No device paired, or a moved vault, means no notice.

## Check my backup (`check.rs`)

- `backup.check` is pushed from Backup's Recovery section. It asks the core for `CheckBackup` with the member's rule, whether the link is metered (metered if unknown) and whether videos are excluded. It polls progress every second and offers Stop. The work is `phone/check.rs`, described in [phone.md](./phone.md).
- Each device gets a row: opens, will not open, files missing, a file damaged, or not run (Wi-Fi, space, stopped, no backup yet, a backup running, no answer). A device that was not checked is never drawn as a pass.
- No answer from the core is a failure with Retry, not "Not checked".
- A verdict is kept (`opens` or `problem` plus the time, in the device store) only when a backup was actually opened. Backup's row then reads "Checked ... ago" or "Found a problem ... ago", or "Never checked".

## Restore entry

- Backup's restore row is hidden on a moved vault. Pressing it posts Home's restore press, and Home closes its sheet and sends the vault command `Restore`. The vault service (`vault/service.rs`) opens `custody::routes::restore()`, which is `words.enter` with purpose Restore.
- `words.enter` (`custody/enter.rs`) has three purposes. Restore takes 24 words plus a gateway's pairing code. A held seed takes only the pairing code. Re-key takes the words alone.
- The core judges each word as it is typed, and the primary control opens only on a valid phrase and, for a restore, a non-empty pairing code (a held seed needs no phrase).
- A restore asks the owner check first, and warns and goes ahead on a phone with no passcode. A re-key asks nothing. The words are dropped on success and on leaving.
- Outcomes: done (the screen closes), an older backup offered, gateway unreachable, nothing held, not taken, did not check, cannot open, newer build, or a refusal. The offer shows the newest as "will not open" and the older as "opens", and the button names the older date.

## What a member reads of the new backup (`states.rs`, #1191 B16)

- A device's footing now ranks worst-first: older backup, paused, too old, another phone took over. `states::standing_words` is the row's second line for every footing, and `states::notes` adds one line each for an old backup it cannot read, a stored piece found damaged and sent again, and deletes this phone made there that are held for a week ("3 old files go Friday 20 November": the earliest date, on the device's clock; a paused device is not counting, so its row says "2 old files kept while it is paused" and shows no date). `states::can_undo` says whether the row offers Undo: held files, a date, and a device that is not paused or moved; Undo is per device and only for holds this phone's own signed deletes made (an undo is a signed write).
- Another phone took over, paused by whoever runs it, and too old each stop only that device's pass. The line names the worst device ("Office NAS is paused") and the reason under it says what to do. A taken-over vault keeps its urgent line, with "Not you? Ask whoever runs your backup device to pause it." as the reason: the person at the backup device has the last word.
- `Reading.damaged` (the vault's quick check failed) makes the line urgent ("This phone's vault is damaged. No new backup is made."), turns Back up now off and leaves the restore row; its second clause says what is safe: "The backups already on your backup devices are untouched." A damaged vault is never "Backed up", whatever the last acknowledgement says.
- `states::rate_sentence` says what a check read: "Each check reads {s} of the {n} stored pieces, chosen at random. On average a piece is read once in {m} checks." ({m} rounds up; a random draw promises no coverage, so only the average is said). A check that read every piece says "Each check reads all {n} stored pieces." It never says verified. `states::restore_ask` is the sentence a restore asks before it claims anything when it cannot prove it has the newest backup.
- `contracts/backup/states.json` holds every sentence above as a case; `crates/screens/tests/backup_page.rs` reads it and the `promises` rule holds the tests to it. Both shells draw the view state these words make, so the words are one fixture. The row carries `notes` (one sentence each, drawn after `held`, `backed_up` and `detail`) and `undo_label`; Home carries `check_rate`, drawn under the check row's status; both shells draw them. `Destination.from_wire` reads the core's own words: `reach_state` (moved, frozen, gateway old, repairing), `manifest_unreadable`, `held_count`, `held_purge_at_ms`, `held_undoable` and the read-back's `sample_checked`/`sample_of` (the device read least often sets the rate). The `UndoHeld` event asks the core's signed undo door (`UndoHeld{gateway_id}`, off-thread, `doors.rs`) for a device whose row offers Undo, lifts every hold there, and the page says "Old files on {name} are back." or "Couldn't undo on {name}. Try again.". A damaged vault is not in the status: `centraid_open` answers `CENTRAID_VAULT_DAMAGED` (-6) and no core exists, so each shell draws a launch screen of its own (`VaultDamagedView.swift`, `VaultDamagedScreen.kt`) from `KitWords.VAULT_DAMAGED_*`, which `cargo xtask design` emits from the Backup catalogue; `Reading.damaged` is set only where a screen holds a reading of such a vault. The launch screen draws "Restore my vault" (`KitWords.VAULT_DAMAGED_RESTORE`) wired to one `reopenForRestore` per shell (`ShellModel`, `AppSession`): it opens again over the same path with the open key `restoreDamaged` (boolean, camelCase; older cores ignore it), and on success attaches the core and sends Home `RestorePressed`, which enters the Rust restore entry (`words.enter`, purpose Restore); if the open fails again the damaged screen stays. The restore ask rides `RestoreResponse.unproven_newest`: the words screen draws it as the offer phase (title "Restore this backup?", the sentence from `states::restore_ask`, "Restore this one"), claims nothing, and only the member's yes sends the restore again with `confirm_unproven`.
