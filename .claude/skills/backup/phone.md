# The phone's backup

What the phone does to back its vault up and to get it back. Wording and rules a member sees: [product.md](./product.md). The design: [`contracts/backup/spec.md`](../../../contracts/backup/spec.md) (section numbers below). Code: [`crates/vault/src/backup/`](../../../crates/vault/src/backup/mod.rs) (the plane: tree, snapshot, state, staging, the `Store` trait, the engine, retention, restore, written against `Store` and no socket) and [`crates/core/src/phone/`](../../../crates/core/src/phone/mod.rs) (a thin I/O driver over it and the gateway client).

## State, and where it lives

- The device state (`<stem>.state.db`) and the staging area (`<stem>.staging/`) sit beside the vault file, never inside it, and so does `<stem>.scratch/`, which exists only while "Check my backup" restores into it. The shells keep them out of OS backup.
- Both are derived. Lose them and the phone re-pairs and re-asks each gateway what it holds. The backup is not lost.
- The core writes no key to disk. Keys arrive through the open configuration. A core without them reads and writes the vault but cannot back up.
- `state.db` (`application_id` `CBS2`, a ladder in `state_ladder/`, a newer rung refused): per gateway its pairing, epoch, `conf` (the head this phone last confirmed there), `troot` and `oroot` (roots whose thumbnails and originals are confirmed whole there), reach, sample counter, scrub cursor, and persistent `GatewayNotes` columns (`collected_ms`, `held_count`, `held_purge_at_ms`, `refusal_code`, `damaged_flag`, `sample_checked`, `sample_of`, `manifest_unreadable`); the node cache (`tree` nodes of every root a gateway's `conf`, `troot`, `oroot`, the newest snapshot and the kept snapshots name); `staged` (name, path, size); `local_bytes` (where a content hash's bytes are on this device; `crates/blobs` reads it); `blob_chunk` (durable chunk refs for `thumbnails` and `originals`, covering OS-only library originals, freed cloud-only blobs, toggled video exclusions, and cached `ByteStore` seals); and `dirty_range` (persisted 64 KiB dirty ranges folded from oversized WALs). **There is no outbox**: a name is a keyed hash of its plaintext, so what a gateway is owed is the difference between two trees.
- **Nothing is recorded as acknowledged but what the engine confirmed.** A gateway's holdings are what its head, `exists` and the bundle answers say. What an OS transport reports only wakes a pass (R7, `engine::os_event_wakes_a_pass`).

## Objects, tree, snapshot

- Every stored object is `centraid-sealed/4` (`CSB4`): one deterministic, length-padded, class-aware sealed chunk of at most 4 MiB (`CHUNK_BYTES`), named by a keyed hash of its plaintext and class, so it is rebuilt from source, never kept, and a resend is byte-identical (spec §2). Outer wire header is `"CSB4" ‖ u8(4) ‖ nonce (24)`; `flags` and `class` live inside the AEAD ciphertext, and exact inner frame lengths are hidden in Padmé buckets (`MIN_INNER_BYTES = 64`). `zstd` level 3 is pinned exactly and applied ONLY on `records` when strictly shorter (never `thumbnails` or `originals`, which are already entropy-coded); a change to its version or parameters changes held bytes and is a format change, and `contracts/crypto/sealed4-vectors.json` and `chunk-digest-vectors.json` fail when it moves.
- The manifest is a tree (v6, `tree.rs`, spec §3): a root, range leaves (up to 1024 ranges of 64 KiB), a blobs radix tree by content hash (`LEAF_ENTRIES = 256` per leaf before splitting by the next byte of `h`), and the sealed gateway directory. Entries carry `EntryKind` (`Original`, `Thumbnail`, `ExcludedOriginal`) and signed `taken_at_ms: i64` ordered by capture time `COALESCE(p.taken_at, e.created_at)`. Every `BlobsNode` carries rolled-up `BlobsStats` (`O(1)` `stats_of`) — `Node::decode` verifies leaf `BlobsStats` against its entries, and full tree traversal (`entries_of`) verifies internal branch `BlobsStats` against their children — and `NodeSource` walks support `O(depth)` `lookup_entry` and `O(Δ log N)` `diff_entries`. Classes are `records` (root, leaves, range chunks, blobs nodes, directory), `thumbnails` and `originals`. Every node is a pure function of its content, so one changed page rewrites one leaf and the root.
- `snapshot.rs` (`take_unlocked` / `take_with_vault_slot`) takes only brief locks on the vault for metadata before pinning and the exclusive checkpoint at the end, keeping `pagesource::PinnedPages` (one pinned WAL read via `sqlite_dbpage`; **no plaintext copy of the vault is written to disk**; the census, `user_version`, the write counter and `quick_check` on the same pin), page/blob sealing, and tree assembly unlocked. Only the **dirty ranges** are read, named and sealed: every connection to the vault file sets `wal_autocheckpoint = 0` and `wal.rs` maps the WAL frames written since the previous snapshot to 64 KiB ranges; the core checkpoints after a snapshot (R5), and continuously folds oversized WALs (`fold_wal_if_needed` at `WAL_FOLD_FRAMES = 4,096`) into `state.db`'s persistent `dirty_range` table even when unpaired or offline. Every 4th snapshot, and at least daily, reads every range and sets `db_hash`, as does the first snapshot of a freshly opened vault handle and any snapshot whose `disk_mark` (main-file length, mtime/ctime ns, inode, dev, page 1, `vault` root page, recorded after the core's own checkpoint) changed, so no write to the main file behind the core goes unnoticed whichever tables it touched; other snapshots carry none and reuse the previous refs for clean ranges. On `VAULT_KNOWN` re-pair after a `state.db` reset, `hydrate_blob_chunks_from_root` populates `blob_chunk` from the gateway's standing head before any snapshot runs. A damaged vault is refused before any root exists (`ERROR_CODE_VAULT_DAMAGED`). A vault that is not WAL, or built without `SQLITE_ENABLE_DBPAGE_VTAB`, refuses with a typed error.
- The pin never spans a gateway call, and the writer is never held for the walk.
- **The index file is in none of this.** `<stem>.index.db` (search, the spatial index, the alerts; `centraid_vault::index::{index_file_for, is_index_file}` name it and its `-wal`, `-shm`, `-journal` and `.founding` files) is derived data attached to the vault. A snapshot pins `vault.db`'s pages alone, so the tree's census names the vault's tables and none of the index file's, staging holds sealed `vault.db` ranges, and `wal.rs` and `dirty_range` map frames of `vault.db`'s WAL only: a write only the index file sees changes no range. `search_owed` (the queue of rows the index file is owed) lives in `vault.db` and so travels in a snapshot; it is harmless in a restored vault, which owes its new index file every entity anyway. `tests/backup_snapshot.rs` holds all of this.

## Blobs: who rents them, what a backup sends, what a pass may free

- **A hash is only ever a foreign key into `blob(hash)`**, so which columns rent a blob is read from the schema (`PRAGMA foreign_key_list`, `blob::references`), by the collector and by the backup alike: `document.blob`, `photo.blob`, `photo.motion_blob`, `person.avatar`, `container.cover`, `note_asset.blob`, `locker_item_field.value_blob`, `message_attachment.thumb`, `derivative.out` and `revision_blob.blob`. `backup::files::RENTERS` only says whose a row of each is (the column naming its entity); `lapsed_blobs` fails naming the column when the schema has a renter it does not list, and `tests/blob_release.rs` walks the schema and fails the same way, so a column that rents bytes cannot be added without saying whose they are.
- **No blob an earlier version names is collected while its entity lives.** A version names every blob it held as a `revision_blob` row (`history::BLOB_SLOTS`; a lane adds a row there, not code), and that foreign key keeps it. The row is written when the commit settles, so `blob::collect*` leaves alone every hash in the noted pre-state of an entity that still exists (`blob::pending_clause`); a command may replace a blob and collect in the same commit, and a purge (which takes the entity's versions with it) still frees both. The blob is then named by its version and is collected only when the entity is purged.
- **A derivative's file is a rented blob and is backed up** (`derivative.out`, class `thumbnails`; it follows its original and lapses with it). Whether a variant is a file is its `derivative_variant.has_out`, a table only a migration writes: `derivative.write`, `derivative.drop` and the staging door read it, no list of variants is kept in Rust. `derivative` stays in `vault.db`, so a restore brings OCR text and captions back without running them again.
- **A Locker sealed file** (`locker_item_field.value_blob`, and the file an earlier version of a field named: slot `field:<id>`) is bytes already encrypted under the Locker key. `ContentFile::sealed` marks it. It is read as opaque bytes (never a video, never a derivative), so no exclusion (the video exclusion) reaches it and it is always in the tree as an original; it is never in `originals::never_freed`, the set the core's "free up space" must subtract; and `blob::write_derivative` (so `derivative.write` and `stage_derivative`) refuses to make anything from it. The link rule is unchanged: it crosses on the links an original may (Wi-Fi by default), and an exclusion never keeps it off the gateway. `tests/backup_sealed.rs` proves it with raw rows; the Locker lane adds nothing here.

## Staging

`staging.rs`: sealed objects are rebuilt when needed, so staging holds only sealed vault ranges between the pin and their confirmation, originals whose bytes only the OS photo library holds (until every gateway confirms them), and the bundle files handed to the OS. The budget is the smaller of 512 MiB and a tenth of free space (`CoreConfig::staging_ceiling`; `spool_bytes` on the wire means staging bytes). A file reaches its name by rename after fsync; opening the area sweeps partials, under one lock per core. A range no longer staged stops the engine with `Restage`: the driver snapshots again with every range restaged and retries once.

## The engine (`engine.rs`, spec §6)

- **A pass per gateway** is a pure state machine; I/O goes through `Store`. Read the head: equal to `conf` is incremental; otherwise it is recovery (drop `conf`, `troot`, `oroot` and the claims for that gateway and learn what is held through `exists`). Records first: owed objects go in bundles (`POST bundle`, frames staged into a packfile and committed in one transaction; a connection that drops leaves every finished frame stored). `taken` with another digest and `state: damaged` frees the name by one signed delete and resends. Then **the commit rule** (asserted: debug builds panic, release builds abort the pass): every records ref reachable from the new root is reachable from `conf`, answered `stored`/`there`/`held` this pass, or reported held by `exists`. Then the signed compare-and-set of the head, then persist `conf`. Thumbnails, then originals, newest first, each a phase for its class ending in `troot` / `oroot`; `GatewayPass::enter_media` seeds `phase.skipped` with unheld entries of that class so `troot`/`oroot` is never confirmed while any in-scope entry lacks sealed chunk refs; a media phase first asks `exists` of its owed names, so a cut-off pass never resends what a gateway holds. While past records the head is re-read every `head_recheck_every(...)` windows and a pass restarts if it moved.
- **The scheduler** serves every gateway's debt by class: records of every gateway before thumbnails of any before originals of any, round robin inside a class. A chunk is read and sealed once per window and sent to every gateway that owes it; `Env::with_peers` repairs chunks missing from local `Staging` and `ByteStore` (such as cloud-only freed originals for a newly paired second gateway) by fetching and opening them from peer gateways. The member's rule applies per class through `Policy`: Wi-Fi only by default, photos optionally on cellular, video originals never on a metered link, "Back up now" sends records on a metered link and never a heavy original.
- `held_whole(env, gateway, hash)` says whether every chunk of an original is reachable from that gateway's `oroot` in `O(depth)` via `tree::lookup_entry` (R4: the Backup screen and the warning before deleting a photo use this one test); the core's `HeldWholeRequest` asks it.
- `debt` and `housekeeping` short-circuit in `O(1)` when a gateway is already caught up (`conf`/`troot`/`oroot` match `newest`, or `diff_entries` finds zero delta). `housekeeping` ends a pass alongside read-back and retention.

## Retention

Keep 7 daily, 4 weekly and 6 monthly snapshots, UTC. A period counts only if it holds a snapshot. The newest is always kept. A snapshot dated after now is judged as taken now. Collection (the core runs it at most every 6 hours, never on a metered link) lists the gateway's names and deletes, by **one signed delete bound to the head it was computed under**, every name not reachable from: the head, `conf`, `troot`, `oroot`, every kept snapshot, the newest snapshot, and anything an Undo restored this week. A kept root whose nodes will not open stops collection for that gateway: doubt never deletes.

## Read-back

After a whole pass, per gateway, the engine reads back a keyed random sample of `SAMPLE_CHUNKS` (64) sealed chunks (8 on a metered link) of the tree at `conf`, limited to what the gateway's confirmed roots say it holds, plus a scrub walk of `SCRUB_NAMES` (32) names after the gateway row's `scrub_cursor`. The draw has no clock: `index(k) = r(k) mod N` with `r(k)` the first 8 bytes of `blake3::keyed_hash(sample_key, u64be(counter) ‖ u64be(k))`, `sample_key = blake3::derive_key("centraid backup v2 sample", K_backup)`, `counter` the row's `sample_counter` (incremented with the result), an index already drawn skipped. The gateway cannot predict it (it lacks `K_backup`). Each chunk is fetched and opened (the tag authenticates it; name and digest are re-derived and compared). A chunk that is gone, will not open or differs is sent to the gateway as a signed **check this name** (`POST check`, which marks a mismatch damaged so one signed delete frees it at once; `intact` deletes nothing) and **every claim for that gateway is withdrawn**: the next pass is a recovery pass that learns what is held through `exists` and sends what is missing. What a member reads says what was read and what opened, never "verified": see [screens.md](screens.md).

## The driver (`crates/core/src/phone/`)

`drive.rs` is the `drain` door, an I/O loop over the engine:

1. **Snapshot when due** on the vault's own clock: about 30 s after the newest snapshot a head named (`SNAPSHOT_SETTLE_MS`; the conductor's debounce coalesces a burst), never while the vault is unchanged, at once when asked, when a gateway's head went backwards, when the directory is dirty or owed, or when a gateway has no `conf` (then every range is restaged and the first read is full).
2. **Reach** every gateway at once under `REACH_CAP` (`link::reach_all`; a dead gateway costs the cap, not a turn). The typed `Reach` (`ok`, `unreachable`, `untrusted`, `too_old`, `pair_again`, `moved`, `frozen`, `busy`) stops that gateway only; `too_old` ends the pass `DRAIN_STOP_TOO_OLD`, and the status draws it as `DESTINATION_REACH_GATEWAY_OLD` ("update your gateway").
3. **Step the engine** in a local loop, checking the deadline between steps; a pass that stops `Restage` gets one retry.
4. **After the pass:** read-back, retention collect, `housekeeping`, and, after a restore left `<stem>.originals-owed`, `fetch::bring_originals` (R3's third phase, with an unbounded `usize::MAX` limit on foreground / `"Back up now"` passes and `ORIGINALS_PER_PASS` otherwise).
5. **Originals only the OS library holds** are named in `need_bytes` (at most 64; the driver asks `exists` of each gateway and releases staged chunks every gateway holds). The shell streams them through the stage door (`stage.rs`), which seals the item's chunks into staging only for chunks owed and only as far as the budget allows, and records every chunk ref in `blob_chunk` so the next snapshot lists the original. Nothing is sealed at import.
6. **OS bundle files:** `DrainRequest.os_uploads` makes the answer carry `os_bundles` (at most `OS_BUNDLES` = 4 files of at most 32 MiB, each a whole `POST bundle` request as a `HandoffPart`). iOS uploads them through a background `URLSession` (Android writes none — WorkManager runs the pass itself inside its window); a finished, failed or lost task only wakes a pass.
7. **Split-brain guard (`pair.rs`):** when pairing a known vault (`VAULT_KNOWN`), `head_is_ahead` always compares `root.writes > own.writes` (plus `epoch > held`) with no local timestamp short-circuit, so a stale vault copy with a later wall-clock timestamp cannot claim over a higher-writes head.

`status.rs` answers `backup_status` per class (records, thumbnails, originals: `ClassStatus` on `BackupStatusResponse.classes` and `Destination.classes`); the per-app `apps` rows are no longer filled. Each class row carries `total` and `held` (files), and the aggregate rows `waiting` (why, per class); `BackupStatusResponse.restoring` is present while a restore still owes previews or originals (R3); `HeldWholeRequest.content_hashes` answers `not_held` for many at once (R4), listing each gateway's originals tree once. What may be sealed and moved under each rule is `Conditions` in [`drive.rs`](../../../crates/core/src/phone/drive.rs); the rule itself is in product.md. Wait reasons come from `status.rs`; a screen never decides one.

## Credentials

The gateway token is kept by the shell in the device secret store (`SecretBatch`), never by the core: iOS `kSecClassGenericPassword` with `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` and no iCloud sync (`AfterFirstUnlock`, so a background pass can read it locked); Android the value AES-GCM sealed under a non-exportable Keystore key without a user-authentication requirement, in preferences excluded from backup. The key is `gateway-token.<vault_id hex>.<gateway_id hex>` (`crates/screens/src/custody/secrets.rs` writes it when a pairing or restore mints a token, and deletes it on forget). `pair` returns the token to the core in memory; the core asks the shell to store it and writes the `gateway` row only after the put answers ok. The core opens with the tokens its gateway rows name, supplied by the shell in the open configuration, and keeps them in memory; a gateway with none is `pair_again` and the member pairs again (a claim at epoch + 1, which revokes the lost token). The token is never a column.

## Restore

- **Order (R3):** records (write the pages, verify `db_hash` when the root has one, `quick_check`, census, then the vault opens), then thumbnails (batched) followed by originals newest first in the background passes after (`fetch::bring_originals`; the restore leaves `<stem>.originals-owed`) or on open (`fetch_original` walks refs from the newest tree).
- **Which backup:** read every listed gateway's head (the sealed directory of ids, addresses, pins and labels, never a token; rewritten when a gateway is paired, forgotten or changes), verify it, and take the greatest `(epoch, generation, writes)`. When the phone cannot prove it holds the newest (the directory lists one gateway, cannot be read, or lists one that did not answer) it claims nothing and answers `unproven_newest`; a second restore carrying `confirm_unproven` proceeds. The ask is "The newest backup I can find is from {date}, on {label}. I can't tell whether a newer one exists on a gateway I can't reach. Restore this one?"
- **Claim (E5):** at every gateway that answered with a verified head, naming the head it checked; one that did not answer or whose head moved is left unclaimed and named in `unclaimed` for the next pass. A claim that landed is never forgotten. The old phone's next write at that gateway is `MOVED`.
- A restore on the handle `restoreDamaged` gives (no vault, the damaged file never read) replaces only that vault's file by atomic rename after its snapshot checked; cancelled or failed, the file is as it was. A vault already on this phone is replaced unless its copy is newer; then it is left and reported unclaimed. If the newest snapshot will not open and an older does, the older is offered and nothing is claimed until the member agrees.
- A backup of an earlier vault model, or written by a newer schema rung than this build reads, is refused with a sentence before anything is written or claimed (`restore::RestoreError`): the root's census is compared with the tables its rung makes (`EarlierModel`: "this backup is of an earlier model of the vault, which this version does not read"), and the rung with the ladder (`NewerBuild`); an older rung is climbed by the vault's own migrations on open. The file's own schema digest is checked again once its pages are laid down.
- **The index file is not restored: it is founded again and rebuilt.** A restore writes `vault.db` only. `Restore::records` removes any index file and sidecars beside the target (`restore::discard_index_file`: an index file's check names only the vault, so one built from the replaced vault's newer rows would otherwise pass as current), and `restore_all` opens the restored vault once, founding a fresh index file and calling `rebuild_index()` (which also empties the restored `search_owed`) under the clock it is given (`restore_all_with`; `restore_all` uses the system's, and a repeating reminder's next alert is a function of it), before it hands the vault to the caller. Search, the spatial index and the alerts table after a restore are what a rebuild from the restored rows gives, which is what they were before the backup (`tests/restore_drill.rs`). A caller that lays the file down itself (the driver's atomic rename into a vault's real path) calls `discard_index_file` for that path too.

## Drill and check

- `backup::drill::dump` writes every row of every table of `vault.db` (the index's queue `search_owed` left out: it is derived, and a restore empties it) so a restored vault can be proved to be the one that was lost; the index file is compared apart, by what it finds (`tests/common/index.rs`). `tests/restore_drill.rs` backs a vault up with the real engine, loses everything and restores in R3's order; `crates/centraid/tests/restore_drill.rs` runs the product's drill against a real gateway. The `restore-drill` gate step runs them in every profile except `mobile-jvm`.
- "Check my backup" (`phone/check.rs`) restores each reachable gateway's records into `<stem>.scratch/`, opens the vault through the ladder, asks `exists` over every media chunk, samples whole files (at most 40 files of 8 MiB, 128 MiB in all) and withdraws a claim (`DeviceState::withdraw`) at a gateway where something is missing or damaged, so the next pass sends it again. It needs the vault's size plus a tenth plus 64 MiB free. That is the only thing a check writes.
- `backup_sim.rs` (the seeded simulation with its faults, invariants and planted bugs, spec §8) is the proof of the engine; a change to the engine runs it with more seeds (`CENTRAID_SIM_SEEDS`).
