# Changing a screen, end to end

The product decision lives in Rust. The shells only draw. Most "UI" work is therefore a Rust change plus two thin views, and the failures come from skipping a layer or from putting a decision in a view.

## 1. What this change touches (in order)

1. **Contract**: `crates/api-proto/proto/centraid/core/v1/<app>_screens.proto` (view states and events), `route.proto` (route arguments), `screens.proto` (the `Route.args`, `ScreenEvent.kind`, `ViewState.kind` and `Effect.kind` oneofs), `kit_screens.proto` (shared vocabulary: `Failure`, `Loading`, `Denied`, `EmptyState`, `StatusLine`, `Confirm`, the trash). A new file is also listed by name in `crates/api-proto/build.rs`.
2. **Screen**: `crates/screens/src/<app>/<name>.rs`, one folder per app, no imports from another app; shared pieces go in `crates/screens/src/kit/`. It is not under `crates/apps/<app>` because the core depends on the app crates and this crate depends on the core (a cycle).
3. **Words**: `crates/screens/src/strings/<app>.rs`, or `<app>_<screen>.rs` for a screen's own, each a `catalog!` block. The kit's fixed words are `strings/shared.rs`.
4. **Registry**: the app's `registry()` returns `Registry::with("<app>.<name>", build)`, merged in `crates/screens/src/lib.rs`.
5. **Android**: `mobile/androidApp/src/main/kotlin/dev/centraid/android/screens/<app>/`, routed from `screens/RustRoot.kt`'s `Page`; effects in `kit/ScreenEffects.kt` (needs the activity) or `session/ShellEffects.kt` (needs only a context). The runtime handle is `dev.centraid.core.Screens` in `mobile/core` (flows `navigation`, `views`, `effects`).
6. **iOS**: `mobile/iosApp/Sources/<App>/`, routed from `RustScreenHost.swift` (the one place that maps `ViewState.kind` to a view); effects in `ScreenStore.swift`; the five-symbol binding is `Core.swift`.
7. **Generated**: design tokens, icon catalogue and kit words into `mobile/androidApp/.../design/{Tokens,Catalog,Words}.kt` and `mobile/iosApp/Design/{Theme,Catalog,Words}.swift`; and `crates/screens/src/catalog.rs` from the app manifests.

## 2. The steps

**Start from the mockups.** A visual or UX change begins in `design/mockups/`: find the screen's board (`canvas.json` lists them) and update the light board in the same change. Dark boards are generated by `cargo xtask design`, never hand-edited; a value that changes goes in `design/tokens.toml`. The behavioural rules (rooms, one way home, status line, search, controls, colour, accessibility, wording) are in the `product-intuition` skill's [design behaviour](../product-intuition/references/design-behaviour.md).

1. **Decide where the change lives.** A label, count, empty-state choice, enabled flag, ordering, destination or accessibility label is Rust's. If a view needs a value the `ViewState` does not carry, add the field in Rust; never compute it in Swift or Kotlin. A copy edit is a `strings/` edit and nothing else.
2. **Edit the proto first.** Put new messages in the app's file and new oneof arms in the app's reserved range (the `screens.proto` header lists them: 100s calendar and reminders, 200s docs, 300s health, 400s locker, 500s money, 600s notes, 700s people, 800s photos, 900s the kit, 1000+ the shell). Compatibility is enforced by `buf breaking` under `WIRE_JSON`: adding fields and arms is fine; never renumber, retype or rename; to remove one, `reserved` BOTH its number and its name. A view has three states (loading, a `Failure`, data); a failed read is never an empty list.
3. **Write the screen.** Implement `Screen`: `update(event, &Ctx) -> Vec<Effect>` and `view(&Ctx) -> ViewState`. Read only with `kit::read::read` (`Data | Denied | Failed`); write only with `kit::act::act`, which answers with the verdict synchronously. Handle `Appeared` (the one load), `DataChanged` (load again), `EffectResult`, `TimerFired`, `Left`. Name apps, actions and queries through the generated `catalog::act::...` / `catalog::load::...` values, never as strings; if an app's `manifest.json` changed run `cargo xtask screens-catalog` (`--check` fails a stale file).
4. **Navigation is data.** A row that opens a page carries a `Route` (`<app>::routes::*`); the shell sends it back as `NavPush`. A finished screen sets `dismissed`/`finished` and the shell pops. One screen reaches another with `Ctx::post(name, event)`.
5. **Strings.** One `catalog!` row per sentence (`plain`, or `counted` for plurals), used in `view` through `strings::<app>::*`. `bun run lint:product` (which runs `scripts/lint-copy.mjs`) bans words (please, simply, seal, ledger, gateway...), dot-joined thoughts and over-long strings by key suffix.
6. **Test in Rust first** (section 5), before any view exists. Behaviour is proven here, not on a device.
7. **Add the Compose view** under `screens/<app>/`, take the `ViewState` arm in `RustRoot.kt`, send `ScreenEvent`s with the `send` lambda. Use only kit controls and tokens.
8. **Add the SwiftUI view** under `Sources/<App>/`, take the arm in `RustScreenHost.swift`. A new `.swift` file or new `.proto` file needs `xcodegen generate` (the target globs a directory; the Xcode project is generated and not committed).
9. **A new effect** (platform work Rust asks for) is an arm in `Effect.kind` plus a performer on BOTH shells. The shell answers with `EffectResult` under the same `effect_id`, in the order asked; a cancel or refused grant answers `EffectFailed`; an effect that answers more than once (a file pick, a network browse) keeps its one id. Never reach the platform from a view outside an effect.
10. **Tokens and kit words.** Edit `design/tokens.toml` (tokens), `design/icons.toml` (icons) or `strings/shared.rs` (kit words), then run `cargo xtask design` (it emits the tables, colour sets, resources and the words) and commit the regenerated files.
11. **Parity.** Run `cargo xtask rules` and fix each finding by reading the field in the other shell.

## 3. What must stay true

- **Views decide nothing.** No `.secondary`, SF Symbols or Material icons; every value is a token or a stated geometry; icons come from the emitted catalogue (24x24 path data; Compose `PathParser`, iOS `Sources/Icon.swift`).
- **A shell never names a screen id or a destination.** `native-spells-no-screen-id` scans both shells against the registry. A route is whatever the row carries.
- **Both shells read every field.** `native-shell-parity` (`crates/xtask/src/native_parity.rs`) takes each field of every `*_screens.proto` and `screens.proto` message and asks whether Compose spells it (`.name`, `name =`, `name_`) and SwiftUI spells it (`.camelCase`, `camelCase:`, `_p`). A field only one shell reads, or neither, fails unless it has a row in `native_parity_register.rs` (`Platform`, `Gap`, `RustOnly` or `Runtime`). The register only shrinks: closing a gap deletes its row, and a new row is not how you pass the rule. The match is by field NAME, not message, so two messages sharing a name share a verdict.
- **A decode that fails renders the loading state**, never an empty one: an empty state claims an empty vault before one was read.
- **Every write uses a fresh invoke key** (`kit::act::fresh()`); the vault journals a key for good and a repeat answers "replayed" without running, a silent no-op.
- **Secrets stay where they are drawn**: never in a route, never in a view not asked to draw them. A view with `secure` set needs capture shielding and no clipboard or keyboard learning on both shells.
- **Icon-only controls carry a label** and decorative glyphs say so (`native-accessibility`).
- **Timers live in the runtime** (`ctx.start_timer`); a shell holds none.

## 4. Pitfalls

- **A stale core.** iOS links `libcentraid_core_ffi.a` by path and Android loads a copied `.so` from `jniLibs`; nothing rebuilds either when Rust changes. The app can show old behavior without an error. Rebuild the core for the target platform before running the shell; see [mobile-verify](../mobile-verify/SKILL.md) for the canonical commands and platform requirements. The Android core script currently uses a macOS NDK toolchain.
- **Hand-edited generated files** are overwritten by the next emit, and the gate's `design` step fails on a diff. Fix the source (the mockups and `design/tokens.toml`, `design/icons.toml`, `strings/shared.rs`), not the output. A guard belongs on the source too.
- **Tokens.** Never write a hex colour or a parallel colour table in a view; a value that is not a token belongs in the mockups and `design/tokens.toml`, then re-emit.
- **A view that works on one platform.** Add the field to the other shell the same day; the parity rule counts spellings, not rendering.
- **`UIImage(contentsOfFile:)`** returns nil for the content store's extensionless files; use `UIImage(data:)`.
- **Swift written without a compiler** is unproven until a Mac compiles it; say so.

## 5. How to check it

Write the Rust test with `centraid_screens::testing::Driver`: `start()`, `send(instance, event)`, `nav(..)`, `answer_effect(..)`, `pump(wait)`, then assert on `driver.views`, `driver.effects`, and `driver.navigation`. [crates/screens/tests/proof.rs](../../../crates/screens/tests/proof.rs) is the model. Cover loading, data, a failed read, empty, a refusal sentence, `Left`, and each effect answer.

Use [mobile-verify](../mobile-verify/SKILL.md) for the canonical check commands, prerequisites, platform capabilities, and device hand-off. Linux can run Compose builds when an Android SDK is installed; an emulator or device is a separate requirement. iOS builds and simulator checks need a Mac. The parity rule checks field spellings in both shells, not whether the views render correctly.

## 6. Final checklist

- [ ] Every decision, string and flag is Rust's; the views only draw the `ViewState`.
- [ ] Proto changes are additive or reserve both number and name; arms are in the app's range; a new file is in `build.rs`.
- [ ] A `Driver` test covers loading, failure, data and each effect.
- [ ] Compose and SwiftUI both exist and read the same fields; `cargo xtask rules` is green and no register row was added to dodge it.
- [ ] A new effect has a performer on both shells and answers under its `effect_id`.
- [ ] Generated artifacts were re-emitted and formatted, never edited; the tree is clean after the emit.
- [ ] New Swift files or protos: `xcodegen generate` was needed and noted.
- [ ] The Rust core was rebuilt per platform before any device check; what was not run (Compose, SwiftUI, a device) is stated.

## 7. Adopting trash in an app

The uniform rule (design-behaviour.md § Trash) is one kit machine and one spec per app; `cargo xtask rules` prints what an app still owes (`owed <app> / Trash: ...`). Written from Calendar, the reference adoption. Do these in order:

1. **Mockups.** `design/mockups/Trash<App>.dc.html`, `More<App>.dc.html` and the page's "Move to trash" exist; change them first if the app's differ.
2. **Manifest** `crates/apps/<app>/manifest.json`: actions on the shared commands, which the app tests and `crates/apps/<app>/src/commands.rs` `ACTIONS` (`act` / `confirmed`) mirror: `entity.trash` (inverse the restore), `entity.restore`, `entity.purge` (`confirmed`, input `id`) and `entity.empty_trash` (`confirmed`, `bulk`, input `kind`: the one kind). Add one `act` scope per new command. Format with `bunx oxfmt -c oxfmt.config.ts --disable-nested-config <file>`.
3. **The trash read.** A `trash` query (manifest entry; a loader in the app crate reading `entity` where `kind = ? AND deleted_at IS NOT NULL`, `read_window`, truncation reported; the core's `app_query/<app>_trash.rs` fills civil days with `zone_if_any`; arms in `app_query.proto` at the same number in both oneofs, rows in the app's proto; dispatch in `app_query.rs`, `load.rs`, `core/tests/query_plans.rs`). Skip it where the app already has one (Notes, People, Reminders, Locker, Docs).
4. **The spec** `crates/screens/src/<app>/trash.rs`: copy Calendar's: `app`, `icon_key`, `noun: shared::trash_noun_<noun>`, `purge_lead` (only if something goes with the record), `back_label`, `denied`, `load`, and `trash`, `restore`, `purge`, `empty` (all required). Register `.with(TRASH, trash::build)` in `mod.rs`, add `routes::trash()`. Write no words: `strings/shared.rs` has every one.
5. **Screens.** The More sheet row: `shared::trash_entry` / `shared::trash_entry_meta`, icon `Trash`, `route: routes::trash()`. The item page or row: a "Move to trash" action (`shared::trash_move`, destructive, no confirm) that calls the trash action and sets the status line with `trash::moved_to_trash(locale, title)`, `shared::trash_undo` and an Undo handler (`StatusActed`; add the arm to the page's event proto if it has none) that restores. Keep the page open on the gone state so the line shows.
6. **Regenerate**: `cargo xtask screens-catalog`; fix the counts the failing tests name (`crates/apps/kit/src/manifest.rs` census, `crates/core/src/catalog.rs`, `crates/nativetools/tests/catalog.rs`) and add the new actions to `contracts/assist/catalog-census.csv` (and the count in `contracts/assist/README.md`); then `cargo run -p centraid-nativetools --bin nativetools -- export contracts/assist/export` and `cargo test -p centraid-nativetools`. Purge and empty are `confirmed`, `card` surface and not reachable from chat (`reachable_from_chat_today` is `no`): they are irreversible, so leave them out of the assistant.
7. **Tests** (Rust, `Driver`, a fixed instant with `with_runtime_at` / `World::seeded_at`): the page offers the verb and asks nothing; the status line and Undo; the record is gone from every surface that read it (grid, agenda, search, notifications) and back after a restore; a trash row's `Deleted .. · Erased ..` meta; Delete forever and Empty trash confirms in the shared words and the writes; a holder or series goes whole (state it in a test); a followed record the member trashed is not resurrected by the next pass; the More entry. `crates/screens/tests/calendar_trash.rs` is the model.
8. **Register.** Flip the app's `Promise::Trash` row in `crates/xtask/src/promises.rs` from `owed` to `kept(.., "crates/screens/src/<app>/trash.rs")`: the rule fails a `Kept` that is false and an `Owed` that is satisfied, so it tells you when you are done.
9. **Shells.** Not yours to edit unless `native-shell-parity` asks: list in the report the new fields (an event arm `status_acted`, a band tab, a route) for the Compose and SwiftUI agents.

## 8. Adopting earlier versions in an app

The vault keeps every record's earlier values at its commit door (#1185); `kit/earlier.rs` is the one screen that lists and restores them, and `cargo xtask rules` prints what an app still owes (`owed <app> / History: ...`). Written from People, the reference adoption. Nothing here touches the vault, the manifests or the proto: the shared door (`shell.earlier-versions`, `shell.earlier-count`, `restore-version`, `undo-change`) and the `Earlier*` messages exist.

1. **Mockups.** `design/mockups/Versions<Kind>.dc.html` and the "Earlier versions {n} ›" row at the foot of the kind's detail board exist; change them first if the app's differ.
2. **The spec** `crates/screens/src/<app>/earlier.rs`: copy People's. `app`, `noun: shared::trash_noun_<noun>`, `denied`, and `line: fn(Locale, &[Field]) -> String`, which words the fields a version held in ONE line the way the kit's page words them (reuse the page's own `fold` helpers; a field the page does not show has no words; `before` and `after` are JSON, `null` where there was none). `build` is `earlier::build(&SPEC, route)`. Write no words: `strings/history.rs` has them all.
3. **Register** `pub const EARLIER: &str = "<app>.earlier"` and `.with(EARLIER, earlier::build)` in `mod.rs`.
4. **The entry.** Add `optional EarlierEntry earlier = N;` to each primary kind's view state (the app's reserved range). The page's `reload` reads `earlier::foot(ctx, EARLIER, &id, &back)` (back is the page's title, which its route to the list carries) and `view` sets `earlier: foot.entry.clone()` and ORs `foot.status(locale)` into the status line, so a count that was not read is said, not drawn as no entry.
5. **A page that keeps its own history screen** (Notes `history.rs`, Docs `versions.rs`) moves onto the spec and deletes its screen, route and strings; its restore command stays the same one.
6. **Tests** (`Driver`, `with_runtime_at`): the entry and its count appear only once something is earlier; the list is Current then each version newest first; Restore asks nothing and ends in "Earlier version restored" with Undo; a change a follow pass made reads "From your phone"; a failed read is the failed state. `crates/screens/tests/people_earlier.rs` is the model.
7. **Register.** Flip the app's `Promise::History` row in `promises.rs` to `kept(.., "crates/screens/src/<app>/earlier.rs")`; the rule fails a `Kept` that is false and an `Owed` that is satisfied.
8. **Secrets in a version (a wall).** An app whose records hold sealed values (only Locker) gives its spec a `kit::earlier::Wall` as `gate`: `closed` (the lock), `secrets` (the sealed values a version held, named, from the fields it held) and `open` (the core's owner-checked reveal of that version's cell). The kit then draws each as `EarlierSecret` (dots, Reveal) and answers `EarlierEvent.reveal` / `conceal`; no value is ever worded in a line. `locker/earlier.rs` is the model.
9. **Shells.** List in the report the new fields (the `earlier` arms of `ViewState` and `ScreenEvent`, the kind's `earlier` entry) for the Compose and SwiftUI agents; the shared screen is drawn once.

## 9. Adopting export in an app

`kit/export.rs` is the one export screen (drawn with the wire Transfer view, so no shell work); `cargo xtask rules` prints what an app still owes (`owed <app> / Export: ...`). Written from Notes and People.

1. **Manifest**: the app's export action declares `"writes_nothing": true` (an export writes nothing) and returns `{name, content (base64), count}`; run `cargo xtask screens-catalog` after a change.
2. **The spec** `crates/screens/src/<app>/export.rs`: a `static SPEC: ExportSpec` with `app`, `title`, `lede`, `back_label` (words), `denied`, `choices: fn(&Ctx) -> Reading<Vec<Choice>>` (the rows: "Everything in <App>", or "All notes" and each notebook), `export: fn(&Ctx, &str) -> Result<ExportFile, String>` (call the command, then `export::file_of(&settled, media_type, fallback_name)`) and `no_passcode: NoPasscode::Warn`; and `pub fn build(route) { export::build(&SPEC, route) }`. Write no words for the kit's parts: `strings/shared.rs` has the headline, the saved line and the failure.
3. **Register** `.with(EXPORT, export::build)` under `"<app>.export"` in `mod.rs`.
4. **The entry**: a row of the More sheet built from `export::entry(locale, EXPORT)` (key, label, icon, route), the same row in every app.
5. **Register the promise**: flip the app's `Promise::Export` row in `promises.rs` to `kept(.., "crates/screens/src/<app>/export.rs")`. Locker keeps its own machine (`OWN_EXPORT`).

**A large export is a streamed file (D17).** `ExportSpec::export` returns `Made`: `Made::Bytes(ExportFile)` (what `file_of` makes, small files, `SaveFile`) or `Made::Staged(StagedFile)` (what `export::staged_of` makes from `{path, name}`, `SaveFilePath`: the shells offer the save sheet for a file already on disk, copy it by streaming and delete it). The command writes the archive itself: it asks `ctx.blobs().staging_dir()` (`<vault>.exports`, beside the store, emptied by the next export) and writes entry by entry through `centraid_vault::portable::zip::ZipWriter` (`add(name, size, reader)`, a fixed 64 KiB buffer, ZIP64 past 4 GiB), copying each original from `BlobStore::path_of`. Never build the archive in a `Vec`. `document.export_zip` is the model. The whole-vault export (`vault.export_all`, Settings' "Export everything", `shell/export.rs`) is the one export no app owns: it writes each app's own entries (the `*_portable` functions) into one archive, leaves Locker out, is a shell command run through `Ctx::command` (no manifest), and is not in the undo or `writes_nothing` tables.

## 10. Adopting share in an app

`kit/share.rs` is the one hand-off of a single item to the OS share sheet (`ShareBytes`: a small file made in memory); the owner check is inside it.

1. **The item** is a file the screen already has or one vault read away (a note as Markdown from the open draft, a vCard from `person.export_vcf` with `person_id`). A new read or command follows `vault-change`.
2. **The detail screen** of the primary record holds a `Share`: its menu row (`share::label(locale)`, icon `share::ICON`) sends a `ShareRequested` event (add it to the screen's event proto, and the label to its chrome) whose handler returns `self.share.tap(locale)`; the `EffectResult` arm returns `self.share.result(ctx, &result, |ctx| Ok(file))`; `Left` returns `self.share.left()`; `status` ORs in `self.share.status()`.
3. **Shells**: add the row beside the menu's others in Compose and SwiftUI (`chrome.share_label` / `chrome.shareLabel`, the event). The effect's performers exist in both.
4. **Register**: flip the app's `Promise::Share` row to `kept(.., "<the detail screen>")`. Docs (`ShareFile`) and Photos (`ExportOriginals`) are named in `OWN_SHARE`; Locker has no share by decision (`NO_SHARE`, D11).

## 11. Offering Undo

Every undoable action says what happened with "Undo" on the status line, through ONE kit door: `crates/screens/src/kit/undo.rs`.

1. Hold `undo: Undo` (`Undo::default()`; Reminders' `Ops` already holds one as `ops.line`).
2. Write only through it: `self.undo.act(ctx, request, &key, |locale| words::note_pinned(locale))` (`act_reverting` for a write whose inverse the core does not know, `act_quietly` for a write that says nothing, `act_also` for a write that follows one already said). It says the sentence with "Undo" exactly when the core answered with an inverse, and a refusal as a refused line. Never call `kit::act::act` or `ctx.act` from an app's folder.
3. Take the kit's one event, on any screen, with no per-screen arm: `Some(E::StatusActed(_)) => { if self.undo.acted(ctx) { self.reload(ctx) } }`. `acted` runs the stored inverse under a fresh key, says "Undone" (or the refusal: the core's plain sentence, else "This changed again, so it was not undone") and offers nothing more.
4. Draw it: `status: self.undo.status()`.
5. On `Left`, or when a newer non-undoable line replaces it, `self.undo.clear()` / `say(..)`.

**The checker.** The `promises` rule's Undo row has a third rule, C: no file under the app's screen folders (`undo_folders` in `crates/xtask/src/promises.rs`; Reminders and Calendar also answer for `agenda/` and `kit/schedule/`) may call `kit::act::act` or `ctx.act` directly. A call whose Undo is offered elsewhere (a notification receipt) carries `// undo-exempt: <why>` on its line or the three above; a marker with no reason exempts nothing. Every app has adopted the door; a new app's Undo row stays `owed` until the rule is clean, then flips to `kept`.

**The test model** is `crates/screens/tests/undo_line.rs`: an undoable act shows the sentence and "Undo"; the kit `StatusActed` reverses it and the line says "Undone" with no verb; an act the core cannot take back shows no verb; a change made again between the act and the tap is refused plainly and the later change stays. Shells: the status line's verb sends `ScreenEvent.status_acted` (the kit arm) for any screen that has no event of its own. Both shells state that send once per page (`\.statusActed` in `RustScreenView`, `LocalStatusActed` in `RustRoot.Page`) and draw every line through the one kit view (`StatusLineView`, `StatusLine(line)`), which takes it when the screen passes no callback; a screen draws the line whole and passes nothing.
