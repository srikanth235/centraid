# Harness defects found, and what stops each recurring

Defects in the EVALUATION, not in Centraid. Product gaps are [srikanth235/centraid#1044](https://github.com/srikanth235/centraid/issues/1044).

An evaluation that is wrong is worse than no evaluation, because it is quoted. Two of the entries below produced a conclusion that was reported upward before anyone noticed it was false. This file exists so the pattern is visible.

## The pattern

**Every one of these was found by a person or a lane happening to cross-check something else. Not one was found by the harness checking itself.**

Three were found only because an audit was explicitly commissioned; two were found by accident while fixing an unrelated thing; one was found because a lane renamed a string for cosmetic reasons and the build went red.

That is not a process that scales, and it is not a process that can be trusted to have found the last one. The guards in the right-hand column are the fix: each converts a defect that was found by luck into one that is found by `cargo test`. Four rows have no guard yet, and two more (#18, #19) are guarded only in part. **#29, #30 and #31 are not evaluation defects at all** — they are facts about the product that the evaluation found by trying to write a case against them, and they are on this page because the alternative was three sessions quietly reworded around them.

## The unguarded properties, in priority order

1. **An extra reveal, and a split rewritten in place** (#18, #19) — the two places the changed-row set cannot see, both named above with the fix each needs.
2. **No turn is dead weight** (#7) — Lane D measured by hand that every one of the 129 turns is failed by at least one degenerate instrument. Nothing asserts it, so the next case added can silently be free.
3. **No expectation is satisfied by the world before the conversation starts** (#4 generalised beyond writes) — **closed for writes** by `no_write_expectation_holds_against_the_untouched_world`, which asks every write expectation in both corpora of an untouched world and requires every one to refuse. Still open for reads: nothing asserts that an `ids` turn's answer is not simply the whole of some small table.
4. **A case's language matches the world it is asked against** (#5) — nothing checks that a temporal phrase in a request corresponds to rows in that window.
5. **An expectation is the right one** (#6) — the hardest. A case expecting `clarify` where the evidence actually resolves is a suite bug that scores a correct candidate as wrong, and it is invisible to every other check.
6. **Key spaces agree across doors** (#8, #9).

### One disagreement was an OPEN QUESTION for the owner — RULED 2026-09-21

`s80` "text Neha and tell her I'm running late" expects **clarify** — the README's reasoning is that neither Neha resolves by being the only reachable one, so the correct outcome is to ask which. `textref` **refuses**: sending a text reaches outside the vault, and if the assistant cannot send one at all then which Neha it would have sent to never arises.

Both readings are defensible and they disagree about what the case is _for_. The expectation was left as it stood and the question put to the owner; **the owner ruled for `refuse`, and `s80` has moved** (`CHANGES.md`, 2026-09-21). `textref` was right and the corpus was wrong, which makes this the second of the ten disagreements to go that way. The question as it was put:

> Should a request that names an action outside the vault's authority be `refuse` regardless of whether its object is ambiguous, or should the ambiguity be asked about first? `s80` is the only case where the two orders disagree. **Recommendation: `refuse` wins, and `s80` moves** — a question about which Neha, followed by a refusal either way, is a worse outcome for the member than the refusal alone, and the `ambiguity_clarify` category already has seven other cases that do not turn on this.

## OPEN — ordering the corpus implies and does not assert (review item B9)

`ordered` is set on **3 of the primary corpus's 71 `ids` turns and 1 of the blind set's 41**. The mirror of the UNDECLARED ORDERING register (a case that asserts a sequence without saying which sort it is) is a case whose REQUEST asks for a position in a sequence and whose expectation is scored as a set.

`validate-suite` now prints the list on every run — advisory, never a refusal, because the fix is a corpus edit and each one is a judgement. Turns expecting a single id are excluded (a set of one has no order) and so are window phrases ("last week", "next month") and the state word "overdue", which is a property of a row rather than a position. What is left, on both corpora:

## OPEN — the one aggregate no description of the world can reach

`s67`/t1 ("how much does Marco owe me for the trip?", `8201`) is the single `value` expectation in either corpus that is still a bare literal, and `validate-suite` now REFUSES any other one: a `value` turn carries a `recompute` or it is named in `UNGUARDED_VALUE` with the reason.

The reason here is the world's own inventory. The number is Marco's share of every trip expense somebody else paid for, LESS what the others owe him on the one he paid for, LESS the settlement the world seeds — and `inventory.json` carries neither the per-expense splits nor the settlement rows, so no description over it can name the pile. **Recommendation: the fix belongs in the WORLD, not in a wider `Recompute`** — record `split:<party>` as an expense fact (the door already exposes it) and settlements as inventory entities, after which `op: "sum"` over two piles and a subtraction reaches it. Until then the number is a literal, and it is the only one.
