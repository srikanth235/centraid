# `centraid-assist` — the on-device chat plane

Centraid is visual-first, and so is its chat: an answer is **one short line and result cards** — real rows (a task, a photograph, a ledger line, a person) that the app's own tile draws and taps through to. The model writes calls over eight flat tools; the runtime reads the vault, composes the line and draws the rows as cards; the apps draw the data. The model is a small language model that runs **on the phone** (llama.cpp, in [`crates/assist-llama`](../assist-llama/src/lib.rs), over a GGUF file the shell downloaded), and a write it proposes parks behind a confirm card until the member taps it.

This crate is the plane, and none of the engine or the vault. The vault side is [`crates/core`](../core/README.md)'s `assist` module (`Request::Assist`, `assist.proto`); the engine side is a [`Model`](src/model.rs) implementation.

| Module | What it owns |
| --- | --- |
| [`native`](src/native.rs) | The native tool runtime, moved here from `crates/nativetools` (#1088, R-1088-4): eight flat tools over a vault, one metadata table they are all generated from, the date-expression evaluator, observations, the system prompt and the `Session` that runs a call. The fine-tuning loop and the phone run this one runtime; `crates/nativetools` keeps its binary, the world seeder and the export. `native::transcript` renders a session as the one text the model is trained, scored and prompted on (`crates/datagen` renders its records with it), and `native::step::decode_step` writes one assistant message through any [`model::Model`] (the think guard, the call rendered from the think, one call per message; the think under a per-step grammar when `StepOptions::grammar` asks, [`native::grammar`](src/native/grammar.rs)). It holds no vault and no path: every read and write goes through its [`Door`](src/native/door.rs) trait (paged table reads, typed commands, ids, the clock), which the harness implements over a vault file and the core implements over the phone's vault. It never writes SQL. A Locker item is a row like any other, and a sealed value is a channel the runtime keeps closed in the harness exactly as on the phone (#1135): its cells are a presence bit, a `reveal` or a secret to set ends the turn in a member action the member completes in Locker (`member`), and a secret the member typed is sealed by the door when its card is confirmed. Money is on in every session (#1099, R-1099-8). `Flags::writes` is the write policy: `Run` (the harness: the vault runs every step) or `Park` (the phone, [`park`](src/native/park.rs)): the steps of a turn's writes are applied to an in-memory patched copy of the world and the turn ends in one `PendingWrite` that `Session::confirm` runs through the door under a key per step and `Session::dismiss` (or any new message) drops (R-1088-2, R-1088-6, R-1088-10). Events are read in the person's own zone through `Door::events`, which is Agenda's `occurrences` (R-1088-8). |
| [`native_turn`](src/native_turn/mod.rs) | The native turn loop (#1088): `NativePlane` drives a `native::Session` the way the fine-tuning driver does (`user`, render the log, `decode_step`, `call_text`, up to `STEP_CAP` steps, a cancel checked between steps), with an `Activity` event per looking step. Every question about the vault takes this loop; a turn with an attachment takes the attached path instead (R-1088-9). A turn ends in the chat's existing `Card` (the one kind to app and entity table, [`cards`](src/native_turn/cards.rs): thirteen kinds into the seven apps, row routes for the kinds the shell opens and the app's home for the rest) and in a line the runtime composes from the final effect out of `copy/chat.json` ([`words`](src/native_turn/words.rs), the `SAID_` keys; a count, a value, the ask's question, a decline reason): no second generation (R-1088-10), except one: a turn that ends in a decline `out_of_scope` is answered with a few words from ONE free generation (`Plane::chat`: no tools, no grammar, 256 tokens, told it has read nothing and can send, call and change nothing), and falls back to the sentence when that fails, is stopped or says nothing. The words are the turn's answer, so a reopened thread shows them. [`log`](src/native_turn/log.rs) is the conversation the model reads, rendered with `native::transcript`. A `NativeChat` is one chat's session in memory; the caller opens a fresh one for a reopened thread, a retry or a failed turn, and between kept turns the session's clock follows the request (`Session::set_clock`: the person's now and zone, the world read again). The session runs `Writes::Park` (R-1088-2): a write is planned against a patched world and the turn ends in one pending write that has touched nothing, said as "Proposed: …" and sunk as `Event::Pending(PendingCard)`, which the core puts on the wire (`AssistPending`, on the stream and on the answer); `NativeChat::confirm` runs its steps through the door, one key per step, and `dismiss` or a new message drops it. The card the member reads is built from the runtime's structured facts, not from the text the model was shown: each parked call keeps a `RowChange` per row (kind, title, the fields that moved old to new, the links gained or lost), and [`pending`](src/native_turn/pending.rs) says it in the words of `copy/chat.json` (`SAID_STEP_*`): one line per row, `destructive` for a delete, removal, cancel or settle. `crates/nativetools/tests/park_card.rs` holds every mapped write's line to the row it changes. ## What a turn is

1. **Steps.** The model writes one message at a time — a think, then one call — and the runtime runs it (`find`, `compute`, `create`, `edit`, `do`, `answer`, `ask`, `decline`; the names S2 was trained on, `search`, `open` and `act`, are renamed as a call enters, [`legacy`](src/native/legacy.rs)), up to `STEP_CAP` messages, a stop checked between them.
2. **Cards and a line.** The turn ends in the rows it found, drawn as cards (the first six), and a line composed from the final effect out of the chat's copy. A write ends in a pending card instead, and nothing is written until the tap.
3. **A free reply** for a decline `out_of_scope`, in place of the canned sentence.

A turn with an attachment skips all of it: one streamed answer over the photograph or the document ([`attach`](src/attach.rs)).

## What stops this crate doing more

| Not allowed | What stops it |
| --- | --- |
| SQL, in any form | `sql-confinement` scans this crate; the runtime reaches a vault only through a `Door` |
| A turn that reads the whole vault, or a number taken from part of it (#1188) | `World::load_pinned` reads each kind as its newest `WINDOW_ROWS` (500) entities and everything else by chunks of those ids; no table or edge set is read whole, so a load's statements are bounded by constants. Older rows are reached through the full-text index by name (`Session::reach`), by an indexed range of the kind's own date, or by `order` over it with a `limit` (`Session::store_reach`), and are kept across reloads (`PINNED_ROWS`). A count of a kind, with at most fixed-list conditions on real columns of its own row (`status = open`), is the store's `COUNT` (photographs and people are not: their `form` has no index) (`Door::count`); any other figure over a kind with unread older rows is refused with a sentence, and a list says it read the newest. Events beyond the occurrence window (31 days back, 120 ahead) are refused for a number and noted for a list. `crates/core/tests/assist_scale.rs` asserts statements, rows per answer and rows held, never durations |
| A sealed value in a prompt, a tool result, an event, the stored thread or the index | `World::load_in` reads each sealed cell as `<cell> IS NOT NULL` (a presence bit) and nothing else, `plan_reveal` ends a reveal in a member action that names the offer and never a value (the card shows the value after the owner check, read by the core and held by the chat screen in memory only: `crates/screens/tests/chat_reveal.rs`), and a secret the member typed is `«sealed»` in the log and the stored question once its card is parked (`crates/core/tests/assist_channel.rs`, which plants a marker in every sealed cell, a sealed custom field and a passkey key and searches every one of those places; `crates/nativetools/tests/locker_parity.rs`) |
| A sealed value reached through a command or a page | The chat's door runs as the owner device and the vault withholds nothing from it (#1135): a typed secret is sealed by `api::command`, the one write function the shell's command and the door's `run_keyed` share, before the vault sees it and serves no sealed column but as a presence bit, and `page::withholds_sealed_value` refuses a page that names a sealed column but as its presence bit (`crates/core/tests/assist_door.rs`, `crates/vault/tests/locker_plaintext_gate.rs`) |
| A write on the phone before the member's tap | `Flags::writes` = `Park`: no step reaches the door until `Session::confirm`, which refuses a stale card (`crates/nativetools/tests/park_confirm.rs`); the patch is held to the vault by `tests/park.rs`; the core's door refuses a bare `run` |
| A claimed action in the free reply | the free reply's system turn says it cannot send, call or change anything, and `prompt::tests::the_free_reply_is_told_it_can_act_on_nothing` pins it; it reads no vault, so it can state no fact about one |
| A persisted transcript | a chat's session is memory; there is no table and no file (R-1088-10) |

## The model record

The model this release ships is pinned in [`model.json`](model.json) (#1188): a Hugging Face URL at a commit, the file's SHA-256 and size, the tool catalogue (`tools_mode`) it learned, the BLAKE3 hashes of that catalogue and of the static system prompt, and its score. `crates/screens/src/chat/asset.rs` reads the record for the download; nothing is typed twice. `cargo xtask model-pin --url … --file … --tools-mode … --score …` writes it (size and SHA-256 come from the file, the hashes from the runtime, the standing record becomes `previous`, the two-model window). The gate's `model-record` step (`tests/model_record.rs`) refuses a build whose record does not match the runtime's catalogue and prompt, or whose pin is not a commit. The record may also carry one adapter beside `current` (a small LoRA file for vault turns: URL at a commit, SHA-256, size, the SHA-256 of the base it was trained against, and the same `tools_hash` and `prompt_hash` an entry carries); absent means the stock model runs alone. `cargo xtask model-pin --adapter-url … --adapter-file … [--adapter-score …]` writes it against the base the record pins (`--no-adapter` removes it; pinning a new base drops an adapter made for the old one), and the gate refuses an adapter not made for this release's base or not on this runtime's catalogue and prompt. `adapter::decide` is the one rule for whether a turn may use it: the release names one, its file is on the phone at its local name (`centraid-adapter-<first 12 hex of its SHA-256>.gguf`, of the recorded size; the shell keeps only a download whose digest matched), it was trained against the base in use, and on this build's catalogue and prompt. Anything else is the stock model under the same grammar, silently. `adapter::for_vault_turn` is the one per-turn switch: the core wraps the model in `model::Switched` for a native (vault) turn, so every generation through it calls `Model::generate_with(request, AdapterUse, …)`, whose default ignores the choice (an engine without an adapter answers as `generate` does); an attached or free reply never switches it on; `contracts/assist/adapter-cases.json` holds the cases. The adapter is part of "the assistant", not a second thing a member sees: the chat's download quotes base plus adapter as one size, fetches the model and then the adapter through the same `ModelDownload` effect (same directory, same Wi‑Fi-unless-the-member-chose-mobile-data rule, one cumulative bar), and loads once both are there; an adapter that does not arrive or will not load leaves the model running alone, with no error. The core lists adapter files apart from other models (`AssistStatus.adapter_files`); an adapter file the release does not name goes with the leftovers (`DeleteModelFile`) when the model in use is the current one. `ModelLoader::load_with_adapter` hands an engine the adapter path (default: ignored; a refusal loads the base alone). When the model in use is the current one and the release's adapter is not on the phone (never fetched, or a newer one), the same row that offers a newer model offers it, quoting the adapter's size; nothing is fetched until the member taps, chat works as it is meanwhile, and the model reloads with it (`ModelHost` counts a model loaded before its adapter arrived as not ready) when no turn is running, or the next time the tab opens. `contracts/assist/adapter-offer-cases.json` holds the cases. The phone fetches a pinned file only when the member asks. A phone that holds the `previous` model keeps chatting with it and is offered the current one in a row above the composer; the new file is fetched beside the old, loaded, and the old one deleted. A model older than that window says an update is needed. In a debug build only, `CENTRAID_DEV_MODEL=<repo>@<commit>/<file>` (with `CENTRAID_DEV_MODEL_SHA256` and `CENTRAID_DEV_MODEL_BYTES`) fetches a named file in place of the pin; a release build compiles that path out. The phone holds the think to the strongest grammar its tools have (`GrammarMode::Full`, with S2's own words for the shipped record: `search`, `open`, a create's kind in `set`).
