# Two-tool surface — draft

A build-time MEASUREMENT of the ceiling, not a shipping design. It drops the project's standing rule that the model never writes SQL; that rule is a runtime/product constraint, and suspending it here is the same move as using Sonnet at all — measure with what you cannot ship, to find out what is reachable. Carrying it into the product needs its own decision.

The question it answers: **with the simplest possible surface and the ability to look things up, how much of the corpus is actually achievable?** Every number we have is confounded by a representation we invented. This has none.

---

## The two calls

### `read(sql) -> rows`

One SQL string against the vault. The model composes it.

    read("select task_id, title, due_at from schedule_task
          where status != 'completed' and due_at < '2026-06-15'")

- **Read-only, enforced.** A single `SELECT` or `WITH`. Anything else — `INSERT`, `UPDATE`, `DELETE`, `PRAGMA`, `ATTACH`, multiple statements — is rejected and the rejection is returned to the model as the result. This is not about hobbling the model: a mutation through `read` would corrupt the session's world halfway through and make every later turn unscoreable.
- **Capped.** First 50 rows, plus the true total (`4636 rows, showing 50`). The measured worst case in the frame runs was 4,636 rows from one read. Long values truncated.
- **Errors go back to the model verbatim.** A SQL error is a tool result, not a harness failure — the model gets to see it and fix its own query. Errors are counted and reported; they are never hidden or retried by the harness.
- **Timeout** per query, returned as a result like any other error.

### `write(command, payload) -> outcome`

A named vault command with its arguments. Not SQL — the model never mutates directly, so the vault's own invariants, ids and audit trail still hold.

    write("schedule.add_task",
          {"title": "Pick up the prescription", "due_at": "2026-06-18T09:00"})

- `command` is one of the **153** generated command names.
- `payload` is that command's own argument schema, already generated by `vocabblock` (`tally.add_expense(amount_minor*, category*, …)`), so the signatures are derived, not hand-written.
- Returns what happened — ids created, rows touched — so the model can verify rather than assume.

---

## What the model is given

1. **The schema.** DDL for the domain tables the 25 kinds resolve to, plus their link tables. **Not all 252** — the vault carries `access_*`, `blob_*`, `audit_*`, `backup_*` infrastructure that no question is about. Derived from the Kind→table mapping, not hand-listed.
2. **The 153 command signatures**, from the existing generator.
3. **Today's date**, read from the corpus, near the top.
4. **The conversation so far**, as a real message array — the person's turns and the model's own tool calls and results, in order. This is the thing the frame harness threw away.

Nothing else. No worked examples, no canonical form, no grammar.

---

## Scoring — outcome, not phrasing

The corpus already carries `Expected::Ids { entity, ids, ordered }` per turn.

- **Read turns:** the row ids from the turn's LAST `read` are compared to the expected ids. Ordered where the corpus says ordered.
- **Write turns:** the command and the resulting vault state.

**The convention the model must be told: the last `read` of a turn is the answer.** With only two tools there is no "answer" call, so exploring after finding the answer would score the exploration. Stating the rule is simpler than adding a third tool.

This kills a whole class of false failures. `max started_at of (…)` and `first 1 of (… ordered by started_at desc)` return the same row; the frame scorer called one of them wrong.

---

## Feasibility — checked, not assumed

**Reads are buildable today.** The dealt world is a real SQLite file: `target/eval-world/world.db` (31 MB, 252 tables) and `target/eval-world-2/world.db` for the second scenario. Python opens it read-only with `sqlite3` and no Rust involved. Verified: `core_party` 181 rows, `schedule_task` 710, `tally_expense` 1256.

**Writes need a Rust shim.** The command handlers live in `crates/vault/src/commands/*.rs` and have no Python binding. A small bin that takes `{command, payload}` on stdin and applies it is the missing piece.

**Each session needs its own world**, because writes mutate it. 31 MB per session; copy per session, or snapshot and roll back.

---

## Known boundaries

- **Sealed data.** Locker secrets are encrypted; raw SQL on the locker table returns ciphertext, not passwords. That is correct behaviour and it means locker reads must go through `locker.reveal_receipt`, not `read`. A two-tool surface therefore cannot answer a locker question through `read` alone — worth knowing before reading the locker scores.
- **252 tables is a lot of schema.** If the domain subset is still too large for the prompt, the fallback is a third tool (`schema(table)`), which breaks the two-call rule. Measure the subset's size first.

---

## Suggested first cut

1. **Reads only**, on the read-heavy sessions. No Rust needed, runs today.
2. Sonnet first — it establishes the ceiling.
3. Add the write shim once the read number is known.

Splitting it this way means the expensive half (Rust) is only built if the cheap half says the ceiling is worth chasing.
