# Flat tool surface for Qwen3.5-0.8B — spec, draft 2

Status: draft 2, approved for build; §14 decisions taken. Draft 2 folds in the second review: dates are a typed expression the model writes and the runtime evaluates (no phrase parsing in the runtime), the ambiguity check reads only the call, one way per read and per write, `more` covers any next call, compaction and `#n` reach agree, and the undefined corners (undo, idempotent writes, balance, guardrail denominators, think guard, duplicate calls) are settled. Accuracy is the only target; cost is not measured or optimised in this phase. Built fresh: a new tool runtime over the real vault, a new world generator, a new scorer and new evaluation sets. Past experiment code (earlier generators, scorers and data) is not reused or depended on, and has since been removed from the tree.

## 1. Principles

1. **The model decides, the runtime computes.** The model owns everything that needs language: what the person wants, which words name things, which kind, which constraint, which of the shown rows, how a date phrase reads, the answer shape. The runtime owns everything computable: retrieval, name matching, date arithmetic, unit conversion, filtering, joins, aggregation, schema validity. **The runtime reads the person's message only where this spec says so**: to retrieve the pre-grounding rows and to list the resolution of its date and time phrases in the block (§6.1), to repair a stated date, pick the in-focus row and check a pick for ambiguity (§3.3), and to read a plain yes that confirms a write it asked about (§4.6); otherwise its inputs are the call and the vault.
2. **Accuracy first.** Extra steps, longer prompts and reasoning tokens are acceptable when they raise accuracy. Cost and latency are out of scope for this phase.
3. **Few flat tools; compose across steps by handle.** No nested expressions. A step does one thing; later steps point at its rows (`#n`) or its whole result (`@n`). The common case is one step.
4. **Plain words, human units.** Model-facing kind and field names are plain English (`person`, `debt`, `date`, `amount`), amounts in currency units, every dated kind has a `date`. The runtime maps to vault names (`core.party`, `obligation`, `dtstart`, `amount_minor`).
5. **No dead ends.** Every observation says what exists and what can be done next.
6. **One name per effect; one way per action.** Exactly one spelling for each write and each read pattern, so equivalent calls cannot differ. Concretely: names are filtered only by `name`, dates only by `when`, values are computed only by `op` (§4.3).
7. **One source of truth.** Tool schemas, the kind card, the runtime tables, the row cap and the generator's vocabulary are generated from one metadata table that lives in the runtime crate (model-facing name, runtime name, unit, kind, links, verbs). The table is held to the vault, not restated: every mapped column exists in a founded vault, every mapped command is registered and is landed by a runtime call for each `(verb, kind, command)` of the table (`tests/verb_coverage.rs`), and every enum equals its column's CHECK list, a deliberate gap declared beside it (`meta::UNEXPOSED`, `tests/meta.rs`). The model's identity (the tokenizer id and the chat and tool-call markers) is one Rust constant, `identity::MODEL`; the runtime's prompt and call reader spell their tokens from it and `render.py` reads it back from `identity.json`. `nativetools export` writes all of it, and the committed copy under `contracts/assist/export/` is diffed against a fresh export on every test run.
8. **Native format.** Calls use Qwen3.5's own tool format (XML tool calls, JSON schemas in the system prompt, `<tool_response>` results). The only reason to deviate is a session that does not fit the training length (§11.6).

Non-goals: the model never writes SQL; no reference operators (`the other one`, `that one`, `it`, `them`, ordinal refs) — rows are named only by `#n` / `@n` the model has seen; the runtime never turns the message into a call: names, dates and amounts arrive typed from the model, and where the runtime reads the message (principle 1) it shows what it read or checks the call against it.

## 3. Row selection — who picks rows

**The harness never chooses between rows on its own judgment.** It returns the rows a stated constraint selects, at the tiers its name reaches (item 4); when several rows share the best tier it lists them, and a write asks.

1. **It returns exactly the rows a stated constraint selects.** `find kind=task name="Benedikt"` returns every live task whose name matches; nothing is dropped or added. A `name` is resolved in tiers (item 4): a read takes the rows it reaches at tiers 1 to 3 (tier 4 when it reaches none), a write the same rows (it acts only when exactly one is reached, item 4; nt12 R6), among the rows every other condition lets through. `Lucia` finds `Lucía`; the hyphens, underscores, apostrophes and spaces of a name are one separator (`yunho`, `Yun ho`, `Yun-ho` and `yun_ho` are one name, `mother in law` is `Mother-in-law`, `obriens` and `obrien` find `O'Brien's`; `search.rs` `Spoken`: a word with a joiner reads as its parts or as the one word they make), and a person's `nickname` is a name of theirs (`kami` finds the person whose nickname is Kami). `find`, `answer`, `compute` and `act` resolve names this way (`resolve.rs`: `resolve`; `Session::select_named`); `search` ranks, it does not resolve (§4.4). `search` alone also takes another form of a word as that word (`search.rs`, `stem_forms`: a light suffix, `er`, `ers`, `s`, `es`, `ing` or `ed`, taken off either side, a doubled last consonant undone and an `e` given back, four letters or more each, so `babysitter`, `babysits` and `babysitting` are one word, and `painter` finds `Painting class`), scored as a word's start, after an exact word; `find` and the by-name `act` do not (nt9, rule 4).
2. **It numbers every row and every result.** Rows get session-wide numbers `#n`; each `find`, `search`, `compute` result gets a handle `@n`. Each row shows its position in its result (`[3]`), so "the third one" is a lookup, not counting.
3. **The one safety check, defined on the call alone.** An `act` whose target is given by a selector (not by `#n`) and whose selector matches more than one live row the verb applies to (§14.1, "verb applicability") does nothing and ends the turn in the ask the runtime composes, `Which one?` with the candidates as options (§4.8); with `--no-compose` (`Flags.compose` off) it returns `ambiguous:` with the candidates and the model goes on. Whether several matches were intended (a bulk write) or not is the model's call, except for a name given as a bare plural (below): it names the rows by `#n` or narrows the selector in the call it writes; it does not ask. The exception is a person who says every row: when the message says all, every, each, both or everyone (a word that quantifies a stretch of time, "all-day", "every week", "the whole weekend", does not count), or the trace says `scope: all`, the write takes every row the selector fits, without the narrowing of focus and date, and says so in a note (§4.8); the cap of §4.6 holds, and a yes after its ask lets the same write through whatever that yes says. A trace with another scope line decides the other way, and a pick by `#n` is never widened. A name given as a bare plural ("the mark 9 tests", "the cousins in toronto") that fits several rows, with none of all, every, each, both or everyone in the message (a stretch of time does not count), is the by-name call and the runtime's `Which one?` over them: the model does not write the rows by `#n`, and it does not star or move them all (D-1044-13, K4). Naming several rows in one act is for a message that says all or both, or lists them one by one ("9b and 9c", "star it and the echo report"). A plural given as a condition rather than a name ("the done kids tasks", "just the cancelled ones", "the finished ones") is not that ask: the person stated which rows, so the model `find`s them and writes them as `rows=@n` in one act, and the cap of §4.6 holds (D-1044-15, B5b). Rows that share one name (the instances of a recurring task or event, "Order composite resin" with its past instances done and the next one open) are the ask like any others: the runtime picks neither the next instance nor the open one, with no date or all-word in the message, for tasks and events alike ("push the gift for kamola to friday" over one open and one done task is the ask over both); the message's own date still narrows (below), the verb's applicability still leaves only the rows it changes (`complete` over one open and two done instances is the open one), and the options of the ask are the rows the verb changes (§4.8). Four things read the message, and nothing else does (real exceptions to "the runtime does not look at the message"): (a) **Date repair** (`ground.rs`): when the model's date expression contradicts the one unambiguous phrase the message states, or cannot be read at all (`"weekday": 8`), the runtime replaces it and says so in the observation; a clock the call wrote malformed (`"time": "9"`) is never repaired, since the words' "at 9" may be 09:00 or 21:00 and a dropped clock would write another hour: the call gets the grammar error and writes `HH:MM`. Narrowed rules: a phrase has a role, `Row` (names the row: "the one due tomorrow", "from monday"), `Dest` (where a write puts it: "to friday", "make it due friday") or `Free`, and a `Row` phrase never becomes a write's new date; ordinals ("the twentieth") never rewrite a date that exists (only a nonexistent one such as 2026-11-31 under a single stated ordinal); a bare weekday is left alone when it is today's weekday, is already past, or a prior result showed a later week (and for a short follow-up to a turn that only asked); a span is repaired only when both its ends resolve to the same day, except that a clock range in the words ("fri 6 to 6.30") puts the end on the start's day. In a _write_ a bare day of the month, a named month and day and "end of <month>" have one reading each (§14.1, "ordinal and month-day" and "end of month"); in a _read_ the model's month stands. An explicit day of the month ("friday dec 11") beats the weekday beside it; "due friday" on a create is the new row's date ("the one due friday" names a row); "sat", "sun", "mon", "wed" are weekdays after next/this/last/on/to/by/till/until. (b) **Focus pick** (`session.rs`, `Session::focus`): a by-name `act` that fits several rows, after the verb's applicability filter (§14.1), takes the one in focus when exactly one is. Rows acted on (a change, an already-so answer, an undo), opened, or offered as an option of an `ask` in the previous or current turn always count; rows of a `find`/`search`/`answer` result count only when the result has at most 4 rows (`FOCUS_RESULT_MAX = 4`); an `ambiguous:` block never counts. The pick counts no row the model was not shown: a row the previous turn acted on counts when the `focus:` line names it (its `acted` part, or the set or `created` part that has it, §6.1), so a turn that wrote more rows than `acted` names (6) leaves the earlier ones out of the pick as out of the line; the line keeps an acted row for three turns, the pick for one. (c) **Pick ambiguity** (`act.rs`, `ambiguous_pick`): the call-only check above misses a row the model picked by `#n` or by an over-specific name ("star pedro" with `rows=#9`, "tick off tiago's birthday" with `name="Tiago's birthday present"`). The words that name the row are the words of the message that are also words of its name, and, when the message itself holds one, those of the message before it (a row named there and only pointed at now: "what's the card number then"; an answer that holds no word of the name, "the driver", names nothing and is never asked about) (compared with accents folded, the same word in another form such as tire/tires or rotation/rotated, one letter off in a word of five or more that starts alike, a word that extends a name word of four letters or more ("renewal" names "Renew passport", so "the passport renewal" fits it and not "Get passport photos"; nt9), `9` for `9B`, never `3` for `30`); the rows they fit are the live rows of that kind. The runtime does not act, and ends the turn as an `ask` with those rows as options (composed, `which one of the N did you mean?`, §4.8), only when all of these hold: the call carries no `where`, `when` or `linked_to` of its own (the model has already stated what singles the row out); at least two of the rows are ones the verb would change (§14.1 "verb applicability"); the picked row is not the only one whose whole name or whole nickname the words state ("tb test" against "TB test reading", "big dan" against Dan Kowalski's nickname); nothing in the message settles which (a date, a plural weekday or an ordinal that names the row, "one", "the other", a state word such as open or done, or a personal pronoun ("it", "them", "him") when the focus of the previous turn holds a row of the picked row's kind for it to point at: "star the wifi, i keep needing it" with two wifi rows and nothing in focus still asks; nt9 part B, F8); a date for this check is read as the `dates:` line reads it: a month name that is also a first name (`june`, `april`, `august`, `jan`) is a month only after a word that says so (`in june`, `from march to may`), and `year`/`month` inside a name (`the year end report`) is no period while `this year`, `every month` and `2 years` are (nt12 B1); neither the date (`narrow`) nor the focus of the _previous_ turn leaves one, nor does a longer list the previous turn showed that holds the picked row and no other row the verb changes (a namesake the verb would leave as it is may be in the list), nor does a lookup of this turn that carried a `where`, a `when` or a `linked_to` of its own and left the picked row, a row the verb changes, and no other such row (the model stated what singles the row out, as a call with its own `where` does; a lookup by the name alone, an over-specific name, bears out nothing, and neither does a condition that left two open instances), nor, for `reschedule` and `cancel`, is the picked row the only fit that is not over (§14.1): the model's pick is then borne out by what the person saw, by the model's own lookup or by the rows' state; a by-name act takes none of these steps. The runtime reads the message for nothing else. The generator applies the same rule, so train and test agree. A fourth reading only shows and acts on nothing: the `dates:` line of the block (§6.1) lists the date and time phrases the runtime can resolve and changes no call, and the `picks:` line (§6.1) names the rows an ordinal of the message counts to in the list in focus.
4. **A name is resolved in tiers, once, in one place** (`resolve.rs`, `resolve`; nt11 R1). Both sides are folded first: case, accents, punctuation, a possessive `'s`, and runs of hyphens, underscores and spaces. The first non-empty tier wins, and a row's tier is the best of its name and, for a person, its nickname: **1** the same after folding (`mother in law`, `Mother-in-law`, `motherinlaw`); **2** the same words in any order (`weiss benedikt`); **3** every word said is a word of the name or the start of one, three letters or more, an article aside (`house` for `Beach House 2026`; `kamin` for `Kamini Rao`; two letters are no start); **4** a typo: as 3, and each word that does not match is of four letters or more, has no digit, and is one edit from a word of the name (a letter more, fewer or different, or two neighbours swapped: Damerau distance, not trigram similarity; `Farukh` for `Farrukh`, `Amma` for `Ama`). A selector resolves among the rows its other conditions let through. **A read** takes every row that reaches tiers 1 to 3 together (a read of `house` shows `House` and `Beach House 2026`: no read returns fewer rows than a name read did before tiers; `Night shift` and `Night shift swap` are both the night shifts), and, when no row reaches those, the rows of tier 4. **A write** takes the same rows a read does (nt12 R6): `house` with a row called `House` and one called `Beach House 2026` reaches both, and so does `Flan` with `Flan 2`, `Dentist appointment` with `Dentist appointment for Hana`, `Book XRD slot` with `Book XRD slot for Lukas`: a lookalike name is never acted on because one of the rows is exact. A name a trashed row has at tier 1 or 2 while the live rows only contain it or are a typo of it is the trashed row's: the "no live task called ... trashed: ..." recovery names it and no live row is taken in its place (a lookup of `trashed` rows resolves among the trashed rows alone, and a `restore` by name among them whether or not the call says `trashed`). A read (`find`, `answer`, `compute`) adds, when its rows are a typo's, one line under the reply, `matched "Farrukh Kasimov" for "Farukh"`, only then (nt11 R2). **A write** acts when its name reaches exactly ONE row at tiers 1 to 3 together (after the narrowing steps below: the verb's applicability, a day the message states, the focus); several rows, an exact name among them, are the ask `Which one?` over all of them (nt12 R6, which replaces nt11 R3's "best tier alone"; `with --no-compose` the `ambiguous:` block of section 5). A name only a typo reaches (tier 4) acts when exactly one candidate of the stated kind is reached, with `matched "<name>" for "<query>"` under the reply (nt12 R6; nt9's near-spelling apply); several candidates are the ask (`Which one?`), and a delete, a removal from a container, a settlement, a reveal and a write the message says takes every row are the ask `Did you mean #n?` whatever the count, since a guess there is destructive, money or a secret (`with --no-compose` a typo is the dead end `0 tasks called ...`). A name that reaches no tier is the dead end and the runtime's own search for it (§4.8). The word-level reading of a message against a row's name in the pick check (`resolve::word_near`: another form of a word, one letter off in a word of five letters, the digits of a numbered name) is the model-free side of `ambiguous_pick`, not a name selector. Under tier 4 sits one reading more (nt13 R3: honorifics dropped and light stems on both sides, `Rank::Light`; see "Resolve more, guess nothing"). Every matcher of a name against rows goes through `resolve` (nt11 R4): the earlier `name_matches`, `row_matches_name`, `row_fits_name`, `row_spelled_by`, `name_candidates`, `fuzzy_fit`, `fuzzy_ambiguity`, `ground_name` and the act-side `near` are gone (`search`'s ranked `word_score` and the hint's wider look, `name_reach`, are not name resolution: they rank and suggest, §4.4, §4.8). It reads the call and the vault, not the message; the writes that may take several rows (trace `scope: all`, "all" or "every" in the message) resolve the same way and take every row they reach (§4.5).
5. **Conventions fill a slot a read leaves out** (`ground.rs`, `Session::conventions`): the defaults of §14.1, read from the call and a few words of the message. They never override a slot the call states; the reply names each one applied.
6. **`=` with a plain word on a free-text field reads as contains** (`session.rs`, `Session::read_as_contains`): `where description = tent` (or `body`, `met`, `role`) that equality answers with no row and contains answers with some takes the contains rows, and the reply carries `note: read as contains: description contains "tent"`; a phrase, another field and an equality that matches are left alone (nt9 part B, F7).

**The model selects in one of two ways, preferring the first:**

- **By constraint (default).** If the choice can be said as a condition — name, kind(s), date, status, amount, link — it says it in `find`/`answer`/`act`. "The Benedikt task and the calendar entry" → `answer kind=task,event name="Benedikt"`. "The ones over fifty dollars" → `answer within=@3 where="amount > 50"`.
- **By pick (only when no condition expresses it).** Ordinals, "the dentist one" where the name doesn't literally match, a row from an earlier turn. The model names `#n` it has seen; its reasoning lists each candidate with a verdict and the picked rows follow from the verdicts (§7). Rows in the pre-grounding block (§6.1) and the vault directory (§6.0.4) count as seen and are pickable; that is their purpose.
- **Large results.** Real vaults return hundreds of rows; only `ROW_CAP` (12, a metadata constant) are shown. Picking by number is legal only among shown rows; anything else is a constraint (`order`, `limit`, `when`, `name`). The generator logs how often a gold answer exceeds `ROW_CAP`.
- **Compacted rows are not addressable.** After compaction (§6.4) a row that was dropped from an earlier result can be reached only through its result: `within=@1` plus a constraint, or `search`. The generator never emits a `#n` from a compacted result; the grammar (§9) forbids it.

## 4. Tools

`rows` accepts a comma list of `#n` and `@n` (mixed). `kind` accepts one kind or a comma list; `any` is allowed only in `search`. `find`'s selection parameters are called the **selector** and are shared by `answer` and `act`, so the common case is one step.

| tool | parameters | returns | ends turn |
| --- | --- | --- | --- |
| `search` | `text`, `kind?` | ranked, fuzzy rows of any kind, with their numbered links | no |
| `find` | selector | the matching rows as `@n`; a name that reaches nothing is a plain miss with a hint, never an answer (§4.8) | no |
| `open` | `row` (one `#n`) | every fact of the row and its links, with counts | no |
| `compute` | `op`, `field?`, `group`, `rows` or selector | `@n` = one number per group | no |
| `act` | `verb`, `rows` or selector, `args?`, `more?` | what changed, dates resolved | yes, unless `more=true`; the runtime also ends it itself for a write over the cap, for a refusal of the vault (§4.6) and for a selector that fits several rows or none (§4.8) |
| `answer` | `rows` or selector; or `op`, `field?`, `rows` or selector; or `value=@n` | — | yes |
| `ask` | `question`, `options?` (rows); the model's asks have no options (§4.8) | — | yes |
| `decline` | `reason` (out_of_scope · unbounded_destruction · sealed_egress · fabricated_secret · never_mind · not_found); the model's declines are the first five (§4.8) | — | yes |

`more=true` on `act` means "another call follows" — another `act`, or an `answer` ("mark it done and tell me what's left"), or a `find`. Without it the turn ends. A turn the runtime ends itself (§4.6) ends whatever `more` says.

### 4.1 Selector

`kind`, `name?`, `where?`, `when?`, `linked_to?`, `within?`, `exclude?`, `order?`, `limit?`, `trashed?`.

- `name` — resolved in tiers (§3, item 4): equal after folding, the same words in any order, every word present or a word's start, a typo; a read and a write take tiers 1 to 3 together (a write acts only on exactly one row, §3, item 4); accents, case and punctuation folded; a person's nickname counts as their name. This is the ONLY way to filter by name; `where` has no name field. A lookup of trashed rows (`trashed`, a `restore`) resolves among the trashed rows, whatever live row has the name. Fuzzy or cross-kind lookup is `search`.
- `when` — a date expression (§4.4) applied to the kind's `date`. This is the ONLY way to filter by date; `where` has no date fields.
- `where` — conditions joined by `and`: `field op value` with op in `= != < <= > >=`, `contains "…"` (text fields other than name), `in ("a", "b")`, `is empty`, `is set`; a linked-count condition `<kind> count op N`. No `or` except via `in`; no `not` except via `!=` / `is empty`. Its per-kind grammar is generated from the metadata table. **`status = open` selects the active rows**: on a task, the tasks whose status is open or in_progress. `status != open` is the rest, `in (…)` reads each member the same way, and `in_progress`, `completed` and `cancelled` select only themselves (§14.1, status).
- `linked_to` — rows the results must be linked to (`kind=photo linked_to=#3` = photos of person #3; `kind=person linked_to=#1` on a group = its members). Link semantics per kind pair come from the metadata table.
- `within` — an earlier result (follow-ups). `exclude` — rows to leave out ("what else").
- `order` — `field asc|desc`; `limit` — N. `trashed=true` searches only trashed rows, and with no `kind` reads the trash of every kind that has one (nt9 part B, F9). A `when` on a read of trashed rows (`find`, `answer`, `compute` with `trashed=true`) that reaches no trashed row is dropped (nt11 R6): a row's date is the day it was for, the trash date is not kept ("what did I delete last week" is no date of any row), so the reply says `the trash date is not kept; showing all trashed tasks` and shows every trashed row the rest of the selector reaches. A `when` that reaches trashed rows by their own date stays ("the pay rent from october" is the row due in October).
- **Multi-kind selectors** (`kind=task,event`) may use only `name`, `when`, `linked_to`, `within`, `exclude`, `limit`, `trashed`. `where`, `order`, `op/field` and `act` require exactly one kind, because fields are per kind.

**Two-step is for looking.** `find` then `answer @n` is used when the model needs to see rows before committing (a pick, a check that a name resolved). A read the model can state as a selector is one `answer`. The trace says which and why.

### 4.2 Verbs

`act` verbs — one per effect, dispatched by the kind of `rows`. The table is GENERATED from the domain commands the gold corpus uses; this is the expected shape:

| verb | applies to | args |
| --- | --- | --- |
| `create` | the top-level `kind` | that kind's fields, `name` included (dates as §4.4 expressions) |
| `edit` | any | `field: value` lines (rename, change amount, set status); `body+: text` (note) and `description+: text` (task, event) add to the end of the text (nt15 R2b) |
| `reschedule` | task, event | `to: <date expr>`; "an hour earlier" is `{"unit":"hour","rel":-1,"anchor":"row"}` |
| `complete` · `reopen` | task | — |
| `cancel` | event | — |
| `delete` · `restore` | any | — |
| `star` · `unstar` | document, person, locker item | — |
| `add_to` · `remove_from` | photo→album, note→notebook, document→folder, person→group | `to: #n` / `from: #n` |
| `log` | person | `kind: call · message · visit · coffee` |
| `settle_up` | person in a group | `group: #n` (amount = their balance unless given) |
| `settle_debt` | debt | — |
| `reveal` | locker item | `field: password · code …` |
| `undo` | the previous turn's writes | — |

- Several writes in one message: each `act` but the last has `more=true`. One write names every row it applies to.
- **`undo`** reverts every write of the immediately previous turn of this session, as one unit, once. A turn whose writes were all already-so (`already: …`, nothing changed) is not a write and is looked past: `restore`, `restore` again, `undo` undoes the first restore, and so do two already-so turns in a row. A turn that read, asked, declined or undid something between ends it, as before. A second `undo`, or an `undo` with no write to revert, returns `error: nothing to undo`. Undo across sessions is out of scope.
- **Already-so writes** (`complete` on a completed task, `restore` on a live row, `star` on a starred row, `cancel` on a cancelled event) are not errors: the runtime changes nothing and returns `already: #12 task "Book the cabin" is completed (2026-06-01)`. The model answers with that. Gold for such turns is "no vault change, answer states the current state".
- **Impossible writes** (`complete` on an event, `reschedule` on a person) are schema errors (§5).

### 4.3 Values

Amounts a person writes with a suffix are plain numbers wherever an amount is read (a `where` on a money field, a debt's `amount`, `settle_up`): `500k` is 500000, `2.5k` 2500, `1m` 1000000; minutes and days take no suffix.

`op` in `count · sum · min · max · balance`. `count` needs no field. `balance` is defined only for `kind=person` (`me` versus that person: positive = they owe me) and for `kind=group` with `linked_to` a person (that person's net position in the group); the metadata table names the kinds it applies to. `answer op=…` is the one-step form; `compute` exists only for `group` (one number per value of a field) and for a value a later step consumes (`answer value=@n`, `where amount > …` cannot take a handle, so this is rare). "Break down by <field>", "split by <field>" and "count by <field>" over the rows in focus are a grouped value, never a row listing, and `within=@n` carries the rows: `compute op=count group=<field>` for tasks and the other plain kinds ("break those down by status"), `op=sum field=amount group=<field>` over debts, where the person means money ("split by direction" after a list of open debts) (D-1044-15, B16). A grouped count whose result has one group is accepted as the plain value too, and the reverse (D-1044-13, G4). The generator never emits `compute` followed immediately by `answer value` when `answer op` would do.

### 4.4 Date expressions

The model writes a small JSON object; the runtime evaluates it. No English reaches the runtime.

```
{"unit":"month","name":11,"rel":-1}                   last november (most recent fully ended November)
{"unit":"day","rel":0}                                today
{"unit":"day","rel":1}                                tomorrow
{"unit":"day","rel":-3}                               three days ago
{"unit":"week","rel":0}                               this week (Mon–Sun containing today)
{"unit":"week","rel":1,"weekday":1,"time":"14:00"}    next monday at 2
{"unit":"hour","rel":-1,"anchor":"row"}               an hour earlier (relative to the row's time)
{"date":"2026-09-30"}                                 a date the person typed
{"date":"2026-09-30","time":"09:30"}                  with a time
{"from":{...},"to":{...}}                             a span, both ends expressions
{"from":{...}} / {"to":{...}}                         open-ended ("since March" in a count runs to today, §14.1; "before Friday")
```

Fields: `unit` (minute · hour · day · week · month · year), `rel` (signed integer), `name` (month 1..12, only with `unit=month`), `weekday` (1..7 Mon..Sun, only with `unit=week`), `time` (`HH:MM`), `anchor` (`today` default · `row`, the target row's `date`; `row` is legal only inside `act`). A unit without `time` denotes the whole period as a range. The runtime resolves to an absolute range or instant, echoes it in the response (`when: 2025-11-01..2025-11-30`), and rejects anything outside the grammar with the grammar's examples. The grammar is shared with constrained decoding, so a malformed expression cannot be emitted in hard mode.

**Lexical leniency** (nt12 R3; `dates::lenient`, read in `normalize.rs` for a `when` and where an act reads its `to` and a create's date): a form that has one reading is read as the grammar's own, with `note: read time 9pm as 21:00`: a `time` written `9:30`, `9pm`, `9 pm`, `9:30pm` or `21:00:00` (a bare `9` stays an error, it is 9 or 21), a `rel` written as text (`"1"`), a `weekday` or a month `name` written as a word (`friday`, `november`), and a date written as its text (`2026-10-05` is `{"date":"2026-10-05"}`). An expression that is still refused quotes only the example of the key that failed (a bad `time` the date with a time, a bad `weekday` `next monday at 2`, and so on; the whole list when no key is named).

**Gold form.** Weekday and relative phrases ("friday", "next monday at 2", "tomorrow", "three days ago", "an hour earlier") are written in the structured form above (`unit`/`rel`/`weekday`/`time`/`anchor`), never as an ISO date. ISO (`{"date":...}`) is used only for an explicit calendar date the person typed ("the 3rd of may", "2026-11-05"). A bare weekday written as ISO is a training-data error: the model would be computing the date, which the runtime owns.

Interpretation conventions ("at 2" = 14:00 for hours 1..7; "last november" = the most recent ended one; "next monday" = the Monday of next week, even on a Sunday) are the model's, learned from the generator's phrase→expression table, and are listed in §14 for the owner to confirm. The runtime evaluates only what it is given.

### 4.5 Parameter repair and the trace guard

- **Salvage** (`parse.rs`, `salvage`): a parameter the model invents for a real one is renamed when the value says which: `result` (or `row`, when the tool has no `row` parameter) holding `@n` becomes `within`, `#n` becomes `rows`, a kind name (or `people`) becomes `kind`. A key the tool really accepts is never renamed: `open` keeps `row`.
- **Trace guard** (`trace.rs`): applies only when the think has a line exactly `intent: <read|count|write|ask|decline>` with an optional quoted phrase (any other think, such as an untrained model's prose, never matches and is untouched). A call is refused, as an error observation that does nothing, when: `intent: write` with an `answer` call; `act` under a non-write intent; `scope: one` with a write naming several rows; `refer -> @k` (or `#n`) with rows outside the referent, or `refer: both` with rows not equal to the whole referent. A refused call still counts as a step but not as the last call, so the same call under a corrected trace is not a repeat. A malformed `scope` or `refer` line is ignored.
- **Resolve, don't reject** (nt12; the principle: the model does language, the runtime resolves what is deterministic). A call the runtime can fix without guessing runs fixed, with one `note:` line saying what was used; a guess (several readings, egress, a dropped filter) still errors or asks. Like every best-effort repair of a malformed call, R1 to R4 are off under `--no-normalize` (the replay of an author's bad steps, which stay the errors they were). (R1) The corrected call of an error that used to end in ` Send <call>` runs in the same step, with `note: used <call>`, when the fix is a whole call that changes no rows: a field swap, a group's balance of the person the message names, a narrowing that lost its `within` when one list is on screen (`recover.rs`, `Session::decidable_fix`, `dispatch`); a reveal (egress) and a `Did you mean #n?` (it changes the rows) stay the error with the call. If the fixed call fails too, the model reads the first error. (R2) One field resolver (`whr::resolve_field`, the table `field_fix` names): a word that is another spelling of a field of the kind (`notes` on a task is `description`, `minutes` is `effort`, `due` in an `order` is `date`) is read as that field in a `where`, an `order`, a `compute` field or group and an edit or create arg, with `note: read notes as description`; a word that is no field of the kind stays the error. (R3) A `where` of one field joined by `or` is `field in (...)` (`note: read ... as ...`), and a number in a unit with a fixed conversion is the field's own unit (`effort > 1 hour` is 60, `effort: 2 hours` is 120, `cadence: 2 weeks` is 14; `note: read 2 hours as 120 minutes`; any other unit is still refused), in `where`, `edit` and `create` (`whr::lenient_where`, `convert_unit`, `normalize.rs`); dates: §4.4. (R4) An `edit` of one field that is a verb is that verb, with `note: used reschedule for the edit of date`: a date is `reschedule` with that `to`, `starred` is `star` or `unstar`, an event's `status: cancelled` is `cancel`, a task's `status` or `completed` is `complete` or `reopen`; args on a verb that takes none (`complete`, `reopen`, `cancel`, `delete`, `restore`, `star`, `unstar`, `settle_debt`) are dropped with `note: ignored args ...`; a `settle_up` with no `group` takes the one group in which that person and you have a balance (`note: used group ...`), a `remove_from` with no `from` the one container of its kind the row is in (`note: used from ...`); with several, the error is what it was. (R5) A message with two calls (`<tool_call>` twice) runs the FIRST and its reply ends with `note: only the first call ran` (`parse::parse_call`, `Session::call_text`); the second is not queued. (B2) One bool parser (`whr::parse_bool`): `yes`, `true`, `1`, `on` and `no`, `false`, `0`, `off` in a `where`, an `edit` and `trashed`/`more`; anything else is the error `... is one of yes, true, 1, on, no, false, 0, off, not "x"`, never a silent no. (B5) A currency symbol on an amount names a currency: `$`, `€`, `£`, `¥` in a money `where` resolve to the vault's code for it (`USD` for `$` in a vault of dollars), a symbol two of the vault's codes share (`$` with USD and CAD) is an error naming them, and an amount in a symbol that is not the currency it is written in (a `€` settlement in a dollar group) is refused, never stored as the other currency (`whr::settle_currencies`, `symbol_conflict`). (B6) A note that names a weekday earlier this week says so: `this Friday (past) Fri 2026-09-25`.
- **Resolve more, guess nothing** (nt13; the same principle: a call the runtime can fix without guessing runs fixed with one `note:` line; several readings, egress, a dropped filter and a changed target row the message does not name still ask or error). ### 4.6 Turns the runtime ends itself: the cap and the vault's refusals

The model judges what the person wants; two outcomes it should not have to compose are the runtime's (D-1044-10, D-1044-11). Each ends the turn at the `act` that caused it, in a typed `ask` or `decline` the runtime writes (`effect.tool = ask | decline`, `effect.composed = true`, `more` does not keep the turn open), the reference calls after that `act` are not sent, and the reply says which of the two the runtime did.

**The cap.** A write whose `rows` name more than `ROW_CAP` (12) rows is never run outright: not under `scope: all`, not when the message says "all" or "every", not under `more=true`. The turn ends in the ask the runtime composes, `asked: "this would delete 734 tasks; delete all of them?"`, and nothing is written. Its effect is an ask with the count and the selector: `ask = {question, options: [], count, verb, kind, selector}` (`selector` is the call's `rows`) and `bulk = {count, cap, verb, kind, rows, confirmed: false}`. The question names the verb (`delete`, `complete`, `change` for an edit, ...), the count with the kind (`13 tasks`, `26 rows: 13 tasks, 13 people`) and, for `add_to` and `remove_from`, the container (`to the Summer album`). The ask is remembered: in the turn right after it, the same write (same verb, same rows, same `args`; `more` is not part of it) goes through once when the person's message is a plain yes: a message of at most ten words that has a yes word (`yes`, `yeah`, `ok`, `sure`, `go ahead`, `do it`, `all of them`, ...) and none that withholds one (`no`, `not`, `n't`, `just`, `only`, `but`, `keep`, `also`, `too`, ...). `yes please`, `go ahead` and `all of them` confirm; `no, just the done ones` and `yes but keep the open ones` do not. The confirmed write echoes its first 12 rows and `… N more changed`, says `note: confirmed, the N rows the runtime asked about.`, and its effect carries `bulk.confirmed = true` and the full diff; `undo` reverts it as one unit. Any other message leaves the write over the cap: the same call asks again, and a different one is its own question. A write over a result handle past the cap ends exactly as the same write by the selector that made the handle does (nt11 R5): when the person or the trace says all (§4.5) it is this ask; otherwise it is the ask `Which one?` over the rows the verb can change, at most `ROW_CAP` of them, with the rest counted, as a selector's own is (`Session::settle_rows`), and, like the cap's own ask, it remembers the write: a plain yes in the next turn ("yes all of them") is that write.

**A refusal of the vault** is the `reason` and the check id (`predicate`) a typed command returns when it will not run (`vaultio.rs`, `Ran`). The runtime reads the id, never the sentence, reads only the refusals of a `restore` and of a `delete`, and only when nothing of the write has landed:

| the write | the vault's check | the turn ends in |
| --- | --- | --- |
| `restore` a row the vault lists as trashed | any check of the restore (`person_trashed`, `document_in_trash`, ...): its window has run out | `decline not_found`: nothing can bring it back |
| `delete` a folder | `folder_is_empty` (a trashed document counts) | an ask, `the Taxes folder still holds 1 document and 1 document in the trash; take them out first, then delete the folder?`; its options are the documents, live first, at most 12 |
| `delete` a group | `group_empty` | an ask, `the Tahoe Trip group still has expenses, so it cannot be deleted; keep it, or rename it instead?`, no options |
| `delete` a notebook | `notebook_has_no_children` | an ask, `the Recipes notebook still holds other notebooks, so it cannot be deleted; keep it?`, no options |

The reply has two lines: `refused: delete #7 folder "Taxes": <the vault's sentence>.`, then `declined: not_found · the runtime ended the turn: …` or `asked: "…" · options: … · the runtime ended the turn and nothing was done`. The effect adds `refusal = {verb, kind, id, n, command, predicate, reason, outcome: decline | ask}`. The options of an ask are numbered and in focus (`asked:`) for the next turn, which is how "yes, move it to Money" reaches them. Every other refusal stays the `error:` of §5 for the model to repair: an input the command's schema rejects (`schema`), a check not in the table (a task parent that is not open or top level, a note over its length, an event that ends before it starts), the refusals of other verbs (a name in use on `create` or `edit`; with `--no-compose` also a member with a balance on `remove_from`, an event that clashes on `create` and a cancelled event on `reschedule`, which §4.8 ends in an ask), and a refusal after part of the write landed (the turn then ends as a write does, the reply names the refusal, the effect has the `diff`).

### 4.7 The compile step

`{"op":"compile","slots":{...}}` on the session protocol (`compile.rs`) turns the slots of a v3 trace into the call the runtime executes:

```
in:  {"op":"compile","slots":{"intent":"count","kind":"task","op":"count","linked_to":[{"pick":{"row":"#8"}}]}}
out: {"call":   {"tool":"answer","args":{"kind":"task","linked_to":["#8"],"op":"count","where":"status = open"}},
      "stated": {"tool":"answer","args":{"kind":"task","linked_to":["#8"],"op":"count"}},
      "notes":  ["status: the message asks what is left; used status = open."],
      "resolved": {"picks":[{"slot":"linked_to[0]","handle":"#8","id":"7d73013f-…","kind":"list","name":"Home"}],"dates":[]}}
refusal: {"refused":{"slot":"pick[1]","why":"#9 is not in the block"}}
```

- slots: `intent`, `via`, `verb`, `kind`, `op`, `field`, `group`, `trashed`, `name`, `text`, `where`, `when`, `linked_to`, `within`, `exclude`, `order`, `limit`, `more`, `set`, `pick`, `rows`, `row`, `value`, `options`, `question`, `reason` (`scope`, `refer`, `target` are accepted and ignored).
- the tool is `via`, else the intent's own (read and count: `answer`; write: `act`; ask; decline). The rows are the explicit `rows` / `row`, else the `ok` entries of `pick`, and only when no other handle slot is given (the rule of the stateless compiler, `think.rs`).
- `where` is a list of typed conditions: `{"field","op","value"}` (op: `= != < <= > >=`, `contains`, `in` with a list, `is empty`, `is set`), `{"link":"person","op":">=","value":2}` for a linked count, an optional `"currency"`. A string is refused. Each is rendered in one spelling and checked against the kind (`where[i]` names the one that fails).
- `pick` is a list of entries: `{"row":"#n","verdict":"ok"|"no"}` (a row the model can see: directory, pre-grounded rows, `focus:` line, visible observations), `{"focus":i}` (the i-th row of the `focus:` line), `{"date":i,"reading":"past"|"upcoming","into":"when"|"set:<key>"}` (the i-th entry of the `dates:` line; `reading` when the line gives two). `{"pick":{…}}` stands where a handle or a date is written. A row resolves to its `#n` and vault id, a date to the date expression of its resolution (a day, a day with a clock, a range; a clock alone is refused).
- `set` is a list of `{"key","value"}` / `{"key","date"}`: the lines of an act's `args`. Dates are written key by key in the call's order (`from, to, date, unit, rel, name, weekday, time, anchor`), `when` as JSON text like the reference calls.
- `call` is `stated` after the grounding and the conventions, i.e. what the runtime executes. Running `stated` through `call` gives the same effect and keeps the notes under the observation.
- a refusal names the slot (`pick[1]`, `linked_to[0]`, `where[2]`, `when`, `verb`, `intent`, an unknown slot by its own name).

### 4.8 Asks and declines the runtime composes: the model judges, the harness composes

The model keeps two judgements that need the person's words: an `ask` with no options, when something the request needs is missing ("which wifi?" with nothing ambiguous, "what should the note say?"), and a `decline` for a policy reason (`out_of_scope`, `sealed_egress`, `fabricated_secret`, `unbounded_destruction`, `never_mind`). Everything else that ended in an ask or a decline is the runtime's, composed at the call that causes it (`compose.rs`; D-1044-11 and, for the refusals, D-1044-10 extended), behind `Flags.compose` (default on, `--no-compose` off). Each composed ending is the same shape as the cap's and the vault's (§4.6): the turn ends at that call, `effect.composed = true`, `effect.compose = {family, action}` says what the runtime did, the reference calls after the call are not sent, and `more` does not keep the turn open. What the runtime decides without ending the turn (a `find` that missed, a write on every row, a write on a near spelling) carries `compose` alone. The runtime still ACCEPTS an `ask` with options and a `decline not_found` from a model that writes them (they run as written, without `composed`), but they are not what the model is taught.

The runtime's search for a name that reached no tier of the selector's kinds (nt11: `resolve.rs` for the tiers, `search.rs`, `name_in_part` for the rest) is, for a write, the first non-empty of: the selector's own rows a typo reaches (§3.3, item 4, tier 4; the call's other conditions kept), the rows of the selector's kinds that hold at least half the words said (`name_in_part`: the rows whose name, nickname or role holds them by exact word, word start or near spelling, only the best-scoring tier kept, live and trashed), the rows of any kind the name reaches at its best tier, the rows of any kind that hold part of it. For a write a candidate is a row the verb applies to, live for every verb but `restore`, whose candidates are the trashed rows; a name that reaches a trashed row as it is said has no candidate (only a restore writes it). A selector with a `when`, `where` or `linked_to` has no search of its own for a write beyond its typo rows; for a read the near rows that meet them are kept. A write by `#n` (`rows`) is the model's pick and is never searched. A write is applied to a row of another kind only when the name reaches that one row at its best tier, 1 to 3 (an `oil change` event is the row, a task `Buy oil filter` that holds one of the two words is a guess for the ask); a candidate of the selector's own kind is never applied to: its tier is 4, and a typo is asked over (nt11 R3). `compute` is unchanged: a count over a name that reaches nothing is 0. The hint of a `find` names the rows the same search finds and issues none of them: they have their `#n` from then on and are rows of the observation, so the next call, and a trace `pick`, may use one, but the model decides what the person meant (`search`, another kind, `answer`); an `answer` is where the near rows become the answer. The plain miss leads with `answered:` as the empty answer does, and the turn is open: the reply is followed by the re-anchor line of §5 when it names no row the model can use. An empty read names the condition that emptied it (nt10 G3; `recover.rs`, `without_rows`). A `find`, `answer` or `compute count` whose selector has two or more conditions (the name, the `when`, each `where` clause, each `linked_to` row, the `within`, `trashed`; the kind is none) and reaches nothing adds, to the hint line of the miss or as a line of its own, one part per single condition whose removal gives rows (one condition must remain): `hint: without where description contains "gutter": #9 task "Pay rent" · without linked_to #12: #4 task "Dinner" and 3 more`, at most four rows in all over the parts, none when nothing gives rows. The guard against a legitimate empty read ("any tasks due tomorrow?" is none, and a gold that ends in the empty answer must still end): a condition the message states is never offered. The name is stated when the message says a word of it (three letters or more, equal or sharing four letters); a `where` clause is offered only when it is free text (`=` or `!=` on text, `contains`, `in`) whose literal the message does not say (an enum, a number, a yes or no, a presence and a count were checked by the vault and are never offered); a `when` only when the message has no date phrase (the `dates:` line would be empty) and no time word (`overdue`, `this`, `week`, `due`, ...); a `linked_to` row only when the message says its name, nor its pronoun for a person, nor my/me for the user's own row; a `within` only when the message points back at a list (those, them, it, ones, that, list, ...); `trashed` only when the message does not ask for the trash. For an `answer` such a row counts as a row to name under the F1 open rule: the first empty answer of the turn stays open with the hint (`compose: answer_miss`), a find miss, an empty search or an earlier hint of the turn ends it as before, and the identical answer sent again is the second miss. A `compute` count stays a value and carries the hint.

What the vault refuses and the model repairs stays an `error:` (§4.6): a schema, a name in use, a parent that is not top level, a cancelled event on `edit`, a member removal that clashes with nothing here, and any refusal after part of a write landed. A read with a `when`, `where` or `linked_to` whose name does reach a row, and no row meeting the rest, is the empty answer of §8.5, unchanged.

- **Result header, kind card, rows:**
  ```

  #12 [1] task "Book the cabin" · Fri 2026-06-19 09:00 (this Friday) · status open
  ```
  `ROW_CAP` rows shown, the rest counted and still addressable through `@3`. Amounts show currency.
- **Links inline** on search hits. **Values**: `@5 = 42.00 USD` (sum of amount over @3, 4 rows).
- **Writes** echo what changed, with resolved dates and the `#n` of any created row (so a group created mid-session is addressable although the directory was rendered at session start).
- **Already-so writes**: `already: …` (§4.2). **Undo**: lists each reverted change.
- **Composed asks and declines** (§4.8): `asked: "Which one?" · options: #3 person "Neha Rao", #4 person "Neha Kulkarni" · the runtime ended the turn: "Neha" fits 2 rows and nothing was done`; `asked: "Did you mean #10?" · options: #10 person "Ray Ochoa" · the runtime ended the turn: 0 people called "Ray Ochoo" match; nothing was done, and the search found one row`; `declined: not_found · the runtime ended the turn: 0 tasks called "Zzyzx" match; nothing was done`; an `answer`: `answered:` the block, then `note: no row called "Ray Ochoo"; showing near spellings`.
- **Over the cap, refused by the vault** (§4.6): `asked: "this would delete 734 tasks; delete all of them?" · the runtime ended the turn: 734 rows is over the cap of 12 and nothing was done; after a yes, send the same write again`, and `refused: restore #10 person "Craig Nolan": it is in the trash but past the vault's restore window, so it cannot come back (vault: …).` then `declined: not_found · the runtime ended the turn: …`.
- **Empty find** (`--no-compose`): `0 tasks called "tabla". Other kinds called "tabla": #13 event "Tabla class"`. Composed (§4.8), a `find` whose name reaches nothing is `answered: 0 events called "ski rentals" match`, and under it, when the search finds rows the name nearly is, `hint: near spellings: #40 event "Vermont ski weekend"`: no result handle, no rows, the turn goes on.
- **A write the runtime applied for the person** (§4.8): `unstarred: …` lines, then `note: 2 rows fit; the message says all, so the write took every one of them.` for a selector that fits several rows when the person says all; and, for a name that matched nothing, the reply opens with `note: no row called "Farukh"; applied to #46 person "Farrukh Kasimov" (near spelling)`, or `note: no task called "oil change"; applied to #21 event "Oil change"` for the row of another kind it names.
- **Typo line** (§3.3, item 4; nt11 R2): when a read's name reached its rows only by a typo (tier 4), a line under the reply says so: `matched "Kamini Rao" for "Kamni"`. A name reached as it is said has no such line. A write by a typo is the ask of §4.8.
- **No link**: `events are not linked to places. Events whose name mentions "Mallaig": #7, #8`.
- **Re-anchor**: an `error:` about rows or handles (`#99 was never shown`), or an empty find, search or act, that names no usable row itself ends with `rows you can still use: #9 task "Pay rent", …` (at most 5 rows: this turn's, then the pre-grounded, then the previous turn's), so the next call can re-anchor. The line is not part of the block and never reaches compaction; repeated-call hints do not carry it.
- **Ambiguous** (§3.3; the reply of `--no-compose`, composed otherwise: §4.8): `ambiguous: "Neha" fits #3 person "Neha Rao", #4 person "Neha Kulkarni"; nothing was done.` At most `ROW_CAP` candidates are listed, then `and N more`, in this order: the rows that are not over (a task not completed or cancelled, an event that has not ended, a row with no date), the nearest date to today first and a row with no date after the dated ones; then the rows that are over, in the selector's order (oldest first). The rows listed are the rows an `ask` after it offers (§8.6).
- **Ask completed** (§8.6; only after an `ambiguous:` reply, so only with `--no-compose`): an `ask` in the step right after an `ambiguous:` reply, whose options are some of that reply's candidates (or none), lists every candidate in the reply's order, at most `ROW_CAP`, and says so: `asked: "Which one?" · options: #29 note "Meera birthday ideas", #28 note "Gift ideas for Tomás", #30 note "Mehndi night ideas" · options completed from the candidates`. The effect carries the full list (`ask.completed = true`). Any other ask is left as the model wrote it.
- **Only trashed** (`--no-compose`): `no live task called "library"; trashed: #9 task "Library books" · trashed`.
- **Error**: `error: tasks have no field "due_on". task fields: date, status, effort, completed. For that use date.` Errors name every valid option and, when it is decidable, end in the call to send instead (nt9 part B, F2; a call whose fix changes no rows is run instead, with `note: used <call>`, §4.5, nt12 R1): an unknown field names the field this kind uses for that meaning (free text is `description` on a task or an event and `body` on a note; a due date or a start is `date`, which an edit changes with `reschedule`; an event's `duration` is a task's `effort`) or else the kinds that have a field of that name (`priority is a field of tasks.`); "X are not linked to Y" names the call that fits (a group's money is `compute op balance, kind group, linked_to the person`; the photos of a person or an album are `find kind photo, linked_to that row`); a secret an item lacks names the one it holds when it holds one (`Home wifi has no cvv. It holds: password. Send reveal field: password.`); a row of the wrong kind in a write (a document where `complete` wants a task, a task put in a document, a `group:` that is no group) is an `error:` ending `Did you mean #7 task "Review lease"?` over the rows of the right kind its name reaches by a word, at most three, and only when there are such rows; with none the refusal is the composed decline it was (§4.8). A call sent again unchanged after an `error:` gets ONE hint rung and the turn stays open (nt10 G1): `error: that is the same call again. <the fix the error ended in>` (its last sentence when that is a fix (`For that use date.`, `Did you mean #7 or #8?`, `Send act verb: …`); the error's own text, without `error:`, when it ended in none); the second identical resend ends the turn in the decline or ask of its family (§4.5), as the first resend did before. A refusal that is no `error:` reply (`no_link`, a write that matched no row) has no rung and ends at the first resend. The repeat hint of a call that ran quotes up to 400 characters of an `error:` reply (160 of any other), so a fix is never cut. **Errors end in the concrete call** (nt10 G2) when every argument of it is decidable, in the model's call syntax, `Send <tool> <param>: <value>, …` (parameters in the tool's order, a name quoted, `args` lines joined by `; `), and never when anything of it is a guess: an unknown field of a `where`, `order`, `field`, `group` or an `args` line the kind names otherwise (`Send find kind: task, where: description contains "cabin"`; a date has none: its expression is the model's); a secret the item lacks (`Send act verb: reveal, rows: #14, args: field: password`); a row of the wrong kind with exactly one right row the words fit (after `Did you mean #7 task "Review lease"?`, `Send act verb: complete, rows: #7`); a balance asked of a group by its `linked_to` or `within` (a person's balance with the group in reach, or `compute op balance` over a person selection) or a group's balance with no person while the message names one (`Send compute op: balance, kind: group, name: "Tahoe Trip", linked_to: #12` where #12 is the one other person the message names, else the user when no one else is in play), and `that is you` with no group in reach when the message names exactly one other person (`Send compute op: balance, rows: #10`); the same calls in the `no_link` reply of a debt linked to a group or of a person and an album (`Send find kind: photo, linked_to: #3`); and a narrowing follow-up with no kind that lost its list (`a selector needs kind (or within=@n)`) when exactly one list of the last two turns is on screen (`Send find when: {…}, within: @1`). Not done, a false positive: a date-range error (`2026-09-28..2026-10-04 is a range`) never writes the range out as a span, since a week or a month in a reschedule means one day in it, not a seven-day event. A call that fails to parse returns `error: could not read the call` plus the tool list. Errors count as steps, and an error repeated verbatim ends the turn (§6.3).
- **Compaction (§6.4)**: an earlier turn's result is replaced by its header plus the rows any later call referenced: `@1 · 23 tasks (compacted; #4, #7 kept)`.

## 6. Turn loop

0. **System prompt**, rendered by the harness at session start, in this order, each part generated:
   1. `today: <weekday> <date>` and the person's own name (`me`).
   2. **Tools** — the §4 tools in Qwen's native `<tools>` block as **signature lines** (`--tools sig`): each tool's params with `?` for optional and enums inline; the date expression's fields once, on `find`. The surface is fixed, so described schemas would repeat identically in every example and teach the fine-tuned model nothing the calls don't. Full described schemas (`--tools full`) are used only for untrained models (the Sonnet smoke test).
   3. **Kind card** — one line per kind: its model-facing name, its fields with enum values and units, its links, its verbs (`task: date (due), status (open|in_progress|completed|cancelled), effort (min), completed · links: subtasks · verbs: create edit reschedule complete reopen delete restore`). About 450 tokens for today's surface; the same lines constrained decoding uses.
   4. **Vault directory** (flag, ablated) — the names of the vault's CONTAINERS, the small sets a message refers to by name: groups, albums, notebooks, folders, lists; each as `groups: Tahoe Trip (#1), Flat 4B (#2)`, pre-numbered so a call can use `#n` directly. Capped at 8 per kind, most recently used first, with `+N more` (reachable through `search`). People, events, tasks, notes and photos are NOT listed: they are too many and change every turn; the pre-grounding block (6.1) covers them. Containers created mid-session are addressable through the `#n` echoed by their `create`.
   5. **Conventions** — none. Policy lives in the training data, not the prompt; a rule in the prompt that the data contradicts is noise to a 0.8B model. The prompt is identical in form in training and at inference; the generator renders the directory from each training world.

1. **The block (flag, ablated, conditional).** The harness prepends to the USER turn a block of up to five lines, then a blank line and the person's message. Each line is there only when it has something to say, and they come in this order. The runtime renders the whole block as one string (the `block` of its `user` reply; `preground`, `focus`, `answer` and `dates` carry the four lines apart) and `render.user_content` writes it in front of the message, so training data, the eval driver and the smoke tests show the model the same text. It is not a synthetic assistant call, so the model does not learn "always search first". Training data includes turns where a line is irrelevant and the model ignores it.
   - **`vault:`**, the pre-grounding. When a word of the message is a word, or the start of a word (three letters or more), of the name of a live row or of a person's nickname, the line `vault: #3 person "Neha Rao" · #4 person "Neha Kulkarni" · …` lists at most 8 rows (`PREGROUND_CAP`). It reads the name index that `search` and every `name` selector read (§3): accents and case folded, a possessive `'s` dropped, trashed rows left out. A filler word, the request's verb and a function word name nothing; a two-letter word such as `dj` only lets in a row whose whole name the message says. Retrieval, not interpretation. Rows rank by (1) an exact name: every word of one of the row's names (a person's nickname counts) is a word of the message, so the list `Christmas` stands before the photos `Christmas 1` and `Christmas 10` when the message says "christmas", and of two exact names the longer; (2) how many of the message's words reach the row; (3) a container before a leaf. No kind takes more than half of the 8 slots while another kind has a hit, so numbered or recurring rows of one kind do not push the others out. A container shows how many live rows it holds after its closing quote (`#37 list "Kids" (75 tasks)`, `#4 group "Tahoe Trip" (3 members)`, `#9 task "Kitchen renovation" (4 subtasks)`, `0` for an empty one); any other row reads `#n kind "name"`. Three rules compose the line beyond the name index, all deterministic and each only when its words are there: (a) a container the message points at by its kind word and a determiner (`that album`, `the folder`, `the list`, `this notebook`) is the container of the focus rows, when the newest focus set whose rows share a container of that kind has one; it leads the line; (b) the person's own row closes the line (never leads it), written `#n person "Sam Park" (you)`, when the message says my, me, I or mine together with a balance, debt or group word (`balance`, `owe`, `debt`, `stand`, `position`, `net`, `tab`, `group`, `share`), or, with a group named in the line, a money word of a group alone and no "my" (`money-wise`, `up or down`, `fronted`, `paid`, `spent`, `put in`, `out of pocket`; nt9 part B, F5), and no one else is in play, so `linked_to: #n` reaches it; with a pronoun for someone else (`him`, `her`, `he`, `she`, `them`), a person the message names, or a person in the focus sets, the options of the last ask or what was created, the row is left out whole (the model took it for the balance's target); the row reads `(you)` wherever the line shows it; (c) a name more than six live rows of one kind share (recurring events: `Dentist` ×19) shows the rows the conversation touched (the focus sets, the options of the last ask, rows created or acted on, rows the previous turn opened or marked), then the nearest to today to make six (an undated copy last), and the rest as `+13 more "Dentist"` after the last copy shown; up to six copies are all shown, since the options of an ask and of a pick are read off the line. The leading and closing rows take slots of the 8.
   - **`focus:`**, what the conversation holds on to, so a follow-up ("put it in the new group", "the second one", "the first Neha") points at rows the model reads again here instead of at a transcript it must search: `focus: created #52 group "Lisboa" · @4: #8 photo "A", #9 photo "B" · in #3 album "Wedding" · earlier: @3 (counted 10 documents in #39 folder "Taxes"), @2: #44 task "Pay rent", #45 task "Call Neha" +4 more · acted #12 event "Dentist" · asked: #21 person "Dan Kowalski" (neighbor · Big Dan · Block Party) · #22 person "Dan O'Brien" (colleague · Book Club)`. Parts, each present only when the session has something to say, in this order: `created`, the rows an `act` created this session (the last 6, then `+N earlier`); **the newest result that holds rows**, `@k: rows`, in the one-set form the model's "point at the last result" habit reads; **`earlier:`**, the other sets among the last three of the conversation, newest first, joined by `, `: a set of rows as `@2: rows`, a count or value in brackets with its word first and its handle without a colon, so it can never be read as a rows set; then **`acted`** and **`asked:`**, below. At most 12 rows in all across the sets (`FOCUS_ROWS`, the lead first, then the newest; the set that does not fit is cut with `+N more`, one that gets no row reads `@1: +9 more`). A set shows the rows the model was shown (a lookup over 12 rows shows 6, the line counts the rest). When every set is a value the line is `focus: earlier: @3 (…)`. **Rows that all share one container** (a list, a notebook, a folder, an album, or a parent task for subtasks; never a group) name it after the rows, ` · in #3 album "Wedding"`; the container is numbered when the line is rendered, so `linked_to: #3` works. **A count or value is a set of its own and keeps its rows**: a `compute` or `answer` with an op gets a handle whose rows are the rows the value was computed over, so `within: @n` and `exclude: @n` work on it, and `rows: @n` of it is `error: @n is a value, not rows.` (never the rows it was computed over, never the next find's: `rows` and the options of an `ask` take rows); it reads `@3 (counted 10 documents in #39 folder "Taxes")` (the container is the selector's `linked_to` container, else the one the rows share), `@3 (summed 50 effort over 5 tasks)`, `@3 (counted by status completed 1; open 4 over 5 tasks)` (a grouped value keeps all its rows); a balance lists the rows it was over, `@3 (balance 70.00 USD over #12 person "Ray Ochoa")`, and a group's balance keeps the person it was linked to. **`acted`**, after the sets: the rows a write changed, an already-so answer named or an undo touched in the last three turns (written at turn 4, there at 5, 6 and 7), `acted #12 event "Dentist", #13 task "Pay rent"`. A row a write reached by a selector or off the `vault:` line is in no result set, so without this part nothing is in focus after the write and "undo that", "and the priority", "make it friday" have nothing to point at. It names the rows no other part names (a row of a set or of `created` is not said twice; a container named after a set's rows is not one of them, so a container the write touched is still here), the last 6 in the order the writes first touched them, then `+N earlier`, outside the 12 rows of the sets. A row the vault no longer holds is left out (a deleted album), one in the trash is not (`restore it` needs it); the options of an `ask` are not acted rows (`asked:` names them). The focus pick (§3.3 b) reaches one turn back where the line reaches three, and counts no row the line does not name. `asked:`, the options of the `ask` that ended the previous turn (at most 12, then `+N more`), there for the one turn that answers it, each with what tells it apart, in brackets joined by `·`: a person's role, nickname and groups; an event's date; a task's date and list or parent; a locker item's type and username; a note's, document's or photo's container. Every row is one the session already numbered, written as in the `vault:` line; the line never mints a number (the turn numbers the containers first). The runtime renders it from the session; the model does not write it.
   - **`answer:`**, after an ask, `answer: "the neighbor" → #21`: when the new message names exactly one of the options by a word of its name, nickname, role, group, date, container, type or username (a word of three letters or more is a hit as a whole word or as the start of one; filler words name nothing), the line says which row the words fit; the model still writes the call. A word that fits two options tells them apart no better than the name did and counts for neither; when the words left fit two options or none, there is no line. The quoted words run from the first to the last word that fits the option, with the article before them (`the`, `that`, `this`, `a`) and a `one` after (`the book club one`), lower-cased as written. It is there for the one turn that answers the ask and sits between `focus:` and `dates:`.
   - **`dates:`**, every date or time phrase of the message that the runtime can resolve, with its resolution, so the model copies a date instead of computing it: `dates: next tuesday = 2026-10-06 · at 9pm = 21:00 · sept first = 2026-09-01 (past) / 2027-09-01 (upcoming)`. Phrases are lower-cased as written, in message order, at most 6; no line when the message holds none. They come from the runtime's own grammar (`phrases.rs`: the §4.4 and §14.1 phrases, plus clocks, offsets, weeks, months and years), and each is read into the date expression the model would write and resolved by `dates::evaluate`, so a line never says what the evaluator would not. A resolution is a day (`2026-10-06`), a range (`2026-09-21..2026-09-27`; an open end is left empty, `..2026-10-01`), a clock (`21:00`) or a day with a clock (`2026-09-27 13:00`). A phrase with two honest readings prints both: a weekday or a day of the month that has already gone by, and a month or a month and day without a year, read `(past)` and `(upcoming)` (§14.1: a write takes the next occurrence, a read keeps the model's month, so the model chooses), except a bare ordinal that ends a span, which has one reading (below); a bare hour with no word that settles it, after "at", "to", "till", "by", "make it" or right after a single day ("tuesday at 3", "sunday 11"), reads both ways, the likelier reading first (1 to 8 pm, 9 to 11 am): `at 3 = 15:00 (pm) / 03:00 (am)`, `at 9 = 09:00 (am) / 21:00 (pm)` (twelve is noon, `12:00`; half and quarter hours read the same way, `half 5 = 17:30 (pm) / 05:30 (am)`). An evening cue (tonight, dinner, drinks, party, movie, evening, afternoon, supper) or a morning cue (breakfast, morning) near the clock settles it, as does am or pm. The line only lists and the model judges the hour; an event's create or reschedule whose day carries no time at all takes the afternoon or evening reading for 1 to 8 and the morning one for 9 to 11 (§14.1 "at N"), and a time the call states is never changed. Further phrases: `the rest of the week = 2026-10-03..2026-10-04` (tomorrow to Sunday; from today when the message also says today; a lone Sunday on a Sunday), `the rest of the month`, `rest of today = 2026-10-02 09:00..2026-10-02 23:59`; `the day before friday`, `3 days before the 15th`, `a week after next monday` (the date shifted; past and upcoming pairs stay pairs); a weekday after another phrase resolves on its own (`friday` in "what's left on friday after that"; only "the friday after that" points back at the talk), except a weekday that ends a span: after a start that is a weekday phrase or a day word that resolves to one day ("from last saturday till sunday 6pm", "from saturday last week up to sunday", "from tomorrow until friday") it is the first such weekday on or after the start (that sunday is the day after that saturday, not the next sunday from today), and after a start that is a week name ("from last week up to tuesday") it is the current week's, as written, past or not (D-1044-15, B7); a bare ordinal that ends a span ("from august up to the sixth", "from first oct to the sixth at 7pm", "notes from the start of july up to the twenty-fifth") is the day of the month the span starts in (`the sixth = 2026-08-06`), one reading and not the past-and-upcoming pair, and the pair stays only when no month starts the span (D-1044-15, B8); a part of the day after a day word on a READ is a span, never an instant (`sunday night = 2026-10-04 17:00..2026-10-04 23:59`; morning 06:00-11:59, afternoon 12:00-16:59, evening and night 17:00-23:59), and on a WRITE (the message says add, schedule, move, book, put, make, ...) it is the time it stands for (morning 09:00, afternoon 15:00, evening 18:00, night 20:00); with a clock of its own in the message the day alone is listed. Phrases that need the conversation are listed only when it holds what they point at (`Session::dates_line`): `that day = 2027-02-08 (the eighth, turn 2)` ("that day", "that date", "the same day", "then" after about/for/by/until/since/from/on ("ok make it 7 then" is no time); the date a write of this turn or the last set, else the last single day the previous message said, else the one day the previous result showed), `the day before that = 2027-02-07 (the day before the eighth, turn 2)`, and `before berlin = ..2027-03-11 (#30 event "Flight to Berlin")` (before, until, till: up to that day; after: from it; the one pre-grounded or focus event whose name the words fit; a date phrase of its own wins). A `dates[i]` pick of such an entry resolves to the date before the parenthesis. A phrase that needs the row it moves ("an hour earlier") is not listed. A four-digit year after for, throughout, year or to reads as that year's span like one after in, from, since, until, till, before, after, during, by, of or through (`2025 = 2025-01-01..2025-12-31`; a year inside a name, `W2 2025`, is no date); the fixed-date holidays new year's day and eve, christmas day and eve, valentine's (day) and halloween read as the month and day they are, a past and an upcoming pair (`christmas day = 2025-12-25 (past) / 2026-12-25 (upcoming)`; `christmas` alone, `new year` alone and a bare `valentine` are no day: a list, an album, a person); "the end of the day" and "end of today" are today (`= 2026-09-27`), as "the rest of today" is today only (nt9 part B, F6). The line changes no call: the date repair of §3.3 is unchanged.
   - **`picks:`**, the rows an ordinal of the message counts to in the list in focus, so the model copies numbers instead of counting: `picks: the last two = #34, #35`, after `dates:`, only when the message holds an ordinal phrase and a list is in focus, otherwise no line (nt9, rule 1). A phrase is `first` to `tenth` (or `1st` to `10th`) followed by `one` or a row noun (`the third one`, `the second task`), `first` or `last` followed by a count of two or more (`the first two`, `the last 3`), `last one` / `last <noun>`, or `the other one`; an ordinal alone ("the first of may", "the first"), one that dates something (`the first two weeks`, `last night`, `last week`) or a `second` that is a unit is no phrase, and there is no line for it. The list is the options of the ask that ended the previous turn, in the order of the `asked:` part, else the newest result set of rows (not a count or a value) that the `focus:` line shows at least two rows of, in the order it shows them (the line's row budget goes to its lead set first). `last` of a list the line cut (`+n more`) and an ordinal past its end name nothing and are left out of the line; `the other one` is named only over a list of exactly two rows of which a write of the last three turns touched exactly one (the other one). Entries run in message order, at most three, `the first one = #30 · the last one = #35`; a row is its `#n` alone.
2. The model makes one tool call per assistant message; the runtime answers; repeat.
3. The turn ends on `answer`, `ask`, `decline`, or an `act` without `more`. **Step cap 6**, counting every model call including ones that returned an error; hitting it is a fail (`cap`). **A call identical to the one right before it is not run again** (a write would land twice), and what follows depends on what the first call got:
   - **A call the runtime ran** (rows, an empty result, an `ambiguous:` reply, a write): the first repeat gets a hint that quotes what the first call returned (`error: repeated call. You already made this exact call and it returned: … Answer from that result, or change the call.`), the second a nudge (`error: repeated call again. Do not send it a third time: …`), and the third ends the turn (`error: repeated call`, diagnostic label `loop`).
   - **A call the runtime refused as invalid** (an `error:` about the schema, a parameter, a field, a verb, a cardinality or a row, with nothing changed): nothing can change between two identical calls, so the first repeat gets one hint rung when the reply was an `error:` (§5, nt10 G1) and the next one ends the turn, and its reply says which step it was: `error: repeated call at step 4: step 2 sent the same call and the runtime refused it as invalid.` (`effect.invalid_repeat = {step: 4, of: 2}`). A write that landed in part is not a refusal. A link the metadata does not have (`no_link`) and a write that matched no row refuse as surely and count the same, but they are no `error:` reply and end at the first resend.
   - **A malformed write is repaired before its first send** (`normalize.rs`, run by every call and by the compile step; each repair is a `note:` line under the reply and an entry of `effect.normalized`): a `create` arg the kind does not take is dropped (a repaired `args` stays the `field: value` lines it was; `note: ignored area: family (notebooks have no area)`; a locker secret is sealed when the item's type keeps it, and dropped, never echoed, when it does not); a `when` on a create is dropped, or becomes the `date:` arg when it is one day or instant and the args carry none; `list: #n` of a task is `parent: #n` and `parent: #n` of a list is `list: #n`, and a `notebook:`, `folder:` or `album:` that is not that container is dropped; a `where` on `name` is lifted into the `name:` selector (`name = "x"`) or dropped (any other operator); rows beside a selector run on the rows; and, in the compile step, a write whose every pick was rejected matches by the trace's `target:` as `name:` when its verb fits one kind.
   - **That first repeat ends in the typed outcome its error family names**, never the generic ask (`failsoft.rs`; `effect.failsoft = {family, action}`, beside the `invalid_repeat` it always had). A read (answer, find, search, compute) drops the constraint the error names (a `where` clause, a `when`, a parameter the tool does not have, a kind that is not one, a link of the wrong kind) and the runtime runs the corrected call as its own step; the turn ends with that result (`effect.tool = answer`) and `note: ignored where "met < …" (met is text)` says what was left out. Rows beside a selector become `within`; `answer value: #n` answers the row; a selector without a kind takes the kind of the rows in reach when they are all one kind; a balance of nobody asks which person among them. A read with nothing selective left would answer the whole kind, so it declines `not_found` instead. An `ask` with an option that is no row (`#80 was never shown`) goes out with the options that are, completed from this turn's `ambiguous:` candidates the way any ask is, or with those candidates when none survives (`ask_options`). A write never falls back to a row the model did not name: rows beside a selector run on the rows; a `reveal` of a field that is not secret answers the row; any other refused write declines, `out_of_scope` when the verb cannot apply (`X does not apply to …`, `a person goes into a group`) and `not_found` otherwise. After a landed write the repeat stays a `loop`.

   **A retraction ends the turn before any call.** When the last clause of the user's message takes the request back (`never mind`, `forget it`, `just kidding`, `skip it`, `scratch that`, `leave it`, `don't bother`, `actually no, forget it`; a `fine` after a question; `phrases::is_retraction`), the `user` reply carries `ended`, the `decline never_mind` the runtime made itself, and a call after it is refused as a call after the turn ended. A message that retracts and then asks or orders something else ("skip it, what's on friday") does not end. The eval driver records one step with `model: ""` and `runtime: "never_mind"` and sends no model step.

   **A `log` that ends the turn also answers the row**: the effect carries `answer: {rows, ordered, result}` beside the `diff` and the reply ends with the row's readout line, so the turn reads as rows plus a diff. With `more: true` nothing changes.

   **Fail-soft**: unless a write landed in the turn, either cut and the cap end the turn as a typed `ask` (`effect.tool = ask`, `effect.failsoft = cap|loop`) that quotes the last failing step and offers the rows the turn saw; the scorer then judges it as an ask, not as `loop`/`cap`. After a landed write they stay `loop`/`cap`. A call that its own trace contradicts (§4.5) is refused without being run and is not a repeat: the same call under a corrected trace goes through.

4. **Compaction.** Before each new turn, results of turns OLDER than the previous one are compacted (§5); the previous turn's results stay whole, since follow-ups pick from them. Rows the model created or acted on are always kept. Earlier turns' **thinking is kept**: the harness renders the history itself (not Qwen's default template, which drops it), so on a follow-up the model sees how it read the earlier turn. Training and inference use the same renderer. The generator renders training sessions with the same compaction.
5. `#n` and `@n` persist across the session; `#n` of compacted rows are not addressable (§3).
6. **Decoding.** The headline score is **greedy** (reproducible). Sampled decoding as Qwen recommends (temperature 0.6, top-p 0.95, fixed seed) is an arm in the first run and stays an arm only if it beats greedy by more than the noise floor. **Think guard**: at 200 think tokens the harness forces `</think>` and lets the call follow; the event is counted (`think_cut`) as a diagnostic, not a fail.

## 7. Reasoning (the slot trace)

A short `<think>` block before each call: one `label: value` line per slot, in a fixed order. The slots say what the call is for (intent, verb, scope), which earlier rows it takes (refer, pick) and where its values come from (target, when), then state every argument of the call, so the call is a deterministic rendering of the think and the decoder writes it from the think instead of sampling it. Every value is a closed word, a quoted span of the user message, or an argument as the call carries it; nothing the runtime can compute (no row lists, no resolved dates). Each slot depends only on the message, the context and the slots above it. The format, the slot rules, the `refer:` rule and the compiler are in [CONTRACT_V3.md](CONTRACT_V3.md). The generator is `authored/trace.py`; the Rust guard (`crates/nativetools/src/trace.rs`) parses the three slots it enforces (intent, scope, refer) from the same text (§4.5).

| slot | values | closed set defined in |
| --- | --- | --- |
| `retry` | the literal `rejected` | `trace.py` `LINE_RX3["retry"]` |
| `intent` | read, count, write, ask, decline | `trace.py` `INTENTS`; Rust `trace::Intent` |
| `via` | find, search, open, compute | `trace.py` `VIA` |
| `verb` | create edit reschedule complete reopen cancel delete restore star unstar add_to remove_from log settle_up settle_debt reveal undo | `trace.py` `VERBS`; Rust `meta.rs` verb table |
| `scope` | one, some, all | `trace.py` `SCOPES`; Rust `trace::Scope` |
| `refer` | it, both, that, nth; handles `@k` or `#n`, comma separated; or `none` | `trace.py` `REFERS`; Rust `trace::ReferKind` |
| `when` | a quote; `now` (the unstated default, from today on); `earlier` with an optional quote (said in an earlier message, or an earlier call's own date); then ` = <date>` | `trace.py` `LINE_RX3["when"]`, `date_to_compact` |
| `pick` reason | kind, name, position, date, status, other | `trace.py` `REASONS` |
| `target`, all quotes | spans of the message | `trace.py` `find_span` |
| `kind` ... `reason`, `set`, `time` | the argument as the call carries it | `trace.py` `RAW3`, `CALL_ORDER` |

Slot order is `trace.py` `SLOT_ORDER3`; `parse3` rejects a line that is not a slot or is out of order. The runtime's `think::compile_think` (`nativetools think`, `runtime_think.py`) turns a think back into the call it states.

refer: it "him" -> @1

## 8. Policy (the decision procedure the generator executes)

1. **Intent.** Question about rows → `answer rows`; "how much / how many / total" → `answer op`; change → `act`; the vault cannot decide → `ask`; outside the vault or unsafe → `decline`.
2. **One step when the selector says it all; look first when it does not** (a pick, an unfamiliar name, a write whose target must be seen).
3. **Unfamiliar name → `search`.** A name is _unfamiliar_ when it appears neither in the vault directory nor in the pre-grounding block of this turn nor in any row shown earlier in the session. Familiar name → selector or `#n`. The generator computes familiarity from the same rendered prompt, so the rule is executable.
4. **Constraint over pick** (§3).
5. **Dead end → recover once.** A dead end is a missing link or an error: take the recovery rows the runtime offered, or `search` the name. A NAME that resolved to nothing (or only to trashed rows) is the runtime's (§4.8): the write goes to the one near spelling of its kind or to the one row of another kind the name names exactly (`delete`, `remove_from`, `settle_up`, `settle_debt` and `reveal` end in its `Did you mean #n?`) or ends in its `Did you mean #n?`, its `Which one?` or its `decline not_found`, an `answer` in the near spellings or the empty answer, and a `find` is a plain miss with a hint the turn goes on from (a `find` is a lookup: the reference looks, then looks again, then answers); the model writes the call with the name and nothing after it. An empty result from conditions alone ("what's due next friday?" with nothing due) is not a dead end: it is the answer, and `answer` returns it and ends the turn. A restore the vault refuses because the row's window has run out ends the turn in the runtime's `decline not_found`, and a delete it refuses because the row still holds others ends it in the runtime's ask (§4.6): the reference stops at the refused `act`. The same holds for every refusal of §4.8.
6. **Ambiguity is the runtime's ask** (§4.8): when the message or the conversation decides which row, the model picks by `#n`; when it does not, the model writes the call it means (the selector) and the runtime ends the turn in `Which one?` with the candidates, unless the person said all (every row the selector fits is written). The model never writes an `ask` with options. (With `--no-compose` the model asks after an `ambiguous:` reply and the runtime completes the options to every candidate of that reply, §5, D-1044-9.)
7. **Answer exactly what was asked**; the kind the question asks for ("who" → people), with one idiom: "who owes me", "who do i owe" and "who's that to" about debts are answered by the open debt rows (each shows its person) or by the people those debts link to, and the gold accepts both; a person's balance is not the answer (D-1044-15, B6).
8. **Follow-ups.** A narrowing fragment ("just the weekend ones") = `within=@n` plus the new condition. A substitution fragment ("and Ray?", "and today?") = the previous turn's call with the one named slot replaced, everything else kept. The trace states which. A question that names its own subject or noun ("and how many do i have a cadence for", "how many priority ones are left", "which debts are still open") is a fresh question, not a fragment: it keeps the kind of the turn before when the message names none, and neither its date scope, its container or person, its role filter nor its `within`. A bare "how many are starred" or "which are due up to sunday" (a verb and a condition, no noun) continues the previous set: `where role = "neighbor" and starred = yes`, `within=@1` (D-1044-15, B10). A word of a narrowing fragment ("just the recital ones") that is, or starts, the name of a container in the vault directory (an album, folder, notebook or list) names that container's members: `within=@n` plus `linked_to=#n`, not a `name` filter, which drops the members whose own names lack the word (D-1044-15, B12).
9. **Corrections add**; `undo` only on "undo that" / "I didn't".
10. **Writes on trashed-only targets** are the runtime's `decline not_found` (§4.8) unless the person asked to restore.
11. **Never a destructive write from a read phrasing** ("is X in the bin" is a read).
12. **Already-so writes** → `act` anyway; answer with the runtime's `already:` state.
13. **Conventions** are the §14 rulings: bare "wifi password" is a read; "diary" is calendar; members are people linked to a group; the §4.4 date readings; `undo` = the whole previous turn; amounts in the default currency; positive balance = they owe me.
14. **A write over the cap** (more than `ROW_CAP` rows) ends in the runtime's ask (§4.6), whatever the trace's `scope` says; the reference is the write, and after the person's yes the same write is sent again. Over a handle, with no all said, the same write ends as its selector's does: `Which one?` (nt11 R5).

## 9. Decoding

Decoding is **free**: no grammar constrains the model's tokens, and the runtime reads what the model wrote (`crates/nativetools/src/parse.rs`, which also salvages leaked parameter syntax). Under HF `generate`, `train/decode.py` adds only:

- the **think guard** (§6.6): at `think_limit` think tokens `</think>` is forced (`think_cut`);
- the **rendered call**: once the think closes, the call the think states is written by `fmt.call_of_think`, the function the data builder checks every authored call against, one forced token at a time (`rendered_call`); a think that does not state a whole call leaves the call to the model;
- **one call per message**: after `</tool_call>` only `<|im_end|>`.

The scoring arm is `free` (greedy; `bundle.py`); rollouts sample (`NATIVE_SAMPLE=1`: temperature 0.6, top-p 0.95, a fixed seed). The grammar-constrained modes (`hard`, `soft`: llguidance masks over an exported Lark grammar) and the llama.cpp arm were deleted on 2026-10-07 (D-1044-18): scoring had used only `free` since phase 7, and a grammar is a second statement of the call format that the runtime's parser already holds.

## 10. Scoring

The new scorer judges each turn by **effect**, never by the call or echo text:

- `answer rows` → the set of vault ids (exact set; the order matters only when gold says `order`);
- `answer op` / `answer value` → the number, with unit;
- `act` → the vault diff (rows changed and the fields that changed), plus, for already-so writes, an empty diff;
- `ask` → the turn ended in `ask` and, when gold names candidates, the options cover them;
- `decline` → the reason. Gold is authored as an effect (ids, number, diff, ask, decline), not as a call, so several valid call paths score alike. Session strict pass (every turn right) is the headline; turns are diagnostic.

## 11. Data and training

1. **Sessions are authored per world** in the eval gold vocabulary (`authored/sessions/<W>*.py`, the recipe in `authored/BRIEF.md`): a user message, the reference calls with `$key` handles, and tags. A world is `authored/worlds/<W>.json`, seeded only through `nativetools seed`.
2. **Train equals inference.** `authored/build.py` replays every session through the eval driver on the real runtime, keeps the sessions whose every turn scores as its gold, and writes the records the trainer reads: the prompt exactly as the harness renders it (§6.4 compaction, the vault block, earlier thinking kept), the §7 slot trace in front of every call, and the call rendered from that trace (`CONTRACT_V3.md`). A record whose call does not round-trip from its own trace is refused.
3. **Loss** only on assistant tokens (trace and call); tool results and user turns are masked, with the decision tokens weighted (`--decision-weight`, default 2). The think values that are verbatim copies of the user's message (the quoted phrase of `intent`, the values of `set`, `text` and `question`) carry no loss (`--copy-weight`, default 0): the model can read them, so their gradient would teach the instance, not the rule. The trainer asserts the mask on a sample.
4. **SFT on one Spot GPU VM** (`train/bundle.py` stages the job, `train/vm/` runs it; `train/vm/README.md`). Checkpoints at 25, 50, 75 and 100 percent; the last is the candidate unless the owner asks for `best` at launch: the trainer evaluates val at every mark and `out/best.json` names the mark with the lowest val decision loss (`out/marks.json` keeps every mark's numbers). The two records of a minimal pair (`pair` on the record) share one optimizer step (`--pair-batches`, default).
5. **Training unit is one session.** One sequence = system prompt + every turn as the harness renders it at inference; a session that does not fit the sequence length after compaction is split at a turn boundary and the split is logged.
6. **Gates on the corpus** before a run: `authored/gate.py` (no near-duplicate of a val or test message in train), `authored/dist.py` (train, val and test one distribution: shape, support, probes), `eval/build_sets.py check` (the frozen sets, the train file, the train-fit sample).
7. **The built artefacts** of the current version are `data/train.jsonl.gz` and `data/train-val.jsonl.gz` (`data/README.md`: counts, hashes, recipes).

## 13. Metric strategy

**Three sets**, frozen in `eval/sets/` (`eval/FROZEN.md`), scored by one script with greedy decoding:

| set | size | use |
| --- | --- | --- |
| **trainfit** | 300 sessions, a fixed sample of train | whether the model learned its own data; gross underfitting and label conflicts show here first |
| **val** | 655 sessions on seven held-out worlds | every fix and every decision is derived here |
| **test** | 656 sessions, the other half of the same pool | the headline; scored only at milestones the owner names; never tuned on |

**Headline**: session pass on test, every turn right, judged by effect (§10). Target 85%.

**Steering metric**: clean turn pass on val (turns not downstream of a session's first failure). A session passes only if every turn does, so 85% session pass over 3.1 turns per session needs about 95% turn pass; val resolves turn-level changes that session pass cannot (2,055 turns against 655 sessions).

**Guardrails** (can veto a run whose headline rose; fixed denominators): wrong-write rate (turns with any vault change gold did not specify ÷ all turns) under 1%; under-ask (acted or answered where gold asks ÷ gold-ask turns) and over-ask (asked where gold acted or answered ÷ gold non-ask turns), neither growing beyond the noise floor.

**Decision rules**: a change inside the 95% interval is not real (about ±3.7 points on session pass and ±1.7 on turn pass at val's size); one variable per run; a cause label per failing session on val after every run (`eval/slices.py`, then a hand read); a runtime change is judged first by `eval/replay.py` on a recorded run, without the model.

**Gold quality**: gold is authored as effects (§10) derived by running the reference calls through the runtime; the reference check (`eval/build_sets.py ref`) must score 100% on val and test before a set is frozen, and a change to a set is a new version with a new hash; a runtime change regenerates the gold with `eval/build_sets.py refreeze` (D-1044-11), which names the convention behind every changed turn.

### 14.1 What each convention means in the authored data

One behaviour per convention; the authored sessions hold to exactly this, and `authored/build.py`'s replay through the runtime is the check.

- **wifi** (`wifi password`, `wifi pw`, `wifi code`): the phrase names a locker row. A message that only names it or asks what or where it is ("wifi pw?", "what's the home wifi password", "where did i save the wifi code", "do i have the wifi password saved") is `answer rows` on the row and never `reveal`. Only a reveal verb aimed at the secret is a `reveal`: "show me", "tell me", "read it out", "read me", "reveal", "give me" the wifi password. When two wifi rows fit a reveal, the turn ends in `ask` with both as options, unless the previous turn starred, edited or created one of them: that row, in focus, is the one revealed or read, and the runtime does not ask (D-1044-13, G11). Sending it ("text", "whatsapp", "email" it to someone) is `decline sealed_egress`, the secret leaving the vault (messaging in general is **messaging**); inventing one ("make up", "invent") is `decline fabricated_secret`. Other secrets follow the ordinary rule ("what's the router password" is a `reveal`).
- **messaging** (D-1044-13, G1): "text X", "email X <thing>", "tell X I said hi", "whatsapp X" is `decline out_of_scope`, because the vault sends nothing, even when the name fits several people (no ask over the namesakes) and even when it names a document ("send the house deed to olivia" accepts `out_of_scope` and `sealed_egress`). Unless the message says to log or note it ("log that i messaged sarah"); "remind me to email kimura friday" is a task. `sealed_egress` is for sending a secret out of the vault: the wifi password, a card number ("text it to the babysitter" about the password in focus).
- **diary**: "diary" (also "my diary", "in the diary", "diary tomorrow") means the calendar, so the reading is kind `event`: "what's in the diary tomorrow" is `answer kind=event when=tomorrow`, "put dinner in the diary thursday at 6" is an event `create`. "diary entry", "journal" and "journal entry" mean a note. A row whose own name contains "diary" (a notebook called "Diary 2019") is addressed by that name like any row, and the convention is off for it.
- **balance**: `answer op=balance` (or `compute`) always ends in a value. The sign comes from the vault and never from the wording: for `kind=person` positive = they owe me, negative = I owe them, so "how much do i owe X" can come back positive (X owes me) and the model reports what the vault says. For `kind=group` with `linked_to` a person, positive = the group owes that person; `linked_to=$me` is my own position ("where do i stand in it"). A named person with no group in play is the person balance; a group in play (named, or carried over from the last turn) is the group balance, and a group balance asked right after a person's balance with "just", "only" or "specifically" accepts both the group's net of that person (positive = the group owes them) and the person's part of the balance in the group's currency (positive = they owe me), as the turn before answered (D-1044-13, K2); totals over all debts ("how much do i owe all in") are `sum` over debts, not a balance. "Who owes me", "who do i owe" and "who's that to" ask for the debts or the people behind them, not a balance (§8.7).
- **weeks**: a week is Monday to Sunday. "this week" contains today (`unit=week rel=0`), "next week" is the following Monday to Sunday (`rel=1`), "last week" the one before (`rel=-1`), on a Sunday too. "before this week" ends with last week.
- **weekend**: "this weekend" and "the weekend" are the Saturday and Sunday of the current Monday to Sunday week (`rel=0`, weekdays 6 and 7; on a Saturday or Sunday that is today's weekend). "next weekend" is the Saturday and Sunday of next week (`rel=1`). Writers who mean the one after a Sunday say "next weekend".
- **next weekday**: "next friday" is the Friday of next week (`rel=1`, `weekday=5`), from any day including a Saturday or Sunday. "friday week" is the Friday of the week after next (`rel=2`).
- **bare weekday**: "friday" alone is the next Friday counting today (`rel=0` while the weekday is still ahead or today, else `rel=1`). Someone who means the Friday a week on says "next friday" or "friday week". A bare weekday that ends a span counts from the span's start when the start is a weekday phrase ("from last saturday till sunday" ends on the first sunday on or after that saturday, not the next sunday from today), and reads the current week when the start is a week name ("from last week up to tuesday"); the `dates:` line prints it that way (§6.1; D-1044-15, B7).
- **at N**: as in the table; ONE function decides a bare hour (`phrases::at_hour(hour, cue, row_clock)`, nt12 B4): a word of the message that says an evening or a morning first, then, for the contested 8, the row's own clock (12:00 or later is 20:00, a morning row 08:00), and with neither 1 to 8 is the afternoon or evening and 9 to 11 the morning, the other reading beside it; the `dates:` line lists it, a day with no time takes it and a reschedule that keeps the row's clock asks it; the row's own name or the message ("dinner", "drinks", "party", "movie", "tonight", "afternoon" evening; "breakfast", "morning" morning) decides first. A bare hour no word settles is listed both ways on the `dates:` line (§6.1); an event's create or reschedule whose message says one such hour ("move the dentist to tuesday at 3") and whose call gives the day with NO time takes 1 to 8 as the afternoon or evening and 9 to 11 as the morning (12 as written) and says so (`date: "at 3" is 15:00 or 03:00; the call had no time; used 15:00 (an hour from 1 to 8 is the afternoon or evening, from 9 to 11 the morning).`); a time the call states, whatever it is, is the model's judgement and is never changed, with one exception: a reschedule of a row whose own clock is 12:00 or later, and a message that says one bare hour from 1 to 8, is the afternoon or evening reading when the call wrote the early one (a 19:00 call moved "to 8" is 20:00 even where the call wrote 08:00, and the observation says so: `date: "to 8" is 20:00 or 08:00; the row is at 19:00; used 20:00 (the row's own time decides: an hour from 1 to 8 is the afternoon or evening).`); the row's own clock is another thing that decides first, with its name and the message, it only turns the early reading of an hour that reads as the afternoon, never a stated time for 9 to 11 or a stated time for a morning row, and the hour of the previous message counts when the previous turn only asked ("move it to 8", the ask, "the 22nd"; nt9, rule 3). A message with another clock or a time the words settle is left alone. Writers who mean the early hour say "3am". A bare hour led by say, around, maybe or about in a message that holds a day-part or evening cue ("the morning, say 9" is `say 9 = 09:00`, "make it evening, say 8" is `say 8 = 20:00`, "tomorrow evening around 8" lists the day and `around 8 = 20:00`) takes that half and N:00, never the start of the day part's window (morning 09:00, evening 18:00); a message with both a morning and an afternoon cue and exactly one hour lets the hour decide (1 to 7 pm, 9 to 11 am, 8 both ways), while a clock for each cue follows its nearest cue ("tonight at 8 and tomorrow morning at 6"); and "same time" on a reschedule whose message states no clock keeps the row's time when the call states another (`date: "same time" keeps the row's time (19:00).`; nt9 part B, F4).
- **time only** (nt9, rule 2): a reschedule of a dated row whose message names a clock and no day (the `dates:` line holds only clocks for it: "move thanksgiving dinner to 5:30") keeps the row's day: a `to` that is a day of its own (a date, or a day from today) and not the row's is put on the row's day, with the same clock, and the observation says so (`date: "to 5:30" names no day; kept the row's day (2026-10-12).`); a `to` anchored on the row, a day or a shift of days the message says ("tomorrow at 5:30", "a day later at 5", "5:30 next week") and a span are the call's own. The clock may come from the previous message when the previous turn only asked.
- **same time**: a reschedule whose message says "same time" (or hour, slot) and no clock moves the day only: a `to` with a day and no time keeps the row's time, and a `to` that is a day alone gets the note `date: the same time keeps the row's time; the call moves the day only.`
- **since**: "since X" is from X up to now. A listing keeps the span as the model wrote it: "what's on since monday" is `{"from": …}`, open-ended, and shows the rows after today too. An aggregate over the interval (a count, a sum, a breakdown by a field: "how many tasks since march", "physio by status since september", "how much since the first") is closed at today: when the message says "since" before a date (a month, a weekday, a day, "last …", "the start of …") and names no end of its own ("up to", "until", "before", "through"), a count, sum or `compute` whose span `when` has no end (or an end at the calendar's limit) gets today as its end and the observation says so; a start after today, or a "since" that opens a clause ("since he's paying"), is left alone. The model may write the span open or closed at today; both count the same.
- **end of month**: "end of march" in a write is March's last day (`{"date":"2026-03-31"}`); "end of the month" is this month's last day; the month named is the next one whose last day is not past.
- **ordinal and month-day**: a bare ordinal ("the 25th", "the eleventh") or a month and day ("dec 11", "the 3rd of may") in a write is its next occurrence, today counting, as for a bare weekday: this month's day if it is today or ahead, else the next month that has it; a month and day is this year's, else next year's. The runtime puts that date in whatever the model wrote (a past one, a later one, a day that does not exist such as 2026-11-31). Someone who means a later month names it ("the 25th of november", "the 25th next month"). In a read the model's month stands, except that a bare ordinal that ends a span ("from august up to the sixth") is in the month the span starts in, not the nearest sixth, and the `dates:` line prints that one day (§6.1; D-1044-15, B8).
- **status**: a word that asks for what is left to do ("open", "left", "still", "remaining", "overdue") is `status = open`, and `open` in a `where` names the active rows (D-1044-7): the tasks whose status is open or in_progress, so a task that has been started is still open. The runtime applies the rule in every form of the condition: `status = open` and `status = "open"` select open and in_progress; `status != open` is the rest, completed and cancelled; `status in ("open")` and `status in ("open", "in_progress")` select the same rows as `status = open`, and `status in ("open", "completed")` adds the completed ones. Every other value selects only itself: `status = in_progress` is the tasks being worked on, `status = completed` ("done", "finished") the finished ones, `status = cancelled` the cancelled ones, and `status != completed` still keeps the cancelled rows. A read that asks for everything has no status condition. A status without an in_progress value is read as written: a debt's `open` and `settled`, an event's `confirmed`, `tentative` and `cancelled`. The tasks not yet started are `status = open and status != in_progress`. The rule belongs to selection: `edit status: open` stores open, and `complete` and `reopen` are verbs, not selections. The authored sessions and the gold write `status = open` for a task read that asks for what is left; `status in ("open", "in_progress")` stays legal and selects the same rows.
- **container readouts**: a read, count or sum of tasks whose selector is a container link (`linked_to` a list or a parent task) and that carries no status condition selects the active rows, the tasks that are not completed and not cancelled (open and in_progress). The reply says `(active rows; add status = completed or all for the rest)`. An explicit status condition is honoured as written, and so is a message with "all", "everything", "done", "completed", "finished", "cancelled" or "closed": the rows of every status. A person, a group or a note is not a container of tasks; `act` selectors are never changed. A parent task's subtasks are a container like a list's tasks.
- **subtasks** (D-1044-15, B9): a subtask is a task created with `parent: #n` ("add a subtask under X: buy balloons", "add a step to X", "under X, add a subtask to order the cake"); a list is `list: #n`, and `add_to` never puts a row under a task. "Its steps", "what's under it" and "how many steps does it have" about a task with subtasks are the parent's subtasks (`linked_to: #n` of the parent), and the `focus:` line names the parent. The kind card carries `links: subtasks`.
- **status words, in a readout**: when an `answer` or `compute` over tasks carries no status condition and the message says "open", "left", "remaining", "still", "overdue" or "due" (and none of the words above), the runtime adds `status = open` and says so (`status: the message asks what is left; used status = open.`). `find` is not changed: it is also how a write looks a row up ("open them again"). "Due" is a status word of the same kind when the message asks what is due on a day or span ("what's due tomorrow", "anything due friday", "how many tasks are due monday"): an `answer` or `compute` over tasks with no status condition is `status = open`, and the runtime says so as it does for "left". "All", "everything", "done", "completed", "finished" and "cancelled" in the message lift it; a "done" under a negation does not ("what's due tomorrow that i haven't done" is open). "Due" also names the kind: a read that says only "what's due" is tasks (D-1044-13, G23, K1). For events, "left", "still on" and "remaining" mean the span's events that are not cancelled (`status != cancelled`): "what practices are left in january" omits the cancelled ones and covers the whole month, not the part from today (a month name in a read is that month). A cancelled row is on no more: "what's on thursday then" right after a cancel leaves out the cancelled row, and the gold accepts the list with it (D-1044-15, B14).
- **kind-less read** (D-1044-13, K1): a read whose message names no kind and no word that implies one (due, open, done, pinned, priority, "on my plate") reads one kind, never the union of events and tasks, and the call names it (an event has no `status = open`). "What's on <span>" and "anything on <span>" are the calendar, events, whatever the turn before read ("what's on tuesday now" after a task write). "What's left" and "what's remaining" read the kind the turn before read or wrote, and tasks as a first read ("what's left this weekend" after a read of an event is events). "Else", "other" and "more" go on with the kind of the turn before ("anything else on for this week" after ticking a task is tasks). A span question with no kind, no "on", no "left" and no word that implies tasks ("what's the plan for next week", "anything next weekend", "what does next week look like", "what've i got next monday") is the calendar, events too, and a fragment ("and tomorrow", "and next week") keeps the kind of the turn before (D-1044-15, B3b).
- **next**: in a listing (`find`, or `answer` without `op`) over a task or an event (the kinds a schedule dates; the date of a person, a note, a document, a photo or a debt is never upcoming), "next" with no `order` and no `limit` in the call reads as the nearest upcoming one: `order = date asc`, `limit = 1`, and `when` from today on when the call has none (`next: …` note). "next" followed by a date unit or a weekday ("next week", "next friday"), by a count ("next 3", "next three", "next couple"), or closing "this week or next" / "the friday after next" is not "the nearest one". A call that states an `order` or a `limit` is never changed. The same query written by the call (`order = date asc`, `limit = 1` and a `when` that starts today, in any spelling: `from day+0`, the day's `{"date": today}`, an open span from today) is a next-query too, whatever the message says: a call with no status condition (and a message with no "cancelled", "all", "done" ...) gets `status != cancelled` over events and `status != completed and status != cancelled` over tasks, and the note says so (`next: the call reads the next one; left out cancelled rows (status != cancelled).`).
- **last one**: "last one" in such a listing reads as the latest past one: `order = date desc`, `limit = 1` when the call has neither, and `when` up to today (`{"to":{"unit":"day","rel":0}}`) when the call has none or has exactly the open span from today on (`{"from":{"unit":"day","rel":0}}`, the mistake the models make). Any other `when` the call states stays (`last: …` note). The call written as `order = date desc`, `limit = 1` and a `when` that has no start and ends today or before is a last-query by its own shape and skips cancelled rows the same way (`last: the call reads the last one; …`). "Latest" and "newest" ("my latest diary entry", "the newest photo") in such a listing, with an `order` and a `limit` of neither in the call, read as the last by the kind's date: `order = date desc`, `limit = 1`, no `when` of their own, with the note `last: the message asks for the latest one; used order date desc, limit 1.`, unless an order, a count or a figure of speech follows or precedes them (`latest first`, `latest to oldest`, `3 latest`, `latest ones`, `the latest on x`); a call that states its own `order` or `limit` is never changed (nt9, rule 5). Neither reads a call linked to a task or an event of another kind (`find kind=person linked_to=#event`, "who's at the next rehearsal": the people of the event are not the next person, and the call keeps all of them).
- **what else** (D-1044-8, D-1044-13, G2): a read of a listing (`find`, or `answer` without `op` or `group`) with no `exclude`, `within`, `rows` or `value`, whose message carries an else/other/after cue (`else`, `others`, `other ones`, `the one after`, `besides X`, `apart from X`, `aside from X`, `except X`, `not the X`; not "the other day", "one or the other", "or else", "after friday") leaves out what the conversation has already put in play, for rows of the call's kind: the last result of the previous turn that holds such rows (`exclude: @n`), the options of the ask that ended the previous turn, the rows a write of the previous turn created or changed, and the row the message or an earlier message names (`exclude: #n`; `besides ama` names Ama, `what else is in there` after `which notebook is the kombu note in` leaves out the kombu note). The note says `(excluding ...)` and the left-out rows are not listed again: `what else is that weekend` after `move it an hour earlier` lists the weekend without the party that was moved; `any other notes with garlic` after an edit of the francesinha note lists the others. A row of another kind is never left out (`who else is on that, besides ama` leaves out Ama, not the event). "The one after" on a next-query keeps `limit 1`. A re-ask without a cue, a call that states its own `exclude` and a count are unchanged; this replaces "any message after a turn that wrote or asked is unchanged". The runtime's default supplies all four (the named rows only when exactly one live row of the kind has that name or nickname); a model's own `exclude` is kept as written. The compile step records the default as a `normalized` entry `{"rule": "default", "default": "exclude"|"next"|"last"}` and the note rides with the compiled call.
- **biggest**: an `answer` without `op` and without `group` whose message says "biggest" and whose call is `order <number or money field> desc` with `limit = 1` is a value: the runtime reads it as `op = max` over that field (`value: …` note). "most", "largest", "longest" and the smallest/least family are not read. Off by default: the train references read it as rows. The gold accepts both shapes for a superlative or "how long": the row, and its value (`answer op=max` over the field); the references stay rows (D-1044-13, G3). A superlative is also "needs the most time", "most effort", "least time" and "least work" (G1, owner ruling 2026-10-06).
- **membership** (D-1044-13, G8): "is X still in the Y folder" is answered by the row or by its container; both are accepted ("is it still in the kids folder" lists the document or the folder).
- **decline reason** (N7, owner ruling 2026-10-06): when the gold of a turn is a decline, a decline with any reason passes (`out_of_scope`, `unbounded_destruction`, `sealed_egress`, `fabricated_secret`, `never_mind`, `not_found`), because the person sees a polite can't either way; `regen.py` records it as the widening convention `decline-any-reason` (the old accept stays, one with every reason is added beside it, val and test alike), and the scorer is unchanged.
- **after a series ask** (G2, owner ruling 2026-10-06): a write by the name of a recurring series ends in the runtime's `Which one?` over its instances (`series-ask`), where the reference may have said something else ("no haircut coming up, want me to book one?"). The turn after it, if its gold is a write written for the reference's dialog ("yeah saturday at 11"), accepts that write or the same `Which one?` over the same series; a retraction ("forget it") or a read there is the same in either dialog and gets no alternative. A reference that itself asked over named rows was the same dialog and widens nothing. `regen.py` records it as the widening convention `after-series-ask` (val and test alike).
- **kindless trash read** (C1): "what's in the trash", "what's in the trash now", "anything deleted" name no kind and mean all kinds: the trash of every kind that has one (`trashed=true` with no `kind`, §3), one answer over the rows of every kind. The kind-less rule above (one kind, never a union) is for what the calendar and the lists hold, not for the trash.
- **am I behind** (C2): "am i behind on anything" is the overdue tasks: open or in-progress tasks dated before today (`status = open` with `when` up to yesterday), the same answer as "anything overdue". "Ahead or behind" about a group or a person is the balance, not this.
- **IOU** (C3): "IOU" is a debt row in either direction. A message with no direction ("how many IOUs are still open", "which IOUs have been settled") counts or lists both ways; "i owe", "owes me", "anyone owes me", "someone" give the direction the words give, never one the word "IOU" implies.
- **remind me when** (C4): "remind me when i fly to berlin", "remind me when <event>" asks when the event is, so it is a lookup of the event (an `answer` over the event by name) and never a reminder written. "remind me to <do X> <when>" is a task `create`, and "remind me who <X> is" a read of the person.
- **remind someone else** (C5): "remind her about it", "remind <person> about X" is messaging (the messaging line above): `decline out_of_scope`, because the vault sends nothing. "remind me to tell <person> X" is a task for me, a `create`.
- **how many are X, after a count** (C6): "how many are overdue", "how many are starred", "how many of those are yoga", "how many are cancelled" right after a count narrow the set just counted, the same kind and the same selector with the new condition added; they never restart over the whole vault. Another count with its own noun ("how many docs are starred vs not" after "how many folders left") is its own question.
- **bulk write**: a write on more than `ROW_CAP` (12) rows is never run outright. The turn ends in the runtime's ask with the count (`this would delete 734 tasks; delete all of them?`) and nothing is written; the same write in the next turn, after a plain yes, goes through (§4.6). "All" or "every" in the message and `scope: all` in the trace do not lift it; a write of 12 rows or fewer is unchanged, and "cancel everything this week, all of it" (9 rows) is the model's call (gold `decline unbounded_destruction`). A write the message narrows by a condition on the rows ("just the finished ones", "just the cancelled ones", "just the garage sale inventory") is a write: over the cap it ends in the runtime's ask with the count, never in a decline (D-1044-13, G13, refining D-1044-12). Only "all my tasks" or "everything" with nothing narrowing it is `decline unbounded_destruction`, and a time span with "everything" or "all of it" does not narrow: "cancel everything this week, monday through sunday, all of it" and "wipe everything from 2024, photos, notes, all of it" are declined although the span bounds them (D-1044-15, X4, amending G13).
- **vault refusals** (D-1044-10): a refusal nothing can lift ends in a decline with the reason: a restore past the vault's window is `decline not_found`; a restore of several rows is the same whatever order they come in: the rows past the window are set aside and reported (`error: restore #33 photo "…" was refused: it is in the trash but past the vault's restore window, so it cannot come back (…)`), the others are restored, and only a restore that brings no row back ends in the decline (nt9, rule 6). A refusal the person can still act on ends in an ask that names what a yes would do: a folder that holds documents (`take them out first, then delete the folder?`, the documents as options), a group with expenses, a notebook that holds notebooks. The ask is the runtime's, the reference ends at the refused call, and the turn after the person's answer is the model's (`remove_from` the documents, then `delete` the folder). The other refusals (§4.6) stay errors the model repairs.
- **asks and declines the runtime composes** (D-1044-11, M1; §4.8): the model judges, the harness composes. A write whose selector fits several rows is the runtime's `Which one?`, unless the person said all (the write takes every row, the cap holding); rows that share one name, tasks or events, are the ask and never a default; a write by a name that matches nothing goes to the one near spelling of its kind, or to the one row of another kind the name names exactly or by a word's start (`delete`, `remove_from`, `settle_up`, `settle_debt`, `reveal`, a near spelling of another kind and a row that fits one word of the name keep its `Did you mean #n?`), and otherwise is its `Did you mean #n?`, `Which one?` or `decline not_found`; an `answer` whose name reaches nothing answers the near spellings or answers nothing, and a `find` is a lookup, a plain miss with a hint that never ends the turn; a refusal nothing can lift is its decline (`out_of_scope`, `not_found` for a trashed target) and one a person can lift is its ask over the rows involved (an unsettled balance, a cancelled event to move, a clash of time; D-1044-10 extended). The model writes the call and stops: its asks have no options, its declines are the policy reasons. The reference ends at the call that is composed, the calls after it are unreached (`regen.composed_ends`: `composed-ask`, `composed-decline`, `composed-refusal`, `composed-answer`), and a reference heading for a write that a composed end cuts short is a verify problem. `composed-answer` is a widening: the old gold (a `decline not_found`, an `ask`) stays and the read's own answer (`rows []` for a plain miss, the near-spelling rows an `answer` carried) is accepted beside it. `composed-apply` names a write the runtime applied to the rows it chose (`apply_all`, `apply_near_spelling`, `apply_other_kind`): the turn ends at it, the reference calls after it are unreached without a verify problem, the old gold is kept when it accepts that diff, and any other gold is UNEXPLAINED. `--no-compose` restores the replies the model used to answer (`ambiguous:`, `0 … called …; nothing was done`, `error: … was refused`), for comparison runs.
- **verb applicability**: ONE principle: a verb's candidates are the rows it would change as they stand, judged before ambiguity, by the write's own already-so test (§4.2). The options of a composed `Which one?` are these rows alone (§4.8), and for `cancel` those not yet over. A row the write would leave as it is is not a candidate (nt12 B3: one function, `act::task_stand`, serves the plan and the candidate filter for `complete` and `reopen`: a completed task is already-so for `complete`, an open one for `reopen`; a cancelled task is a candidate for `reopen`, completes when it is the only row the name fits, and gives way to an open row the name also fits). The one named exception is `reschedule`: a row already at the time asked is a legitimate target the person may be re-confirming, so it is not filtered.

  | verb | a candidate is | not a candidate |
  | --- | --- | --- |
  | `complete` | a task not completed or cancelled | a done or cancelled one |
  | `reopen` | a task that is not open | an open one |
  | `cancel` | an event not cancelled and not over | a cancelled one |
  | `reschedule` | every event and task, including one already at the time asked (the exception) | — (a row that is over only bears out a pick, below) |
  | `edit` (and so a pin) | a row where some field would change | a row that already has the values (a pinned note) |
  | `star` · `unstar` | an unstarred · a starred row | the other |
  | `add_to` · `remove_from` | a row that is not · is a member | the other |
  | `delete` · `restore` | a live · a trashed row | the other |
  | `settle_debt` · `settle_up` | an open debt · a person with a balance in the group | a settled one · a person with none |
  | `reveal` | an item that has the field asked for | one that has not |
  | `log` · `create` · `undo` | every row (the state decides nothing) | — |

  A name that fits several rows is ambiguous only if more than one survives. When exactly one does, the act is on it (with a note), ahead of the date and focus steps; "tick off pay" with a done and an open "Pay …" is the open one, "cancel the swim class" with one already cancelled is the other, two open ones stay `ambiguous:`. A pick by `#n` of a row the verb cannot change, when the words fit exactly one row it can, goes to that one. A call that cannot be planned (a malformed argument) filters nothing: the write reports the error.

  Rows that are _over_ (an ended event, a task that is done or cancelled) are not removed from a by-name `reschedule` or `cancel`: "move the dentist" with one past and one coming dentist stays `ambiguous:`, since a name that fits both is the person's to settle, and a past row is as often the one meant (a date in the words reaches it). They count only to bear out a pick: when the model picked the one fit that is not over, the pick stands (`ambiguous_pick`). The ask over a series (two or more live events or tasks of one name, no date, ordinal or all-word) is the by-name call's (D-1044-13, M5d, M5e): the runtime takes no instance by default. A pick by `#n` of the one instance that is not over (an event) or not closed (a task), made after the model looked at the rows, stands, and the gold accepts that write and the ask (D-1044-15, amending D-1044-13's `series-ask`).

- **last month name**: "last november" is the most recent November that has fully ended (`unit=month name=11 rel=-1`).
- **broken-off request** (D-1044-13, K3): a message that breaks off mid-sentence ("...", "hmm", "no", "wait") and goes on runs only its last complete request; what the broken-off clause would have done is not done until the person asks again ("move the router setup note into... hmm i don't have a home notebook. create one called Home" is the create alone). A message that ends in a retraction ("... no wait. never mind") is the retraction (§6.3).
- **Trace slots** (`authored/trace.py`; the lexicon is `VERB_RX`, `COUNT_RX`, `READ_LEAD`, `DECLINE_RX`, `ALL_RX`, `BOTH_RX`, `PLURAL_RX`, `EXCEPT_RX`, `IT_RX`, `NTH_RX`, `REFER_PHRASE_RX`):
  - `intent`: the deciding phrase is the first match of the intent's lexicon in the message: for a write the verb's `VERB_RX` entry ("tick it off", "call off", "push"), for a count `COUNT_RX` ("how many", "owe", "total"), for a read `READ_LEAD` (the question word plus the next two words), for a decline the reason's `DECLINE_RX` entry. When no lexeme matches, `intent_phrase` falls back to `lead_phrase`: the whole message if it has at most 7 words, else its first clause (cut at `, ; : . ! ?`, a dash, "so" or "because") if that has 2 to 7 words, else the first 5 words, and flags `intent-phrase-fallback`. About 24% of intent phrases take this fallback (3,548 of 14,940 good calls in the final train file; the refer phrase falls back on 17.4%, 376 of 2,165), mostly fragment follow-ups ("3 is fine").
  - `verb`: the closed verb set, read off the call; no quote.
  - `scope`: `one` has no quote; `some` quotes the exception clause (`EXCEPT_RX`: except, besides, apart from, other than, but not, minus ...) plus up to 4 words, else the `BOTH_RX` match or a count word; `all` quotes the `ALL_RX` match (all, every, each, whole ...).
  - `refer`: a follow-up is a call that names rows an earlier turn showed and the message does not name. Kind by order: `both` when the call takes a whole multi-row result and the message has a `BOTH_RX`/`ALL_RX` word; `nth` for an ordinal (`NTH_RX`: "the second one", "number 3", "3 is fine", "the other one") when one row is meant; `it` for a personal pronoun (it, its, him, his, her, he, she); `that` for other `IT_RX` words (this, that, there, the same, the one). If none matches, the quote is the stretch of the message that shares words with the referent's names, else the first date phrase, else `lead_phrase` (flag `refer-phrase-fallback`).
  - `target`: the spans of the message the call's names, attributes and values match (`find_span`, at least half the words).
  - `when`: the date phrase as said (`date_clusters`); `earlier` when it is from an earlier message or an earlier call; `now` for the unstated default (`is_default_now`). No phrase found is flagged `when-no-phrase` and fails the argument-source check.
  - `pick`: one verdict per shown candidate, with a reason from `REASONS`.
